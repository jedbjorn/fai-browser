# FAI Browser: architecture

Status: the Phase 2 architecture (2026-10-04: a long-lived daemon, a WebSocket push channel to the extension, an MCP server and a skill), updated through 0.6 for Agent direct, several browsers, approved frames, invites and wakes and the self-updater. The host agent makes every choice. The runtime loop, settle policy and capture pipeline are unchanged from Phase 1. [PROPOSAL.md](docs/design/PROPOSAL.md) has the roadmap and decisions; [RESULTS.md](docs/results/RESULTS.md) has the benchmark history.

## Product contract

A host agent works in one tab the user approved. **The host drives**: the MCP opening call (`fai_browser_open`) requests approval and returns a compact page (a digest ranked by the task, and only the actions the granted level and the request's restrictions allow, each bound to a single-use revision); every `act` returns the next page and offer, and an expectation on the final act verifies the outcome independently. The extension runs each action in that one tab, the user can watch it and pause or stop at any time, and every action passes the same guardrails twice (runtime offer, page script at dispatch). The goal is the most capable, safe and token-lean browser an agent has used: one short line per action, the page text under an untrusted heading, no screenshot unless asked.


## Components

```text
coding agent ── MCP stdio (src/mcp.js, bin fai-browser-mcp) ─┐
shell / script ── CLI (src/cli.js) ─── SDK client (src/client.js) ──┤ loopback HTTP /v1/*, bearer client-token
                                                                     │
                     daemon (src/daemon.js) on 127.0.0.1:4318: tab requests, leases, acts, traces, retention
                              │
                     BrowserRuntime (src/runtime.js) per lease
                              │ bridge: observe / execute / capture
                     hub (src/bridge.js): WebSocket /ext/ws (src/ws.js), long-poll fallback
                              │ pairing secret + exact extension Origin
                     MV3 extension: background.js ── page.js (in the tab) ── offscreen.js (annotate + encode)
                              │ site access from Approve in the request modal, or activeTab from the toolbar click
                         selected tab
```

Clients auto-start the daemon (`ensureDaemon`: health check, spawn `src/daemon-main.js` detached, poll until healthy). One listener serves three things by path: `/v1/*` is the client API, an upgrade on `/ext/ws` is the extension's WebSocket, and everything else is the extension's long-poll fallback. The daemon keeps one `BrowserRuntime` per lease, so an observe's offer cache survives across HTTP calls. `src/home.js` resolves the state files (`client-token`, `daemon.json`, `daemon.lock`, `logs/daemon.log`, `config.json`) under `$FAI_HOME` (or `$FAI_DAEMON_DIR` for runtime state); `src/settings.js` owns `.env.local`. `src/trace.js` and `src/retention.js` write and prune run records inside the daemon. `createCompanion` remains for in-process SDK use and the CLI's Phase 1 mode, which only an explicit `--in-process` selects; `--port` always names the daemon port.

## Tab requests and leases

An agent calls `POST /v1/requests` with exact origins, a mode and a one-line reason; it returns a `requestId` at once. The extension shows a card per pending request ("Agent says: …", rendered as text), and the user's **Approve** in the task tab's request modal (browser site access) or click on **Approve this tab** in the popup (the `activeTab` gesture) binds that request to the current tab at the level picked in the card's **Allow** selector (the lease message carries `level`; the daemon stores it as `record.grant` and clamps every run and observe to it). States: `pending → active`; `active → paused` on Pause, a tab switch, an origin change, a child tab or a lost connection (3 s grace); `paused → active` on **Resume on this tab** or a reconnect with the same lease; `released`, `cancelled`, `expired` and `denied` are terminal and kept for an hour so `wait` can report them. Only one lease is active at a time per browser; approving another request in the same browser supersedes it (several browsers each hold their own, see [Several browsers](#several-browsers)). Every approval names its request (the card's, the armed tab's or the modal's `requestId`); a lease message without one (an older extension) gets the newest pending request for the origin, else a paused one only on its own tab in the same browser, never the oldest, never a paused request on another tab and never an invited tab. A paused request whose agent asked for a newer tab since (one that was then denied, cancelled or expired unapproved does not count), or that no live agent session owns and sat idle 5 minutes, is `stale` in its view (`staleOf`): the popup folds it away below the new requests and paused tasks, and status names it so its agent can release it. Pause ends the current run as `needs_user/paused`; the agent waits for `active` and starts a new run.

Every blocking call is bounded: `POST /v1/wait` and the `waitMs` of runs are clamped to 45 s and return the current snapshot (`state: "running"` or `pending`) when they elapse, because Codex's default MCP tool timeout is 60 s. Task outcomes are always HTTP 200 with a v1 result; HTTP errors (`unknown_request`, `mode_not_granted`, `run_active`, ...) mean bad parameters or infrastructure failures. Client routes reject any request with an `Origin` header or a non-loopback `Host` and require the client token, compared in constant time.

## MCP server and skill

`src/mcp.js` is a dependency-free newline-delimited JSON-RPC 2.0 server for MCP 2025-11-25 (it also answers 2025-06-18 and 2025-03-26 clients): `initialize`, `ping`, `tools/list`, `tools/call`, outbound `notifications/progress` and inbound `notifications/cancelled`. `initialize` never starts the daemon; the first tool call does. Seven tools (`fai_browser_open`, `act`, `observe`, `wait`, `status`, `release`, `evidence`) declare closed JSON Schema 2020-12 inputs with one- or two-sentence descriptions and no output schema; the loop guidance lives in the `instructions` string (about 1.65k characters, bounded by test/mcp.test.js) and the skill. The host model re-reads the tool list on every request, so its size is a per-request cost (17.3 KB before the efficiency pass, 7.3 KB after).


Each call has a hard deadline (`FAI_MCP_MAX_CALL_MS`, default 45 s); daemon waits get the remaining time minus a 2 s margin. Run results are one readable text block with no `structuredContent` mirror: `next (<kind>)` first, then trusted lines (`status`, `code`, `verification`, `granted`, `needs.message`, `warnings`), then one "untrusted page text" heading over the URL, title, digest and offered actions. The server keeps a ledger per `requestId`: calls and run time used against `maxCalls`/`maxMs` (50 calls and 20 minutes by default; the user's popup setting, reported by the extension and served by the daemon, else `config.json` `budget` read through `src/settings.js`; the agent cannot change it). `applyBudget()` writes `verdict.budget` and turns a `choose` or `observe` into `stop` when no call is left; beyond the budget a call returns `budget_exhausted`/`task_budget` without reaching the daemon. Observe returns `{revision, page {url, title, digest}, actions [{id, description}], moreActions?, warnings?}` (the daemon's listing: at most 40 control actions at read-only and reversible, 80 from interactive up, the most relevant to the task when there are more, with `controls_capped:<n>`; scroll, wait, allowed URLs and consent buttons always listed; see docs/REFERENCE.md "Offered actions") with a text block of digest lines and `a3  click "About"` action lines; status, wait and evidence metadata use compact `key: value` lines; screenshots and trace JSON stay separate content blocks. No image is sent unless asked: `returnImages` defaults to `none` for act and observe; `final` and `all` fetch screenshots through the evidence route (files over 1.5 MB are skipped and listed in `imagesOmitted`). `isError` is only for schema violations, daemon 4xx/5xx, an unreachable daemon and internal errors. An act that waits for the user's Approve click and outlasts the call window returns `state: "running"` with `next.kind: "wait"`, and `fai_browser_wait {runId}` follows it. A cancelled act is stopped. On stdin EOF the server stops its acts and releases the requests it created.

`skills/fai-browser/SKILL.md` is the agent guide and the single source for the tool loop and how to read results, linked at `.claude/skills/` and `.agents/skills/`. Task know-how is not in it: `tasks/<name>/SKILL.md` (today flights and hotels) is a short task guide the main skill points at, installed beside it as `tasks/<name>/SKILL.md` (`skills/fai-browser/tasks` links to `tasks/`), and `tasks/<name>/index.js` holds the task's question vocabulary, listed statically in `tasks/index.js`, the only place the core (`src/digest.js`) takes it from; nothing in `src/` names a site or a task. `fai-browser install --host claude|codex|opencode` (`src/install.js`) writes the host's MCP entry with absolute `node` and script paths and copies the skill with a version marker.

## Agent sessions, invites and wakes

Each MCP server registers with the daemon after `initialize` (`src/mcp-session.js`, without ever starting it) and holds one long-poll for wakes, keyed by a random per-session key (`src/sessions.js`); entries go when stdio closes, the pid dies or polling stops for 90 s. The popup's **Invite agent** is an extension-channel `invite` message (accepted by the worker only from `popup.html`): the daemon creates a request on the tab's exact origin, binds it at once at the chosen level through the same lease path as an approval (`bindRecord`), creates a single-use 10-minute invite id and queues a wake for the chosen session. Approving or resuming a request an MCP server created queues a wake for that owner. The daemon queues fields only; the MCP server writes the fixed text (`src/wake.js`) to its own host's channel (Claude Code's messaging socket, `codex queue`, FAI's OpenCode plugin socket), skips a wake a call in flight already waits for, and reports the outcome, which the popup shows (or the copy line `join FAI invite inv-…`). See [docs/REFERENCE.md](docs/REFERENCE.md#invites-and-wakes).

## Receipt v2 and the oversight ladder

Every result carries `verdict {kind, oversight, answer, why, budget}` and `next {kind, text}` (OVERSIGHT-SPEC.md section 2). The runtime writes the verdict in `Session.receipt()` at close from mechanical signals: the expectation shape from `lintExpectation()` (`url_path`, `url_guess`, `text_menu`, `text_unique`, `absent`), the final URL, the auto-confirm rule (`autoConfirm()` in `src/digest.js`: top candidate at least `answerConfirm`, the intent's shape, a margin of `answerMargin`, and not a list, Nth or late-load intent from `classifyIntent()`; for an aggregation over the fact memory, only its unique first item over fully read items). `buildVerdict()` in `src/result.js` maps code plus signals to kind, oversight and next kind; results without runtime signals (daemon outcomes, older traces) get a verdict from the code alone. `nextFor()` renders the text with the requestId. The answer gates live in one `thresholds` object (`src/oversight.js`: `answerConfirm` 0.8, `answerMargin` 0.5), settable in `config.json`.

Guardrails (`src/guardrails.js`) are one policy object per permission level (read-only < reversible < interactive < full < testing; each level a fixed set of capabilities: `navigate`, `controls`, `submit_safe`, `submit`, `delete`, `consent_accept`, `sign_in`, `purchase`), rendered as the mechanical label and field check (`PURCHASE`, `COMMIT_OTHER`, `SUBMIT_WORDS`, `DELETE_WORDS`, `SIGN_IN_WORDS`, `SAFE_SUBMIT`, payment fields and the request's or config's additions, applied in `legalActions()`/`blockedEntries()` through `controlBlock()`). The level is enforced three times, by parties that do not trust each other: the runtime clamps the run's mode to the grant (`clampLevel`), the hub clamps each command's `level` to the lease, and the service worker intersects that with the level the user chose and passes the capability list (`allow`) to `extension/page.js`, whose `riskOf` classifies every control (`purchase`, `submit`, `delete`, `sign_in`, `consent_accept`, `submit_safe`, `reversible`, `navigation`, `forbid`) and refuses dispatch of any class not allowed; the label patterns are byte copies (drift tests). A refusal a higher level would lift carries `needs.level` and relays to the user.



## The loop

What the runtime does around each host action (the choice itself is the host's, through `act`).

1. **Observe once** at the start. `page.js` returns the URL, title, visible-region text (up to 8000 chars, `textTruncated`), up to 100 controls with role, label, state, bounds and risk class, the viewport, and a **semantic revision**: a hash of URL, text, control labels, states and element identities. Attribute-only mutations, live regions, spinners and scrolling leave the revision unchanged. Derived views (`collectViews`) replace raw text in `text` and blocks without entering the revision: an SVG chart becomes a `chart` block of its labels or of values read from bar heights against numeric axis ticks, a grid with row and column headers (or an ARIA grid) gives one keyed line per row ("Oct 10 × Oct 17: €312"), a list row's fields are joined with " · " (a row is a list item, an article, or a repeated element that is not a panel: no section-like element or heading child, and never two "Label: value" lines with different labels), and regions held only as pixels (canvas, unlabelled chart marks, chart images) or cut by the 1500-character grid budget are listed in `unreadable` with the warning `unreadable_region`. Repeated records (cards, grid tiles, list items, table rows) are detected by structure and sent as `records`, one compact entry each with its title, fields and typed hints, from the whole list; the core reads each as one item (docs/REFERENCE.md "Records"). Explicit result count, sort and pagination from the primary module go in `recordState`; Agent direct projects at most 600 characters of task-relevant rows from the primary list with offered open action ids, retains `truncated` and count metadata when rows do not fit, and leaves omitted rows in its digest.
   What covers the page is described, never handled automatically: a cookie dialog's reject buttons are offered as actions from `reversible` (an accept button only at `full` and `testing`), and any other blocking overlay the page script detected (`detectOverlay`: open dialogs, a layer hit-tested over the viewport centre, a separate backdrop, inert main content, a bottom sheet) is reported as the observation's `overlay` with the warning `blocking_overlay`; its controls and blocks are marked `overlay` and ranked after the main content (its close button, like any button, from `reversible`). Sign-in controls and password fills are never offered below `testing`.
2. **Offer legal actions** (`legalActions`). In `read-only` that means same-origin links to approved origins (a link that would open a new tab is offered as `navigate_allowed_url` to its href in the selected tab, marked `newTab`), plus `scroll up|down` and `wait`, and `navigate_allowed_url` for exact listed URLs. `reversible` adds clicks on ordinary controls and script links, `select` options and `fill_supplied_text` per supplied name, plus a click (`opens: true`, no typing) on a text field that opens a picker: read-only, `aria-haspopup`, `inputmode=none` (the page script's `opens`), a combobox, a date or time input, or a date- or time-ish label or placeholder ("Departure", "Check-in"); `interactive`, `full` and `testing` add the classes their capabilities allow (password inputs become fill targets only at `testing`, with `sensitive: true` and the value redacted from receipts and traces). Disabled, hidden and sensitive controls, and any control whose page risk class, label class (`controlBlock`) or payment-field shape the level does not allow, are never offered. Page-level actions are reserved slots inside the 250-action cap.
4. **Execute.** There is no pre-execute freshness observe. `page.js` checks the expected revision and the target's identity atomically, then dispatches, settles and observes in one round trip. `stale` and `target_unavailable` mean nothing happened: the runtime re-observes and asks again, up to 2 consecutive retries, without pausing the lease. A host `act()` that comes back `stale` re-observes once and runs the same control when exactly one action offered on the fresh page has its type, role, label, value, destination and frame (with several, the one whose neighbouring controls carry the same labels), on the same origin and path (`decision.reason: "stale_reresolve"`, `why` `act:stale_reresolve`); otherwise it stays `stale`.

   For the answer, the runtime keeps the observations it saw and builds a **fact memory** from them (`src/facts.js`, lazily at answer time): one state per semantic revision, not URL, so same-URL states (single-page panels, a day list redrawn in place) count; at most 6 question-relevant lines per state and 80 per run, supplied values redacted. The states before the final one become `trail` (`[{url, state, lines}]`, at most 3 lines per state, 12 states, 40 lines), so a multi-hop answer ("the guide by the documentation lead named on About") keeps the fact from the earlier page. When the final page is weakly relevant and the task is not a join, remembered lines also become candidates (tagged with their state; `answer.source`). A question that asks for an extremum or a filter over items ("the cheapest in-stock tent", "the cheapest flight between 10:00 and 12:00") is aggregated deterministically: currency amounts, times and counts are parsed from the remembered lines, the filter words applied, and the first five items lead the candidates; an aggregate over a list the run did not fully read (pages left, show-more offered, run not verified) is `partial` and never auto-confirmed. The trace keeps the memory as `facts`. See docs/REFERENCE.md "Fact memory and aggregation".
6. **Capture off the critical path.** See below.

Cancellation: `pause()`/`stop()` and the caller's `signal` abort through one combined signal. An action interrupted mid-flight stays in the trace with `interrupted: true`. `onAction` is fire-and-forget unless `awaitCallbacks` is set, and a throwing callback never fails the run.

**Host-driven control.** `observe(options)` returns the compact page and the offered actions, keyed by revision; the last four offers are cached. `act(actionId, {revision})` runs one of them with the authority (mode, origins, supplied text) fixed when `observe` was called, and returns the same result schema plus `offer`: the actions offered on the page it landed on (same authority, listed by the observe's task hints, cached like an observe), which the lean result lists as `revision`, `actions` and `moreActions` with a `choose` next, so the next `act` needs no `observe` in between. FAI makes no model calls. Host-driven offers also include Enter in a filled text field (`submit_field`), gated as the form submit it is.

## Settle policy (extension)

| Action | Settle | Reported `settle` |
|---|---|---|
| Navigating (a load starts within 150 ms) | `tabs.onUpdated` complete (cap 3 s), then two frames + 100 ms of quiet among relevant mutations (cap 1.5 s) | `load_complete` or `cap` |
| In place (click, select, fill, scroll) | two animation frames + 50 ms quiet (cap 300 ms) | `quiet` or `cap` |
| `wait` | 500 ms sleep, then observe | `none` |

Mutations inside live regions and off-screen elements don't reset the quiet timer. `page.js` is injected once per document (after `input.js`, the realistic mouse, keyboard and wheel input it dispatches through; docs/REFERENCE.md "Detection"): the first call probes for it, so normally each command costs a single `executeScript`.

## Capture pipeline

Execute returns the settled observation immediately, and the screenshot follows on `POST /screenshots`, bound to the command id. The bridge reserves a screenshot slot before sending the command, so a screenshot that arrives before its result is kept. The slot resolves `{error: capture_failed}` 5 s after the result if nothing arrives, and it never rejects. In the extension:

- A capture gate serializes captures, and the next execute waits for it until the frame is taken. An action can therefore never change the page between the single pre-capture revision check and `captureVisibleTab`.
- **Chrome quota.** `captureVisibleTab` allows two calls per second, so captures are spaced 500 ms apart. With `capture: "each"` this is the step-rate ceiling: the real-browser bench measures 516 ms p50 per step. `capture: "last"` (the default) runs every action with `capture: false` and, when the run ends, sends one `capture` command for the final step. `capture: "none"` never captures. Both measure about 166 ms per step.
- The offscreen document decodes with `createImageBitmap`, downscales to at most 1280 px wide and draws boxes and badges for the post-action controls (the control refs; or, when the capture command carries the offer's `labels` for the frame's revision, the offered action ids, only on offered controls, badges placed clear of each other), plus a footer naming the action (never supplied text). The badges drawn come back as `tags` for the trace. It then encodes a JPEG at quality 70 with a DOM canvas `toDataURL`. `OffscreenCanvas.convertToBlob` stalls about 1007 ms per frame in headless Chromium; the DOM canvas takes about 5 ms. The smoke script records both encoders.
- The image is labelled with the revision it actually shows. The runtime discards it as `revision_mismatch` if that differs from the step's observation.
- A point click (`act` with `point {x, y}` in screenshot pixels) is two commands: `locate` (the control under the mapped CSS point on the expected revision, described as an observation control, with its id when the observation listed it) and then `execute` with a `click` carrying the same point, which page.js dispatches only to the element it located, once, after the same capability check as any target. The runtime runs the offered action when the control was offered, else the same gate and guards as an offered action (docs/REFERENCE.md, Point clicks).

## Extension protocol

Phase 2 pushes commands over the WebSocket at `/ext/ws` (message schema v3: `hello`, `lease`, `lease_level`, `settings`, `deny`, `status`, `requests`, `command`, `result`, `screenshot`, `cancel`, `lease_update`, `used`, `move`; `lease_level {leaseId, level}` reports a level the extension lowered on its own, such as a testing session whose origin was removed from the list, and can only lower a grant; `settings {settings: {budget}}`, and `hello.settings`, carry the popup's per-request budget setting, answered with the budget in effect, see docs/REFERENCE.md "Per-request budget"). The extension authenticates in the upgrade through the `fai-auth.<secret>` subprotocol and the exact extension Origin, so no unauthenticated socket exists. The HTTP long-poll below remains as the fallback transport and as the in-process companion's protocol; its command methods and arguments are unchanged in v3.

### Several browsers

Several browsers may be paired with one daemon at once (issue #9). Each extension install reports a stable browser identity: a random `browserId` kept in its extension storage, sent as the `browser` query parameter of the WebSocket URL and the `X-Fai-Browser` header of every long-poll call, with `hello.browser {product, name, version}`; an older extension that reports none is identified by its extension Origin (`connectionIdentity` in src/bridge.js). An id is bound to the Origin it first came from (`identify`; kept with each browser's last use in the daemon's `browsers.json`, handed back as `knownBrowsers`), and extensions only ever see names with `mine`/`self`, never another browser's id. The hub keeps one connection per identity (socket or held polls, outbox, liveness and grace timer, settings, last use, recent closes). A newer socket of the same identity closes the older one with `4003` (CLOSE_SUPERSEDED), which the extension does not answer with a reconnect; nothing ever closes another identity's socket. (Before, every upgrade closed the one socket with `4000` and two browsers replaced each other forever.) Leases carry the `browserId` of the browser that approved them, and `takeCommand`, `push` (cancel, lease_update), status and `lease_level` route by it; a lease bound without one (an embedding, a test) belongs to the browser used last. `publishRequests` sends each connection the request views plus the connected `browsers`; an older extension gets only the requests meant for it. `used {}` (popup opened, toolbar click) and approvals record the browser's last use, and `move {requestId}` is the popup's "Open here".

The daemon gives every pending request a `browser` (`assignBrowsers`, on every change): the one the agent named (`browser`, `pickBrowser`: product, name or id of a connected browser, else `409 browser_not_connected` naming the connected ones), else the browser used last, re-assigned when it disconnects; "Open here" pins it. Only that browser's extension opens the approval UI and badges it; the others list it with **Open here**. One active lease per browser: an approval supersedes only leases of the same browser. A `disconnected` event or a hello without a session pauses only that browser's leases. Popup settings (budget, open right away, Approve gate asks) are kept per browser and apply to the requests that browser holds or awaits (`settingsFor`). Results and screenshots are accepted only from the connection the command went to. Status lists the browsers (`extension.browsers`, `browsers`) and adds `extension_flapping` when one closes more than 8 times in 60 s, and `extension_duplicate_identity` when a live, hello'd socket over 10 s old is superseded.

### Companion long-poll (version 2)

Loopback HTTP on `127.0.0.1`. Every route requires the exact `chrome-extension://<id>` Origin and `Authorization: Bearer <pairing secret>`, compared in constant time. Commands carry `{version, id, deadline, method, args, lease, allowedOrigins}`. The methods are `observe`, `execute {action, expectedRevision, capture}` and `capture {action, target, fromUrl}`.

| Route | Purpose |
|---|---|
| `POST /commands?wait=25000` | Long-poll. Answers with the next command as soon as one is queued, or `{command: null}` after the wait. POST because Chrome sends no Origin header on extension GETs. |
| `POST /results` | `{id, result}` or `{id, error: {code, message, recoverable}}` |
| `POST /screenshots` | `{id, screenshot}` or `{id, error}`, for execute captures |
| `POST /lease` | The user's approval of a request card (or the icon click on an armed tab): `{requestId, tabId, origin, level}`. The origin must be covered by the request. |
| `POST /lease-level` | `{leaseId, level}`: the extension lowered the lease's level (testing revoked); a higher level is refused with `level_not_granted`. |
| `POST /settings` | `{settings: {budget}}`: the popup's per-request budget setting changed; the reply carries the budget in effect. |
| `POST /status` | Pause, stop or end the session with a reason code |
| `POST /validate` | The extension checks that a command is still wanted before acting |

An open long-poll counts as liveness. A dropped long-poll with no re-poll within 3 s marks the lease `disconnected`, and so does 35 s with no request at all. Commands time out after 30 s. Error codes are `stale`, `target_unavailable`, `capture_failed` (all three recoverable), `blocked_risky`, `cross_origin`, `child_tab`, `tab_changed`, `origin_changed`, `session_inactive`, `timeout`, `unsupported`, `disconnected`, `paused` and `stopped`. Only `tab_changed` and `origin_changed` (and user Pause/Stop) end the extension session; everything else fails just that command. Chrome's own error page on the approved URL (an HTTP error without a page body, a network failure; executeScript fails with "showing error page" or names `chrome-error://`) is not an origin change: observe paths report it as a `browserErrorPage` observation and page actions there fail with `target_unavailable`.

## Extension lifecycle and security

- **Pinned ID.** The manifest `key` makes the ID `ikkpdnokohfcjhfidepcledkbepmkfcm` for every unpacked install (`PINNED_EXTENSION_ID`). `host_permissions` is only `http://127.0.0.1:4318/*`. Tab access comes solely from `activeTab`, granted by the user's click, with no optional host permissions and no remembered sites. Changing the companion port currently means editing the manifest.
- The session lives in worker memory only. A worker restart tells the companion to pause the old lease with `session_inactive`, and the user must select the tab again. While a session exists, a `chrome.storage.session` read every 20 s keeps the worker alive.
- A child tab opened by the leased tab, a tab switch in the leased tab's window, closing the tab, or leaving the origin each pause the lease with the matching code. A `child_tab` or `origin_changed` pause names the origin the page opened or went to when the browser shows it (`status.origin`, origin only; `childOrigin`/`leftOrigin` in the view and result, untrusted). One exception: a session on a `consent.*` host follows one redirect to an origin listed in the same request (the daemon's lease reply carries the request's origins); a second origin change, or any other destination, still pauses it. Same-origin `target=_blank` links are blocked in the page and reported as `child_tab`.
- The pairing secret lives in extension storage, which is not a vault. `.env.local` (mode 0600, atomic write) never reaches the browser.
- Supplied text is resolved into the bridge command only at execution time. It never reaches the history, the annotation or the written trace, which keeps `suppliedName` only. The in-memory SDK result keeps `action.text`.

## Updates

`src/update.js` checks GitHub's latest release about once a day from the daemon (cached in `update-check.json` in the state directory, shown as `update` in status, the hello and the popup; an API 404 falls back to `git ls-remote` on the clone's verified remote, `src/update-git.js`, which also builds the secret-free environments every updater child gets). While an update runs (`update.lock`, written by the daemon when it starts the updater) the daemon refuses new tab requests and approvals. `src/update-install.js` installs only on the user's popup click (the extension's `update` message; the daemon starts `fai-browser update --tag <tag>` detached, since it restarts the daemon) or `fai-browser update` (`src/update-cli.js`): refusals first (lease held, not a clone of the repo, local changes, unpushed commits, another branch), then fetch and verify the tag, fast-forward `main` or check the tag out on a detached HEAD, `npm ci` when the lock changed, `update --finish` from the new code (native host, user-level skills), restart, and roll back on failure. The worker reloads an unpacked Chromium extension once the restarted daemon reports a newer version. See [docs/REFERENCE.md](docs/REFERENCE.md#updates).

## Result, trace and retention

The result schema is in PROPOSAL.md section 5 and `src/index.d.ts` (`RunResult`, `AgentResult` with `Verdict`, `TraceRecord`), with the status taxonomy and exit codes in [docs/REFERENCE.md](docs/REFERENCE.md#output-status-and-exit-codes). Results are version 2; the trace keeps the verdict and next as written. `writeRun` writes `trace.json` plus one image per kept screenshot and no base64. Control bounds are stripped, credential-like option keys removed, and `suppliedText` values replaced by `[redacted]`. `prune` keeps at most 50 runs, 500 MB and 7 days by default. It runs after every daemon write, never deletes the current run, and only considers real directories that contain `trace.json`.
