# FAI Browser reference

The detailed manual for FAI Browser: setup, the daemon, the MCP server and CLI, result shapes, status codes, screenshots, traces, the SDK, policies, guardrails and limits. The [README](../README.md) is the overview; [ARCHITECTURE.md](../ARCHITECTURE.md) covers the design and [PROPOSAL.md](design/PROPOSAL.md) the roadmap.

An agent gives an instruction. A decision provider picks one of the browser actions on offer, the extension runs it in a tab the user approved, and the agent gets back a verified outcome, the final page text, annotated screenshots and a trace on disk. `step` runs one action. `run` runs a short bounded sequence. TypeSafe Jev is the default provider; local SystemOne-compatible servers also work.

Requires Node 22+ and Chrome/Chromium 116+. The runtime has no npm dependencies, and everything runs locally except calls to a hosted provider and the daily [update check](#updates) (one GET to GitHub's releases API; `FAI_UPDATE_CHECK=0` turns it off). Commands below run from the package root.

## One-time setup

1. Run `npm run setup` in the package directory. It moves settings left in the checkout by an older version, saves the pairing secret to `.env.local` (mode `0600`) in the settings directory (see [The daemon](#the-daemon)), installs the [native messaging host](#native-messaging-pairing) for every browser it finds, starts or reloads the FAI service (the daemon), and offers to register FAI Browser with each coding agent on your `PATH` ("Register FAI Browser with Claude Code? [Y/n]"; user scope, through `install --host`). It ends with a three-step checklist. Your agent drives (no key) unless `config.json` already names the Jev autopilot. `--yes` registers every detected agent without asking, `--no-register` skips that; `--driver jev` opts in to the experimental Jev autopilot and asks for its key at a hidden prompt (or whether to replace a saved one); `--driver agent` switches back; `--extension-id <id>` overrides the pinned ID for a re-keyed manifest. Other settings and existing keys are preserved.
2. Open `chrome://extensions` (`brave://extensions`, `edge://extensions`), turn on Developer mode, click **Load unpacked** and select `extension/`. The manifest `key` fixes the extension ID at `ikkpdnokohfcjhfidepcledkbepmkfcm`, so you don't need to copy it. The extension pairs by itself through the native host: nothing to paste.
   Firefox: `npm run build:firefox` writes `dist/firefox/`; load it from `about:debugging#/runtime/this-firefox` (**Load Temporary Add-on**, pick its `manifest.json`). [Firefox](#firefox) has the permanent install options.
3. Pin the FAI Browser icon (puzzle-piece menu, then the pin): you approve every agent request by clicking it. The popup shows how while it is not pinned.
4. Restart your coding agent so it loads the MCP server and skill (or connect one by hand, [next section](#coding-agents-mcp-and-skill)), or use the CLI directly.

### Native messaging pairing

`npm run setup` (or `node src/cli.js install-native [--browser chrome,brave] [--all] [--dry-run]`) writes a launcher, `native-host` (`native-host.bat` on Windows) in the settings directory, that runs `src/native-host.js` with the absolute path of the Node that ran setup (and `FAI_HOME` when set), and a host manifest named `fai_browser` for every browser whose profile directory exists for this user:

| Browser | Linux | macOS |
|---|---|---|
| Chrome (Beta, Dev/Canary) | `~/.config/google-chrome{,-beta,-unstable}/NativeMessagingHosts/` | `~/Library/Application Support/Google/Chrome{, Beta, Canary}/NativeMessagingHosts/` |
| Chromium | `~/.config/chromium/NativeMessagingHosts/` | `~/Library/Application Support/Chromium/NativeMessagingHosts/` |
| Brave | `~/.config/BraveSoftware/Brave-Browser/NativeMessagingHosts/` | `~/Library/Application Support/BraveSoftware/Brave-Browser/NativeMessagingHosts/` |
| Edge (Beta, Dev) | `~/.config/microsoft-edge{,-beta,-dev}/NativeMessagingHosts/` | `~/Library/Application Support/Microsoft Edge/NativeMessagingHosts/` |
| Vivaldi | `~/.config/vivaldi/NativeMessagingHosts/` | `~/Library/Application Support/Vivaldi/NativeMessagingHosts/` |
| Firefox | `~/.mozilla/native-messaging-hosts/` | `~/Library/Application Support/Mozilla/NativeMessagingHosts/` |

On Windows the manifest goes next to the launcher and its path is the default value of `HKCU\Software\<Google\Chrome | Chromium | BraveSoftware\Brave-Browser | Microsoft\Edge | Vivaldi | Mozilla>\NativeMessagingHosts\fai_browser` (written with `reg add`). Chromium-family manifests allow only `chrome-extension://<pinned ID>/` (`allowed_origins`); the Firefox manifest allows only the add-on IDs `fai-browser@jedbjorn.github.io` (the signed ID the Firefox build declares) and `fai-browser@local` (older dev builds) (`allowed_extensions`). Firefox on Linux counts as installed when `~/.mozilla` or, for Firefox 147+ profiles, `$XDG_CONFIG_HOME/mozilla/firefox` (default `~/.config/mozilla/firefox`) exists; its manifest goes to `~/.mozilla/native-messaging-hosts/` in both layouts (Firefox 159 reads user manifests only there, and creating that directory leaves the profile location alone). `node src/cli.js uninstall-native` removes the launcher and every `fai_browser` manifest (files whose `name` is another host are left alone).

The host speaks the native messaging protocol (32-bit length, then JSON) and answers two requests: `ping` (`{ok, version}`) and `pair`, which starts the FAI service when it is not running and returns `{ok, endpoint, secret, version}`. It checks the caller again from its arguments (the extension origin Chromium passes, or the add-on ID Firefox passes) and refuses anyone else; it writes nothing but protocol frames and never logs. The worker pairs through it on install and browser start when no secret is saved, every 30 s while unpaired, and again when the service stops answering (it may have been restarted or set up again), at most every 30 s; the popup's **Pair with the FAI service** button asks at once. The secret goes only to `chrome.storage.local` and to the service on `127.0.0.1`; the popup never shows it. Without the host, paste the secret under **Advanced, Connection** (`node src/cli.js pair` prints it).

## Agent direct

**Your agent drives by default** (`DEFAULT_DRIVER = "agent"` in `src/home.js`; `config.json` without a
`driver` means the same). The **Jev autopilot** is experimental and opt-in: `npm run setup -- --driver jev`
saves the choice and asks for the Jev key; once a key is saved, **Your agent / Jev autopilot
(experimental)** under the extension's **Advanced** section switches between them. No terminal
command or agent restart is needed: the daemon names its driver on every authenticated answer
(`X-Fai-Driver`), and the MCP server follows it, sends `notifications/tools/list_changed` and prefixes
the next result with what changed. Before the daemon has answered, the MCP server reads `config.json`
as a hint and never fails on it (a malformed file means the default driver, logged to stderr). Setup
belongs to the user; agents must not read pairing files or run interactive setup on their behalf.

**MCP surface.** With your agent driving the server lists `fai_browser_open`, `fai_browser_act`,
`fai_browser_observe` (these three with `_meta["anthropic/alwaysLoad"]`), `fai_browser_wait`,
`fai_browser_status`, `fai_browser_release` and `fai_browser_evidence`. `fai_browser_run` (with step
lists, retries and the call budget arguments) exists only while the Jev autopilot is selected; a host
whose tool list predates a switch may still call either surface's tools, and a run in direct mode opens
the task instead (a step list is refused).

- `fai_browser_open {origins, reason, task?, requestId?, mode?, suppliedText?, allowedUrls?, policy?,
  returnImages?}` requests the tab (or reuses a covering request), waits for approval within the call
  and returns the page. `task` is shown on the request and ranks the digest and the action listing;
  it never runs. The first `allowedUrls` entry is the page approval opens.
- `fai_browser_act {actionId | point | url | nav | key | tab | fills | dialog, revision?, text?,
  submit?, hover?, path?, reason?, requestId?, expectation?, returnImages?}` runs one offered action
  (or a [host-composed act](#host-composed-acts)) and returns the landing page with its actions and a
  new revision, and `did`: one trusted line per action that ran (`fill "Search" (12 chars)`, `press
  Enter in "Search"`; a typed value is never echoed, only its length). Revisions are single-use; an
  unknown or spent one is refused with the current revision. Without `returnImages` nothing is
  captured.
- `fai_browser_observe {requestId?, task?, focus?, digestChars?, waitFor?, maxMs?, logs?, mode?,
  suppliedText?, allowedUrls?, policy?, returnImages?}` reads the page again. `focus` ranks this digest
  by its words; `digestChars` (500-6000, default 1500) widens it. `waitFor` (`textIncludes`,
  `textAbsent` and/or `urlIncludes`) polls the page every 400 ms until it matches, up to `maxMs`
  (default 10 s, at most 30 s), matched on the redacted page the host is shown (a secret never
  matches); the result says `waited {passed, ms}`. `logs: true`: see [Dev logs](#dev-logs-and-javascript-dialogs).

**Standing terms.** The daemon keeps every request's host terms: forbidden labels are unioned, supplied
values and allowed URLs added (a later value for a name replaces the earlier one). An observe that
omits them keeps them; nothing can remove them, and an act inherits the terms of its offer.

**Results.** Open, observe and act return `{status, code?, requestId, verification?, page{url, title,
digest, truncated}, granted{level, asked}, revision, actions, moreActions?, consent?, overlay?, needs?,
did?, tabs?, dialog?, logs?, waited?, warnings?, callsLeft?, next}`: `status` is `observed` for a page read, `acted` for an act that landed
without an expectation to check, else the runtime status (`completed`, `needs_user`, ...). No verdict,
answer candidates, cost or step list. The text block puts `next`, the status, `granted: <level> (asked
<level>)` when the user approved less, needs and warnings first, then the page under the untrusted
heading (digest, cookie dialog, popup, one line per action). `next.kind` is one of `choose`,
`observe`, `answer`, `relay`, `wait` or `stop`; a stale page, an unavailable target or a failed
capture says observe again and choose.

**Enter submits.** A filled single-line text field offers `press Enter in "<label>"` (`submit_field`):
the page script classifies what its form submit amounts to (a search field or a safe submit label is
`submit_safe`, granted from `interactive`; any other form `submit`, from `full`; a form with a password
or payment field `sign_in` or `purchase`) and checks it again before it dispatches the key and
submits the form.

The daemon makes no provider calls, including warm-ups, action guards and answer ranking, even with a
saved key. Switching to your agent driving replies at once; it interrupts only Jev's own runs and
steps (a host act keeps going) and clears retained providers, without waiting for them to end. The
popup uses an authenticated extension-only `driver` message (HTTP fallback `/driver`) to read or save
the choice; no agent API exposes this change. Built-in origin, permission, action and field
restrictions, forbidden labels, approval and budgets remain; Jev's model-based purchase and commit
checks are absent. A purchase is offered as `needsApproval` ("asks the user") from `full` and runs only
after the user's **Approve once**; with that ask turned off, or below `full`, it is refused (`next.kind:
stop`: tell the user to do it themselves), as it always is with the Jev autopilot below testing. Login
and credentials stay the user's outside their approved testing environment.

### Host-composed acts

Beyond one offered id, `fai_browser_act` (and `POST /v1/act`) takes these, checked against the offer
before anything runs (`src/runtime.js` `checkActChoice`; a malformed one is `invalid_params`). Levels,
`policy.forbid`, the origins, the Approve gate, standing terms and secret redaction apply to each as to
an offered action, and the page script checks each again at dispatch.

- **Typed text.** A host-driven offer lists `fill "<label>" (act with text)` for every ordinary text
  field from `reversible`: never a password, payment, secret or sensitive field (secrets go through
  `fill_secret`; the page script refuses typed text there at every level, `testing` included). `text`
  (at most 5000 characters) is typed through `extension/input.js` like any fill. `submit: true` then
  presses Enter in that field as its `press Enter in` action (`submit_field`): the form submit's own
  class decides (`interactive` for a search, `full` for any other form; sign-in and purchase forms are
  refused), checked on the page the fill left. `fills: [{actionId, text}]` (at most 20) types several
  fields in one call in order, each on the page the previous one left (a field that changed label or
  class there ends the batch `stale`), then `submit` in the last. `suppliedText` keeps working.
  Results, traces and the audit log record a typed value's length only.
- **Navigation.** `url` opens an http(s) URL (relative to the page) on the granted origins at any
  level; another origin is `cross_origin` with `needs.message` naming it (request the tab again with
  it added, `fai_browser_open` with the `requestId`), a URL that names an action (sign-out, delete,
  payment) is refused, and the landing page's origin is checked again. `nav: "back" | "forward" |
  "reload"` uses the tab's own history (`tabs.goBack`/`goForward`/`reload`, the same in Firefox);
  where the page can tell (the Navigation API lists same-origin entries) a move with no entry on the
  approved site is refused before it runs, and otherwise the landing page's origin check pauses the
  lease as for any navigation.
- **Keys and hover** (`reversible` and up). `key` is one of Escape, Tab, Shift+Tab, the arrows, Home,
  End, PageUp, PageDown, Space and Enter, pressed in `actionId`'s control (focused first) or where focus
  is; a Ctrl/Cmd shortcut (a letter or digit, Shift allowed) needs `full`. Enter only as a filled
  field's submit (above). Space activates a focused control only when the page script clears it at the
  level (never a Delete button below `full`). `hover: true` with an `actionId` rests the pointer on that
  control (pointer path and boundary events, no press): a menu that opens on hover. A hover or key is
  gated by the level, never by the control's class.
- **Revisions.** `revision` is optional for plain clicks, links, fills, scrolls, keys and navigation:
  without it the act runs on the host's latest offer, and if the page changed meanwhile the same
  control is re-resolved on the fresh page only when exactly one offered action there has the same
  type, role, label, value and destination, on the same origin and path, its control the same risk
  class, with the same neighbours and no dialog in between (a click on a button also needs the page
  text unchanged); a label that names a class (delete, submit, purchase, ...) is never re-resolved, and
  the result warns `act_reresolved`. `revision` stays required for actions marked `needsApproval`,
  `fill_secret`/`copy_secret` and `point`.
- **The Approve gate's wait.** One act waits for the user's Approve click at most 60 s
  (`GATE_MAX_WAIT_MS`; with the act itself a call stays near 90 s, under Codex's 120 s
  `tool_timeout_sec`), and in Agent direct an open waits as long for the tab approval. On timeout
  `next.kind` is `approve`: the approval stays open for 5 minutes, and repeating the same act picks up
  a click given meanwhile at once.

### Popups and new tabs

**Tab access** defaults to **One task tab**. A page-created child pauses control for the user; it is
not adopted or closed. An offered approved-site `target=_blank` link can still open in the same tab.
**Multiple task tabs** is an explicit approval grant (`tabMode: "multiple"`), with visible host-access
permission for the approved origins. Enabling the preference does not expand an existing grant;
disabling it pauses an active multiple-tab session until a new approval.

With that grant, `fai_browser_act {openTab: "https://approved.example/path"}` opens and follows an
additional task tab, and page-created children on approved origins can join. The same mode and
origin restrictions apply in every tab. At most eight task tabs belong to a request; unrelated
personal tabs are never adopted. Task tabs share the managed group/window where browser grouping
is supported. Results list `tabs [{id: "t0", url, title, current?}]` (untrusted page text);
`act {tab: "t1"}` switches only among that list. A child outside approved origins or without host
access pauses the request. A closed child returns control to another remaining task tab.

CLI equivalents are `act --request ID --open-tab URL --revision R` and
`act --request ID --tab t0 --revision R`; the SDK accepts `client.act({requestId, openTab, ...})`.

### Frames

A **same-origin** frame (depth 1) is read as part of the page, as before. A **cross-origin** frame is read only when
its own origin is one the request approved: one of its exact `origins` (or the tab's origin), or with an approved
domain root an https origin under that root, and only when every frame above it was read too (nested frames up to
four levels, at most eight frames per page). Every other frame stays unread: nothing of its text, controls or
screenshot boxes is used, and it is only named.

- **How.** `page.js` lists each cross-origin frame it sees as a slot (its position in `window.frames`, its box in the
  viewport, the origin its element's `src` names) and never reads it. The worker
  ([extension/frames.js](../extension/frames.js)) asks the browser which frames the extension can reach (one
  `scripting.executeScript` with `allFrames`: a probe that returns each frame's own origin and path, nothing else; no
  `webNavigation` permission), runs the same `page.js` in each approved frame (pinned to its document) and merges the
  result: text after the page's, blocks after its blocks, controls with ids `f<n>.<id>` (`frame: "f<n>"`,
  `frameOrigin`, bounds moved into the top viewport), a frame's cookie dialog or popup when the page has none, and
  the union of the warnings. Frames get up to half of the 100-control cap (more when the page leaves room) and up to
  half of the 200 blocks; text is capped at 12000 characters in all. Structured records and derived views come from
  the top document only. Every frame call is bounded, so a busy or hung frame never holds a command or a screenshot:
  a probe gets 2 s (one that does not answer leaves the frames `unavailable`, and a screenshot boxes the frame whole
  and is taken again, then withheld), a read 3 s, and an act fails as `timeout` once the frame has not answered for
  6 s and a further 2 s probe.
- **One revision.** With frames read, the observation's revision stands for the page and every frame
  (`<page revision>.<n>`). An act on `f<n>.<id>` runs in that frame on the frame's own revision; the worker first
  probes the frame again: gone or on an origin the request does not approve, `cross_origin` (nothing runs, the
  session stays active); another document on an approved origin, `stale`. It also looks at the page again (one cheap
  read of the top document): a page whose revision changed since the observation is `stale`, and the frame runs with
  the page's current facts (a page that turned into a checkout makes the frame's "Continue" a purchase). An act on a
  page control (click, Enter in a field, a key, a select, a fill, an upload; not a hover) first takes one cheap look
  at each frame read, for the same reason. A
  frame document the browser no longer has when the act is injected is never reported as done: the frame is probed
  again (`stale` or `cross_origin`). In the frame, `page.js` checks again that
  the frame and every ancestor the browser names (`location.ancestorOrigins`, Chromium) are on approved origins. A
  link that would navigate the tab from a frame (`_top`) must stay on the tab's approved site; a link that navigates
  the frame must land on an approved origin. A frame-local navigation is waited for (3 s cap), then the whole page is
  observed again.
- **Same protections.** The frame runs the same page script with the same level, `forbid` list, Approve gate, secret
  redaction, vault and consent detection. An Approve card for a frame control names the frame's own origin "in a frame
  of" the page, and the approval is bound to that origin (a secret's cross-site warning compares with it). One page context covers the tab: a purchase page, a password or payment
  field, or a credentials page in any document (page or frame) applies to every document (a "Continue" in a frame
  of a checkout page is a purchase control; a search submit is not a safe submit when a frame holds a password
  field). One that no longer applies anywhere is dropped again, and the documents are read again without it.
  Screenshots place each read frame's own boxes (secrets and fields) by where the frame is at the capture: the page
  script names every cross-origin frame's current box by its current position in `window.frames`, and the worker finds
  each read frame again by its frame id (its current position, origin, document and size), never by the position it
  had (removing an earlier frame, as ad rotation does, shifts every later one). The frames are asked in parallel within
  one 2 s cap. A read frame that does not answer, a box whose frame is not the one read there, and **every
  cross-origin frame, `<object>` or `<embed>` that was not read** are boxed whole, so nothing of them shows; frames
  past the slot and frame caps, deeper than four levels or not found in `window.frames` are boxed by the page script
  itself. A read frame that moved more than 2 px between the queries before and after the capture, that changed size,
  or that no query can place, makes the capture be taken again, then withheld.
  Strict mode still boxes every cross-origin frame. A frame whose own size does not match the box `page.js` saw at its
  position (the page moved its frames in between) is not read (`unavailable`), and an opaque (`null`) ancestor refuses
  every call in the frame. A point click on a frame is refused as
  `point_frame`: name the frame control's action id instead.
- **Results.** `frames` lists the page's cross-origin frames: `{id: "f1", origin, read: true}` for the ones read and
  `{origin, read: false, reason}` for the others, `reason` one of `not_approved` (the request does not list the
  origin), `no_access` (it does, but the browser gives the extension no access to it), `sandboxed` (an opaque
  origin), `limit` and `unavailable`. `declared: true` marks an origin only the frame element's `src` names (the
  browser did not report one). Every origin there is page content (a page chooses its frames): `frames` sits with the
  untrusted page text, and the trusted `next` only counts the unread frames and says to ask the user and call
  `fai_browser_open` with their origins added; check them with the user first. Any unread frame keeps the
  `cross_origin_frame` warning. Origins are all a result ever carries of an unread frame.
- **Browser access.** The extension needs host access to the frame's origin. Approving in the request modal asks
  the browser for the tab's host and the request's other exact origins in one prompt (at most 10 of them; the ones it
  adds are removed again when the session ends; a list it cannot ask for falls back to the tab's host alone); "Allow on all sites" covers every origin. A toolbar-icon approval grants `activeTab`, which covers
  the tab's own origin only, so approved frames on other origins come back as `no_access`: approve from the request
  modal instead. Firefox: the same code path (`frameIds` in place of document ids, no `ancestorOrigins` check) is
  untested.
- **Example: Microsoft Entra admin center / Azure portal.** The content blades are cross-origin frames on separate
  portal-hosting origins. Observe once with the portal's origin: `frames` names the blade origins (`not_approved`).
  Then request them up front, together with the sign-in origins, for example `origins: ["https://entra.microsoft.com",
  "https://login.microsoftonline.com", <the blade origins from frames>]`. The exact blade hosts vary by portal and
  tenant; take them from `frames`, not from this page.

### Dev logs and JavaScript dialogs

**Test site only.** A session granted at `testing` (every origin listed under Test sites) registers
`extension/devhook.js` in the page's own world and `extension/devlog.js` beside `page.js`, at
`document_start` for its origins (`scripting.registerContentScripts`, `world: "MAIN"`; Firefox 128+ has
the same), and injects both into the page open then. Nothing is registered at any other level, and the
registration goes when the session stops. The hook wraps `console.error`/`warn`, `fetch`,
`XMLHttpRequest`, `alert`, `confirm` and `prompt` in the page's world: **the page can see it and can
forge what it reports**, so it is acceptable only on the user's own test sites, and everything it
reports is untrusted page text, redacted like the page.

- `fai_browser_observe {logs: true}` returns `logs [{kind, text, method?, url?, status?}]` since the
  last read: console errors and warnings, uncaught errors and unhandled rejections, and fetch/XHR
  responses with status >= 400 or a network failure (method, URL without its query, status; never a
  request or response body or header). At most 50 per read (`logsDropped` counts the rest). Below
  `testing` the observe carries the warning `logs_need_testing` and nothing is read.
- **Dialogs.** `alert`, `confirm` and `prompt` never block on a Test site: each is answered at once,
  dismissed unless `act {dialog: "accept" | "dismiss", text?}` armed the answer for the next one (once,
  within 60 s; `text` is a prompt's value). The result after it shows `dialog {kind, text, answered}`.
  Accepting after a dialog whose text names a delete or purchase asks **Approve once** (kind `dialog`;
  the card shows the dialog's text). Below Test site no hook exists: a native dialog blocks the page,
  and a page call that stops answering (a one-line probe after 6 s gets no answer within 2 s) fails as
  `js_dialog` (`needs_user`, relay: the user answers it, then observe). No `debugger` permission is
  involved.

### Uploads

An `<input type=file>` is offered from `full` (Act and Test site) as `upload a file to "<label>" (act
with path) (asks the user)`; a styled picker that hides its input is offered at its label. `act
{actionId, path, revision}` names a file in the host's workspace: the MCP server resolves `path`
against `FAI_WORKSPACE` (else its own working directory, the project the host runs in) through every
symlink and refuses anything outside it (`..`, an absolute path elsewhere, a symlink that leads out),
anything but a regular file, and files over 10 MB. The daemon reads that real path again (same size)
and sends the bytes to the extension only. Every upload asks **Approve once**, whatever the settings:
the card shows the file name, its size and the site that receives it, and the approval binds to that
name and size (the worker checks the bytes it got against them). `page.js` delivers it as a user's pick
would (`DataTransfer`, the input's `files`, then `input` and `change`). Results, traces and the audit
log keep the name and size only.

Status reports `driver` and `provider.default: null` in direct mode. HTTP/SDK `POST /v1/runs` returns
`409 agent_direct`. CLI users use `request-tab`, `wait`, `observe` (`--capture last` for a screenshot),
then `act`; `run` and `step` need the Jev autopilot. The installed
[skill](../skills/fai-browser/SKILL.md) describes the loop; [jev.md](../skills/fai-browser/jev.md)
the experimental autopilot. The published benchmarks measure the Jev autopilot.

## The daemon

One long-lived daemon on `127.0.0.1:4318` owns tab requests, leases, runs, traces, retention, provider settings and the Jev key. The CLI, the MCP server and the SDK client start it automatically on first use, so you rarely touch it:

```sh
node src/cli.js daemon status            # running?, extension connection, open requests and runs
node src/cli.js daemon logs --lines 50   # JSON lines; never contains keys, secrets or page text
node src/cli.js daemon stop | start | restart
node src/cli.js daemon                   # run in the foreground (what auto-start spawns)
```

With the Jev driver, at start and whenever the user approves a tab, the daemon warms the provider connection in the background (an unauthenticated `GET /v1/models` that sends no key), so the first decision does not pay for DNS, TCP and TLS. Readiness never waits for it, and a missing key or an unreachable network only logs `provider_warm_skipped` or `provider_warm` with `ok: false` (codes and timings, never messages).

State lives outside the checkout, in per-user directories. **Settings** (`.env.local`, the optional `config.json` with driver, retention, provider defaults, request TTL, thresholds, `guardrails`, `retry`, `slim`, `profiles`, `updateCheck`, and the native host launcher) go to `$XDG_CONFIG_HOME/fai-browser` (default `~/.config/fai-browser`) on Linux, `~/Library/Application Support/fai-browser` on macOS and `%APPDATA%\fai-browser` on Windows. **Runtime state** (`client-token`, created by the daemon on first start and sent by clients as a bearer token, `daemon.json`, `daemon.lock`, `daemon.pid`, `logs/daemon.log`) and `artifacts/` go to `$XDG_STATE_HOME/fai-browser` (default `~/.local/state/fai-browser`) on Linux, the same Application Support directory on macOS and `%LOCALAPPDATA%\fai-browser` on Windows. `$FAI_HOME` puts all of it in that one directory instead; under `node --test` without `FAI_HOME` a per-user temporary directory stands in, so tests never touch the real settings. [Site profiles](#site-profiles-experimental-opt-in) are read from the package's `domains/` (or `$FAI_HOME/domains`, `$FAI_DOMAINS_DIR`). Every CLI command except `install`, `install-native` and `uninstall-native` starts the daemon when it is not running; `--no-auto-start` makes it fail with `daemon_unreachable` instead. `--port N` (or `FAI_DAEMON_PORT`) selects the daemon port everywhere; a port other than 4318 also needs `host_permissions` in `extension/manifest.json` for the HTTP fallback (the native host tells the extension the port). `fai-browser serve` is a deprecated alias for `daemon`.

A tab request (`POST /v1/requests`) may carry `url`, the page the extension opens when the user approves: an http(s) URL on one of its `origins` (at most 2048 characters; off the origins is `422 origin_not_granted`). Without it the daemon uses the first exact origin's root, else `https://<root>/` for a request with only domain roots (the site may redirect that apex to www). Every request view (`GET /v1/requests`, `/v1/wait`, the extension's request list) has `url`. The MCP server fills it from the first `allowedUrls` entry on the origins, else the first URL the instruction (or first step) names after a navigation verb ("Open https://...") on the origins, never one a `{{answer:N}}` writes in; the CLI does the same from `--origin` and the instruction (it has no `--url` flag).

|---|---|

### Several browsers

The extension may be paired in more than one browser at a time (say the signed Firefox add-on and an unpacked
Chromium, or two Chrome profiles), all with the same daemon and pairing secret. Each install keeps a random browser
id in its extension storage (`browserId`, created once) and sends it with every connection: the `browser` parameter
of the WebSocket URL, the `X-Fai-Browser` header of every long-poll call, and `hello.browser {product, name,
version}`. Origins and the secret are checked per connection exactly as before, and an id is bound to the extension
Origin it first came from (kept in `browsers.json` in the state directory with the browser's last use): a claim of a
known id from another Origin is refused (WebSocket close `4004`, HTTP `403 identity_refused`). The refused extension
gives up its own claim once: it creates a new id and connects again; refused a second time, it stops and its popup
says so until opened again. Status then shows `extension_identity_refused` (how many connections, and when last) for
ten minutes. The daemon remembers the 64 ids it saw most recently, dropping disconnected ones first. Extensions are
never sent another browser's id or lease: their request list marks each request `browser {product, name, mine}`,
keeps `lease` only on the browser's own requests, and lists the connected browsers as `{product, name, self}` (two
with one name read "Chrome" and "Chrome (2)"); agents see ids and leases in status.

**Legacy extensions.** The 0.5.0 Firefox add-on and older unpacked builds send no id and are known by their extension
Origin (unique per Firefox install; shared by Chromium-family browsers that load the same unpacked extension). They
connect side by side with other browsers without fighting, but see only the requests meant for them, with no **Open
here**, until they update (the next release's signed add-on carries it). Two legacy Chromium-family builds of the same
unpacked Origin still count as one browser and can replace each other; `extension_flapping` shows it.

- **Connections.** The hub keeps one connection per browser, each with its own socket or long-polls, outbox and
  liveness. A newer connection of the same browser (a restarted service worker) closes the old socket with `4003`,
  and the extension never reconnects on `4003` (until the popup opens, or after five minutes), so two copies of one
  profile swap the connection at most on each popup open or every five minutes; a superseded socket that had said
  hello and lived over 10 s adds the warning `extension_duplicate_identity`. A connection of another browser never
  closes anyone. Before 0.6 every new connection closed the previous one with `4000`, whatever the
  browser, and two paired browsers replaced each other about twice a second (issue #9); the extension now backs off
  on repeated `4000`s from such an older service (at least 4 s, then 8 and 15 s) and its popup says another browser
  keeps taking the connection. A connection only resets its backoff after lasting 10 s.
- **Which browser a request opens in.** A new tab request waits in the browser the user used FAI in most recently:
  the last approval, popup open or toolbar click there (the extension's `used` message); never used, the one connected
  last. An agent may name one: `browser` on `fai_browser_open`, `fai_browser_run`, `request-tab --browser` and
  `POST /v1/requests`, matched (case-insensitive) on the product the extension reports (`firefox`, `chrome`,
  `chromium`, `edge`, `brave`, `opera`, `vivaldi`), its name, or a browser id from status. A browser that is not
  connected is refused with `409 browser_not_connected`, whose message names the connected ones ("Connected: Chromium
  (chromium), Firefox (firefox)"). When a request's browser has been gone longer than the disconnect grace (3 s), a
  request nobody named moves to the one used last; one the agent named, or the user moved with Open here, waits a
  minute first (a laptop sleep or a service restart moves nothing). It then gets `browserNote` ("Firefox disconnected;
  the request now waits in Chromium."), which the agent's approval hint repeats, until the user moves or approves it;
  with no browser connected it waits for the first one. The last
  use survives a daemon restart or update (`browsers.json`).
- **Every popup lists it.** Only the browser a request waits in opens its approval window or task tab and shows the
  `?` badge. Every other connected browser's popup lists it as **In another browser** with **Open here**, which moves
  it there (the `move` message; the request then stays in that browser). Deny works from any of them.
- **Leases belong to a browser.** The approval binds the lease to the browser that approved it; every command, cancel
  and `lease_update` for it goes to that connection only, and a status or `lease_level` from another browser is
  ignored, as is a result or screenshot from a connection the command was not sent to; Release (Deny on a paused
  request) works only in the browser that holds the tab. One active lease per browser: approving a second request in
  the same browser supersedes the first there,
  while a tab in another browser keeps running. A browser that disconnects, or whose worker restarts (a hello without
  a session), pauses only its own leases (`disconnected`, `session_inactive`).
- **Where it shows.** Request views carry `browser {id, product, name}` (the browser that holds the tab, else the
  one it waits in) and `lease.browserId`; receipts' `permissions.browser` and the direct result's `granted` line name
  it. `daemon status`, the CLI `status` and `fai_browser_status` list every connected browser under
  `extension.browsers` (and every known one under `browsers`): `id`, `product`, `name`, `version` (the extension's),
  `browserVersion`, `transport`,
  `connectedAt`, `lastSeen`, `lastUsedAt`, `closesLastMinute` and its `leases`. A browser whose connection closes more
  than 8 times in a minute adds the warning `extension_flapping: <name> (<id>) lost its connection N times in 60 s`
  (and logs `extension_flapping` once), so a reconnect loop is never silent again.
- **Settings.** Each browser's popup settings stay its own: the per-request budget, "Open requested pages right away"
  and the Approve gate's asks apply to the requests that browser holds or awaits (the browser used last when a request
  has none yet), and so do its Permissions, test sites and secret redaction. Status shows the budget of the browser
  used last.

### Updates

FAI Browser tells you when a newer **tagged release** of [jedbjorn/fai-browser](https://github.com/jedbjorn/fai-browser/releases) is out and installs it only on your click or command; it never tracks `main` and never installs on its own.

```sh
node src/cli.js update --check   # look now and print the update view (installs nothing)
node src/cli.js update           # install the latest release into this git checkout
```

**The check.** The daemon asks `GET https://api.github.com/repos/jedbjorn/fai-browser/releases/latest` (GitHub leaves drafts and prereleases out; a draft, prerelease or a tag other than a plain `vX.Y.Z` counts as no release) 30 s after it starts when the last check is more than a day old, then about once a day (after a failure, again after an hour; after a rate limit, after GitHub's reset time, at most a day away; a last check dated in the future counts as due). When the release is newer than `package.json`'s version, one more GET (`/repos/jedbjorn/fai-browser/commits/<tag>`) asks which commit the tag names (always the tag itself, never the release's `target_commitish`). Both requests are plain https: `User-Agent: fai-browser-update-check`, no token, no cookie, nothing about you or your machine, `If-None-Match` with the cached ETag, a 10 s timeout, no redirects. Nothing of the answer is kept but the tag, its version, the commit and the publish time; the release notes link is built from the tag. A failure only sets `status`, and a check stopped by a daemon shutdown records nothing. The result is cached in `update-check.json` in the runtime state directory (next to `daemon.json`), so the CLI and the daemon share it. Off: `FAI_UPDATE_CHECK=0` or `"updateCheck": false` in `config.json`; under `node --test` the daemon never checks unless a test asks it to.

**A private repository.** The anonymous API answers a private repository with 404. Then a git clone falls back to `git ls-remote --tags <remote>` on the clone's own remote that is `github.com/jedbjorn/fai-browser`, with your own git credentials (ssh agent or credential helper; FAI stores and reads no token), never prompting (`GIT_TERMINAL_PROMPT=0`, ssh in batch mode unless you configured an ssh command for git), with a 30 s timeout and the same scrubbed environment as every updater git call. Every updater git call runs in a process group of its own, and a timeout kills the whole group, so no ssh or credential helper is left behind. The automatic check runs this fallback about once a day, **using your ssh agent or credential helper in the background**: an agent that confirms each use (1Password's ssh agent, `ssh-add -c`, a FIDO key that wants a touch) may then ask once a day. `FAI_UPDATE_CHECK=0` or `"updateCheck": false` in `config.json` turns the automatic check off; `node src/cli.js update --check` still checks when you run it. It takes the highest plain `vX.Y.Z` tag and, for an annotated tag, its peeled commit (`^{}`). That path cannot see drafts or prereleases, so **only final releases may get a `vX.Y.Z` tag** (prereleases use `vX.Y.Z-rc.N`, which never counts). `source` says which path found the release (`api` or `git`); the notes link is still built from the tag and needs repository access to open. A fork or a clone with no remote of that repository has no release there: `not_found` (`update` says `no_release`, exit 0), as when no tag matches. A real git failure (network, credentials, timeout) is `error` with `git_failed`.

**Where it shows.** `node src/cli.js status`, `daemon status` and `fai_browser_status` carry `update`:

| Field | Meaning |
|---|---|
| `enabled` | the automatic check is on |
| `installable` | this copy is a git clone that can update itself; false (an npm install): the popup says to update the way you installed it and shows no button |
| `source` | `api` or `git` (see above), null before a check |
| `current`, `latest`, `tag` | this version; the latest release's version and tag (null before a check or when there is none) |
| `available` | `latest` is newer than `current` |
| `notesUrl` | `https://github.com/jedbjorn/fai-browser/releases/tag/<tag>` when available |
| `checkedAt`, `status`, `error` | last answered check; `never`, `ok`, `not_found` (no published release), `error` (`network`, `timeout`, `http_<status>`, `bad_json`, `git_failed`) or `rate_limited` |
| `install` | the last install: `{state: running\|succeeded\|failed\|rolled_back\|up_to_date, from, to, at, step, error, message}`, or null |

The extension popup shows **Update available vX.Y.Z** with a **Release notes** link and an **Update** button; `fai_browser_status` adds one line telling the agent to tell you, never to update itself.

**Installing** (the popup's Update button, or `node src/cli.js update`). The popup's click reaches the daemon only over the extension's paired channel, and there is no client-API route for it, so an agent's MCP call cannot start an update; an agent with a shell can run `node src/cli.js update` like any other CLI command, the same trust the CLI already has (it could run `git pull` just as well), and every refusal below still applies. On the click the daemon starts `node src/cli.js update --tag <tag>` in its own process (the update restarts the daemon) and at once creates `update.lock` (exclusively; when another update took it in the meantime, the child just started is stopped and the click is refused with `update_running`) and a `running` install record for it, so a second click finds the update running; an updater removes the lock only while it still names its own pid. **While an update runs the daemon refuses new tab requests** (`POST /v1/requests`: 503 `update_running`, "retry in a minute") **and tab approvals** (the popup shows the same reason), since the restart would cut such a task off. A lock or running record whose process is gone is stale, and so is one whose pid now belongs to another process: on Linux the record keeps the process start time (`/proc/<pid>/stat`) and compares it; elsewhere a record older than 45 minutes counts as stale.

1. **Refusals, before anything changes** (each prints what to do instead, and the popup shows it): a tab lease is active or paused (`lease_active`); the package is not a git clone (`not_git`: an npm install updates with npm); no remote is `github.com/jedbjorn/fai-browser` (`wrong_remote`); tracked files have local modifications (`dirty`; the updater never stashes, resets or discards them); the checkout is on a branch other than `main` (`other_branch`); `main` has commits its upstream lacks (`unpushed`); another update runs (`update_running`). An error of git itself here (a corrupt index) is reported with its own reason as `failed`, "Nothing was changed".
2. `git fetch --tags <remote>`, then the tag must name the commit the release names (from the API's `/commits/<tag>`, or the `ls-remote` peeled commit) and its `package.json` must carry the release's version (`tag_mismatch`, `tag_missing`), and the checkout's commit must be inside the release (`not_fast_forward`). A checkout already at the release commit is not moved or installed again.
3. **The move.** On `main`: fast-forward `main` to the tag's commit (`git merge --ff-only`). On a detached HEAD (an earlier update or a clone of a tag): check the tag's commit out, detached. Never any other branch. When git refuses (an untracked file in the way) nothing moved: `move_failed`.
4. **Best effort:** `npm ci --include=dev --ignore-scripts` only when `package-lock.json` changed and `node_modules/` exists. The runtime has no npm dependencies, so a failure is a warning in the result and the record (run `npm ci` yourself for the development tools), never a rollback.
5. The new version's refresh, `node src/cli.js update --finish`: the native messaging host launcher and the manifests that already exist, and the skill in each user-level skill directory an earlier `install` wrote (`~/.claude/skills/fai-browser`, `~/.agents/skills/fai-browser`; symlinked or foreign skills are left alone; a project-level install is not discovered, its version marker says to re-run `install`). Settings, keys and the pairing secret are never changed, printed or asked for (the manifest names the extension ID it already names).
6. The daemon restarts and must come back with the new version. **Right before it stops the daemon the updater reads the leases again**: a tab approved in the meantime (only a race gets past the gate above) rolls the update back without stopping the daemon, so that task keeps its tab (`lease_active`, "update again when it is done"). A Chromium-family browser then reloads the extension by itself (`chrome.runtime.reload()`, once per new service version, never during a session), so `extension/` loaded unpacked runs the new files. Restart your coding agent to load the new MCP server and skill.

A failure in steps 5 and 6 rolls back: `main` goes back with `git reset --keep <previous>` (only when `main` is still at the release commit; `--keep` refuses to touch a file with local changes), a detached checkout checks the previous commit out, then the refresh runs again for the old version, and the old daemon is started again only when the update had sent it a shutdown (after a refresh failure, or a restart that stopped at the lease check, the old daemon never stopped and keeps running); `node_modules/` is left as it is. The result and the popup say `rolled_back`, or `failed` with the reason when the rollback itself failed. From the move on, the install record names the release commit and the commit before it. An update that stopped after the move (the updater killed, a failed rollback that left the release checked out, or a resume a held tab refused, which keeps its resume marker) is finished by the next `node src/cli.js update`, but only when HEAD is that recorded commit and the checkout passes the same checks as an install (a git clone of the repository, no local changes, `main` or detached): the refresh and the restart of the version on disk. Anything else takes the normal path, so a checkout that merely says the same version in `package.json` is never "finished". Every run leaves an install record (also `up_to_date` and early refusals), except while another live updater owns it.

**Secrets and environment.** The updater and everything it starts get the daemon's launch environment, taken before the daemon adds the Jev key from `.env.local`, without `TYPESAFE_API_KEY`, `FAI_BRIDGE_SECRET`, `FAI_CLIENT_TOKEN` or any variable whose name ends in KEY, TOKEN, SECRET, PASSWORD, PASSWD, PASSPHRASE or CREDENTIALS (`OPENAI_KEY`, `AWS_SECRET_KEY`, `SSH_PRIVATE_KEY`), and without `GIT_DIR`/`GIT_WORK_TREE`. git and npm get only an allowlist (`PATH`, home and locale, ssh agent, the credential helper's session bus, `GCM_*` and `GH_CONFIG_DIR`, proxies and CA files, git config location). The restarted daemon reads its key from `.env.local` again, so a key you removed stays removed (a key exported only in the shell that started the daemon is not carried over). Each step goes to `logs/update.log` (events, versions, step names, first lines of git errors with any credentials in a URL removed). Every git, npm and node call is `execFile` with an argument list (no shell); the only values from the network that reach one are a tag matching `^v\d+\.\d+\.\d+$` and a 40-hex commit. `update` prints one JSON line with `state` and exits 0 (`succeeded`, `up_to_date`, `no_release`) or 1 (`refused` with a `code` and `hint`, `failed`, `rolled_back`, `check_failed`). Windows is untested.

**Firefox.** The signed add-on carries `update_url` (the latest release's `updates.json`), so Firefox updates the add-on itself; the updater updates the clone and the service only. **While the repository is private that URL needs a GitHub login Firefox does not have, so Firefox cannot update the add-on**: install the new release's `.xpi` by hand from the Releases page. A temporary add-on loaded from `dist/firefox/` needs `npm run build:firefox` and a reload in `about:debugging` after an update.

## Coding agents (MCP and skill)

```sh
node src/cli.js install --host claude     # ./.mcp.json + ./.claude/skills/fai-browser/
node src/cli.js install --host codex      # ~/.codex/config.toml + ./.agents/skills/fai-browser/
node src/cli.js install --host opencode   # ./opencode.json + ./.agents/skills/fai-browser/
```

Options: `--scope user` (Claude: prints `claude mcp remove --scope user fai-browser 2>/dev/null; claude mcp add-json --scope user fai-browser '<entry>'`, since `claude mcp add` has no flag for `alwaysLoad` and `add-json` refuses an existing entry, and installs the skill in `~/.claude/skills/`; OpenCode: `~/.config/opencode/opencode.json`; skills in `~/.agents/skills/`), `--link` (symlink the skill), `--dry-run` (print the planned writes as JSON), `--force` (replace an existing Codex entry or a foreign skill directory), `--command-name` (write the bare `fai-browser-mcp`) and `--always-load` (Claude only, see below). It writes absolute `node` and `src/mcp-main.js` paths because the package is not on `PATH`, and adds `FAI_HOME` as server env when set. JSON configs are merged (only the `fai-browser` entry) after a `<file>.bak-<timestamp>` copy; running it twice changes nothing. A JSONC file or a hand-written Codex entry is left alone: the snippet is printed and the command exits 2. Restart the host afterwards.

The Claude Code entry is `{"mcpServers":{"fai-browser":{"type":"stdio","command":"/abs/node","args":["/abs/src/mcp-main.js"]}}}`. Claude Code defers MCP tools behind tool search by default, which costs one extra model round trip the first time a session uses them. The server marks the tools of its loop with `_meta: {"anthropic/alwaysLoad": true}`, which Claude Code honours per tool (with your agent driving: `fai_browser_open`, `fai_browser_act` and `fai_browser_observe`; with the Jev autopilot: `fai_browser_run`), so the loop is in the first request without any config and the rarely used tools stay behind tool search. `--always-load` adds `"alwaysLoad": true` to the entry: all seven schemas (about 2k tokens, cached, of which about 1.5k are the six rarely used tools) go into every request, and Claude Code waits for such a server at startup (up to about 5 s) instead of connecting it in the background. Use it only when choose/wait/observe paths are frequent enough that their tool-search turn matters. Both were checked against Claude Code 2.1.289: its stdio server schema accepts `alwaysLoad` ("all tools from this server are always included in the prompt and never deferred behind tool search"; `"alwaysLoad": false` defers all seven, overriding the `_meta`) and `claude mcp add-json` keeps it. In project scope a rerun with or without `--always-load` updates the entry, with a backup; in user scope the printed command removes and re-adds it. Codex (0.160) and OpenCode (1.18) have no per-server loading option, so their entries are unchanged and `--always-load` is refused for them; Codex's first-use schema load stays. The Codex block also sets `startup_timeout_sec = 20`, `tool_timeout_sec = 120` and `default_tools_approval_mode = "approve"`, which `codex exec` needs because it cannot answer approval prompts.

`fai-browser-mcp` (`src/mcp-main.js`) is a stdio MCP server (spec 2025-11-25; also answers 2025-06-18 and 2025-03-26 clients) with seven tools per driver. With your agent driving (the default) they are `fai_browser_open`, `fai_browser_act`, `fai_browser_observe`, `fai_browser_wait`, `fai_browser_status`, `fai_browser_release` and `fai_browser_evidence`, described in [Agent direct](#agent-direct); its server instructions (about 1.65k chars, bounded by `test/agent-direct.test.js`) cover that loop. The rest of this section describes the surface of the experimental **Jev autopilot**:

| Tool | Purpose |
|---|---|
| `fai_browser_run` | the default and usually the only call: a bounded task with an `expectation` and optional `answerQuestion`, or a `steps` list of such hops in one call (see [Step lists](#step-lists)). With `origins` and `reason` it reuses or creates the tab request and waits for approval first; `maxActions: 1` is a single step; optional `minConfidence` (control floor), `policy` (extra control labels to refuse, see Guardrails), `maxCalls` and `maxMs` (the request's call budget) |
| `fai_browser_wait` | wait for a running run (`runId`) or a pending request (`requestId`), `maxMs` ≤ 45000 |
| `fai_browser_observe` / `fai_browser_act` | host-driven control: the page digest and offered actions as short lines (`a3  click "About"`; at most 40 control actions at read-only and reversible, 80 from interactive up, the most relevant when there are more, with `controls_capped:<n>`: see [Offered actions](#offered-actions)), then one of them by `actionId` and `revision`, or a `point {x, y}` of the observe screenshot instead of an `actionId` (see [Point clicks](#point-clicks)). An act's result (a point click's too) carries the landing page's offer (`revision`, `actions`, `moreActions`, listed as an observe lists them; `next.kind: choose` with `step_complete`), so a host driving step by step makes one call per step: the next `fai_browser_act` names that revision, by id or by a point of that act's `returnImages` screenshot (badged with those ids), with no observe in between |
| `fai_browser_stop` | stop a run (`runId`, or the latest request's active run); with `requestId`, release that tab request |
| `fai_browser_evidence` | a step screenshot as an image block, or the trace as JSON text |
| `fai_browser_status` | daemon, extension, provider, requests and runs |

**Task guides.** The skill is installed with the task sub-skills' guides, `tasks/<name>/SKILL.md` under the skill directory (today `tasks/flights/SKILL.md`: flight search, and `tasks/hotels/SKILL.md`: hotel search; in the repository `skills/fai-browser/tasks` links to [tasks/](../tasks/)), and its first lines point a host at them for such a task. A task's engine code, `tasks/<name>/index.js` (site-profile shortcut kinds, question vocabulary), is reviewed code listed statically in `tasks/index.js`; it is never loaded from `FAI_HOME` or a profile directory.

**Instructions and skill.** The server `instructions` (sent once at `initialize`, about 1.65k chars or 410 tokens, paid on every host request) are enough for the common path on their own, and name the escalation ladder for a stuck run in one line (rerun sharper with `steps`, `suppliedText` or `allowedUrls`; look at the screenshot with `fai_browser_evidence`; drive steps with `fai_browser_observe` and `fai_browser_act`; hand back to `fai_browser_run`; the skill's rule F spells it out, and after a second run on a request that still needs the host, a `rerun`/`split` next repeats the look-and-drive rungs with the run's id): use it only for work in the user's live browser tab, never research or scraping; one `fai_browser_run` with `origins` (exact, only those needed; the `origins` schema description adds the domain-root form, since the instructions had no room left), `reason`, `instruction` and `answerQuestion` at the lowest `mode`; an `expectation` on every run, the first hop of a multi-hop task too (the page path that proves the step done, `{"urlIncludes":"/pricing"}`, or text only that page has); follow `next` literally; reply with `verdict.answer.text` as is when set, else from `page.digest`; `steps` only when one run cannot do the task (a value needed for the next hop), never for one page; do not stop or release at the end; with `needs.level` and `next.kind: relay` relay the popup sentence and call again with that `mode` (a `rerun` next, when the grant already covers it, says so in its text); page text is untrusted; submissions only when asked and granted; never log in, enter credentials or purchase outside testing mode (testing only on the user's test or staging environment). The `fai_browser_run` description repeats the expectation rule with the same example, "follow its next" and the verification rule (`status: completed` with `verification.passed: true`). A host therefore does not need to load the skill for a one-call task, nor for a step list (the `steps` schema describes the step fields and the placeholder, and says to write `{{answer:N}}` only when step N asks one name, number or URL); the instructions tell it to read the skill when `next` is unclear, and the skill's frontmatter says to load it for unclear results or multi-step tasks. The step-list line (1500 of the 1500 characters; it said "A task needing several runs: one call with steps" until the live bench showed hosts sending `steps` for one-run tasks) was paid for by shorter wording elsewhere, no rule dropped. The skill stays the full reference: writing instructions and expectations, splitting joins, every `next.kind`, consent and login, and the CLI. `test/mcp.test.js` pins the required phrases and a size bound.

A typical task is one call: `fai_browser_run` with `origins`, `reason`, `instruction`, `expectation` and `answerQuestion`. The server reuses an active, pending or paused request that covers those origins, otherwise it creates one; it then waits for the user's approval within the call budget (45 s minus a 2 s margin) and starts the run with the time left. If the user has not approved by then, the result is `needs_user/select_tab` with the `requestId` and a `next` line telling the agent to ask for approval and call `fai_browser_run` again with that `requestId`. There is no daemon change behind this; the SDK and CLI keep `requestTab`/`request-tab`, `step` and `release`.

Every call returns within 45 s (`FAI_MCP_MAX_CALL_MS`), plus up to 60 s waiting for the user's approval (`FAI_MCP_APPROVAL_WAIT_MS`); a longer run returns `state: "running"` and the agent continues with `fai_browser_wait`. MCP results have **one model-visible payload, a readable text block, and no `structuredContent`** (the tools declare no `outputSchema`; see [the host research and choice](dev/mcp-result-shape.md)). A run result puts `next (<kind>)` first, then trusted lines (`verdict`, `why`, `suggested`, `budget`, `needs.message`, ids) and everything page-derived under one "untrusted page text" heading (final URL and title, the auto-confirmed answer, `answer.candidates`, `page.digest`, `trail`, decide options, the step path), then the trace path. Its `earlier pages` section groups `trail` by state, prints a section heading shared by a state's lines once, leaves out lines already listed as the answer or a candidate and stops at 2000 characters (the evidence trace keeps every line). `reason` is left out of the text when `verdict.why` has machine codes. Status, wait, release and evidence metadata use compact `key: value` lines rather than a JSON mirror; screenshots and trace JSON remain separate content blocks.

Loop stoppers: each `requestId` has a call budget (`maxCalls` run/act/observe calls and `maxMs` of run time; 50 calls and 1200000 ms, 20 minutes, by default). Its ceiling is the user's: the popup's **Per-request budget** fields under Advanced (see [Per-request budget](#per-request-budget)), else `"budget": {"maxCalls", "maxMs"}` in `config.json`, else the defaults; a call's own `maxCalls`/`maxMs` can only lower it (a higher value is clamped with a `budget_capped:<field>:<ceiling>` warning). Bounds everywhere: `maxCalls` 1 to 500, `maxMs` 1000 to 14400000 (4 hours). `verdict.budget` shows what is used; with nothing left, a `rerun`/`choose`/`split` next step becomes `stop`, and further calls return `budget_exhausted` / `task_budget` without reaching the daemon. A `select_tab` result costs nothing. A `fai_browser_run` that repeats the previous call's instruction, expectation, `allowedUrls` and `maxActions` after a `needs_host`, `unverified` or `budget_exhausted` outcome is refused with `invalid_params` naming what to change; a suggestion is sent at most once per request, and a `suggested.instruction` equal (ignoring case, punctuation and the "From the current page" framing) to any instruction already run on the request is dropped (`why` `suggested_repeated`). A `urlMatches`/`urlEquals` expectation adds an `expectation_weak` warning at call time, and a `fai_browser_run` without an expectation adds `expectation_missing` (`expectation_missing: no expectation, so this run cannot be verified and may stop early; ...`), except for a single step (`maxActions: 1`): every run should carry one, the first hop of a multi-hop task included, since the provider's "done" is otherwise unchecked. `expectation` stays optional in the input schema (a single step or an SDK caller may omit it); a run without one that the provider ends as done is `unverified` / `no_expectation`. When `page.digest` holds a likely answer (top `answer.candidates` confidence at least 0.5) its next is `answer_from_digest` (answer from the digest, no tool call; the warning is what tells the host to pass an expectation next time); otherwise it is `rerun`, whose text says to run again with `verdict.suggested.expectation` or an expectation of its own, and which the call budget turns into `stop` when no call is left. No image is sent by default: `returnImages` is `"none"` for run, act and observe; `"final"` (the last screenshot) and `"all"` (up to six, which also switches the run to `capture: "each"` unless it sets `capture`) are explicit, and `fai_browser_evidence` serves any screenshot the run captured (by default only the final step's, see [Screenshots](#screenshots)) or the trace. Tools declare input schemas only, with one- or two-sentence descriptions; the common-path loop guidance is in the server `instructions` (and, briefly, the `fai_browser_run` description), the rest in the skill. Task outcomes such as `needs_user` or `failed` are normal results; `isError` is reserved for bad parameters, daemon HTTP errors and an unreachable daemon. Progress notifications report each step by action type and ref, never page text, and cancelling a call stops its run. When the host closes the server, it releases the tab requests it created. The skill ([skills/fai-browser/SKILL.md](../skills/fai-browser/SKILL.md)) is the full guide to the agent loop and how to read each status; the instructions cover only the common path.

## Step lists

A task one run cannot do, which the host would otherwise split into several `fai_browser_run` calls (which item or page to open depends on a value read first, or more than three clicks), goes in one call as `steps` instead of `instruction`, `expectation` and `answerQuestion`; one page, or a join of named links (the `trail` carries the earlier page), stays a single run: MCP `steps`, the daemon body's `steps` (`POST /v1/runs`, operation `run`), SDK `client.run({ requestId, steps })` or `runtime.run({ steps })`, CLI `--steps-file FILE`. Each call saved is a host round trip (3-6 s and a third to a half of a task's host cost); the extra Jev decisions cost almost nothing.

```json
"steps": [
  {"instruction": "Open Featured. Read which guide is featured.", "expectation": {"urlIncludes": "/featured"},
   "answerQuestion": "Which guide is featured?"},
  {"instruction": "Click Guides, then the {{answer:1}} guide. Read how often metrics are sampled.",
   "expectation": {"urlIncludes": "/guides/"}, "answerQuestion": "How often are metrics sampled?", "maxActions": 3}
]
```

- **Shape.** 1-15 steps. Each has an `instruction` and a declarative `expectation` (required: every step is verified like a single run), an optional `answerQuestion` and `maxActions` (1-30 through MCP, 1-100 for the SDK, daemon and CLI, default 8). A top-level `expectation` or `answerQuestion` next to `steps` is never refused (hosts send an expectation on every run): the last step takes it when it has none, an identical one changes nothing, a different expectation is checked on the final page whenever the list reached its last step, whatever that step's outcome (a blocked or still-loading page included), so verification never passes without it (when it fails, a last step that passed its own check ends `expectation_failed`, and `why` gets `steps:final_expectation_failed`); every `next.steps` carries it: merged into the last resent step when no field conflicts, else in `next.expectation`, which `next.text` says to send with the steps, and a different question is ignored with the warning `answer_question_ignored` (the step's own is asked); a placeholder cannot go in a top-level expectation unless it fills the last step. A top-level `instruction` next to `steps` is accepted too (live hosts send an overall instruction with the steps on their first call): the steps are the task and the instruction is kept only as its summary, a non-empty string of at most 4000 characters that is never sent to the provider; it names the task on the approval card (without it, the first step's instruction does), leads the trace's `instruction` and is not counted as an instruction already tried. MCP `maxActions: 1` and daemon `operation: "step"` with `steps` are refused, as is an invalid summary or list: `invalid_params` from MCP, 400 `invalid_options` from the daemon, exit 1 from the CLI, all before any tab request or provider call (`src/steps.js` validates and folds for every entry point). An MCP server talking to an older daemon that refuses the pair resends the steps without the summary.
- **One run.** The steps run in order in the same tab, request, lease, origins, level (the call's `mode` clamped to the grant; a grant lowered during the list holds for the rest of it), guardrails, `policy`, supplied values, `allowedUrls`, retry and slim switches, under one `runId` and one trace. The [in-call retry](#in-call-retries) bounds are the list's, not each step's: at most 2 second opinions, 1 back-out and 1 self-rerun per list, and no retry starts once the list has sent its decisions plus 4 provider requests; the `slim.terminal` memo (pages asked once, off after a fallback) is shared too. The call's `maxActions`, `maxDecisions` and `timeoutMs` cover the whole list (defaults: the steps' `maxActions` summed, at most 60, that plus 3 per step, and 45 s or 6 s per step when that is more, at most 120 s; the call's `maxActions` may set the list's total up to 120, and MCP clamps the time to what is left of the request's `maxMs`); each step gets the smaller of its own budget and what is left. The 45 s MCP window does not end the list: a longer list returns `state: "running"` with `next.kind: "wait"` (progress notifications per action with a progress token), and `fai_browser_wait` with its `runId` follows it (more progress, `state: "running"` again after each window) until the result arrives with every step in `stepResults`. A 15-step list of fast hops is one `fai_browser_run` plus the waits it needs.
- **Ending a step.** A step ends as soon as its own expectation passes after at least one action of that step, whatever the provider's `done` says: another decide on a page that already proves the hop only risks overshooting it (a second "Next page", a second click on a toggle). When the step names clicks or pages ("Click Tue 13 Oct, then Show 4 more flights"), each named one must have been done first, in the instruction's order and one action of the step per named item (the action's label as whole words, or the title or path of the page it landed on; an action that changed nothing does none): "Click Next page, then Next page" needs two clicks, and a Settings page whose title mentions billing does not do "then Billing". A purpose clause ("to open the date grid") names no item, and a repeat ("twice", "again") makes an item no action does. Otherwise, and for a step that names nothing unless its own action made the expectation pass, the done-gated rule of a single run applies. Instead of the terminal decide the step sends the slim done-and-guards request (`cost.requests` kind `step_guards`, not a decision) next to its answer ranking: a blocked score marks the page `guard:blocked_page` and stops the list (`confirm_page`), an injection score is noted as usual. A provider without that request (custom SDK providers; TypeSafe and the local SystemOne provider have it), or a failed request, keeps the terminal decide. A step whose expectation already passed when it started (a read step on the page the previous step reached) keeps the terminal decide too. `why` gets `step:expectation_end`.
- **Stop.** A step lets the next one start only when it ends `completed` with `verification.passed` and a next the host would accept as is (`answer` or `answer_from_digest`; not a page scored `guard:blocked_page` or still loading). Anything else (a failed expectation, a handoff, `needs.level`, a refusal, a relay, a stop, the time budget) ends the call with that step's receipt. Between steps the list also stops before the next step when under 1 s, no action or no decision is left (`time_budget`, `action_budget`, `decision_budget`) or the user paused or stopped the tab. Nothing is dropped silently: every step is in `stepResults`.
- **Placeholders.** `{{answer:N}}` (N an earlier step that has an `answerQuestion`) in a later step's instruction, answerQuestion or a positive expectation text field (`urlIncludes`, `textIncludes`, `titleIncludes`, `titleEquals`; never `urlMatches`, `urlEquals` or `textAbsent`, and every step keeps at least one expectation field without a placeholder, so a page value never chooses its own check) is filled only from step N's auto-confirmed `verdict.answer`: the step completed verified, the answer is the value (not a whole line, `exact: false`), at most 120 characters on one line without braces, backslashes or control and format characters, from a page without an injection guard of 0.8 or more, at least 3 characters when it goes into an expectation field, and neither the value nor the filled instruction asks for an irreversible action the step as written did not (commitIntent). In the instruction and question the value is written in ASCII double quotes with every embedded quote escaped (a quote pair the host wrote around the placeholder is replaced); in expectation fields it is bare. An instruction or question whose placeholders, filled at their longest, could pass its length limit is refused at validation. At `read-only` and `reversible` (the call's level), a step whose answer was not auto-confirmed may still fill a placeholder from its likely answer: the auto-confirm rule run at `thresholds.placeholderFloor` (default 0.35) and `placeholderMargin` (0.15, the lead over the second candidate) instead of `answerConfirm` and `answerMargin` (so still the question's shape, never a list, Nth or late-load question, never loading text, the value cut from its block), only from candidates the provider ranked (the page's only candidate, which a run does not rank, is sent to the provider to rank first and then needs at least 0.6, since with no runner-up the margin says nothing; without the provider's `choose`, or when that ranking fails, it never fills), not on a page scored blocked or still loading nor for a join task without a trail line, and then every check above. A likely value fills only the instruction and question, never an expectation field (those take auto-confirmed values only). Such a step's entry has `answerSource: "likely"` and no `answer`, `verdict.why` gets `steps:likely_fill:N`, the MCP `steps:` line marks it `(likely)` (its `candidates` hold the value), it never counts as confirmed (a full pass then has next `answer_from_digest`, not `answer`), and `next.steps` never writes it in (`{{supply:N}}`; `next.text` then says to write the value in place of it). At `interactive` and above only an auto-confirmed answer fills. Both numbers are thresholds (run option, daemon body or `config.json` `"thresholds"`). Otherwise the call stops before that step: `needs_host` / `placeholder_unconfirmed`, the step's entry has `why: ["placeholder:answer:N:<reason>"]` (`answer_not_confirmed`, `answer_whole_line`, `answer_injection`, `answer_too_long`, `answer_too_short`, `answer_characters`, `answer_command`, `filled_too_long`, `step_not_verified`), and `next` (`rerun`) says where to read the value (`page.digest`, `trail` and `answer.candidates` when step N ran last, else step N's `candidates` in `stepResults`) and to send `next.steps` with the value written in place of `{{supply:N}}`. Page text never fills a placeholder any other way.
- **Receipt.** The top level is the stopping (or last) step's receipt (`status`, `code`, `verdict`, `page`, `answer`, `trail`, where earlier steps' pages count as earlier pages), with `steps` (the actions) numbered across the list, `cost` summed and `retries` merged (`listStep` names the step). `verification.passed` is true only when every step ran and passed. `stepResults` is kept small: `{i, status, code, passed}` per step that ran, plus `asked`, `answer {text, line?, exact?}`, `answerSource: "likely"` (see Placeholders), `url` and (an earlier step without an auto-confirmed answer) its top two `candidates` for a step that asked, and `kind` (its verdict kind), `expectation` and `url` for the step the list stopped at; `{i, status: "not_run", code, why?}` for the rest (`code` names the stop decided before that step, else `not_run`). A step whose expectation passed but which the list did not accept has `held` (`guard:blocked_page`, or `next:<kind>`): it counts as the step the list stopped at, `next.steps` start with it, `next.text` names it and its reason, and when it was the last step to run `verification.held` is `step:<n>:<reason>`. `answer`, `candidates` and `url` are page text; the rest is trusted. A five-step pass with a question per step is about 2.4 kB (a single run about 1.1 kB). `verdict.why` adds `steps:<passed>/<total>` and `steps:stopped_at:<k>` or `steps:stopped_before:<k>`, and `reason` starts with "Step k of n" (or "All n steps passed"). When every step passed and more than one step (or only an earlier one) asked a question, `next` is `answer` when all of them were auto-confirmed (then `verdict.answer` lists them: `text` is one `step N: <value>` line per step, `confidence` the lowest, `steps [{i, text, line?, exact?}]` by step number) else `answer_from_digest` (then `verdict.answer` is null and the text points at `stepResults[].answer`). A list that stopped (next `rerun`, `split`, `relay`, `confirm_page`, `choose` or `answer_from_digest`) carries `next.steps`: the steps to send next, from the stopping step on, renumbered so the list stands alone (a placeholder for a step inside it is renumbered; one for a step that already ran is written in from its auto-confirmed answer, or becomes `{{supply:N}}`, which validation refuses until the host replaces it). `next.text` says which steps passed ("never send them again") and to send exactly `next.steps` (after the relay, with `mode` = `needs.level`, or with its first step sharpened from `verdict.suggested` after a failed step); after a time, action or decision stop the whole text is replaced. A `stop` lists which steps passed and which did not run. The MCP text block adds one trusted `steps:` line and a `next.steps` line, and lists the step answers, guesses and URLs under the untrusted heading.
- **Guardrails.** A list can do nothing a sequence of single calls could not: each step's instruction gets the refusal check, the purchase and commit guards and `policy` apply to every decision, the grant caps every step, and in-call retries run inside the steps under the list's one set of retry bounds. Nothing is new at the level of actions. The MCP server counts the list as one call of the request's call budget, refuses an identical repeat after an outcome it cannot change, and adds every step's instruction to the instructions a suggestion may not repeat.
- **Replay format.** A step list is the format a future site profile or recipe stores and replays: the hops of a verified task, each with its own expectation, sent as one call with every guard and Jev decision still live, so a page that changed fails a step's expectation instead of being acted on blindly.

## Running a task from the shell

```sh
node src/cli.js request-tab --origin https://app.example.com --reason "Check the members list"
node src/cli.js wait req_Q2x9mP0aLk3s                         # until "state":"active"
node src/cli.js wait req_Q2x9mP0aLk3s --until active --timeout 30m   # blocks until approved/resumed (exit 0)
node src/cli.js run "Open Members" --request req_Q2x9mP0aLk3s --expect-url-includes /members
node src/cli.js observe --request req_Q2x9mP0aLk3s            # page digest, offered actions, revision
node src/cli.js act --request req_Q2x9mP0aLk3s --action a3 --revision r_ab12
node src/cli.js act --request req_Q2x9mP0aLk3s --point 640,310 --revision r_ab12   # pixels of the observe screenshot
node src/cli.js release req_Q2x9mP0aLk3s
node src/cli.js runs --limit 5 && node src/cli.js evidence <runId> --step 2 --kind screenshot
```

`run`/`step` without `--request` create the request themselves, write `ACTION NEEDED` to stderr and wait for the user to approve the request (its page opens in a new tab in the existing browser window by itself and one click on the FAI Browser icon on that window approves it; for `--mode full` or `testing`, **Open** in the FAI Browser window first, then the icon on the page it opens; 120 s by default; `--lease-timeout-ms`, `leaseTimeoutMs` or `FAI_LEASE_TIMEOUT_MS`). If nobody approves in time, they return `needs_user` / `select_tab` with exit code 2 and the pending `requestId`. The lease is kept after the run, and the result carries `lease.requestId`, so the next command can pass `--request` and needs no new click; `--release` releases it at the end. Options files keep working: `node src/cli.js run "Find the members list" my-options.json --max-actions 4`, where `allowedOrigins` becomes the requested origins. `--origin`, `--reason` and `--expect-url-includes|--expect-text-includes|--expect-title-includes` let a run work without an options file. Ctrl+C stops the run; a second Ctrl+C exits 130.

**Waking the agent on Resume.** `wait <requestId> --until active [--timeout 30m]` blocks until the request's lease is usable: the user approved a pending request or clicked **Resume** on a paused one. It loops over the daemon's own long poll (`POST /v1/wait` holds each round up to 30 s while the request is `pending` or `paused`; a round that returns early is not repeated within 250 ms), so it does not busy-poll. `--timeout` takes a duration with a unit (`ms`, `s`, `m`, `h`; default `30m`, the paused-lease lifetime; at most `24h`). It never starts a daemon, not even on its first connection (`--no-auto-start` makes no difference to it): tab requests live in the daemon's memory, so a newly started daemon could not know the request. When the daemon stops answering (a restart, a reset connection, `503 shutting_down`) it retries with a 0.25 to 5 s backoff, re-reading the client token on each reconnect; after 30 s without an answer (`FAI_WAIT_DAEMON_GONE_MS`) the request is taken as gone and the wait ends as `unknown` with `reason: "daemon_gone"`, and a daemon that answers but no longer knows the request ends it as `unknown` with `reason: "unknown_request"`. It prints one JSON line on exit: `{state, requestId, until: "active", reason, lastState?, waitedMs, reconnects, request, next {kind, text}}`, where `state` is `active`, the terminal request state (`released`, `expired`, `denied`, `cancelled`; `reason` says why, e.g. `stopped`, `superseded`, `paused_timeout`), `unknown`, `timeout` (with `lastState` `pending` or `paused`) or `interrupted` (SIGINT/SIGTERM); `reconnects` counts outages it rode out. `next` follows the daemon's driver: `observe` with `fai_browser_observe` for your agent driving, `rerun` with `fai_browser_run` for the Jev autopilot. A failure (a bad flag, a refused token, an unexpected daemon answer) prints `{state: "error", requestId, until, error {code, message, hint?}, next {kind: "relay", text}}`, whose next asks the user to say when they have resumed. Exit codes: 0 active, 3 the request ended or is unknown, 2 timeout, 130 interrupted, 1 an error. `--until` takes only `active` and a requestId (not `--run`); `--max-ms` is for the one-call `wait`; `--until` and `--timeout` are refused with any other command. This is the command the trusted `next.text` of a paused or pending relay names: the MCP server's absolute node path and `src/cli.js`, preceded by shell prefix assignments of the MCP server's `FAI_HOME`, `FAI_DAEMON_DIR`, `FAI_DAEMON_PORT` and `FAI_BRIDGE_PORT` when they are set (never the client token), for example `/usr/bin/node /opt/fai-browser/src/cli.js wait req_Q2x9mP0aLk3s --until active --timeout 30m`. A host that runs background commands and is notified when they exit (Claude Code's Bash `run_in_background`) starts it, unless one is already running for that request, and ends its turn, so the user's click wakes it; other hosts ask the user to say when they are done. To let Claude Code run it without a prompt, allow its prefix: `Bash(/usr/bin/node /opt/fai-browser/src/cli.js wait:*)` with your node and install paths (as `next.text` shows them); with `FAI_HOME` or another carried variable set, the command starts with that assignment, so the rule must too: `Bash(FAI_HOME=/path/to/home /usr/bin/node /opt/fai-browser/src/cli.js wait:*)`.

Flags: `--request`, `--release`, `--origin`, `--reason`, `--answer TEXT` (`answerQuestion`: a question answered from the final page as `answer.candidates`), `--policy P` (guardrail additions: `"Upgrade,Gift wrap"` or JSON `["Upgrade"]` / `{"forbid":["Upgrade"],"note":"…"}`; options-file `policy`), `--output-dir`, `--capture each|last|none`, `--max-actions`, `--timeout-ms`, `--mode read-only|reversible|interactive|full|testing` (the level the task needs; the user's approval in the popup caps it, see [Permission levels](#permission-levels)), `--min-confidence F`, `--no-retry` (no [in-call retries](#in-call-retries); options-file `retry`), `--slim on|off|<switches>` ([slim provider requests](#slim-provider-requests); options-file `slim`), `--profile on|off` ([site profiles](#site-profiles-experimental-opt-in); options-file `profiles`), `--lease-timeout-ms`, `--instruction-file`, `--steps-file FILE` (a [step list](#step-lists): a JSON array or `{"steps": [...]}`, instead of an instruction; `run` only, and no `--answer` or `--expect-*`; an optional summary instruction goes as the positional before the options file, or alone when it does not end in `.json`, or as the file's `instruction`), `--no-prune`, `--pretty`, `--port`, `--no-auto-start`. Precedence is flags, then environment, then options JSON. Retention limits move to `config.json` in daemon mode.

Confidence floors are per action class and live, with every other gate, in one `thresholds` object (run option, daemon body or `config.json` `"thresholds"`): `linkFloor` (default 0: link clicks are never gated), `controlFloor` (default 0.5: buttons, selects and fills, `reversible` and above), `doneThreshold` (0.5), `strongDone` (0.8), `answerConfirm` (0.8), `answerMargin` (0.5), `placeholderFloor` (0.35) and `placeholderMargin` (0.15) (a [step list](#step-lists)'s likely fills), `secondOpinionMargin` (0.2, see [In-call retries](#in-call-retries)) and `commitVeto` (0.7: the Jev commit and purchase guard level at which a button/select/fill is refused; a run may lower it, never raise it above `config.json`'s value or the default). `minConfidence` (`--min-confidence`, options-file and MCP `minConfidence`) is an alias for `controlFloor`. Below a floor nothing executes: the result is `needs_host` / `low_confidence` with `needs.alternatives` (up to five offered actions with `id`, `description`, `probability`) and `needs.revision`, and the receipt's `verdict.decide` lists them, so the agent can run one with `act` and no new observe. A provider that reports no confidence is gated only by a floor set explicitly. The descriptions embed page labels and are untrusted.


### Output, status and exit codes

Stdout is exactly one JSON line (`--pretty` indents it). `step`, `run` and `act` print the lean agent result (the daemon/CLI object, which MCP renders as readable summary text rather than duplicating in `structuredContent`): `v`, `runId`, `status`, `code`, `reason`, `needs {who, message, level?}` (only when someone must act; `level` when re-approving the tab at that level would let the task go on), `verification {checked, passed, expectation}`, `page {url, title, digest, truncated}` (`digest` is a list of block texts; `textExcerpt` only when the digest is empty), `answer {method, candidates[{text, confidence, state?}], source?, aggregate?}` (top three; see [Fact memory](#fact-memory-and-aggregation)), `trail [{url, state, lines}]` (relevant lines of earlier page states in a multi-hop run, same-URL states included), `steps [{i, action {type, label, toUrl}, class?, confidence, ms}]` (`class: "consent"` marks a cookie-dialog reject click, `class: "dismiss"` a popup dismissal, see Blocking overlays under [Policies and providers](#policies-and-providers)), `cost {decisions, inputTokens, outputTokens, elapsedMs}`, for an `act` the landing page's offer (`revision`, `actions [{id, description}]` as `observe` lists them, `moreActions`: the next `act` may name that revision with no observe in between; absent after a cross-origin landing or a refused act), `warnings` (`password_field`, `blocking_overlay` (a popup other than a cookie dialog covers the page), `browser_error_page` (the tab shows the browser's own error page, see `error_page` below), `expectation_weak`, `expectation_prepassing` (see below), `controls_capped:<n>` ([Offered actions](#offered-actions)), `cross_origin_frame`, `unreadable_region:<kind>` (the page holds a region only as pixels or a derived view had to cut it: `chart` values only as bar geometry, `canvas`, a chart-like `image` with alt text only, a `table` over the text budget; the trace's observation lists each region's label, reason and bounds); MCP also adds `expectation_missing` for a run without an expectation and details after a colon), `permissions {requested, granted, effective, testing, scope}` (the level the agent asked for, the user's grant for the tab, null before approval, the level the run used, and `scope`: `origin` or `domain`, what the approved tab covers, see [Domain roots](#domain-roots); absent before approval), `retries [{kind, why, outcome, ...}]` (only when the call ran an [in-call retry](#in-call-retries)), `stepResults` (only for a [step list](#step-lists)), `lease {requestId, state}` and `trace`. Results are receipt v2 (`v: 2`): `verdict {kind, oversight, answer, why, decide, suggested, budget}` (kind `verified|likely|needs_decision|needs_user|failed`; `answer` is set only when a provider-ranked candidate is at least 0.8, has the question's shape (price: a currency amount, count: a digit, hours: a time of day, quantity (what share, how long, how often): a number or a frequency word), is not a navigation trail ("Home › Guides › Backups"), leads the runner-up by 0.5, and the question is not a list, Nth-item or late-load question (for an aggregating question, also only when the top candidate is the aggregation's unique first item over items the run fully read); `why` is machine codes; `decide` holds options for `fai_browser_act`; `suggested` is a ready-to-send instruction/expectation/maxActions; `plan.split` advises splitting a join or 4+-page task) and `next {kind, text}` with `kind` one of `answer`, `answer_from_digest`, `confirm_page`, `choose`, `rerun`, `split`, `relay`, `approve`, `stop`. Per-step observations, screenshots, probabilities and control bounds stay in `trace.json` (and behind `evidence`). `observe` prints `{revision, page {url, title, digest}, actions [{id, description}], moreActions?, warnings?, consent? {text, buttons [{label, kind}]}, screenshot, trace, next {kind: "choose", text}}` (`moreActions` counts offered actions the listing left out; ids keep their offered numbers, so a gap in them shows where), MCP observe renders those fields as readable text (`consent.text` and button labels are untrusted page text). Other commands print the daemon's JSON, or `{"error":{code,message}}` with exit 1. Diagnostics go to stderr. Page-derived text appears only under `page`, `answer.candidates`, `answer.source.url`, `trail`, `steps[].action.label`, `verdict.answer.text`, `verdict.decide.options[].label` `needs.dialog` and `needs.control`. `reason`, `needs.message`, `needs.level`, `permissions`, `retries`, the rest of `verdict` and `next` are written by FAI Browser and can be trusted.

| Status | Meaning | Typical `code` | Exit |
|---|---|---|---|
| `completed` | The expectation passed on the settled page | `expectation_passed` | 0 |
| `unverified` | The provider said done, but there was no expectation or it kept failing; or it stopped sure of the outcome (done ≥ 0.8) on a page the expectation did not match | `no_expectation`, `expectation_failed`, `expectation_mismatch` | 0 |
| `checkpoint` | `step` ran its one action; the expectation has not passed yet | `step_complete` | 0 |
| `budget_exhausted` | The action, decision or time budget ran out, or the request's call budget (MCP) | `action_budget`, `time_budget`, `task_budget` | 2 |
| `needs_user` | The user must act (for `refused_action` with `needs.level`, or `login` on a run that asked for `testing`: re-approve the tab at that level) | `select_tab`, `paused`, `consent_banner`, `login`, `blocked`, `cross_origin`, `child_tab`, `tab_changed`, `blocked_risky`, `refused_action` | 2 |
| `needs_host` | The host agent must decide | `handoff`, `no_progress`, `fill_not_kept`, `stale`, `unsupported`, `low_confidence`, `request_closed`, `placeholder_unconfirmed` | 2 |
| `stopped` | Stopped by the user, or Ctrl+C | `stopped`, `cancelled`, `interrupted` | 2 |
| `failed` | Configuration, daemon or runtime failure, or the run reached an HTTP error page | `config`, `daemon_unreachable`, `unknown_request`, `provider_error`, `timeout`, `error_page` | 1 |

A request paused as `origin_changed` because the tab went to an origin the request does not list names that origin
when the browser showed it: `leftOrigin` in the request view (status, `wait`) and in the paused result, shown with
the untrusted page text (a page decides where it sends the tab). `needs.message` only says that it went to an origin
the request does not list and where to find it. It is the origin only, never the path or query, redacted like any
reported URL; with a toolbar approval the browser often withholds the URL and nothing is
named. Ask the user and request that origin up front next time (a sign-in hop through another host, for example).

`wait <requestId> --until active` has its own exit codes (see [Waking the agent on Resume](#running-a-task-from-the-shell)): 0 active, 2 timeout, 3 ended or unknown, 130 interrupted, 1 error. Other commands exit 0 on success and 1 on an error.

`refused_action`: the instruction itself asks to buy, order, pay, delete, remove, send, submit or log in (an imperative clause that starts with the verb, in its dangerous sense: "remove the filter", "submit a search" and "send me the list" do not count) and the only page controls for it are ones the approved level refuses (refused filter chips and search buttons do not count). The run ends before any provider decision, in one of three ways. A purchase below `testing` stops: verdict `failed`, `next {kind: "stop", text: "FAI never purchases outside testing mode. Tell the user what to do in the tab."}`. A control the user's `forbid` additions reserve, or one no level allows, stops the same way with its own text. Anything a higher level would allow (a submit at `reversible`, a sign-in below `testing`) is a level request: `needs.level` names the lowest level that allows it, `needs.message` says "The user approved Use (no submit) for this tab; this task needs Act. Ask them to approve the new request at Act in FAI Browser (it is preselected).", the verdict is `needs_user` and `next.kind` is `relay` (call `fai_browser_run` again with `mode` set to `needs.level` once they have; the MCP server then opens a new tab request at that level); when the user's grant already covers it (the run asked for a lower `mode` itself) `needs.who` is `host` and `next.kind` is `rerun`. `why` has `refused:<intent>` and, for a level request, `level:<needed>`. The commit and purchase guards (see Guardrails) end a run the same way with `next.kind: "stop"` when Jev chose a button, select or fill they veto (nothing is executed; `needs.control` names the control, untrusted) or handed off while such controls were offered; `why` has `guard:commit_veto` or `guard:purchase_veto`. `error_page`: the run landed on a 404, 410, 500, 502, 503 or 504 page (the document's HTTP status from Navigation Timing, an error title or first heading such as "Page not found" or "Internal Server Error", or, only when the HTTP status is unknown, a tiny page whose first line is an error line; body text that merely mentions a status never counts, and "HTTP 404" titles count only without a successful status); it ends before any further decision with verdict `failed` and `next.kind: "stop"` naming the status (`why` has `http:<status>`). A host that asked for that page (its expectation passes there, "read the error reference the Billing page shows") is not stopped; `why` still notes `http:<status>`. The browser's own error page (below) is never exempt: it keeps the URL the tab tried and a fixed text, so an expectation that matches it is not a verified outcome (`verification.passed` is false). The browser's own error page counts too: for an HTTP error sent without a page body (an empty 500, for example) and for a refused or dropped connection, Chrome shows `chrome-error://chromewebdata/` while the tab keeps the URL it tried, and no extension script runs there. The extension reports it as an observation of that URL with `browserErrorPage: true`, no controls, a fixed text and the warning `browser_error_page`; the status is unknown, so `why` has `http:error` and `error_source:browser`, and `next.text` says the tab stays approved and can be reloaded later. The session stays active (it used to pause as `origin_changed`, or fail as `unsupported`): a page action on that page fails with `target_unavailable` (recoverable), while a history move (`nav: "reload"`, back, forward) and an approved `url` still run. In Agent direct an `observe` of it returns the page with the `browser_error_page` warning (no controls, no scroll actions), while an `act` that lands on it ends `error_page` (`next.kind: "stop"`) before any expectation is checked and keeps the page's offer for a later reload; an ordinary error page with a body is still read by the host. With a toolbar (activeTab) approval only, Chrome withdraws access when its error page commits: the URL is withheld and nothing can be read, so that session pauses as `origin_changed` (approve again once the site is back); approval in the request modal (browser site access for the exact host) keeps the session. Firefox's network error pages (`about:neterror`) are not handled and may still pause as `origin_changed`.

The provider decides when the task is done and the expectation verifies it. Each Jev decision asks two questions in one request: which offered action to take, and `done`, a probability that the requested outcome is already visible. A run completes when the expectation passes and `done` is at least `doneThreshold` (default 0.5); a passing expectation with a lower `done` keeps going, so a loose expectation that also matches an intermediate page no longer ends the run there. When the action budget runs out with the expectation passing, the result is `completed` with code `budget_reached_expectation_passed`; when the provider hands off on a page where the expectation passes (common on the last page of a multi-hop task, whose answer combines several pages), it is `completed` with `handoff_expectation_passed`. Without an expectation, `done` of 0.8 or more ends the run as `unverified`. If `done` is at least `strongDone` (0.8) while the expectation fails, the runtime waits 300 ms and observes once more (a navigation may have started late). If the expectation still fails and the provider chose `handoff` or `done`, or this is the second consecutive such decision, the run ends `unverified` / `expectation_mismatch` with `verdict.suggested.expectation` set to the real final path; otherwise the provider's click still runs (it can be sure the answer is one click away). If `done` stays between `doneThreshold` and `strongDone` for two decisions while the expectation fails, the run ends `unverified` (`expectation_failed`). Two named-button rules (the buttons the instruction names as click targets, as for the `named` guidance line below, counted against the run's own clicks) adjust this. A decision whose choice is a named button not yet used up does not count toward either failing limit, once per page revision (`why`: `named:done_pending`): "Choose Standard, then click Next" reads as done after the select while the provider's own choice is the Next still to come; the click still meets every guard, veto and floor. And on a page where the expectation passes, once every named button has been clicked as often as the instruction names it and at least one of those clicks changed the page (a named click that did nothing on a start page the expectation already passes does not qualify), a choice below its floor ends the run `completed` / `handoff_expectation_passed` as a handoff there would (`why`: `named:clicks_done`) instead of `low_confidence`; nothing runs. Neither rule ever runs a control the provider did not choose, and neither applies below `reversible` or to links. Custom providers that report no `done` keep the old rule: the expectation is checked after every action and the run ends as soon as it passes. Two exceptions end a run on its expectation whatever `done` says, right after an action of the run (never on the start page): a [step list](#step-lists) step (see "Ending a step"), and a run whose instruction is a bounded imperative (it starts with an action verb, optionally after a place phrase such as "On the results page,", names one or two clicks or pages, and does not loop, scan or repeat: no "each", "every", "until", "while", "keep", "browse", "twice", "again", "3 times", "all 13 pages") once every named click or page is done, as for a step. Both send the slim guards request instead of the terminal decide (as above; `why` `step:expectation_end` or `early_end:named_actions`), with the answer ranking next to it whether or not the run has an `answerQuestion`. Both also need the read clause met: when the run asks a question (or its instruction reads, finds or reports something) whose intent is a price, a count or an hours/time of day, a page with no line of that shape does not end it; and a bounded imperative with a read clause ends early only when the ranked top candidate passes the auto-confirm gates. Otherwise the done-gated terminal decide judges the page (`why` `early_end:read_unmet`), so "Open the Contact page and read the opening hours of the Lisbon office" goes on from Contact instead of answering there; a named entity inside the read clause ("the Lisbon office") is never a hop. **Pre-passing expectations.** A text or title expectation (no URL field) that already passes on the start page while the instruction names a click or page the run has not reached (a `textIncludes` of a toggle's own label, "Date grid") proves nothing: the run records `expectation_prepassing` in `warnings` and `why`, and the pass counts only after at least one action of the run and on a page whose revision or URL differs from the start (a done of 0.9 on the start page no longer completes it). An instruction that names no action ("read the price on this page"), or whose last named page is the start page, keeps its pass. **Vacuous passes.** Any declarative expectation, URL fields included, that passed on the start page and has not failed on any page since does not complete a run that acted through a handoff at `done` 0.3 or less (a `urlIncludes: "/travel/flights"` matches every page of the site): the result is `needs_host` / `handoff` with `why` `expectation:prepassing` (warnings `expectation_prepassing` and `expectation_weak`, shape `expectation:url_start` for a `urlIncludes`), `verdict.suggested` never carries that expectation again, and `next.text` asks for one only the result page passes. A run that took no action (a read on the start page) keeps `handoff_expectation_passed`. **Named URLs.** When the instruction's first named URL follows "open", "go to", "navigate to", "load", "visit" or "browse to" (not after "do not", "never" or "don't") and the tab is not on it (same origin and path, every query parameter of the named URL present with its value; a site's own extra parameters do not count), the runtime navigates there without a decision (`decision.by: "url"`, reason `named_url`, `why` `url:direct`): the `allowedUrls` entry for it, else the literal URL when it is on the approved site; never a URL whose path or short query words sign out, unsubscribe, submit or trip a guardrail class (`url:refused`), never off the granted origins (`url:outside_origins`), on a consent dialog or with the last action of the budget, and each URL once per run. A later URL ("open A, click X, then open B") is the provider's. When the expectation first passes on the page this opening hop landed on and the instruction names an action after the URL ("Open <url> directly. Set trip type to One way, ..., read the grid"; prose and a question to read there do not count), the run does not end on the hop: the landing page counts as the start page for vacuous passes (`why` `expectation:url_landing`), the provider decides next, and a handoff that never saw the expectation fail and pass again is reported as above (`expectation:prepassing`, `next.text` naming the page the opening URL landed on). "Open <url>." or "Open <url> and read the flights." still ends verified after the hop. In a list step or a re-run only a URL the host wrote counts: one that a `{{answer:N}}` placeholder wrote in (page text) never hops. **Persistent status text.** On a page with at least three list or table rows of its own, a loading placeholder the page script marks `hidden` (a visually hidden, screen-reader status, or a block of a visible bar whose text all comes from such hidden elements: Google Flights' toolbar "Fetching results") does not count (no wait). A visible placeholder ("Loading…" the user sees) that is still there after two consecutive content waits (or, when no wait ran, on the two latest earlier observations of the same URL) while the rest of the page did not change and carries at least three list or table rows is status text; never on the first observation after an action, which gets the normal waiting, so stale rows next to a placeholder that resolves on the second or third wait are waited for, not loading (`why` `content_status:persistent`): the run stops waiting, sets no `content_loading` and suggests no `textAbsent`, for the rest of the run and the list's later steps, on pages with such rows (on a page without them the same text is loading). A list step whose own expectation passed goes on even while a placeholder shows (its receipt keeps `content_loading`). **Toggles.** The control whose click made the expectation pass without leaving the page is not offered again on that page while the expectation still passes, unless the instruction names it again and the run has not used it up (the record clears on any other URL) (`why` `toggle_excluded`), so a late re-decide never clicks the same toggle again and closes what it opened (the consent rule "never the same button twice", for toggles). **Missed text.** When a run ends unverified (any status but `completed`) and the expectation's `textIncludes` or `titleIncludes` is not on the final page, `verification.hint` says what the page has instead, and `next.text` repeats it (not for an `answer`, `stop`, `relay` or `approve` next): `expected text "Departing flights" not found; the page has "Top flights", "Other departing flights" (quoted page text, untrusted)`, up to five of the page's headings and short prominent strings (blocks of at most six words: tabs, buttons, short lines) ranked by word overlap with the expected text (headings first, then page order; with fewer than three sharing a word, the first headings fill in), or for a title, the page's title; each page string is quoted, cut to 60 characters and stripped of control and format characters, and `verdict.why` gets `expectation:text_missing`. A host that guessed the page's wording ("Departing flights" where the live page said "Top flights") corrects its expectation from it. Declarative fields are `urlEquals`, `urlIncludes`, `urlMatches` (regex), `textIncludes`, `textAbsent`, `titleEquals`, `titleIncludes` and `changedSinceStart`. `textIncludes`, `textAbsent` and `titleIncludes` ignore case, and every field you supply must match. `textIncludes` and `textAbsent` are substrings of the observed visible text, in which the fields of one list row are joined with " · ", the cells of one table row with " | ", and a grid with row and column headers reads "Oct 10 × Oct 17: €312" (lines that used to be separate are joined this way, never text that used to be one line); write one field's text ("€121", "Air France"), not text spanning fields. `textIncludes` also passes on text the page renders outside the viewport: each observe sends it to the page script (`expectText`), which looks for it in the whole document's rendered text when the viewport text lacks it and lists what it found in the observation's `textFound`, so a run that scrolled below "departing 2026-10-12" (a "View more flights" click) still verifies; hidden text never counts there (display or visibility hidden, `aria-hidden="true"`, a screen-reader-only clip or a box of 1px or less, a zero-size box that clips its overflow). `textAbsent` reads only the viewport text, so an off-screen "Loading more" row does not hold a finished page back. A provider's `done` without a passing expectation is `unverified`, never `completed`. For `completed`, `unverified` and `checkpoint` results a provider with `choose` ranks `answer.candidates` (page blocks matching `answerQuestion`) in one more request. When the expectation already passes on the page a decision is made on, that request is sent alongside the decision instead of after the run (not for a local SystemOne server, which may serve one request at a time); its result is used only when the run ends on that page with the same question, candidates and earlier-page trail, and is otherwise discarded, so the outcome is the same as ranking after the run (a discarded request that had already answered still counts in `cost`). If that early request failed (timeout or provider error) and time remains, a fresh one runs after the loop instead, and after any provider error the run stops starting early rankings; the trace's `answerDetail.early` says `used`, `fallback` or `off`.

### Fact memory and aggregation

A long single run (12-15 hops in one call) often reads its answer on an earlier page state: a flight on Thursday's list when the run ends on Sunday, the cheapest tent on page 11 of 13, a token in a log panel of a single-page app whose URL never changes. With a question (`answerQuestion`, else the instruction), the runtime keeps a **fact memory** of every page state the run saw (`src/facts.js`): one state per semantic revision in first-seen order (so same-URL states count), each with at most 6 lines that match the question (page blocks, never generated, supplied values redacted as for the provider; aggregation items come on top, see below), at most 12 lines per state seen and never fewer than 80 nor more than 400 in the run, a line seen in an earlier state not repeated. A line under a section heading (h2-h4) reads `<heading> › <line>` ("All 8 departures on Thu 15 Oct › 10:55 Vueling VY 7713 … €61").

- **`trail`** is the memory's lines of the states before the final one, grouped by state in run order: `[{url, state, lines}]`, at most 3 lines per state, 12 states (the most relevant when there are more) and 40 lines; lines the final page still shows are left out (`page.digest` has them). With an aggregating question a state shows its items first, then its other lines while it has room, except lines with a value of the aggregated measure that are not items (a decoy's price). Untrusted page text.
- **Answer candidates.** The final page's blocks as before; for a task that is not a join (`isJoinTask`: there the earlier fact is context, not the answer) and whose final page is weakly relevant (its best block scores under half the best remembered line), up to 8 remembered lines that outscore it go first. `choose()` gets at most 24 candidates and the most recent 4 trail states (lines that are not already candidates) as `earlierPages` (on a run that never left the final page's URL, only lines that state a fact, with a digit, a "label: value" or a name; a prompt such as "Select a region to see the shipping cost." is left out, and with no line left `earlierPages` is not sent). A candidate read on an earlier state has `state` in `answer.candidates[]`, and `answer.source {state, url}` names where the top one was read; `verdict.why` adds `answer:from_state:<n>`. The auto-confirm rule is unchanged.
- **Records.** The page script detects repeated records by structure, never by site (`detectRecords` in extension/page.js): sibling subtrees with the same tag, role and descendant shape (at least 3), or the same template under sibling wrappers that hold nothing else (a grid split into rows), scored as a list from several text boxes per member, a link or heading, prices, ratings and numbers (a shared class token is a weak bonus). Navigation, banner and footer landmarks, menus, tab lists, toolbars, dialogs, a blocking overlay's content, hubs of plain links (footer columns) and filter panels (two or more checkboxes, radios or sliders per member) are never records. Members are compared by their value skeleton too: a sibling with other markup that has the name, price and rating the similar members have is a member (badges, extra wrappers), and a same-tag sibling with no name, or none of their values, is an insert (a notice, a promo) and left out. When one group's members contain another, the inner one wins only when it spreads over two or more of them and holds most of their text with two or more members each (sections of cards, rows of tiles); a group of whole records (a name and a price or rating each) inside one member is a module of its own (a strip of other offers between the cards) and that member leaves the outer list; any other inner group is a record's parts (its name, score, room and price boxes) and the outer list wins. The page's main results rank first: among the lists scoring at least a quarter of the best, a carousel (a strip that scrolls or snaps on the x axis, or one row wider than the viewport) ranks after every other list, then the lists inside `main` and after the result-count line ("8 properties found", not a filter option's count; else after the h1), then the score. The best list and at most two more are sent as `records` (at most 60, from the whole list, not only the viewport): `{id, list, title, href?, ref?, fields, hints?, sponsored?, unavailable?, offscreen?, struck?, blocks}`, the title being the first heading or the main link, the fields the record's visible texts in order (screen-reader-only text only with a digit, struck-through prices dropped, a rating held in an aria-label or alt kept, template text most records repeat without a digit such as "See availability" dropped, at most 300 characters), the hints `price`, `prices` (when several differ), `rating` and `scale` (the rating stated nearest the review count, so a guest score beats a star class), `ratings` (every distinct one, when several), `reviews`, `when` and `counts`; `recordLists [{list, total, kept, main?, afterCount?, carousel?}]` and `recordsTruncated` say whether the list was cut and where each list sits (inside `main`, after the result-count line, a carousel; each flag only when true). Explicit page-level state goes in `recordState`: the global `resultCount` (with `approximate` for a count ending in +), `sort` only from a named sort select or `aria-sort`, and `pagination` only from a pagination landmark or `rel=next/prev` (current/total pages when stated, previous/next control refs when offered). A generic Next button elsewhere is not pagination and filters or ordering are never inferred. Agent direct projects list 0 as `page.results`: at most 600 characters of rows, chosen by task relevance and returned in document order, with their title, typed date/price/rating/reviews when known, only the remaining context `fields`, flags and an `open` action id when its title link was listed. `shown` is the projected count and `total` the detected rows on this page; `resultCount`, `sort`, `pagination`, `truncated` and `complete` retain the accuracy metadata. `complete` is false for a cut or projected list, either pagination direction, an approximate count, or an exact global count that differs from the detected primary-list total. Omitted rows remain in the direct digest, and only projected rows are replaced there and in text rendering; ordinary Jev digests, candidates and aggregation are unchanged. Two records never share a line of the visible text, and over the 200-block cap the blocks inside a record after its first are dropped first. In the core (`recordsOf`, `blocksOf` in src/digest.js) a list of at least 3 records replaces its blocks with one `li` block per record ("<title> · <field> · ..."; a record that already is one row block keeps that row when it holds every field with a number), so the digest, the candidates, the fact memory and the aggregation read a card as one item. Records aggregate on the final page alone too, the main list first: when the main list has items for a question that ranks or bounds a value (cheapest, rated 8 or more) only they count, else the other lists' records, else the blocks (a carousel of cheaper extras never answers a question about the results). The main list is list 0 (the page script's best) unless the provider chose another (**Which list**, below); a rating bound above 5 reads a rating on a scale above 5 (a 5-point rating neither passes nor fails it), and a record line is remembered whole (300 characters); a sold-out record is no price item, a titled record is never `unnamed_item` or `decoy_name`, and a cut list adds `records_cut` to `partial`. Without records everything is as before.
- **Aggregation.** A question that asks for an extremum (cheapest, least expensive, most expensive, earliest, latest, lowest, highest, most, fewest, ...) or a filter (`between 10:00 and 12:00`, `before 2 pm`, `under €50`, `in stock`/`available`, a rating bound such as `a rating of 8 or more`, `rated 8+`, `4 stars or more`, `a score above 8`) has a measure: a price (the line's first currency amount: symbols and codes, thousands separators, `€1.299,50` and `$1,299.50`), a time (the first 24 h or 12 h time) a rating ("highest rated": "Scored 7.8", "4.5 out of 5 stars", "8.4/10", "8.7 Excellent", never a review count) or a count (a line's only number, else the one next to a question word). Items are remembered lines with the measure's value that pass the filters (a time inside the window, a price inside the bound, not out of stock or sold out); when an item has a whole table cell made of the question's item words (the `Tents` category column for "which tent"), only such items count (an accessory row is not a tent). Each state then keeps its items first (up to 30; the final page's own state keeps all of them, its observation being in hand) and at most 2 other lines, and its trail entry shows the items only. In a step list, a step's question aggregates over its own pages only, never over the pages carried from earlier steps, unless it spans days or pages ("across", "each day", "all pages"). "Before noon", "midday", "midnight" and "morning" are time windows. When items come from two or more states, the 5 first in order (lowest first for a minimum) lead the candidates, and `answer.aggregate {op: min|max|filter, measure, items, states, partial, why?, tie?}` (trusted) summarizes it, with `verdict.why` `aggregate:<op>_<measure>:<items>`. `partial` (why `pages_unread`: a "Page X of Y" was not seen for every X; `more_unread`: a "showing X of Y" state was not followed by a fuller one; `more_offered`: the final state offers next page, load more or show more; `memory_full`: items fell off the memory bounds; `not_verified`: the run did not complete verified; and when every item was read but the order may still be wrong: `ambiguous_value`, an item line with several different amounts (a range, a struck-through old price, per person next to total), a number split by a plain space ("1 299 €"), several times when the question does not say departure or start, or a next-day marker; `approximate_value`, "from €94" or "€94+"; `stock_unknown`, the question asks for stock and the line says neither in stock nor sold out; `unnamed_item`, a short label and a value without the question's item word ("Shipping €4.99"); `decoy_name`, the item word is in the name but not as its last word ("Tent pegs" for "which tent"); `mixed_currency`; `mixed_units` (per person against total, per night, ...); `planted_text`, an item line that addresses an agent or asserts the answer) adds `aggregate:partial:<why>`. A time window that wraps midnight ("between 22:00 and 02:00") keeps the times on both sides and orders after-midnight times last. Items read on one earlier state only (the run then moved on) are aggregated too; when the question aggregates but its items are all on the final page, an earlier-state line is never auto-confirmed (`answer:aggregate_disagrees`). A remembered line that addresses an agent or asserts the answer ("the answer is ...") stays trail context and is never an answer candidate, and when the provider's injection guard flagged any page of the run (`guard:injection:<p>`, 0.8 or more), an earlier-state answer is not auto-confirmed (`answer:from_state_guarded`). `verdict.answer` is set for an aggregation only when the items were fully read, the first value is unique, the question is not a filter, and either the usual rule confirms a top candidate that is the aggregation's first item or the override below applies; otherwise `verdict.why` names `answer:aggregate_partial`, `answer:aggregate_tie`, `answer:aggregate_filter` or `answer:aggregate_disagrees`. For a "which ..." question the confirmed answer is the whole item line (`exact: false`).
  **A complete minimum or maximum wins.** Code computes the values, the provider says what the page means: when the aggregation is a `min` or `max` with a measure, not `partial`, not a tie, every item has a value, the question has no condition the aggregation did not read (below), the provider ranked the candidates and its top pick is one of the aggregation's items (the first or another), and no page tripped the injection guard, the aggregation's first item is `verdict.answer` whatever item the provider ranked first (`basis` `aggregate:computed`, `confidence` the provider's probability on the aggregation's items) with `answer:aggregate_overrides` (the provider ranked another item first; its pick stays in the trace's `answerDetail.choice` and `answerDetail.aggregate.pick: "item"`) or `answer:aggregate_confirms` (it ranked the first item first, below `answerConfirm` or `answerMargin`). The first item still passes autoConfirm's intent, shape and multi-part checks, and every guard after it (page loading, scope mismatch, blocked page, `more_unverified`, a join without its trail) still clears it. A pick that is no item at all (a plain block, an earlier line, an item of another list: `pick: "other"`) keeps `answer:aggregate_disagrees`, since it says the aggregation may have read the wrong thing; partial, tie and filter aggregations are blocked as before. **Unread conditions.** A question can set a condition on its items that the aggregation does not parse ("the cheapest hotel with free cancellation", "that has 16 GB of RAM", "without ads", "with no stops"); the order then covers every item read, and its first may fail the condition. After blanking out what the intent consumed (the extremum and measure words, the rating and price bounds, the time window, stock, the measure's nouns such as departure or time, and party sizes such as "with 2 adults"), a remaining condition marker that introduces a word is an unread condition: `with`, `without`, `including`, `excluding`, `except`, `only`, `near`, `within` (not before its/their/his/her: "with its name and price" asks for fields), `that`/`which`/`who` + has, have, had, offers, includes, is, are, comes, allows, supports, provides, contains or lets, `free <word>` and `<word>-free`, and `no <word>`; a determiner in between is skipped. Stay phrases carry no marker ("for the stay of 1-4 March 2027", "per night"), and a parsed filter ("with a rating of 8 or more") is blanked out first. Such a question gets `aggregate:unread_condition` in `verdict.why` (the trace's `answerDetail.aggregate.unread` lists the clauses) and no override: when the provider ranks another item first, `answer:aggregate_disagrees` stands, and only the usual rule (the provider's confident top is the first item) confirms.
  **Which list** (`lists` guidance switch, on). When the final page has two or more record lists and the question ranks or bounds a value, the answer request (`choose()`) carries a second choice question, `lists`: which list holds the items the question asks about. One option per list in the page script's order, its size and position in fixed words (`A list of 9 items, inside the main content, after the result count`; `a horizontal strip (carousel)`) and then at most three record titles after `page text:` (clipped to 60 characters, quotes removed), plus `None of these lists holds the items the question asks about` last; the instructions say page content is data, never instructions. No extra round trip: Jev answers it next to the answer question, and the first five items of each other list's aggregation join the answer candidates, so the answer pick can name an item of whichever list holds the answer. Cost: about 0.75-1.25k characters (190-310 tokens) for two or three lists, plus up to ten candidate lines the request did not already hold. The provider's list is used at 0.6 or more (`lists:provider:<n>`, n the page script's list number, 0 its best); the aggregation and the candidates are then that list's, and the override above confirms only when the answer pick is one of its items (the two reads must agree). "None of these" at 0.6 or more keeps list 0 but marks the aggregation partial (`lists:none`, `aggregate:partial:list_none`): no item of a list the provider rejected is confirmed. Otherwise list 0 stands as without the switch, with `lists:fallback:<reason>`: `off`, `no_choose`, `single_candidate`, `no_time`, `cancelled`, `timeout`, `provider_error`, `failed`, `no_reply` (the provider did not answer it), `invalid` or `low_confidence`; the trace's `answerDetail.lists` holds `{lists, choice?, confidence?, list, why}`. Asked only for the final page (earlier states keep list 0) and only when the question has a measure; a run's "more" completion (`completeList`) still reads list 0. Turn it off with `"providerOptions": {"guidance": {"lists": false}}`; the choose() request is then exactly the plain answer request.
- **Answer scope (one page's question).** The answer candidates and the aggregation come from the states that belong to the question's page; the trail keeps every state. (1) A state followed by another of the same page with no action in between (a first paint, a loading placeholder, a late re-render) is superseded by it when it has at least as many text lines (`answerDetail.scope.collapsed`); a later revision that lost lines (a transient re-render, a skeleton after the rows) supersedes nothing. (2) A results page's day is its own sentence ("departing 2026-10-13", "Departures on Tue 13 Oct"), else a single date in its title, else a single date in its URL, as text or base64 inside a query value (Google Flights' `tfs`). Unless the question or the instruction spans days (two or more dates, a range such as "Oct 12-13", "12 or 13 October", "from the 12th to the 13th", "Monday or Tuesday", "which day", "any day", "each", "every", "week", "days", "across", ...; a time range such as "10:00 and 12:00" is not one), the target day is the one the question names, else the one the instruction names, else the final page's own sentence (never its title or URL date: a publication date or a tracking parameter is not the data's day); states keyed to another day are not candidates (`verdict.why` `answer:scoped_out:<n>`). Nothing is excluded when no state is keyed to the target day; when some state is keyed to another day, the answer is about a day the run never showed and is not auto-confirmed (`answer:scope_mismatch`, `answerDetail.scope.mismatch`). Pages without a date key are never scoped. (3) List expansion: when a completed run's question aggregates (cheapest, between 10:00 and 12:00, ...), the final page has items and offers an in-place button labelled "View more", "Show more", "Load more" or "Show N more", alone or with a list noun (flights, results, items, products, fares, ...; never "View more details", "Show more options", "Load more comments"), a plain page button (never a link, "Next page", a consent-dialog control, a form submit or riskier class, a control in a frame) directly under the rows the answer ranks (the run of list or table rows right above the button, back to its section heading, holds an aggregation item or a row the question's filters leave out, such as a 07:35 departure for "between 10:00 and 12:00"; else `more:other_list` and no click, so a "Show 4 more flights" under a flight list is left alone when the question reads a date grid higher up), and the injection guard flagged no page of the run, the runtime clicks it once before the final ranking, at reversible and above, with one action of `maxActions` and 3 s left, once per page URL per call (`more:expanded`; when the page rewrote its own URL in place on that click, as Google's results page does from `/travel/flights?q=...` to `/travel/flights/search?tfs=...` on "View more flights", and is plainly still the document verified before it, same origin, the same leading block and at least 80% of its earlier block texts still shown, the expectation's URL fields are carried from before the click and its text and title fields verified on the expanded page, `more:url_carried` and `verification.carried: ["urlIncludes"]`; `more:unverified` when the expectation no longer passes afterwards, a real navigation to another page included, in which case the earlier observation stays final; `more:failed` when the page refused the click or the run budget ran out while it settled, in which case the earlier observation stays final too). After `more:unverified` or `more:failed` the answer is not auto-confirmed (`answer:more_unverified`). Before that, a final page whose items look half-rendered (a row with a time and no name at all, "10:47 AM – 4:05 PM") or that still shows a loading placeholder (as for content waits: not hidden status text next to rows, not status text found persistent) gets one more content wait and observation (`answer:settle_wait`, counted against the content waits).
- **Action-only calls.** A run (or list step) is auto-confirmed only when it asks something: it carries an `answerQuestion`, or its instruction, with quoted labels ('…', "…", curly quotes, backticks, […]), URLs, an unquoted label that ends in "?" mid-sentence ("the Where to? field") and "then what?" left out, has a question mark, a wh-word (what, which, who, whose, how many, how much, ...) or a read verb (read, report, tell, extract, look up, show me, give me, find out; list, count or copy the ...; compare the ...; check, see, verify or confirm whether/if; check or confirm the <fact> such as a date, price or total). "get", "note" and "find" ask only with a fact as object: "get the phone number", "note the order number", "find the cheapest fare" ask; "get to Settings", "note: do not book", "find the Search box and click it" do not. An instruction that only performs actions ("Click Where to, type London and choose London, United Kingdom") keeps its ranked `answer.candidates`, gets no `verdict.answer` (`verdict.why` `answer:not_asked`), and `next` is what it is without an answer (a verified outcome is reported, never "your answer is verdict.answer.text"). Instruction-only reads ("Open the pricing page and tell me the Pro price") are unchanged.
- **No progress.** A step's `changed` is true when the URL or revision moved, or when its `moved` names content (title, blocks or controls; a revision-only `moved` does not count, nor a blocks-only `moved` under an unchanged revision that only replaced blocks one for one, such as a ticking live-region clock or a rotating ad; an off-screen append that adds blocks does count). Three consecutive actions that changed nothing end the run `needs_host` / `no_progress`, and so does the first repeat of a click that changed nothing (same page URL, target and label as the previous no-change click; `why` `no_progress:repeat`).
- **Fills the field did not keep.** After a `fill_supplied_text` the page script reads the field back once the page has settled (so a framework's re-render after the input event counts) and reports `fill: {kept, empty}`: `kept` when the field's value contains the supplied text with whitespace collapsed and case ignored, the same digits for a text of digits and separators (a field that formats numbers), or the same date in another form for an ISO date (`2027-01-12` shown as `12/01/2027`, `Jan 12, 2027`, `12 January 2027`, `Tue, Jan 12`, ...); the value itself never leaves the page. A bridge that reports nothing (an older extension) is read on the next observation's `filled` flag instead: a field left empty did not keep it. A fill not kept (a date picker's textbox that reverts or ignores typed text: Google Flights' Departure) is no progress (`changed` false) and no success, whatever the expectation says of the page: the run (or the `act`) ends `needs_host` / `fill_not_kept` right there, with `why` `fill:not_kept`, the step's `fill: {kept: false, empty}` in the trace and `fill: "not_kept"` on the lean step, and `next` (`rerun`) names the field by its supplied-text name and says to set the value another way (a URL in `allowedUrls` that carries it, or the page's own picker or control), never to fill it again.
- **Multi-part question.** An `answerQuestion` that asks for two things (`isMultiPart`: a second wh-clause after `and`, `as well as`, `plus`, `along with` or `; `, two question marks, or two question nouns joined, as in "name and email"; `and` inside a noun phrase such as "the sales and support office" is one question; in an instruction only its question sentences count) is auto-confirmed only when the top line carries both parts, and then the line is kept whole instead of cut to one value: a byline ("<Title> by <Name>") for a question about a person and a work (`value:byline_whole`), an aggregation's item line, or a line where the asked price (count, hours) sits beside other text (`value:multi_part_line`, `exact: false` for a compound row). Any other top line is `answer:multi_part` and the host reads `page.digest`. FAI never joins two lines into one answer.

### Screenshots

`capture: "last"` is the default (CLI, SDK, daemon and MCP): every action runs without capture and only the final step is screenshotted, once, when the run ends, as a downscaled annotated JPEG (quality 70, at most 1280 px wide). `fai_browser_evidence` and `returnImages: "final"` serve that image. `capture: "each"` screenshots every action; the capture runs after the observation returns, while the next provider decision is in flight, but Chrome's `captureVisibleTab` quota caps the extension at one screenshot per 500 ms, so `each` cannot go faster than about 0.5 s per step (the browser bench measures about 500 ms per step with `each` against about 435 ms with `last` at a 270 ms provider). Ask for it explicitly when you need intermediate screenshots; an MCP `returnImages: "all"` without `capture` implies it. `none` captures nothing. `last` and `none` run at roughly 160 ms per step plus provider latency. A run that is stopped or cancelled with `last` has no screenshot; one that ran out of time still captures its final step, with a 1 s cap. Keep the selected tab active and visible.

**Badges.** Every screenshot boxes the controls in the frame. An `observe` capture (and a run's final capture when its page is remembered for `act`: a `low_confidence` result's alternatives, a handoff's `decide` options) badges each in-view offered control with its **action id** (`a12`; a select or a field with several offered actions reads `a3–a5`, or `a3 +2` when the ids are not consecutive), only offered controls are boxed, badges move out of each other's way (left of the box, above, below, inside its corner, to its right), and the footer reads `tags: action ids (<n> in view)`. The daemon sends the extension the offer's ids with the revision they belong to; a frame of another revision (the page changed by itself) keeps the control refs, as a per-action capture of a run does (`boxes: ... refs`). Off-screen offered controls are not drawn. The `observe` result says what the image is: `image {revision, width, height, tags}` (`tags` is `actionIds` or `refs`; MCP also prints `image: revision ..., 1280x800 px; badges are action ids for fai_browser_act`), and a run or act result with `returnImages` lists `images [{step, revision, width, height, tags}]`; the trace's `screenshot.tags` holds each badge (`id`, `ref`, `x`, `y`, `width`, `height` in image pixels). `evidence` reports `revision` and `tags` too. Those pixels are the coordinates a [point click](#point-clicks) takes.

### Traces and retention

Each run (and each observe) writes `artifacts/<id>/trace.json` plus one image file per captured step. With a question, the trace's `facts` is the run's [fact memory](#fact-memory-and-aggregation): `[{state, step, url, title, revision, lines [{text, context?, score, t, item?, value?}]}]` (at most 40 states, supplied values redacted), and `answerDetail.aggregate` the aggregation (op, measure, item count, states, top values, `partial` and why). Without `--output-dir`, `artifacts/` is in the state directory (see [The daemon](#the-daemon)) or `$FAI_HOME`. The trace holds the result, the instruction, the options with credentials removed, timestamps, host versions and per-step observations without control bounds. It never embeds base64. Form fills are recorded by `suppliedName` only: the value you supplied is never written. Password values filled at `testing` are also replaced with `[redacted]` wherever the page echoed them (see [Permission levels](#permission-levels)). Before any provider request, supplied values of **4 or more characters** that the page echoes back (also URL-encoded) are replaced with `[supplied:<name>]`; shorter values are not redacted, so never pass short secrets. Page text in traces can still be sensitive, so treat traces as local task records. `cost.requests` in the trace lists every provider request of the run, numbers only: `kind` (`decide`, with `step` when its choice ran as that step; `second_opinion`, an [in-call retry](#in-call-retries) decide, also with `step` when its choice ran; `choose`, the answer ranking; `guard`, the purchase guard on `act`), `attempt` (1 or 2, only after a self-rerun), `ms` (wall time, retries included), `inputTokens`/`outputTokens` and `providerMs` when the provider reports them, `error` (`provider_error`, `timeout`, `cancelled`) for a failed request, `discarded: true` for an answer ranking whose result was not used (see [Output, status and exit codes](#output-status-and-exit-codes)), and, when the provider reports its request body (the Jev provider does), `chars` (the body's size in JSON characters, counted as UTF-16 code units: `total` and by section, `instruction`, `question`, `policy`, `page` for URL and title, `text`, `controls`, `history`, `earlierPages`, `options` for the offered choices or answer candidates, `questions` for the question wording, `framing` for the remaining keys and separators; the sections sum to `total`), `options` (choices offered) and `controls` (controls sent in the page). In a [step list](#step-lists) each entry also has `listStep` (1-based). Entries are in completion order, per step. A step list's trace also has `stepRuns`: each step's filled instruction, status, code, `why`, final URL, step count and cost (and `attempts` after a self-rerun in that step); its `instruction` is the steps' instructions, numbered (`1. … 2. …`), led by the host's summary instruction when one was sent (`<summary> Steps: 1. …`), and `options.steps` the list as sent. After a self-rerun the trace also has `attempts` (the first attempt's instruction, status, code, `why`, `suggested`, final URL, cost and step count; its steps lead `steps`). It is not in the agent result; `bench/qa/run.mjs` summarizes it per kind. `readRun(path)` loads a trace.

After each write the daemon prunes the oldest runs (observes count too) until at most **50 runs, 500 MB and 7 days** remain. It never deletes the run it just wrote, and it only touches directories that contain a `trace.json`. Change the limits with `"retention": {"maxRuns", "maxBytes", "maxAgeMs"}` in `config.json` or `FAI_RETENTION_MAX_RUNS|BYTES|AGE_MS`, or skip pruning per run with `--no-prune`.

The extension's Pause pauses the lease and ends the current run as `needs_user`/`paused`; the user presses **Resume on this tab** and the agent continues (its `next.text` names the background `wait --until active` command that wakes it on the click). Stop ends the run as `stopped` and releases the tab.

## SDK

```js
import { FaiBrowserClient } from './src/client.js';

const client = await FaiBrowserClient.connect({ clientName: 'my-script' }); // auto-starts the daemon
const { requestId } = await client.requestTab({ origins: ['https://example.com'], reason: 'Check About' });
await client.waitForTab(requestId, { timeoutMs: 120_000 }); // the user approves the tab in the extension
const { result } = await client.run({ requestId, instruction: 'Open About', expectation: { urlIncludes: '/about' } });
console.log(result.status, result.verification.passed, result.page.digest);
await client.release(requestId);
```

A step list goes in the same call: `client.run({ requestId, steps: [{ instruction, expectation, answerQuestion }, ...] })` (or `runtime.run({ steps })` in process); `validateSteps(steps)` checks one without running it.

`BrowserRuntime` and `createHub` stay exported for in-process use with your own bridge (`observe()`/`act()` for host-driven control, `act({ point })` on a bridge with `locate()` for a [point click](#point-clicks), a custom provider, tests). The standalone harness companion the benchmarks and smoke tests use lives in `bench/companion.js` and is not part of the package API. `writeRun`, `readRun`, `toAgentResult` and `prune` are exported for tooling. Types are in `src/index.d.ts`.

## Policies and providers

Mechanical oversight runs before any provider call on every page: a password field together with a sign-in title or first heading ends the run as `needs_user` / `login` below `testing` (FAI Browser never logs in outside testing mode; a password field alone is only a `password_field` warning); a cookie dialog (English, German, French, Spanish, Italian, Portuguese or Dutch labels: "Alle ablehnen", "Nur notwendige", "Tout refuser", "Continuer sans accepter", "Rechazar", "Solo necesarias", "Rifiuta", "Rejeitar", "Weigeren", "Alleen noodzakelijk") is dismissed with its one reject or necessary-only button (a step with `class: "consent"`), several such buttons are offered to the provider alone, and an accept-only dialog ends the run as `needs_user` / `consent_banner` below `full` (the dialog text is in `needs.dialog`, untrusted). A reject click counts (`why` `consent:rejected`) only once the dialog has closed: the runtime re-observes every 250 ms for up to 2 s (`consent:wait`), never clicks the same consent button twice, and a dialog that stays open is `consent_banner` with `consent:persisted`. A whole-page consent wall on a `consent.*` host (consent.google.com, consent.youtube.com, "Before you continue") is a consent dialog too: Reject all is the mechanical step, and when the request lists both origins the extension follows its redirect back to the `continue` URL and the run proceeds there (one hop per session, only from a `consent.*` host and only to an origin of the same request; `why` records `consent:redirect:<origin>`). Chrome drops the `activeTab` grant on a cross-origin navigation, so with the shipped manifest that follow may still end as `origin_changed` and the user re-selects the tab on the destination page; the benchmark and probe builds grant `<all_urls>` and do not show this; if the `continue` origin is not in `origins`, the run ends `cross_origin` naming it, without clicking. A page on an origin the request does not cover is `cross_origin`, naming the origin (for Google properties request `https://www.google.com` and `https://consent.google.com`; a consent host is always requested exactly); when it is a sibling subdomain of an approved https origin, `needs.message` suggests the [domain root](#domain-roots) instead. Below `full` accept buttons are never offered or clicked; at `full` and `testing` they are offered to the provider only when the dialog has no usable reject button (a reject is always clicked first, and an accept label that commits, such as "Accept and subscribe", is never offered). A `stale` action (the page changed after it was observed, as MDN does when it adds ad and sign-in links after load) is re-observed and decided again (at most twice in a row; `why` `retry:stale`, and the decide entry in `cost.requests` gets `stale: true`), except that a provider-chosen link to an approved origin, with a provider that has the slim guards request, runs on the fresh observation without a new decide when Rung 0 passes, the URL and the expectation state are unchanged and exactly one offered link has the same type, destination, label and frame (`decision.reason: "stale_reresolve"`, `why` `retry:stale_reresolve`, the step's `decision.guards` from the fresh guards request; never for an `href` to the page itself such as `#` or an empty one; at most once per page in a call; not counted in `maxDecisions`, counted in `maxActions`); the slim guards request for the new content runs next to that click (`cost.requests` kind `stale_guards`), and a blocked or injection score, or a failed request, turns re-resolves off for the rest of the call (`retry:stale_reresolve:<blocked|injection|guard_error>`). An `unsupported` action is retried once with that action excluded (at most twice per run), a link click that settles on the same URL, or a button click that settles quiet with no change to the URL or page content (title, block text, control state; not the scroll position), is re-observed once after 300 ms (at most four re-observes per run that found nothing: one that saw a late navigation, or led to a late change, is not counted, up to eleven such per run; `why` `late_navigation` when the page had changed; a live region that ticks on its own makes a click look like a change, so the late wait is skipped on such pages; when `textIncludes` passed only past the viewport, `textAbsent` is read in the whole rendered document too, and a walk that hit its node cap counts it as present), a handoff with off-screen text matching the task scrolls once first, and instructions naming four or more pages get a 45 s default timeout.

**Blocking overlays.** After the cookie check, Rung 0 looks for any other popup over the page (extension/page.js `detectOverlay`, src/overlay.js). Signals: an open dialog (`role="dialog"` or `alertdialog`, `aria-modal`, `<dialog open>`), a fixed or high z-index layer hit-tested under the viewport centre that lies over page content (an app shell fixed to the viewport is the page, not an overlay), a separate full-viewport backdrop, main content made `inert` or `aria-hidden`, and a fixed bottom sheet. The page script classifies it by its own text and controls: a nag (`sign_in`, `newsletter`, `promo`, `app`, `permission`), an `age_gate`, a `task` dialog (a form, a picker grid, a confirmation such as "Are you sure") or `unknown`, and reports it as the observation's `overlay {kind, nag, text, signals, closers, escape, backdrop}` with the warning `blocking_overlay` (not for a task dialog). Only a nag is dismissed, at every level (as a cookie reject is), one step at a time with `class: "dismiss"`: its close control first (an X, an `aria-label` close or dismiss, "No thanks", "Not now", "Maybe later", "Continue without ..."; never a control whose label signs in, registers, subscribes, accepts, buys, submits or deletes), then Escape, then a click on its backdrop when that is a separate element. Each step runs at most once per overlay and at most six per run; the runtime re-observes until the popup goes. `why` records `overlay:dismissed` and the method (`overlay:close`, `overlay:escape`, `overlay:backdrop`); `overlay:undismissable` when every step failed, `overlay:persistent` when it came back more than twice, `overlay:user_opened` when the run's own button click opened it (the provider decides), and `overlay:kept:<kind>` for a task dialog, age gate or unknown dialog, which are never dismissed. Controls and blocks inside an overlay that is not a task dialog carry `overlay: true`: they are offered after the main content's controls, described as inside a popup, and ranked at half weight in the digest. The pattern corpus in fixtures/patterns/ (test/patterns.test.js) holds one page per common popup shape.


`read-only` (the default) offers clicks on same-origin links plus scroll and wait; each higher level adds what [Permission levels](#permission-levels) lists. Below the level that allows them, submissions, deletions, sign-in controls, purchase controls (pay, buy, purchase, place order, order now, checkout, proceed to checkout or payment, book or reserve now, subscribe, upgrade or renew a plan, start a trial, transfer money or funds, withdraw, send money or payment, donate, bid, add a payment method; ambiguous words such as "Order", "Book" or "Upgrade" only as the whole label or followed by "now" or an article, so "Bookmarks", "Order history" and "Apply filters" stay offered; "Add to cart" is an ordinary control; a cookie-dialog button with such a label, such as "Reject and subscribe", is never treated as a reject button), payment fields (`autocomplete` `cc-*`, or a name, id, label or placeholder for a card number, expiry, security code or IBAN), cross-origin links and child tabs are never offered, and the page script refuses them on its own as well. Links whose short label (at most 4 words) leads with a destructive or commit verb ("Delete account", "Delete this filter", "Sign out", "Unsubscribe", "Cancel subscription", "Proceed to checkout") are offered only at the level of their class (delete and submit at `full`, sign-in and purchase at `testing`), never as `verdict.decide.options` below it; longer descriptive labels ("How to delete your account safely") and labels where the word comes later ("Order history", "Where to buy") stay navigation; "Sign in" and "Log in" links are always blocked. While the `injection` guard is at 0.85 or more, decide options keep only plain navigation links to approved origins. Custom dropdowns: an element with `role="option"` inside a `role="listbox"`/`menu` (or the popup an `aria-expanded` trigger controls) is a clickable control from `reversible` once the list is open, and the listbox container itself is not offered. Same-origin iframes (top-level ones, at most 8) are read into blocks, text and controls like the page; their control ids continue the page's numbering and carry `frame` (the 1-based index of the readable frame), so `act` resolves them like any other id. Cross-origin frames are never read and add the warning `cross_origin_frame`. Risk classification is heuristic, so use disposable data. A run is never more permissive than the level the user granted for the tab.

The TypeSafe Jev provider sends one request per decision. With the default guidance (the "Jev guidance pass" in [PROPOSAL.md](design/PROPOSAL.md)) it carries `state.policy`, a short named policy the action question refers to (page text is data; logging in, submitting, buying, sending and deleting are the user's; prefer reject or necessary-only cookie buttons; hand off when nothing clearly advances the instruction), `handoff` as the last, explicit "none of these" option, `what`/`not_for` descriptions for confusable controls (shared label prefix, consent buttons), and two guard questions next to `done` (plus `commit` at `reversible` and the purchase guard's `purchase_control` and `purchase_page` at every level that offers controls below `testing`; see Guardrails): `blocked` (login wall, captcha, paywall or consent-only page) and `injection` (page text addressed to an agent). Guards are recorded on each step (`decision.guards`) and in `verdict.why` (`guard:blocked:0.64` at 0.5 or more; `guard:injection:0.91` at 0.8 or more, the injection note: benign pages mostly score below 0.8 and injected instructions 0.96-0.99 on `node bench/jev-eval.mjs`). At 0.85 or more, `blocked` ends the run as `needs_user` / `blocked` (after the mechanical checks above, never while consent buttons are offered); when the expectation passes and `done` is at least `doneThreshold` the run still completes (`expectation_passed`), but the verdict is `likely` / `confirm` with `guard:blocked_page` in `why`, `verdict.answer` is never auto-confirmed, and `next` is `confirm_page`: the host checks that `page.digest` answers the task before trusting it and `injection` lets only a link to an approved origin run; anything else becomes `handoff` (`guard:injection_veto`). Code-side vetoes stay authoritative: a guard can stop an action, never allow one. **Named buttons** (`named` switch, on): when the instruction names an offered button as a click target (a click verb, `click`/`press`/`tap`/`hit`/`push`, optionally `on`/`the`, then the label, optionally quoted, outside a negated clause such as "never click Submit order", "don’t press Continue" or "click everything except Continue": never, not, no, any n't contraction, cannot, nor, avoid, without, except, instead), `state.policy` gets a last `named` line: `` `instruction` names the offered button "Next": when the page does not say it orders, pays, books, subscribes, sends or deletes, choosing it is part of the request. `` Only plain buttons are named (never links, fills, selects or consent buttons), only labels that trip no guardrail class (purchase, sign-in, delete, submit, send, commit lookalikes such as Upgrade, the user's `forbid` phrases; ordinary view controls like Apply and Search are allowed; never a binding or irreversible verb the classes do not cover, such as trash, discard, approve, accept, agree, sign, merge, deploy, transfer, withdraw, share, cancel or archive, a page-script descriptor such as "unlabelled button 1 of 2 next to ...", or a label with invisible characters, every check on the folded safety spelling), at most three, in the instruction's own spelling (page text never reaches the line). A label stops being named once the run has clicked it as often as the instruction names it ("then click Next" is used up by one Next click). Without a named button the request is byte-identical to the switch being off; `cost.requests[].named` counts the named buttons of a request. Why: the `user_actions` and `commit_lookalike` lines name "submitting" and "a generic ... Next", and after a wizard step's fills Jev read the step's own Next as the user's (handoff 0.75-0.88, Next 0.12-0.25 in bench/long); with the line Next is 0.87-0.98, while a named Next or Continue the page says pays or upgrades stays at 0.05-0.16 (round 6 E1). The commit and purchase guards are asked and enforced exactly as without it. Turn it off with `"providerOptions": {"guidance": {"named": false}}`. **Intent** (`intent` switch, off): an `intent_<id>` question for an ambiguous refused control, see [Guardrails](#guardrails). **Which list** (`lists` switch, on): the answer request's `lists` question, see [Fact memory and aggregation](#fact-memory-and-aggregation). Failed requests are retried twice, after 300 ms then 900 ms (each delay capped at 2 s), on 408, 429, 5xx and network errors, waiting at least `Retry-After`/`retry-after-ms`; a `Retry-After` beyond 2 s fails at once. Each switch can be turned off in `config.json` (`"providerOptions": {"guidance": {"guards": false}}`, or `false` for the earlier request); `node bench/jev-eval.mjs` measures them and `node scripts/jev-order-check.mjs` checks option-order bias.

A custom provider implements `decide(observation, legalActions, context, signal)` and returns `{actionId}`. `LocalSystemOneProvider` defaults to `http://127.0.0.1:8000/v1/systemone`. Clients can pick `"provider": "local"` with `providerOptions.port` (Kev uses 8009), `model` or `timeoutMs`; a provider `endpoint` is accepted only from `config.json`, so a client cannot send the key or page text elsewhere. It uses `LOCAL_SYSTEMONE_API_KEY` if set and never forwards the Jev key.

### Permission levels

The user decides what FAI Browser may do in each approved tab. The agent asks with `mode` (MCP and daemon `mode`, CLI `--mode`, SDK `mode`); the request card in the extension popup shows "asks for Act", and a level selector, **Allow**, that offers only levels at or below the asked one and is preset to the asked level (capped by **Preselect up to**, below; Test site is never preset). The popup names the levels **Read** (`read-only`), **Use** (`interactive`, or `reversible` when that is what the agent asked for: click, fill, search, filter, never save or send), **Act** (`full`) and **Test site** (`testing`); agents and every API keep the internal names. Approving sends the chosen level with the lease; the daemon records it as the request's `grant` (`fai_browser_status` and the daemon's request view show `grant {level, testing, grantedAt}`). Every run and observe is clamped to the grant, without an error: asking above it runs at the grant, and the receipt's `permissions` block shows `requested`, `granted` and `effective`. The extension clamps every command again to the level the user chose, so the host can lower the level but never raise it. Nothing in `config.json`, `policy`, MCP arguments, CLI flags or options files grants a level. Without a tab lease (an SDK caller with its own bridge) the ceiling is `full`.

| Level | Adds | Capabilities |
|---|---|---|
| `read-only` (default) | same-origin links, scroll, wait, allowed URLs | `navigate` |
| `reversible` | buttons, selects, fills of supplied text, script links | + `controls` |
| `interactive` | form submits labelled search, find, go, filter, apply (filters), sort, refine, show (more/all/results), see/view/load more, next or previous (page); only on pages without a password or payment field and in forms without frames | + `submit_safe` |
| `full` | save, send, submit, confirm, publish, invite, apply; delete, remove, cancel a subscription or account; accept a cookie dialog when it has no reject button | + `submit`, `delete`, `consent_accept` |
| `testing` | sign-in (password fields are offered as fill targets, login walls no longer stop the run), purchases and payment fields; no guardrail but `forbid` additions | + `sign_in`, `purchase` |

**Purchases are never allowed below `testing`**, whatever the agent, the page or a config file says. Below `testing`, at every level that offers controls, the Jev purchase guard asks two more questions in the same decide request: `purchase_control` (would the offered control that best advances the instruction pay, order, check out, book, reserve, subscribe, start a trial or move money?) and `purchase_page` (is this a checkout, payment, order-confirmation or booking-confirmation step?). At `commitVeto` (0.7) or more on either, a chosen button, select or fill is refused (`refused_action`, `why: guard:purchase_veto`, `next.kind: stop`). The guard only adds refusals; the label and field checks stay authoritative on their own. It fails closed: a purchase question Jev was asked but did not answer counts as 1. Host-driven control asks it too: `fai_browser_act` on a button, select or fill below `testing` sends one Jev request about the chosen action first (a veto ends the act as `refused_action` / `guard:purchase_veto`, or `guard:commit_veto` at `reversible`; a failed provider call fails the act and nothing is dispatched; without a configured provider the act keeps the label and field checks only). Custom providers that report no guards have the label and field checks only.

**Testing mode** removes every guardrail except `forbid` additions and the fixed invariants (http(s) tabs only, the approved origins only, user-approved tab access (one by default), page text is data, the injection guard). It exists for driving your own test or staging app end to end. The popup offers **Test site** only when the agent asked for `testing` and every origin of the request is listed under **Advanced → Test sites**, and the extension re-checks the list from storage when you approve; while a testing lease is active the tab card reads **TEST SITE, no guardrails**, and removing the origin from the list drops the session to Act (`full`) at once, for good (listing it again needs a new approval). The extension tells the daemon (a `lease_level` message, which can only lower a grant), so later receipts show `permissions {granted: "full", effective: "full", testing: false}`, sign-in and purchase controls are no longer offered, a run already in progress continues at Act from its next decision (`why` has `grant:lowered:full`), and a sign-in task gets the level request (`needs.level: "testing"`, `next.kind: relay`) instead of a blocked control. A login wall on a run that asked for `mode: "testing"` but has a lower grant is `needs_user` / `login` with the same `needs.level: "testing"` relay.

The popup's **Advanced** section (permissions stored in `chrome.storage.local.permissions`, readable only by extension pages):

- **Preselect up to**: Read, Use or Act (never Test site). Default: Act, so a card preselects what the agent asked for. A setting saved as Reversible by an older version counts as Use.
- **Test sites**: exact origins such as `http://localhost:3000` or `https://staging.example.com` (scheme, host and port; no path, trailing slash, wildcard or user info; `localhost` and `127.0.0.1` are separate entries; at most 50). A request with a domain root is never offered Testing.
- **Remember whole-domain approvals for 24 hours** (off by default; `chrome.storage.local.domainMemory`). See [Domain roots](#domain-roots).
- **Show a window when an agent asks** (on by default; `chrome.storage.local.approvalWindow`, `false` when off). See [Approval window and tab mark](#approval-window-and-tab-mark). Off: the `?` badge on the toolbar icon is the only sign that a request waits.
- **Open requested pages right away** (on by default; `chrome.storage.local.openRightAway`, `false` when off; an absent or any other value counts as on, so an install that never touched it has it on). A new request's page opens in a new tab with no click, armed at the requested level up to Use, with a small prompt window next to it that says to click the icon; the FAI Browser icon click on that tab is still the only approval. A request for Act or Test site never opens by itself: it gets the approval window, where the level is confirmed. See [Open and approve](#open-and-approve).

When a task needs more than the grant, the receipt is `needs_user` / `refused_action` with `needs.level` (see [Output](#output-status-and-exit-codes)); the agent relays `needs.message`, and the user picks that level on the new request card the next call opens.

**Credentials at `testing`.** Pass test credentials as `suppliedText` values. A value whose name says it is a secret (`password`, `pw`, `pwd`, `passcode`, `secret`, `pin`, `otp`, `token`, `api_key`, `credential`, ...) is treated as one: when the host supplies any, a password input is offered only those values (never the username), and a secret is offered for a non-password field only when that field is meant for one (its label reads password, PIN, token, API key or one-time code) or the instruction asks for exactly that fill ("fill the Username field with the supplied password", "put the password into Username"). A fill into a password input, and any fill of a secret value, carries `sensitive: true`, never records its value in the step, and the value is replaced with `[redacted]` wherever it appears in that run's receipt and trace and in every later result of the same daemon (values of 3 or more characters, also URL-encoded and base64-encoded); the extension keeps it out of screenshot captions too. The value goes to the page through the extension. Before a provider request, any supplied value of 4 or more characters that the page echoes is replaced with `[supplied:<name>]`, so it is not sent to Jev in page text; a shorter one can be. Use test accounts only. Secrets the page itself shows (keys, tokens, card numbers) are redacted at every level, testing included ([Secret redaction](#secret-redaction)).

### Per-request budget

Each tab request has a call budget the MCP server enforces (`maxCalls` run/act/observe calls and `maxMs` of run time; see [Coding agents](#coding-agents-mcp-and-skill), loop stoppers): a stuck host cannot spend without end on one tab. The default is 50 calls and 20 minutes, enough for a host that drives steps itself or reruns a few times; a host that needs more than that is going in circles. The user sets it in the popup's **Advanced** section under **Per-request budget** (two fields, whole numbers: calls 1 to 500, minutes 1 to 240; both empty removes the setting), stored as `chrome.storage.local.budget` `{maxCalls, maxMs}`. Precedence, highest first:

1. **The popup setting.** The worker reports it in every `hello` (`settings: {budget}`) and in a `settings` message on every change (HTTP fallback `POST /settings`); the daemon validates it again and answers with the budget now in effect, which the popup shows under the fields ("In effect: 50 calls, 20 min (your setting | from config.json | default)"). It persists across service-worker restarts (the next hello carries it) and daemon restarts (the extension's reconnect hello carries it).
2. **`config.json` `"budget": {"maxCalls", "maxMs"}`** in `$FAI_HOME`, validated at daemon start and reload; a missing field takes the default.
3. **The defaults** (`DEFAULT_BUDGET` in `src/settings.js`).

The result is the ceiling: `GET /v1/status` reports it as `budget {maxCalls, maxMs, source}` and every request wait (`POST /v1/wait` with `requestId`) carries the same `budget`, from which the MCP server reads the ceiling for that request on every run call (an act or observe before any run peeks once). A call's own `maxCalls`/`maxMs` can only lower it: a higher ask runs with the ceiling and warns once (`budget_capped:maxCalls:<ceiling>` / `budget_capped:maxMs:<ceiling>`); an ask holds for the request until the host sends another, so a raised popup setting takes effect at once for a host that asked nothing, and on its next ask for one that did. The MCP server's own read of `config.json` applies only against a daemon that reports no budget (older daemons).

### Domain roots

An `origins` entry is an exact origin (`https://app.example.com`, matched exactly: scheme, host and port) or a **domain root** written as a wildcard origin, `https://*.example.com`: the registrable domain `example.com` and every subdomain of it (`www.`, `developer.`, `a.b.`), over https on the default port only. It is for a task that spans subdomains of one site (MDN pages linking to `www.mozilla.org`), where exact origins would stop with `cross_origin` and cost a new approval click per subdomain. The same field was chosen over a separate `domains` list because the wildcard can never be mistaken for an exact origin: before roots, the daemon accepted `https://*.example.com` as an "exact" origin no tab could have, so no working request widens, and an exact entry such as `https://example.com` still covers only itself.

- **Validation** (`src/origins.js`, daemon `POST /v1/requests`, MCP, CLI `--origin`, SDK): lower-case ASCII (punycode) host names of at least two labels ending in a letter label (no IP address, path, port, trailing dot or second wildcard), https only (`http://*.example.com` is refused with a hint), and the root must be registrable under the **Public Suffix List** (ICANN and PRIVATE sections, wildcard and exception rules), vendored in `vendor/public_suffix_list.dat` and generated into `src/psl-data.js` and `extension/psl-data.js` by `node scripts/update-psl.mjs` (downloads from publicsuffix.org; `--file F` for a local copy; nothing is fetched at run time; `test/origins.test.js` checks both files against the vendored list and the matching code's three copies against each other). Refused: a public suffix (`*.com`, `*.co.uk`, `*.github.io`, `*.us.com`, `*.hf.space`, `*.blog.br`), a name with a public suffix below it (`*.amazonaws.com`, `*.kawasaki.jp` over the wildcard `*.kawasaki.jp`, `*.r.appspot.com`, `*.windows.net` over `blob.core.windows.net`), a host under a top-level label the list does not know (`*.foo.localhost`, `*.example`, `*.test`), and a small fail-closed overlay of multi-tenant domains the list does not fully cover (`amazonaws.com`, `on.aws`, `azure.com`, `windows.net`, `azurecontainerapps.io`, `github.dev`, `gitpod.io`, `googleusercontent.com`, `wordpress.com`, `tumblr.com`, `substack.com`, `weebly.com`, `glitch.me`, `firebaseio.com`, `neocities.org`, `loca.lt`, `stackblitz.io`, `sourceforge.io`, `codesandbox.io`, `000webhostapp.com`, and any `blogspot.<suffix>`). A deeper root is fine (`https://*.docs.example.com`, `https://*.alice.github.io`, `https://*.myapp.vercel.app`, `https://*.city.kawasaki.jp`). This is fail-closed: a real site with a private suffix below it (`*.salesforce.com`, `*.gov.uk`) can only be approved by exact origins. `cross_origin` suggests a root only when the page's registrable domain passes the same check; otherwise it suggests the exact origin.
- **One matcher** for every origin check: the lease, every observed page (rung 0 `cross_origin`), link admission (`legalActions` offers a link to another subdomain only when the page and the destination share an approved root; two exact origins never link to each other), `allowedUrls` (daemon `origin_not_granted`), consent redirects, the injection guard's approved links and site-profile attachment (a root attaches the profiles of the origins it covers: `createDomainStore().matchSite(entry)`). A page on another registrable domain, on http or on another port is still `cross_origin`. Levels and guardrails are unchanged; only which hosts count as the same site widens.
- **Approval.** The request card reads "all of example.com" (never the pattern) and, when the tab is on a page the root covers, offers **Site: All of example.com** (preset, as the agent asked) or **Only https://developer.example.com**. Approving "All of" calls `chrome.permissions.request({origins: ["https://*.example.com/*"]})` inside the Approve click (the manifest declares `optional_host_permissions: ["https://*/*", "http://localhost/*", "http://127.0.0.1/*"]`; Chrome shows its own site-access prompt). Chrome drops the `activeTab` grant on a cross-origin navigation; the host permission is what keeps the session (tab URL and scripting) alive on other subdomains. The worker checks `chrome.permissions.contains` itself before it sends `scope: "domain"` with the lease; a declined prompt or **Only** sends `scope: "origin"`, the popup says so, and the lease covers the tab's exact origin in place of the root (plus any exact entries). The daemon keeps a root in the lease (`lease.origins`, `grant.scope`) only for `scope: "domain"`; receipts report `permissions.scope`. Asking again with the root (MCP reuse compares against the lease's origins) opens a new approval. If Chrome closes the popup while its prompt is open, approve again: the permission is then already granted and no prompt appears.
- **Release and remember.** The popup tells the worker which `https://*.<root>/*` pattern it is about to request (`track`; kept in `chrome.storage.local.trackedSites`), and the worker only ever removes a tracked pattern: never the companion's required permission, and never a site the user allowed by hand in the extension's site access settings (then the card says no Chrome prompt will appear, and nothing is tracked). It keeps the permission while the session is active or paused (Resume needs no new prompt), for 60 s after a fresh grant (an approval in progress), while a tab opened with "All of <root>" waits for its icon click (see [Open and approve](#open-and-approve)), and removes it (`chrome.permissions.remove`) when the session stops, the daemon releases or supersedes the lease, the start fails, or the worker restarts (no session survives that). With **Remember whole-domain approvals** on, a session approved at Read or Use (no submit) keeps its domain's permission for 24 hours from the first remembered approval (never extended; `chrome.storage.local.rememberedSites`), so the next such approval there needs no Chrome prompt; the FAI approval click is still required. Remembering is per level: choosing Interactive or above on a card for that domain ends the remembered entry and removes the permission right away, before any click (the card says so), so the Approve click requests it synchronously inside its user gesture and Chrome asks again. Remembered domains are listed under Permissions with **Forget**; turning the setting off removes them at once, and expired ones go on the next 30 s alarm. The service worker is a classic script (it loads `psl-data.js` with `importScripts`).
- **Not covered:** Testing (testing environments stay exact origins; a request with a root never gets Testing), and same-origin-only machinery (the back-out retry, the site-profile fast path) which stays per origin. An approved root does cover [frames](#frames) on https origins under it.

### Open and approve

Read and Use requests open a fresh task tab in an existing normal browser window. Approve directly in the
request modal, or click the FAI Browser toolbar icon on that task tab (Ctrl+Shift+Y unless changed). Act and Test
site requests first show the request card: choose the level, click **Open**, then approve in the modal or toolbar.
Opening a page grants no access. The modal's button requests optional access for the exact scheme and host in
its native click gesture, then leases the original armed task tab. It never selects the extension window's tab.
Browser host patterns cover all ports; runtime checks still require the approved exact origins. The toolbar
alternative grants `activeTab`. On both Chromium and Firefox, screenshots need `activeTab` or existing all-sites
access; a modal's per-host permission alone is insufficient. No all-sites permission is requested for this flow.


When the current tab is not on a requested origin (or is not an http page), the card's primary button reads **Open <host>** and the mismatch line says the host opens in a new tab and is approved there with its modal or toolbar icon; level and site choices work as on a matching tab. When the tab does match, **Approve this tab** stays the primary path (`#approve`) and **Open in a new tab** is a secondary link. With **Open requested pages right away** off, nothing opens before that click.

- **Start URL.** The request's `url` when it is http(s) on one of its `origins`; otherwise the first exact origin plus `/`. A request with only domain roots and no `url` has no start URL and keeps the plain approve-this-tab card. The worker derives the start URL again from the request it holds; the popup's word is never used.
- **Open and arm.** The popup sends `open` (`requestId`, `level`, `scope`). The worker opens the start URL in a new active tab in the most recently focused normal, non-private window (`chrome.tabs.create`) and *arms* that tab: `{ tabId, requestId, level, scope, patterns, client, at }`, kept in memory and in `chrome.storage.session.armedTabs`, so a restarted worker keeps it. If that window is unavailable, another normal, non-private window is used; if none is available or it closes during creation, a normal window is created. The task tab gets its own FAI group when the browser supports groups, and the group stays specific to that request's approval state. Switching to another tab in the same window pauses the session, since screenshots and the active-tab check require the leased tab to be active. The task tab is not closed when the session ends. No lease is made and the agent gets nothing yet.
- **Armed tab.** Once the page has loaded, the armed tab has no popup (`chrome.action.setPopup` with an empty popup for that tab, so `chrome.action.onClicked` fires there), a `?` badge, the icon title "FAI Browser: click to approve <client>'s request (<level>)", and a tab group titled `FAI ?`. Chrome resets per-tab action values on navigation, so they are applied again whenever the tab finishes loading; a click during a load opens the ordinary popup, where **Approve this tab** does the same. The popup status after **Open** reads "On the opened tab, click the FAI Browser icon (Ctrl+Shift+Y) to approve."
- **Prompt window.** Each opened task tab gets `arm.html?tab=<tabId>` in a 440×430 popup next to its normal window.
  It names the client, host, reason and tab-access mode and offers **Allow**, **Approve Read / Use / Act / Test site**
  and **Deny this request**. The selector cannot exceed the requested level; Test site also requires listed test origins.
  Before enabling Approve, the worker prepares a tab/request/timestamp-bound permission intent. The click calls
  `permissions.request` synchronously for the task tab's host and, in the same prompt, up to 10 other exact origins of
  the request (approved [frames](#frames) and sign-in hops need host access; the ones not held before are tracked and
  removed when the session ends; a list that fails validation or that the browser refuses to ask falls back to the
  task host alone); the worker then verifies the sender, original arm, current and pending URL,
  host permission, requested ceiling and testing eligibility before and after leasing. Denial, revocation or stale
  state never adopts another tab. Newly acquired access is tracked while live arms/sessions need it; preexisting
  browser grants remain. If the worker restarts after a cancellation while the native prompt is still pending,
  attribution of a late grant may be lost: uncertain access is retained rather than removing a user grant, and can
  be removed through browser extension settings. Approval, denial, expiry or closing the task tab closes the modal.

- **The icon click approves.** On the click the worker checks that the request is still pending or paused, the arm is under 10 minutes old and the tab's origin (readable now, under `activeTab`) is covered by the request, then leases that tab at the armed level and scope with the usual lease message (`requestId`, `tabId`, `origin`, `title`, `level`, `scope`); the `FAI ?` group becomes the session's `FAI` mark. A redirect inside the request's origins is fine. Otherwise nothing is leased, the popup comes back on that tab and says "The request was no longer waiting or this tab left its site: nothing was approved." (`chrome.storage.session.openNotice`); a refused lease shows its reason the same way. Testing mode is checked as for any approval, against the tab's origin.
- **An arm ends** on the approval, after 10 minutes, when its request leaves pending/paused (approved elsewhere, denied, expired), when the tab closes or is seen leaving the request's origins, and when another tab is leased for the same request. The popup, badge and title go back to normal and the tab leaves the `FAI ?` group.
- **"All of <root>".** For a request with a domain root, the roots' site-access prompt is still requested inside the **Open** click, before anything is awaited, and reported with `track`. In the same click the popup sends an `intent` (`requestId`, `level`, `patterns`): Chrome can close the toolbar popup when its prompt takes focus, before the popup's own `open` is sent, so the worker's `chrome.permissions.onAdded` listener opens and arms the tab itself for an intent under 60 s old. Exactly one window opens: an `open` from the popup after that waits for the worker's and answers with it, and an `open` that comes first uses the intent up. The arm's scope is `domain` only when Chrome holds every root's permission; a declined prompt opens the page with scope `origin` and the status line says so. A domain arm holds the roots' permission until it is approved (the session then holds it) or ends unapproved (it is removed, unless remembered).
- **Approve on the FAI tab.** In the approval window, a new request that the live session's own tab already covers (an agent asking for a higher level on the tab it drives) reads **Approve on the FAI tab**: the worker leases that tab directly at the picked level, under the `activeTab` grant it still holds, with no new window. If that lease is refused or the tab's URL is no longer readable, the tab is armed instead and the status says "Click the FAI Browser icon on the FAI tab (Ctrl+Shift+Y) to approve."
- **Open requested pages right away** (Advanced, on by default). A new pending request with a start URL that asks for `read-only`, `reversible` or `interactive` skips the approval window: its page opens armed at the requested level (Preselect up to plays no part); the prompt window's level choice never goes above it, and the worker refuses an `arm_level` above it, with scope `origin` and the prompt window. The icon click is still required, so approval is one click. A request for Act or Test site never opens by itself: it gets the approval window, where the user confirms the level explicitly. A request without a start URL, or one the FAI tab already covers, gets the approval window as usual. The worker reports the setting to the daemon (`settings.openRightAway` in the hello and in every `settings` message), and the daemon's request view says how a pending request is approved: `approval: "page"` (the page opened by itself; the icon click on it approves) or `"window"`; the `select_tab` result's `needs.message`, the MCP `next.text` and the CLI's `ACTION NEEDED` line are worded by it ("its page opened in a new Chrome window; one click on the FAI Browser icon on that window approves it", else "click Open in the FAI Browser window, then the FAI Browser icon on the page it opens").
- **Host permissions.** The manifest's `optional_host_permissions` is `https://*/*` (domain roots) and `http://*/*` (only for "Allow on all sites"); no exact-origin pattern is requested, tracked or remembered, and http origins (`localhost`, `127.0.0.1` testing environments) need none because approval is always `activeTab`.
- **Allow on all sites** (Advanced, Site access; also on the setup card). One click asks the browser once for every http(s) site (`https://*/*` and `http://*/*`; `<all_urls>` in Firefox): no site-access prompt per site afterwards (domain roots, Firefox's exact origins after a navigation, a popup the lease follows), and Firefox screenshots keep working after a navigation. It gives the extension access, never the agent: every tab is still approved by the user, at the level they pick, and leases, levels, the Approve gate and the guardrails are unchanged. **Ask per site instead** gives it back. The companion's required `http://127.0.0.1:4318/*` is never requested, tracked or removed.

### Guardrails

What FAI Browser does at each level is one policy object (`src/guardrails.js`), rendered two ways: the mechanical label and field check (applied in the runtime's offered actions and refusal receipts, and again by the extension's page script at observation and dispatch) and the `state.policy` text Jev receives. Its **core** is fixed per level and can never be relaxed by a run or by config: sign-in and MFA (`SIGN_IN_WORDS`, password fields) and purchases (`PURCHASE`, payment fields) only at `testing`; deleting (`DELETE_WORDS`, cancelling a subscription or account) and sending, publishing, inviting, saving, submitting or applying (`SUBMIT_WORDS`, `COMMIT_OTHER`) only from `full` ("save" before an amount, "Save 30%", "Save €20", "save up to 40%", "Two years (save 30%)", is discount wording and no class; price and billing words on a plan picker, "€9/month", "billed yearly", trip none either, while "Subscribe for €9/month" and "Pay €9" stay purchases); search-like submits (`SAFE_SUBMIT`) from `interactive`; never browser-internal pages; cookie dialogs rejected first. **Additions** can only restrict: per run with `policy` (`fai_browser_run`, `client.run`, the daemon body, CLI `--policy`) and per install with `config.json` `"guardrails": {"forbid": ["Upgrade", "Gift wrap"], "note": "Never change the plan."}`; the two are merged. Each phrase is plain text (at most 20 phrases of at most 60 characters, letters, digits, spaces and `- ' & / : , ! # % @` only; regex metacharacters are rejected; the `note` is at most 200 characters with no control, format or invisible characters, whitespace collapsed; invalid input is a validation error before any tab request or Jev call: `invalid_params` from MCP, 400 `invalid_options` from the daemon, exit 1 from the CLI) and matches case-insensitively as whole words anywhere in a control label (links, buttons, select options and fields alike), so `"Upgrade"` refuses "Upgrade to Pro" but not "Upgrades". The extension receives the phrases as strings in each observe/execute command, compiles them itself and refuses matching controls as well, while keeping its own hard-coded core block. Additions apply at every level, `testing` included. Jev's `state.policy` lists the core lines with a `mode` line and a `user_actions` line for the level (at `full`: buying, paying, subscribing and logging in belong to the user; at `testing`: every offered control may be used), then the additions and the note appended after them as short named lines, so the core lines never move; it is byte-identical for identical input (prefix caching).

Safety checks normalize Unicode compatibility forms, combining marks, invisible formatting, common Greek/Cyrillic Latin lookalikes and spaced single letters, while display labels remain unchanged. Independent accessible, visible, title and button-value names cannot hide a refused label. Native select options receive the same core and addition checks at offer and dispatch; refusal receipts name blocked options. Additions preserve their first spelling and input order, deduplicating by normalized spelling; changing phrase order intentionally changes the rendered policy, while object key order does not. A handoff with every remaining control mechanically blocked ends `refused_action` (`why`: `refused:all_controls_blocked`), as a level request (`needs.level`, `relay`) when a higher level other than for purchases would unblock one, else `stop`, except when the injection guard is at least 0.85. A failed extension policy compilation blocks controls until a fresh policy is successfully supplied.

The **commit guard** (at `reversible`; the purchase guard in [Permission levels](#permission-levels) covers every level that offers controls below `testing`) is the automated second opinion for labels the regexes cannot judge ("Continue →" on an order review page, "Yes" in a "Delete workspace?" dialog, "Next" under "Review and pay"). In `reversible` mode, whenever a button, select or fill is offered, the same Jev request carries a third guard question, `commit`: would the offered control that best advances the instruction order, pay, book, reserve, subscribe, send, publish, delete, sign in or otherwise commit the user? At `commitVeto` (0.7) or more, a chosen button/select/fill is not executed, and a handoff while such controls are offered is not passed on as a handoff: the run ends `needs_user` / `refused_action` with `next.kind: "stop"` (`why`: `guard:commit_veto`). A read whose answer is on the page completes first (done and a passing expectation end the run before the guard is consulted), and on a page whose text addresses an agent (`injection` at 0.85 or more) the handoff stays a handoff, since that text can push the commit score either way; no control runs there anyway. `commitVeto` is a regular threshold (`thresholds.commitVeto`); through the daemon a run can lower it but never raise it above `config.json`. Links, scrolling, waiting and consent reject buttons are unaffected; read-only runs never ask the question. It costs no extra request and no measurable latency (about 45 input tokens); the policy also tells Jev to judge a generic control by what the page says it does. Turn it off with `"providerOptions": {"guidance": {"commit": false}}`.

The **intent question** (`intent` guidance switch, **off** by default; turn it on with `"providerOptions": {"guidance": {"intent": true}}`) lets Jev clear a label flag the regexes raise on wording that is only sometimes a commit, never add a permission. Tiers (`src/guardrails.js` `labelTier`): a label is **ambiguous** when every class it trips comes from save, confirm, send, invite or publish (never "submit"), or from order, book, reserve or upgrade as the whole label, or book/reserve before a, an or the ("Book a demo", "Reserve a table"); everything else is **hard** and never cleared: buy, pay, purchase, check out, place order, subscribe, donate, start a trial, add a payment method, send money, withdraw, bare Transfer, Bid and Renew, any word followed by "now", book/reserve before this, it, your or my, complete/confirm an order, purchase, payment, booking or reservation, every delete, cancel, apply and sign-in label, a flagged label naming a card, payment, billing, bank, wallet or IBAN ("Save card"), and any mix of a hard word with an ambiguous one. With the switch on, a button or option refused at the run's level only for ambiguous words, that the instruction names (at most two per decision), on a page with no payment or password field, not a form submit, consent control or a control with a hard hidden name (the page script marks these itself, `ambiguous`), and not a label the user's `forbid` reserves, is offered to Jev's own choice with one `intent_<action id>` choice question in the same decide request (about 700 characters, under 200 tokens; no extra round trip): what would activating it do, `purchase_or_payment`, `submit_or_send_user_data`, `change_account_settings`, `marketing_or_discount_text` or `select_option_or_navigate`, the label quoted as page text. If Jev chooses it, it runs only when all hold: the answer is `select_option_or_navigate` or `marketing_or_discount_text` (or, at `full`, a submission or settings answer) at confidence 0.9 or more, `purchase_or_payment` below 0.1, `purchase_control`, `purchase_page` (and `commit` at `reversible`) answered and below `commitVeto`, `injection` answered and below 0.8; it then runs at the run's level as what Jev said it is (`why: intent:cleared:<class>`; the extension clicks it only on its own `ambiguous` mark with the granted capability). Anything else, an unanswered or invalid reply, a provider error or timeout included, refuses it as before (`why: intent:kept:<reason>`, reasons `unanswered`, `purchase_or_payment`, `hard_tier`, `forbid`, `payment_field`, `password_field`, `purchase_guard`, `injection`, `commit_guard`, `purchase_doubt`, `low_confidence` or the class whose level the run lacks): `purchase_or_payment` and every kept purchase label stop with the purchase text, a kept submission relays `needs.level: full`. A task refusal for such a control waits for the decision (`why: intent:deferred`) and refuses as before when the decision hands off. `fai_browser_act` on such a control sends its guard request with the question and refuses it without a provider. Off, nothing is marked and the request is byte-identical; at `testing` nothing is asked. It is off until `bench/jev-eval.mjs` measures the answer on real pages: the labelled corpus in `fixtures/intent` (test/guard-intent.test.js) clears no purchase with an honest answer, and a fooled answer could clear only a bare ambiguous label on a page with a stored card and no payment field.

### Approve gate

Some actions are worth doing for the user but not without their say-so. With your agent driving (`fai_browser_act`), such an action is **offered** marked `needsApproval` (purchase, secret, delete or submit; its description ends "(asks the user)"), and acting on it asks the user to click **Approve once** in the extension for that one click. Nothing is ever approved in advance, and there is no "always allow".

**What asks** (`src/guardrails.js`, byte copies in `extension/page.js`, which applies them at observation and again at dispatch):

- **purchase**: a `PURCHASE` label or a payment form submit, and on a **purchase page** a button or submit that is inside the **checkout region** (its form holds a payment field, or an ancestor up to eight levels up is named checkout, payment or billing in its class, id or aria-label) or whose label commits (`COMMIT_LIKE`: pay, place order, confirm, complete, continue, next, submit, buy, subscribe, purchase, checkout, proceed, finish; not when it names an account detail: "Confirm email address", "Continue with email"), except a back-out (`BACK_OUT`: Cancel, Back, Close, Keep my plan, ...), a quantity stepper (`STEPPER`: +, −, Increase quantity, Qty) or a consent reject (`purchaseControl`). Everything else on the page keeps its own class: a Save, Search, Publish or Add to cart is not a purchase, and navigation (`nav`, `role=navigation`) and search forms (`role=search`, a search field) stay as they are whatever their labels; page.js reports the region it saw as `control.region` (`checkout` or `navigation`). Links stay navigation and options (a plan picker) stay options. A purchase page has a payment field, a path segment `/checkout`, `/payment(s)`, `/billing`, `/order`, `/subscribe`, `/upgrade` or `/plans`, also as a file stem (`/billing.html`, `/checkout.php`) (`PURCHASE_PATH`, whole segments: `/orders` is not one), or a line that starts with Total, Order summary, Amount due or Due today with a currency amount close after it (`PURCHASE_TOTAL`). Approvable from `full` only; below `full` a purchase is refused as before, and at `testing` it runs without asking. Payment fields are never filled outside testing, approval or not.
- **delete** (commit dialog): a button in a `dialog`/`alertdialog` whose text says are you sure, cannot be undone, permanently, delete, remove or cancel a subscription, account, membership or plan (`COMMIT_DIALOG`), unless it backs out. Below `full` it asks; at `full` it runs as granted.
- **secret**: a control that generates, creates, regenerates, rolls, rotates, revokes, reveals, shows, views, copies or unmasks a key, token, secret, password, credentials or recovery/backup codes (`SECRET_ACTION`: "Show password", "Create API key"), and an eye toggle right next to a password or secret field (page script only). It asks at **every** level, `testing` included, from `reversible` up.
- **submit / delete above the level**: from `reversible`, a submission or deletion the granted level does not allow asks instead of being refused; the result also names `needs.level` so the agent can ask for the level instead. A search submit keeps its level request.

Never approvable: a label the user forbade (`policy`, `config.json`), a page outside the approved origins, browser-internal pages, anything at `read-only`, sign-in and password or card fields outside `testing`, consent accepts below `full`. A run (Jev, or any bridge without `approve`) is never offered a credential action: page.js refuses one at dispatch without an approval.

**The exchange.** `fai_browser_act` on a `needsApproval` action sends an `approve` command to the extension and blocks, with progress notifications, up to `FAI_MCP_APPROVAL_WAIT_MS` (default 60 s, at most 60 s per call; daemon `POST /v1/act` `approvalWaitMs`, at most 120 s). The worker reads the control from the page itself (`approvalInfo`: label, label hash, class, a detected total), refuses a class the page script does not see (`class_mismatch`), and shows a small **"Approve this action?"** window, a red `!` badge and a card in the popup: the site and tab title (from the browser), what kind of action it is, the control's label in quotes marked as page text, the total the page shows and **"Agent says: …"** (the act's optional `reason`, marked as not checked). Neither button has focus. Answers:

- **Approve once**: the worker mints a random single-use `approvalId` (`crypto.randomUUID`) bound to the tab, lease, revision, target, class and label hash (SHA-256 of the label, first 128 bits as hex, computed in plain JavaScript so plain-http pages can be approved too), valid 60 s; the act runs the click with it at once (no model guard second-guesses it, and it is never re-resolved on another revision). The worker spends the id before dispatch and page.js rechecks the target's class and label hash itself. A new revision voids it (`stale`), and an id the worker did not mint (a daemon cannot) is refused (`blocked_risky`).
- **Deny**: `refused_action`, `why: approval:denied`, `next.kind: stop` ("The user denied this action in the FAI Browser window. Tell the user; do not retry it.").
- **No click in time**: `needs_user` / `approval_pending`, `next.kind: approve`: "Tell the user to approve '<label>' (page text) in the FAI Browser window (Approve once), then call fai_browser_act again with actionId a7 and revision "…"; it returns at once if they already approved, else waits up to 60 s (the approval stays open for 5 minutes: repeat the call if it returns pending again)." (`needs.approval {class, actionId, revision}`; for a submit or delete also "Or ask for full: ..."). One act waits at most 60 s (`GATE_MAX_WAIT_MS`); the revision stays usable, the approval stays open 5 minutes, and an approval given meanwhile is picked up by the next act at once.

**Uploads and dialog accepts** ask too: an [upload](#uploads) always (the card names the file, its size and the site), and on a Test site accepting a JavaScript dialog whose text names a delete or purchase ([dialogs](#dev-logs-and-javascript-dialogs); the card shows the dialog's text).

**Settings** (popup, Permissions, Approve gate; `chrome.storage.local.approvals`, never `config.json`): **Ask before purchases**, **Ask before credential actions**, **Ask before actions above the level**, all on. Off means the old behaviour: purchases refused outside testing, credential actions run at their level, actions above the level refused with a level request. The worker reports the three switches (booleans only) to the daemon in its `hello` and `settings` messages (`settings.approvals {purchase, secret, level}`), so an offer marks "(asks the user)" only what the extension will ask about: an action whose ask is off is listed as it will run (a credential action as an ordinary click) or not at all (a refused purchase or submit). Until an extension reports them, all count as on. Secret handle uses (below) ask whatever these say.

**Point clicks** on a control the offer marks `needsApproval` ask the same way: the runtime locates the control first (nothing runs), asks with the control's id, and the approved click runs by that id (never re-resolved, never by pixels); `why` carries `act:point_approved`. A control the observation left out (ref `"point"`) has no id to bind and is refused as before.

**Time.** The wait for the click is not the agent's: the act's result carries `approvalMs` (trusted), and the MCP server leaves it out of the request's time budget (`maxMs`), as it does a tab approval wait.

### Secret redaction

An agent that reads a settings page must never hold a value the user would then have to rotate. FAI Browser **redacts** secrets rather than blocking the page: the agent keeps reading and acting (dispatch is by control id, so a link whose URL lost a token still works), only the value is gone. It is deterministic (no model is asked) and always on, at every level including `testing`; there is no "off".

**Placeholders.** `[secret:N kind prefix…last4 len L]` for a known format (`[secret:3 openai sk-proj-…Ab12 len 164]`, `[secret:5 card …4242 len 16]`), `[secret:N password]`, `[secret:N private-key]`, `[secret:N totp]`, `[secret:N recovery-code]`, `[secret:N param]` for a kind with nothing public to keep, and `[secret:N]` for the generic rule. N is stable per value for the tab lease: the page script tags each value with a hash salted per lease (`~<hash>`, never the value) and the extension worker numbers the tags 1, 2, 3, ... per session; a value the daemon's own pass finds is numbered `d1`, `d2`, ... A second pass never changes a placeholder.

**What is found** (`src/secrets.js`; the rule block is byte-identical in `extension/page.js` and `extension/background.js`, drift check in `test/secrets.test.js`, copied by `node scripts/sync-secret-rules.mjs`):

- Known formats, always: Anthropic `sk-ant-`, OpenAI `sk-`/`sk-proj-`/`sk-svcacct-`/`sk-admin-`, GitHub `gh[pousr]_` and `github_pat_`, Slack `xox[abposr]-` and webhook URLs, Discord webhook URLs, AWS `AKIA`/`ASIA` key ids and the 40-character secret after one, Google `AIza`, `ya29.`, `GOCSPX-`, GitLab `glpat-`/`glptt-`, Stripe `sk_`/`rk_` `live`/`test` and `whsec_`, npm `npm_`, PyPI `pypi-AgEI`, Hugging Face `hf_`, Groq `gsk_`, xAI `xai-`, Replicate `r8_`, SendGrid `SG.`, DigitalOcean `dop_v1_`, Shopify `shpat_`/`shpss_`, Linear `lin_api_`, Postman `PMAK-`, Supabase `sbp_`, Atlassian `ATATT`, JWTs, PEM private-key blocks (also split over several elements, one per line), connection-string passwords (`scheme://user:PASSWORD@host`), payment card numbers (13-19 digits, a card network prefix, card grouping, Luhn-valid), and URL parameters (query and fragment) named token, key, secret, sig, signature, code, auth, session, password, credential, access_token, id_token, `X-Amz-Credential`/`Signature`/`Security-Token` and the like: the value goes, origin, path and other parameters stay, so origin checks and `urlIncludes` paths still work.
- Context rules (Standard): a run of 20 or more key characters that mixes letters and digits with at least 3.5 bits of entropy per character, not a path and not dashed words, counts only next to a word that says key, token, secret, password, bearer, credential or recovery/backup code: in the 60 characters before it, its column header, its row's first cell, the `dt` before it, an `aria-label` or the previous sibling's text. A base32 TOTP seed near "setup key"/"authenticator"/"2FA"; the codes under a "Recovery codes"/"Backup codes" line; the value in an environment-variable row (an UPPER_SNAKE name containing KEY, TOKEN, SECRET, PASSWORD, DSN, PRIVATE or CREDENTIAL, or `DATABASE_URL`); "Password: X".
- **Secret pages** (warning `secret_page` in observe and run results): a path such as `/settings/tokens`, `/api-keys`, `/apikeys`, `/credentials`, `/security`, `/2fa`, `/mfa`, `/totp`, `/recovery`, `/personal_access_tokens`, `/service-accounts`, `/webhooks`, or a top heading such as "API keys", "Access tokens", "Environment variables", "Recovery codes". There the generic rule needs no context and every run of 16 or more non-space characters in `code`, `pre`, `kbd` or `samp` is masked too.
- Fields: a field that holds a secret (a read-only input with a key, a textarea with a private key) is reported `sensitive: true` and never offered; a password field shown as text by a show-password toggle is still reported `type: "password"` (a fill target only at `testing`). Input values are never reported at all.

**Where.** The extension is the primary barrier: `extension/page.js` scrubs everything it returns (observe, execute, settleAndObserve, locate, error messages: page text, blocks, records, views, control labels, select options and values, link hrefs, the page URL), and an expectation's `textIncludes` is matched against the redacted text only, so it cannot be used to guess a value. The live page is never modified (redaction works on extracted strings only, so a site cannot detect it). The worker redacts the URLs and titles it reports itself, including the screenshot footer. The daemon runs the same rules again (defense in depth): on every observation and action result entering the runtime, on the provider request body, on `trace.json`, the daemon log, every HTTP response and every MCP message.

**Settings** (extension popup, Permissions, Secret redaction; stored in `chrome.storage.local`, never `config.json`, which an agent with a shell could edit): **Standard** (default) or **Strict** (the generic rule without context and code runs masked on every page), and **Relaxed origins**: exact origins where only the known formats apply (no generic or context rules, no secret pages), for a docs site whose examples look like keys.

**Screenshots.** Every screenshot is redacted on its pixels before it leaves the extension; the page is never touched (no style, attribute or element, so a site cannot detect it). Right before `captureVisibleTab` the worker asks the page script for the boxes to fill (`redactionRects`): every element that holds a secret the text scan found (PEM lines included), every password field whatever its value, every payment field, every field that holds a secret, every cross-origin frame of a payment or sign-in widget (Stripe, Braintree, Google Pay, Google accounts, PayPal, Adyen, Checkout.com, Square, Klarna, Recurly, Chargebee, Apple ID, Microsoft and Okta/Auth0 sign-in, and a few more), and in Strict mode or on a secret page also every canvas, every other cross-origin frame and every `code`/`pre`/`kbd`/`samp` block; each box is padded 4 px and clipped to the viewport. It asks again right after the capture, with a watch armed in between (a MutationObserver and capture-phase scroll and input listeners in the extension's isolated world, invisible to the page). The offscreen document fills the union of both sets solid black on the captured frame, before control boxes, badges and the footer are drawn, and labels a box with its placeholder number (`secret:3`) when it holds one, so image and text agree; a point click still works on the image (boxes move no pixels). When the page changed between the two queries (a mutation, a scroll, boxes that moved by more than 2 px) the frame is taken again once; still unstable, or a scan that hit its node, holder or box cap, and the whole frame is filled solid black (`redaction: "withheld"`). A query that fails or takes over 2 s, or an offscreen document that does not confirm every box, means no image at all (`capture_failed`). Screenshot metadata carries `redactions` (the box count) and `redaction`; the MCP image caption tells the agent the black boxes (or the full-frame fill) are deliberate and to use the digest.

**Limits.** Text drawn on a canvas, text inside images, cross-origin frames the request does not approve (never read; approved ones are scanned by their own page script, see [Frames](#frames)) and closed shadow roots are not scanned; on screenshots canvases and code are boxed only in Strict mode or on a secret page, and every cross-origin frame that was not read is always boxed (with the extension's frames.js; payment and sign-in widget frames always). A value with no known format, shorter than 20 characters and with no context word nearby (a short password in plain prose) is not found. `node scripts/secret-sweep.mjs [--strict]` observes every fixture page and lists every placeholder; the corpus has none outside `fixtures/secrets`.

### Secret handles

Redaction keeps a secret from the agent; a **handle** lets the agent still use it, with the user's say-so each time, without ever seeing it. Typical: copy a new API key from one site into another site's settings field.

**The vault.** When page.js redacts a value from page text or a read-only field (a new key shown with a copy button), it hands the value to the extension worker with that result (`__faiVault`, only when the worker asks; a bridge without the worker never receives one). The worker keeps value ↔ `secret:N` in memory only (never storage, never the daemon), at most 50 values, each for 30 minutes after it was last seen. Payment card numbers and URL parameters are never kept, nor a value FAI filled itself. A session that takes over from a live one (the agent's next approved request, on another origin too) keeps the vault and the numbering, so `secret:3` stays `secret:3`; stopping the session, a release or an expiry clears it, and a restarted worker starts empty. Every observation lists the handles (`secrets [{handle, kind, origin, label}]`: the placeholder and the origin the value came from, never the value).

**The actions** (offered from `reversible`, to an agent driving through MCP only, never to a run):

- `fill_secret "API key" ← secret:3 (openai key from platform.openai.com) (asks the user)`: pastes the value into one field that takes a secret: a password field that is not part of a sign-in form (no current-password, no username or email field next to it), or a single-line text field whose label, name, id, placeholder or autocomplete says key, token, secret, password or credential. Never a textarea, contenteditable, search, comment, message, email, username, one-time-code or payment field, nor a read-only or disabled one, nor a label the user forbade. At most three fields, each with the three newest handles.
- `copy_secret secret:3 (openai key from platform.openai.com) to the clipboard (asks the user)`: writes the value to the OS clipboard from an extension context (the offscreen document on Chromium, reason `CLIPBOARD`, permission `clipboardWrite`; the background page where there is no offscreen API). Local programs, the agent included, can read the clipboard, and the card says so. At most three handles.

`fai_browser_act` takes the `actionId` as usual; there is no value anywhere in the API. Both always go through the Approve gate (class `secret`, `kind` and `handle` in the `approve` command) at every level including `testing`, whatever the Approve gate settings, same origin or not. The card and the window read "Paste secret:3 (openai key from platform.openai.com) into "API key" on vercel.com" or "Copy secret:3 (...) to the clipboard", add "This secret came from <host>, another site than <host>" when the origins differ, and show the field label as page text. The approval binds to the tab, lease, revision, field (target and SHA-256 label hash), kind and handle; page.js checks again at dispatch that the field takes a secret. The daemon cannot mint an approval, and an execute that carries a value instead of a handle is refused.

**After a fill.** The field is a secret field from then on: never offered again, never reported (its control says `sensitive` and `secretValue: "[secret:3]"`), boxed on every screenshot, and wherever the page echoes the value (a preview) it is redacted as `[secret:3 ...]`. The act's step records `handle: "secret:3"` and `fill {kept, empty, holds: "[secret:3]"}`; traces never hold the value. The worker keeps the value out of screenshot annotations.

**Limits.** A value split over several elements, drawn on a canvas or shown only in an image is never vaulted. The clipboard keeps the value until something else is copied. A page that reads the field can of course send the value anywhere it likes: approve only fields on sites that should have the secret.

### In-call retries

Before a result goes back to the host, the runtime takes the obvious next step itself, because every receipt that needs another host turn costs the host 3-6 s and a third to a half of the task's host cost. Three retries, on by default:

- **Second opinion** (`secondOpinion`), links only. When a link choice leads the best other link by less than `thresholds.secondOpinionMargin` (0.2) or is below `linkFloor`, or a handoff leads the best link by less than that margin, the provider is asked once more with the non-terminal options in reverse order (handoff stays last). The same choice keeps the more confident of the two; a different choice wins only with a higher confidence and only if it is a link (or a handoff instead of a link): a second look never turns anything into a button, select, fill, scroll or wait, and a button, select or fill choice never gets one (it keeps `controlFloor` and goes to the host with alternatives as before). The two requests' guards merge by their maximum, so a second look can add a blocked or injection veto but never lift one, and every code-side check then runs on the chosen decision as usual. Never on a consent dialog, with an injection guard of 0.8 or more or a veto already standing, on a page where the expectation passes and `done` decides, without probabilities, with no link as rival, or with less than 1 s left. At most 2 per call; they do not count against `maxDecisions` (they do count in `cost.decisions`), and when the second decide's choice runs, both decide entries in `cost.requests` carry its `step`.
- **Back-out** (`backOut`). Only at `read-only`, with an expectation, and only when every step so far was a link, scroll, wait or consent reject: when the provider hands off (or chooses below its floor) on a page the last link reached, that page fails the expectation, and neither the link label nor the page title or path matches any page the instruction names (without named pages it never backs out), the runtime navigates back once to the same-origin URL before that link (a step with `decision.by: "runtime"`, reason `back_out`, counted in `maxActions`) and decides again with that link's destination no longer offered. At most once per call.
- **Self-rerun** (`rerun`), read-only runs only. When the result's `next.kind` is `rerun` with a concrete `verdict.suggested` (a new instruction, or the same instruction while a loading placeholder shows), the code is not `expectation_failed`, `expectation_mismatch` or `expectation_error`, the run asked no one for anything (no `needs.level`, no relay, no refusal), every step was a link, scroll, wait or consent reject, and at least 5 s of the run's time is left, the suggestion runs once in the same call from the current page: same origins, level, grant, guardrails, supplied values and question, and **always the host's own expectation** (the loading case only adds `textAbsent`; a suggested expectation for another page is never adopted). The host's budgets cover the whole call: the rerun gets the remaining `maxActions` (at most the suggested `maxActions`), the remaining `maxDecisions` and the remaining time, and does not start when none is left. The call returns the rerun's outcome; `steps` lists both attempts' actions in one sequence, `cost` covers both, and the MCP server counts the suggested instruction as already tried. `next.kind: split` (joins, 4+ pages) is never rerun.

Request cap: a call sends at most `maxDecisions` decides plus 2 second opinions, and no second opinion or rerun starts once the call has sent `maxDecisions + 4` provider requests (decides, second opinions and answer rankings together). That threshold only stops retries from starting; it does not cap answer rankings, and a discarded early ranking plus its serial fallback can add 2 per attempt, so a call with a self-rerun can send about `maxDecisions + 6` provider requests (more if several early rankings are discarded), or `maxDecisions + 7` with [`slim.terminal`](#slim-provider-requests) on (its requests count toward the threshold, and a call sends at most one that falls back), plus one slim guards request per site-profile fast hop, per stale re-resolve and per run or list step that ends on its own expectation (`site_guards`, `stale_guards`, `step_guards`). A step list repeats the per-attempt part for every step (each step has its own answer ranking, its possible serial fallback and its `step_guards`), so a list can send about `maxDecisions + 3 × steps + 7`. In numbers: a single MCP run at its maximum `maxActions` 60 has `maxDecisions` 63 and can send about 71 requests (one more per fast hop or stale re-resolve); a 15-step list at its default 60 actions has `maxDecisions` 105 (actions + 3 per step, at most 200) and can send about 157, and at an explicit 120 actions about 217. When a rerun ran, `retries[].instruction` is the instruction that produced the final page and `verdict.answer`, not the host's original one.

`retries` in the receipt lists what ran, in order: `{kind: "second_opinion", why: "close"|"handoff_close"|"floor", outcome: "agreed"|"changed"|"kept"|"error"|"invalid", step, first {p}, second {p, same}}`, `{kind: "back_out", why: "handoff"|"low_confidence", outcome: <the run's final code>, step, from, to}` (URL paths) and `{kind: "rerun", why: <the first attempt's code>, outcome, status, first {status, code, steps, url}, instruction?, expectation?, maxActions}`. `verdict.why` gets `retry:second_opinion:<outcome>`, `retry:back_out` and `retry:rerun`. In a [step list](#step-lists) the bounds and the request cap above hold for the whole list (the cap counts the list's `maxDecisions`), and each entry carries `listStep`. The host reads `next` as always; `retries` only says what FAI already tried, and the MCP text block lists it as a trusted line. Turn them off per run with `"retry": false` (daemon body, SDK, options file; CLI `--no-retry`) or for every run with `"retry": false` in `config.json`; an object switches single ones (`{"rerun": false}`), and the run's value wins over `config.json`. The MCP tool has no switch for it. `node bench/qa/run.mjs --sim-jev --retry on|off` measures them without a key (see [bench/qa/README.md](../bench/qa/README.md)).

### Offered actions

**Labels.** Every control carries its accessible name, resolved in the page script in the order of the accessible-name computation: `aria-labelledby` (the named elements' `aria-label` or text), `aria-label`, the field's `<label>` (`for=` or wrapping), a button input's `value`, an image input's `alt`, the text (`role=button` divs included), names on descendant icons (an `aria-label`, `alt` or SVG `<title>` inside an icon-only button, or the nested link that names an otherwise empty `role=button`), then `title`, `placeholder`, `alt` and a form field's `name`, and for an element with none of those a tooltip attribute (`data-tooltip`, `data-tooltip-text`, `data-tip`, `data-title`, `data-original-title`) or the text its `aria-describedby` names (at most 80 characters). A control with none of these is never sent with an empty label: it gets a descriptor, `unlabelled <kind>[ <i> of <n>][ next to "<context>"]` (kind `button`, `text field`, `date field`, ...; position among the unnamed controls of that kind with the same context; context: the name of the nearest labelled container, field, legend or heading around it, else the nearest heading before it), and the control is marked `unnamed` in the observation. An unnamed button whose direction is reliable says it first and ends in `(unlabelled)`: exactly two unnamed buttons left and right of one field on its row (a stepper) read `previous-value button before "<field>" (unlabelled)` and `next-value button after "<field>" (unlabelled)`, two adjacent ones on a row around a short text ("Photo 3 / 8") the same with that text, and tokens of the button's and its descendants' `class`, `id`, `name`, `data-*` and SVG `<use>` references (`prev`/`previous`/`back`, `next`/`forward`, `decrement`/`minus`, `increment`/`plus`; `left`/`right` only beside an icon word such as `chevron` or `arrow`, never whole class names, and never an SVG path's shape) name the word (`previous`, `next`, `decrease`, `increase`), with `beside "<context>"` when there is no pair; a lone icon beside a field (a calendar or clear icon) keeps the plain descriptor. On Google Flights the date steppers next to the departure field read `previous-value button before "Departure" (unlabelled)` and `next-value button after "Departure" (unlabelled)` (before: `unlabelled button 1 of 2 next to "Departure"`). A descriptor, derived direction included, never makes a control one the instruction names (the `named` policy line and the named-clicks rules): offered actions of unnamed controls carry `unnamed: true` and are refused there, as are labels starting with `unlabelled` or ending in `(unlabelled)`. The descriptor's context is page text like any label and counts toward the risk classes, so it can only make a control stricter (an unnamed button next to "Delete account" is a `delete`), never looser. A calendar day cell named by its number alone (`14`, `14 €47`, no `aria-label`), inside a month grid (at least 28 such cells of one tag, each day once, within three levels) under a month-and-year heading (the grid's `aria-label`, a caption or a heading: `October 2026`), reads `Wednesday 14 October 2026 €47`. Calendar day cells named only by their number ("14", "14 €47") inside a grid of exactly one month's days in order read "Wednesday 14 October 2026 €47" under one month-and-year heading, and "9 October €49" under one heading that is exactly an English month name with no year at that level (the weekday only when the grid's own header row gives it for that column; the year is never taken from the clock); a rolling grid with a neighbouring month's days, two months under one row of headings, another language or a grid of the wrong length keeps the number.

**Late changes.** After a click on a control that re-renders late (a derived-label stepper arrow: previous / next / decrease / increase, with or without `-value`; a picker-open click; a control inside an open dialog, `dialog: true`; or a control a site profile pins) that settled quiet and whose one rung 1c re-observe still shows no change to the URL or page content (a click in an open dialog that only closed it, with the URL and every control outside the dialog as before, counts as no change: a calendar's Done on a results page; a Done that filled an empty Departure field moved the page), the runtime looks again at 1.5 s and 3 s (`lateChangeMs`, default 3000, 0 off; never past the run's deadline less 3 s) for a URL or content change, as for an app that updates its URL and results seconds after the click (Google Flights' date arrows). The step then records `settle: "late_change"` and `why` `late_change`; a wait that saw nothing records `late_change:none` and is not repeated in that call. The decision after a late change that was waited for is offered no `wait` while the page shows nothing loading (`why` `wait_excluded`). A late change that lands on a page still showing a loading placeholder (its first paint) gets the content waits before the next decision, as a page the expectation passes does (`content_wait`, at most the run's content waits). "Content" here is the title, every block's text (on screen or not, live regions included) and every control's state, regardless of scroll position: a click that only scrolled its offscreen target into view changed nothing, and one that filled a live region (`aria-live`, which the page revision leaves out) changed the page. When the observation cannot tell (blocks or controls capped) the revision decides. A click step records what changed as `moved`: `url`, else the content parts that differ (`title`, `blocks`, `controls`, joined with `+`), else `revision` when the content cannot tell; it is absent when nothing did. Any other button gets one look 700 ms after the re-observe, and only while the page shows work pending (the clicked control now disabled, or a loading placeholder); with no such sign, no wait (a button that does nothing costs nothing extra).

**Stale host actions.** An `act()` whose offer went stale (the page changed after `observe()`) re-observes once and, for a link, a derived-label stepper arrow (`unnamed`, a previous, next, decrease or increase label, with or without `-value`, the same labels the late-change wait reads as steppers) or a picker-open click (`opens`) only, runs the one freshly offered action that is the same control: same type, role, label, value, destination and frame, on the same origin and path, with the same number of such controls on both pages (neighbour labels break ties). Any other button, select or fill (a "Next" on a later wizard step, an "OK" on another dialog) stays `stale`. It never re-resolves a delete, submit, purchase, sign-in or commit label, a control whose risk is above reversible, or on a page that now shows a consent dialog; a re-resolved click is judged again by the purchase and commit guards on the fresh page. The step records `decision.reason: "stale_reresolve"` and `reresolved` (the action id that ran), `why` `act:stale_reresolve`, and the result warns `act_reresolved`: the host's observation is out of date, so observe again before relying on it. Otherwise the act ends `needs_host` / `stale`.

### Point clicks

A host with vision can click what it sees instead of naming an id: `fai_browser_act` (and `POST /v1/act`, `act --point X,Y`, `runtime.act({ point })`) takes `point {x, y}` instead of `actionId`, with the `revision` still required (exactly one of the two). The coordinates are pixels of the screenshot served for that revision (`observe` with `returnImages: "final"`, at most 1280 px wide; the result's `image` gives its size), so the daemon maps them back to CSS viewport pixels with the size it noted for that capture (without one, the size the extension would make of the viewport: device pixels downscaled to 1280 wide). The act then asks the page script what is under the point on that revision (`locate`: the element there, through open shadow roots and same-origin frames, or its nearest clickable ancestor, the same elements an observation lists), and:

- a control the observation listed with an offered click runs **exactly that offered action**, by its id (`decision.actionId`, `why` `act:point_offered`);
- any other control (one the caps left out, or a field offered only as a fill) is described as an observation control and goes through the **same gate as an offered action** (`src/runtime.js` `pointAction` on `offeredActions`: the request's and config's forbidden labels, the risk classes purchase / delete / submit / sign-in, password and payment fields, the level's capabilities, links only on the approved site and never into a new tab) and then the same purchase and commit guards as an `actionId`; what passes is a **click** (`why` `act:point`): a field or select is focused or opened, never typed into. The page script dispatches only the element it located, on that revision, when the point still resolves to it, once, and checks its risk class against the granted capabilities again.

A point click needs at least `reversible` (below it: `refused_action` with `needs.level: "reversible"`, before anything reaches the page). A point on an offered control that asks the user goes through the [Approve gate](#approve-gate) bound to the control's id. Refusals and their codes: `point_outside` (off the image or outside the viewport; nothing reaches the page), `no_control` (text, an overlay, or an element the page script does not drive), `point_frame` (inside a frame from another origin, or deeper than the page script reads; for an approved [frame](#frames) name its control's action id), `stale` (the revision is not the current page, or the control under the point changed; a point is never re-resolved on the fresh page, unlike a stale link id), `refused_action` (the gate: purchase with `PURCHASE_REFUSAL_TEXT`, a forbidden label, a class a level would allow with `needs.level`, a password field; `needs.control` names the control), `cross_origin` (a link off the approved site or into a new tab), `target_unavailable` (disabled), and the page script's own `blocked_risky` / `cross_origin` / `child_tab` as for any action. `why` carries `point:<reason>` (`point:off_image`, `point:no_control`, `point:delete`, `point:purchase`, `point:forbid`, `point:sign_in`, `point:cross_origin`, `point:level`, ...). The receipt records the click: `steps[].point {x, y, ref, offered}` (`ref` `"point"` for a control the observation left out) and `point {image, css, scale, imageSize, control {ref, label, offered}}` (also on a refusal); the trace's step `decision` has `point {image, css}` and `resolved {ref, label, offered}`, and the trace `options.point` the pixels sent.

**Caps.** The page script observes at most 100 controls (consent buttons, then in-view controls with instruction words first, off-screen term matches, other off-screen controls) and reports `controlsDropped` when it leaves some out. A decision offers at most 250 non-terminal actions (a select contributes one per option); above that the most relevant stay (below). `observe` lists at most 40 control actions at `read-only` and `reversible` and 80 from `interactive` up, plus scrolling, waiting, explicit `allowedUrls`, consent buttons and fills of supplied values, which are always listed. Above a cap the actions kept are chosen by relevance to the task (`src/relevance.js`, local only, never sent): links whose destination or label satisfies the expectation always; then labels naming a page the instruction names, labels holding an instruction or `answerQuestion` word, instruction words in a link's path; ties keep page order (in-view first). The task for `observe` is the body's optional `instruction`, `expectation` and `answerQuestion` (daemon), else the request's last run, else the request's `instruction`; MCP and the CLI rely on the last run. Ids keep their offered numbers, and `act` accepts every offered id, listed or not; `verdict.decide` options and low-confidence alternatives come from the full offered set.

**Warning.** Whenever anything was left out, the result says so: `warnings` carries `controls_capped:<n>`, `n` adding the page script's `controlsDropped`, the 250-action cap and (for `observe`) the listing cap. A run keeps one entry, the largest count it met; a bare `controls_capped` comes only from an older page script that sends no count. The `slim.cap` provider-request cap below is not counted here: it trims one request, uses the same ranking (so its 40 are always among the actions the other caps kept) and is recorded per request as `cost.requests[].optionsDropped`.

### Slim provider requests

The `slim` switches shrink what the Jev provider is sent on busy pages without changing what the runtime checks: every label, risk-class, origin, purchase, commit and injection rule reads the full observation and the full offered set as before. Each switch is off by default until the live gates confirm it (`DEFAULT_SLIM`):

- **`controls`**: every control is sent once. A link the run offers appears only as its option in the action question (`"12 link Pricing"`), not again in `state.page.controls`; the path relative to the page (`"12 link Pricing (/pricing)"`, at most 80 characters) is kept for at most 24 links: the 12 most relevant to the instruction, `answerQuestion` and expectation, links with an empty or vague label ("More", "Read more", ...) and links that share a label with a link to another place. Other controls (buttons, fields, selects, links the run does not offer) stay in `state.page.controls` without hrefs.
- **`terminal`**: on a page where the expectation already passes (the request that usually only confirms `done`), the provider is first asked only `done` and the `blocked` and `injection` guards about the page's URL, title, text and the history, without controls or an action question. When `done` reaches `doneThreshold` the run completes exactly as the full decide's `done` would have completed it (a `blocked` guard at 0.85 or more still marks it `guard:blocked_page`); otherwise, or when the request fails, the full decide follows as before. That fallback is outside `maxDecisions`. The slim request is sent at most once per URL in a call, and never again in the call after its first fallback, so it adds at most one request per call (it counts in `cost.decisions` and toward the in-call retry threshold). In `cost.requests` the slim request is `kind: "terminal"`, with `fallback: true` when the full decide followed.
- **`cap`**: a request offers at most 40 non-terminal options (output length grows by about 6 tokens per option). Always kept: scrolling, waiting, explicit `allowedUrls`, consent buttons and links whose destination satisfies the expectation's URL condition; the rest are the most relevant to the instruction, `answerQuestion` and expectation (a label naming a page the instruction names, the expectation's title or text, instruction words in the label or path; ties keep page order), sent in page order with `handoff` last. Only the request is capped: low-confidence alternatives, `verdict.decide` options and `act` keep every offered action. `cost.requests[].optionsDropped` counts the options a request left out of the offered set (actions the [offer caps](#offered-actions) left out are counted in `controls_capped:<n>` instead, never twice).

Set them per run with `"slim"` (daemon body, SDK, options file; CLI `--slim`) or for every run in `config.json`: `true`/`false` sets every switch, an object single ones (`{"terminal": true}`), and the run's value wins over `config.json`. The MCP tool has no switch for it. The trace's `options` record the switches the run used, and `cost.requests[].chars` shows the effect per section. `node bench/request-size.mjs` replays recorded pages offline to compare sizes; `node bench/jev-eval.mjs --slim <switches>` and `node bench/qa/run.mjs --slim <switches>` are the live quality gates (see [bench/README.md](../bench/README.md)).

### Site profiles (experimental, opt-in)

Site profiles are experimental and opt-in: off unless `"profiles": "on"` is set per run (daemon body, SDK, options file; CLI `--profile on`) or in `config.json`; the run's value wins, `{"fastPath": false}` or `{"hints": false}` turns one part off, and `"off"` uses no profile at all, its restrictions included. The MCP tool has no switch for it. A profile is versioned per-origin knowledge the daemon applies by itself: it follows known links without a Jev decision and gives Jev a short hint on the hops it still decides. Nothing in it is a permission.

**Where.** `$FAI_HOME/domains/<host>[_<port>]/profile.json` (or `$FAI_DOMAINS_DIR`), one directory per origin, e.g. `github.com/`, `127.0.0.1_8080/`. A profile applies only to an origin it lists in `origins`, matched exactly (scheme, host, port). The repository ships curated profiles in [domains/](../domains/) (`github.com`: repository home, issue and pull request lists, single issues and pull requests, the license file; `developer.mozilla.org`: the JavaScript reference down to Array method pages; `www.google.com`: Google Flights only, the search page and one-way results pages, with the per-day date shortcut, pinned date controls, status lines and notes below) and the QA fixture template `domains/_templates/qa-fixture.json`. Without `FAI_HOME` they are read from the package where they are; with `FAI_HOME` set, copy them: `mkdir -p "$FAI_HOME/domains" && cp -r domains/github.com domains/developer.mozilla.org domains/www.google.com "$FAI_HOME/domains/"`. One directory holds one profile per origin, so a later profile for another part of www.google.com has to join the Google Flights one. The daemon re-reads a profile when its file changes; an invalid file is ignored and logged (`profile_invalid`).

**Format** (schema 1, validated strictly; an unknown key anywhere rejects the file). No profile string is ever compiled as a regular expression. `schema`, `id`, `version`, `origins` (1-4 exact origins), optional `description`, `restrict.forbid` (plain phrases, merged into the guardrail additions after `config.json` and the request, so they only add refusals; the 40-phrase cap drops them first), `defaults` (`mode`, `maxActions`: advisory, not applied), `pageTypes`, `edges`, and the optional `shortcuts`, `controls`, `status` and `notes` (next paragraphs but one). A page type has a plain `label`, a `url` path template, `checks` that must all be found on the observation (literal, case-insensitive text in the `title`, an h1 `heading`, a `link` label or the page `text`), `expect` templates that name the type from the run's `expectation.urlIncludes`, and the advisory `expectation` template and `answers` literals (not applied yet). An edge has `id`, `from`, `to` and a `link` with a required `href` template, an optional literal `label` (the whole label, or its start followed by a non-letter) and an optional `hint`. Templates are paths with `{name}` placeholders: `/{owner}/{repo}/issues`, `/search/r/{n}.html`, `/q.html?page={page}`, and a final `?*` for any query (otherwise no query is accepted); a placeholder matches 1-100 of `A-Z a-z 0-9 . _ ~ @ : % + -`, two placeholders need a separator (`/ ? & =`) between them, a template has at most 120 characters, and inputs over 2048 characters never match, so every match is linear. An href may not name an account or commit endpoint (logout, delete, checkout, pay, order, subscribe, ...). Labels and hints are plain navigation phrases with no action word. There are no URL edges: a profile holds no URL of its own, and the only navigation to a URL the page does not link is a shortcut, a reviewed built-in rewrite of the current page's own URL (below).

**Fast path.** In a `run` (never a `step`, `observe` or `act`) whose declarative expectation names a page type of the origin's profile, with a provider that has the slim done-and-guards request: when the current page proves a page type (URL template and every check) with a route to that target and the expectation does not already pass there, the route's next hop runs with no decision, as a step with `decision.by: "profile"` (`reason: "site_fast"`, `edge`). The step is always one of the links `legalActions` offers for this page and level (a same-origin link whose href is on the page, or the same-tab form of one that would open a new tab); exactly one destination must match; a placeholder named like a capture of the current page's URL must have the same value (from `/foo/bar` an edge `/{owner}/{repo}/issues` only follows `/foo/bar/issues`); and on the route's last hop the destination must also satisfy the expectation (`urlIncludes` at path boundaries, so `/issues/123` never takes `/issues/1234`, or `urlEquals`). Never a button, select, fill, submit, host-supplied URL or a link whose label or path reads like an account or commit action, at any level. In parallel with each hop the runtime sends the slim done-and-guards request for the page it leaves (`cost.requests` kind `site_guards`, not counted in `cost.decisions`); its guards join the run's guard signals, and a blocked score at 0.85 or an injection score at 0.8 ends the fast path. Every landing must prove the edge's target type; the first mismatch, a landing off the origin, an action error (except one click per run that the page refuses as stale because it changed after it was observed, as MDN does when it adds its ad and sign-in links after load: the edge is then resolved again on a fresh observation, counted `stale` in the stats), a failed guards request, a consent dialog, a login wall, an error page or page text addressed to an agent ends the fast path for the rest of the run, and the normal loop decides from that page on. Rung 0 runs on every page as before; a fast step never uses the last action of `maxActions`, never completes a run by itself, and the landing page always gets the normal terminal decide (done and the guards) and answer ranking. Fast steps count against `maxActions`, not `maxDecisions`. The hint words of the links on the route (at most six) join the instruction terms the page script orders controls by under its 100-control cap, so a needed link is observed on a busy page; that changes ordering only, never what is offered.

**Shortcuts, pinned controls, status lines and notes.** `shortcuts` (at most 4: `{id, on, to, kind}`) name a reviewed transform a shipped task defines ([tasks/](../tasks/), `tasks/<name>/index.js`; [src/shortcuts.js](../src/shortcuts.js) registers them from `tasks/index.js` and checks that a transform keeps the page's origin and path) by `kind`; the kinds today are the flights task's `flights_tfs_date` and `flights_query` ([tasks/flights/index.js](../tasks/flights/index.js)) and the hotels task's `booking_search` (a Booking.com results URL built from the step's destination, ISO dates and guest counts, defaults 2 adults, 0 children, 1 room, at most 30 nights) and `booking_dates` (the same results URL for another check-in and check-out, every other parameter kept) ([tasks/hotels/index.js](../tasks/hotels/index.js)). Google Flights carries the whole search in the results URL's `tfs` parameter, a base64url protobuf whose one flight-leg message (field 3) holds the departure date as the 10-byte string `YYYY-MM-DD` (field 2). When the step's instruction (or its `expectation.textIncludes`) names exactly one real date, never right after a word that makes it something other than the departure date (a negation such as `not` or `except`, `return`/`returning`, `before`/`after`/`by`/`until`, `as of`; such a date means no shortcut), and the host's own text names that date too (a step list's step before its `{{answer:N}}` placeholders were filled, never a re-run instruction the runtime wrote: a date a page supplied never builds the URL), the page proves the `on` page type and its `tfs` holds another date, the runtime decodes `tfs`, checks it is a well-formed protobuf that re-encodes to the same text, replaces the date's bytes (same length, so no length prefix changes), re-encodes in the input's own alphabet and padding, keeps every other query parameter in order, drops `tfu` (the page's UI state) and the fragment, and navigates there with no decision: a step with `decision.by: "profile"`, `reason: "site_shortcut"`, `shortcut: <id>` and `verdict.why` `site:shortcut`. The rewrite refuses (no shortcut, the normal loop decides) a round trip or multi-city search (more than one leg, a leg with no date or with two), an unparsable or over-long value, two `tfs` parameters, an invalid date and a URL that would change origin or path. Guardrails as for a fast hop: a `run` with a declarative expectation, profiles and the fast path on, a provider with the slim guards request (sent for the page left, as `site_guards`), level `reversible` or above, the result on an approved origin (the extension refuses anything else again), never on a consent dialog, never with the last action of `maxActions`, never on a page addressed to an agent, and the landing must be the `to` type's URL holding the date asked for (else the fast path ends, `mismatch`). Unlike an edge, a shortcut may run where the expectation already passes (the page shows another date). `flights_query` (the profile's `search-query`, `on: "search"`, `to: "results"`) is the first hop from the search page `/travel/flights`, which has no `tfs` to rewrite: when the step's instruction mentions flights, names a route as `from <place> to <place>` (the last such pair; a place is 1-40 letters, digits, spaces and `. ' -`) and exactly one plain date (one way, with or without the words "one way") or two dates in order with a round-trip word or written as a range (round trip), and the host's own text builds the same query, the runtime navigates to the page's own origin and path with `q=` set to one fixed text built and URL-encoded by code, `One way flights from Marseille to London on 2027-01-12` (round trip: `Round trip flights from A to B on D1 returning on D2`; the one-way form is the URL a live run opened by hand on 2026-10-08 when the Departure textbox ignored typed text), every other parameter kept and `q`, `tfs` and `tfu` dropped. No text of the step goes into the URL as written, and a `q` the code could not have built is never read as a value. The landing counts (`hit`) on the search page's own path with that `q`, or on a `tfs` results URL whose legs hold the query's dates (Google may redirect); anything else ends the fast path (`mismatch`). On a results page the date rewrite applies instead. `controls` (at most 12: `{label, pin?, name?}`, literal labels) apply with hints on, on the profile's pages only (a URL matching one of its page types' `url`): `pin: true` keeps an action whose label is the literal (or starts with it followed by a non-letter) through the offer cap and `slim.cap`, like an essential option, and adds the label to the page script's ordering terms (at most six, ordering only); `name` may only rename a page-script name (`unlabelled button 2 of 2 next to "Departure"`, `next-value button after "Departure" (unlabelled)`) of a control the page script marked `unnamed` (a page label that reads the same is never renamed) to a plain phrase in what the provider is shown; the name may not claim a direction the page script did not derive (previous/next/earlier/later words on an `unlabelled ...` descriptor, which the page script leaves without a direction on purpose, or the opposite direction on a derived one: the profile refuses to load) (options and page controls, in copies; ids, targets and the recorded observation keep the page script's label). `status` (at most 6 literal texts) names blocks that are not loading placeholders on the profile's pages when the page carries at least three text rows of its own, the rule persistent status text follows too (Google Flights keeps "Loading results" and "Fetching results" on every results page; on a page without rows the line may be the only sign of a real load and keeps its waits): no content wait, no `content_loading`, no `textAbsent` suggestion for them. `notes` (at most 3 filtered sentences of at most 160 characters: letters, digits, spaces and `. , ; - ' " / ( ) &`, no colon, no host name such as `example.com`, no instruction or injection words, no risky label class) go with every full decide on the profile's pages as `state.site.notes`, with the same `site_hints` policy line.

**Hints.** When a planned link hop cannot be taken mechanically, the next full decide (never the slim terminal or guards request) carries `state.site` (after `state.policy`): `{page, target, next: "The usual next step toward the <target> is the link labelled \"<hint>\"."}`, built from fixed templates over the filtered plain phrases, plus one policy line, `site_hints`, saying hints never allow anything the policy reserves for the user. It adds 310-330 characters to the request (about 80 tokens, half of them the policy line), only on decides that carry a hint; without one the request is byte-identical to before. Off with profiles off; provider switch: `"providerOptions": {"guidance": {"site": false}}`.

**Receipt and stats.** The trusted `site` block lists what ran: `{profile: "github.com@2", fastSteps, path: [edge and shortcut ids], shortcuts?, hinted?, noted? (decides that carried notes), renamed? (options shown under a profile name), fellBack?: {reason: "mismatch"|"cross_origin"|"consent"|"login"|"injection"|"blocked"|"guard_error"|"error_page"|"action_error"|"ended", edge?, step?}}`, merged across a self-rerun's attempts and a step list's steps, and `verdict.why` gets `site:fast` (`site:shortcut`). Hit/miss counters per page type, edge and shortcut, fast steps, hints and fallbacks per run go to `domain-stats/<host>[_<port>].json` under the state directory (or `$FAI_HOME`) when that is not inside the package, else under the daemon state directory (`FAI_DAEMON_DIR`) when that is outside the package, else in a per-user temporary directory: never next to a profile and never inside the repository (0600; reset when `version` changes; never read back into a decision).

## Detection

Agents act in the user's own browser profile, so a site that flags the input as a bot flags the user (a CAPTCHA, a blocked action, an account review). The extension therefore makes its input look like a person's to page scripts, and adds nothing else a page can see.

**Realistic input** ([extension/input.js](../extension/input.js), injected with `page.js` into the same isolated world: `executeScript` files `['input.js', 'page.js']`; without it `page.js` falls back to its plain dispatch). `page.js` still decides what may run (targets, guardrails, navigation checks); `input.js` decides only how it looks:

- **Click**: a small think time; an off-screen target is scrolled to with wheel steps (`revealMaxPx`, 4000 px; farther, or inside an inner scroller, `scrollIntoView`); the pointer moves from where it was (or a resting point 150-380 px away) along a slightly curved, decelerating path of 3-7 `pointermove`/`mousemove` events with `movementX/Y`, with `pointerover`/`pointerenter`/`mouseover`/`mouseenter` (and the matching out/leave) wherever the element under it changes; it aims near the middle of the element's visible part at a point where the element (or something inside it) is on top; then `pointerdown`, `mousedown`, focus (the nearest focusable ancestor, `focusVisible: false`; on nothing focusable, the focused element blurs), a 25-130 ms hold, `pointerup`, `mouseup`, `click`. All carry `clientX/Y`, `screenX/Y` (window position plus browser chrome, the same offset on every event), `view`, `button`/`buttons`, `detail` (1 on press, release and click), `pointerId` 1, `pointerType: 'mouse'`, `isPrimary`, `composed`. The click is a `PointerEvent`, as browsers send it. As with a mouse: a page that cancels `pointerdown` gets no `mousedown`/`mouseup` (the click still comes); one that cancels `mousedown` keeps focus where it was; a target the press removed or disabled gets no click (a dropdown that selects on `mousedown`). The control's label and state are rechecked right before the press; a change while the pointer moved is `stale`, with nothing pressed. The click is the last event and nothing is awaited after it, so links navigate and submit buttons submit exactly once (activation runs from the dispatched click, as for `el.click()`). A point click presses at the agent's point.
- **Typing** (`fill_supplied_text`, and `fill_secret` with a secret handle's value): a click into the field unless it has focus; Ctrl+A (Cmd+A on macOS) when it holds text; then per character Shift as needed, `keydown`, `keypress`, `beforeinput`, the insertion (native value setter at the caret, so React and Vue controlled inputs see it; `maxlength` respected), `input` (`InputEvent`, `insertText`), `keyup`, with US-layout `key`/`code`/`keyCode`, timed by the typing rhythm below. A whole value whose planned rhythm fits in 1.4 × `typeBudgetMs` (1000 ms) is typed in full; a longer one is typed up to `typeBudgetMs` or `maxTyped` (40 characters) and the rest goes in as one `insertText`, so a 400-character fill takes about 1.3 s. A key the page cancels inserts nothing; when the field does not show the text afterwards, the plain set runs (the old behaviour), so a key-swallowing field still fills. `change` fires when focus leaves the field (the next click or fill) or on Enter, as for a user, not right after typing.
- **Typing rhythm** (`typingPlan` in input.js; the same plan drives the synthetic and the trusted path): each lease draws a typist once (the worker sends a random `rhythmSeed` per lease; a document without one draws its own): a median keydown-to-keydown interval of 75-108 ms and a median hold of 62-92 ms. Each interval is log-normal (σ 0.3, so right-skewed) around that median, scaled by context: common English bigrams (×0.8) and a change of hand (×0.88) are quicker; the same finger on another key (×1.3), Shift (×1.35), digits and symbols (×1.25), keys outside the US layout (×1.4) and Enter (×1.6) slower; a new word (×1.3), the key after punctuation (×1.5) and the start of a burst (keys come in runs of 3-8: ×0.92 inside one, ×1.3 at its start) later. About 2% of keys follow a hesitation of 250-550 ms, at most 600 ms per fill. Holds are log-normal on their own (σ 0.22, 30-180 ms), so a key may still be down when the next goes down (rollover), never across a Shift change, on the same key, or for Enter and keys outside the US layout; at most two keys are down and no two events come within 8 ms. The result is about 9 characters a second (95-120 WPM) with a coefficient of variation of the intervals of about 0.4 within a fill (0.25-0.33 with the earlier fixed jitter). A secret (`fill_secret`, a password field) is planned blind: intervals and holds from its length alone, no rollover, Shift slotted into the gaps, so the time a fill takes (`inputMs`) and how much of it is typed depend on its length only. Synthetic typing plays the plan against the clock (a slow page handler eats into the next gap); more than 400 ms behind it, the rest goes in as one insertion. Deliberate typos and corrections are not modelled: a corrected value can trip validation or autocomplete on the way. Typing alone, measured in headless Chromium (no think time or focusing click): 10 characters about 1.07 s (0.90 s before), 30 about 1.00 s (1.11 s), 100 about 0.97 s (1.11 s).
- **Enter** (`submit_field`): `keydown`, `keypress`, the field's `change`, then the browser's implicit submission: a keyboard click (`detail` 0, `pointerId` -1) on the form's default button, whose own handlers run, else `requestSubmit()`; nothing when the page cancelled the key or already submitted. `keyup` follows. Never two submits.
- **Select**: a click on the `<select>` (an untrusted press opens no popup), a moment to pick, then the value with `input` and `change`.
- **Scroll**: the pointer over what scrolls, then `wheel` events of 100 px notches at the pointer, each followed by its share of the 70% scroll (12-24 ms apart). A notch the page cancels is not scrolled; if the page cancelled and nothing moved, the whole distance is scrolled directly.
- **Escape** and **backdrop** dismissals: a key press with a hold; a full mouse click at the backdrop point.
- **Timing**: 15-70 ms think time before each action; nothing waits in a hidden tab (its timers are throttled). The time added is reported per action as `inputMs` in the execute result. Measured in headless Chromium (`test/real-input.test.js`): click p50 about 180 ms (max 240), an 18-character fill about 1.4 s including its focusing click, a 400-character fill about 1.35 s, Enter 20-70 ms, select 0.35-0.45 s, scroll 120-160 ms.

**What a page can still tell.** Every event dispatched from a content script has `isTrusted: false`, and none gives the page transient user activation (`navigator.userActivation`), so features that need a real gesture (popups, clipboard writes, fullscreen) stay unavailable, as they were with `el.click()`. Scripts that check `isTrusted` on clicks or keys (some bot-management sensors do) see it; only the browser's own input changes it (trusted input below). Also visible: input arriving while the window is not focused (`document.hasFocus()` false; the extension never steals focus to hide it), the pointer starting fresh on each new document, and main-thread time: an observation's layout reads run on the page's thread, so a page timing its own frames (or a `longtask` observer) can see that something worked, though not what. Not detectable below Test site: the extension itself (no `web_accessible_resources`, so no probe by extension ID), page-world globals (none; both scripts run in the isolated world), DOM changes (none: no attributes, styles or nodes; screenshots are annotated in the offscreen document), console output (none), `navigator.webdriver` (untouched: no automation protocol in the user's browser), and the MutationObservers and listeners `page.js` uses (isolated world). `fixtures/detection/detector.html` scores an event stream with the published heuristics (click without `pointerdown`/`mousedown`/`mouseup`, `pointerId` -1, zero or inconsistent coordinates, no pointer movement or hover, value without key events, `input` that is not an `InputEvent`, key without focus, missing `code`, shifted key without Shift, instant press or key, uniform key rhythm, `change` with nothing committing it, scroll without wheel, submit without a gesture); the realistic path trips none, the plain path trips fourteen. On a **Test site** session the [dev hook](#dev-logs-and-javascript-dialogs) runs in the page's own world (wrapped `console`, `fetch`, `XMLHttpRequest` and dialog functions, a `__faiDevHook` marker): a page can detect it there, which is acceptable only on the user's own test sites. Keys (`act {key}`) and hover use the same realistic path (key events with modifiers held around them; Tab, Space and the paging keys do what the browser would after an uncancelled key).

**Trusted input (opt-in, Chromium only).** With Advanced, **Trusted input** on, `input.js` hands the same sequences (pointer path, press and release, keys, wheel notches) to the worker ([extension/trusted-input.js](../extension/trusted-input.js)), which replays them with `chrome.debugger` (`Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, `Input.insertText`): the events come from the browser, `isTrusted: true`, with user activation, native focus, `change` and implicit submission. The worker accepts steps only from its own content script in the top frame of the leased tab, only that closed set, inside the viewport, with bounded waits and text; it attaches for an action and detaches 600 ms after its last step. The press goes out only while the element (or something inside it) is on top at the point; otherwise, and whenever nothing could be dispatched, the synthetic events above run. `<select>` stays synthetic (a trusted press would open the native popup).

Trade-offs: Chrome shows "FAI Browser started debugging this browser" on every window while attached, so the bar appears and disappears with each action; the user can cancel it, which ends that action's trusted input. `debugger` cannot be an optional permission in Chrome, and as a required one it adds install warnings ("Access the page debugger backend", "Read and change all your data on all websites"). So the regular extension never carries it and never offers the setting: `npm run build:trusted` ([scripts/build-trusted.mjs](../scripts/build-trusted.mjs)) copies `extension/` to `dist/trusted/` with the permission added (same key, same extension ID); load that instead, then turn the setting on. Firefox has no `chrome.debugger`: unsupported there (its build leaves `trusted-input.js` out; `input.js` ships there).

## Limits

One active tab lease at a time; approving another request supersedes it. Domain roots follow the vendored Public Suffix List as of its last refresh ([Domain roots](#domain-roots)). Pause ends the run rather than suspending it. A daemon restart forgets requests (clients get `unknown_request` and request again). Login, MFA, frames on origins the request does not list ([Frames](#frames)), unusual widgets and browser-internal pages need the user. Capture is limited by Chrome's quota. Nothing verifies arbitrary prose tasks; supply an expectation. Linux and macOS only.

### Approval window and tab mark

- **Approval window.** When the daemon's request list shows a new pending request, the worker opens the popup page in a small window of its own (`chrome.windows.create` with `popup.html?window=1`, `type: 'popup'`, 420×620, focused), so the user need not notice the badge. Each request id opens it at most once, also across service-worker restarts (the ids shown are kept in `chrome.storage.session.shownRequests`, the last 100). Only one exists at a time (`chrome.storage.session.approvalWindowId`): a new request while it is open focuses it, and its page re-renders from `chrome.storage.session.requests`. It is not opened when the setting is off, the extension is not paired, or the live session already serves that request. In the window there is no current tab (the card at the top reads **AGENT REQUEST**), so every card uses **Open <host>** (or **Approve on the FAI tab** for a request the live session's tab already covers); a request with no start URL cannot be approved there, and its card says to open a page it asked for and approve with the icon. The window closes itself after a successful open, and when no pending or paused request is left (approved, denied or expired). With **Open requested pages right away** on (the default), a request whose page opened by itself gets no approval window: its prompt window (`arm.html`, see [Open and approve](#open-and-approve)) stands in; a Full or Testing request still gets the approval window.
- **Tab mark.** While a session is active or paused its tab sits in a Chrome tab group titled `FAI` (`FAI ⏸` while paused, grey), whether the tab was opened with **Open <host>** or approved with **Approve this tab**; a tab that is open and armed but not yet approved sits in a group titled `FAI ?` with a `?` badge. The group is made by the extension (`chrome.tabs.group`, `chrome.tabGroups.update`) and the tab is ungrouped when the session stops, the daemon ends or supersedes the lease, or a new session takes over; a restarted worker ungroups the tab its predecessor marked (`chrome.storage.session.markedTab`). A tab already in a group the user made is left there and gets no group mark. The toolbar badge shows `ON` (active) or `Ⅱ` (paused) only on that tab (per-tab badge text, visible while it is the selected tab), cleared when the session ends; the pending `?` and a paused request without a session show on every tab. Nothing is injected into the page and its title is never changed (run expectations read titles; screenshots are evidence). Popup-type windows have no tab strip, which is one reason the opened tab gets a normal window. The `tabGroups` permission this needs shows the install warning "View and manage your tab groups"; `chrome.tabs.group` and `ungroup` need no `tabs` permission.

### Firefox

`npm run build:firefox` ([scripts/build-firefox.mjs](../scripts/build-firefox.mjs)) copies `extension/` unchanged to `dist/firefox/` (`--out <dir>` for another place) and writes a Firefox manifest; the Chromium extension is never modified and loads nothing Firefox-specific. The manifest differences: `background.scripts` (an event page: `compat.js`, `psl-data.js`, `frames.js`, `background.js`) instead of the service worker; `browser_specific_settings.gecko` with `id: "fai-browser@jedbjorn.github.io"` (the AMO-signed ID; `--gecko-id fai-browser@local` builds the old dev ID; the native host's `allowed_extensions` take both), `update_url` (the latest GitHub Release's `updates.json`; signed-ID builds only), `strict_min_version: "140.0"` (the oldest supported ESR; `tabGroups` needs 139) and `data_collection_permissions: {required: ["none"]}`; no `key`, `minimum_chrome_version` or `offscreen` permission; `content_security_policy.extension_pages` `script-src 'self'; object-src 'none'`, without Firefox's MV3 default `upgrade-insecure-requests`, which rewrote the worker's `ws://127.0.0.1` WebSocket to `wss://` and left only the long-poll; no `host_permissions` (a Firefox match pattern with a port matches nothing, and neither the WebSocket nor the CORS-answered long-poll needs one); `optional_host_permissions` `https://*/*`, `http://*/*` and `<all_urls>`. `npm run lint:firefox` runs `web-ext lint` on the build: 0 errors, and the only warnings are `offscreen.hasDocument` and `offscreen.createDocument`, which compat.js provides.

**compat.js** ([extension/compat.js](../extension/compat.js)) loads first in the Firefox event page and only fills in what is missing, so the rest of the extension keeps calling `chrome.*` (Firefox's `chrome` namespace returns promises in MV3):

- `chrome.offscreen`: Firefox's background is a page with a DOM, so the offscreen document is a hidden `<iframe src="offscreen.html">` in it. The same `offscreen.js` runs there and answers the same `annotate` message, so screenshot drawing, action-id tags and [secret boxes](#secret-redaction) are one code path in both browsers.
- Exact-origin keeper. Chrome keeps `activeTab` until the tab leaves its origin; Firefox drops it at any navigation, after which the worker could neither read the tab's URL nor run `page.js`, and paused the lease (`origin_changed`). In the Firefox build the approval click (the toolbar click on an armed tab, or the popup's **Approve** or **Open <host>**) also asks, inside that click, for the request's exact origins as host permissions (`https://host/*`, port dropped; domain roots keep their own prompt). Firefox shows its permission prompt once per new site. The keeper records each pattern Firefox reports added after such a click (`chrome.storage.local.compatGrantedOrigins`) and removes it once no pending, active or paused request in `chrome.storage.session.requests` needs it; a site the user allowed by hand is never recorded, so never removed. Declining the prompt keeps the approval: the session works until the first navigation, which pauses it.
- Feature-detected as in Chrome: `tabGroups` (the tab mark; without it the badge and title remain), `action.getUserSettings` (the pin hint), `storage.local.setAccessLevel` (absent in Firefox, where `storage.local` is also readable by the add-on's own content scripts; `page.js` runs isolated from the page, so a page still cannot read it). The same in both: `storage.session`, `scripting.executeScript` with `func`/`args` (Firefox returns no `documentId`, so the injection retry targets the tab), `action.setPopup`/`onClicked`, `windows.create({type: 'popup'})`, `commands` (`_execute_action`, Ctrl+Shift+Y), `alarms`, `runtime.sendNativeMessage`.

`chrome.tabs.group` names the tab's own window (`createProperties.windowId`): Firefox otherwise moved the tab into the last focused window, the prompt popup, and closing the prompt then closed the leased tab. Chrome already grouped the tab in its own window.

**Screenshots.** Firefox's `captureVisibleTab` needs `activeTab` or `<all_urls>`; a host permission for the site is not enough (`Missing activeTab permission`). The approval click grants `activeTab`, so the first page captures; after the first navigation an observe or act returns no image (never a wrong one) unless the user chose **Allow on all sites** (Advanced, or the setup card), which requests `<all_urls>` once, or turned on **Access your data for all websites** (about:addons, FAI Browser, Permissions). With it the exact-origin prompts after a navigation disappear too. The add-on requests it only on that click.

**The service side.** Firefox gives every install a random origin, `moz-extension://<UUID>`, so the hub accepts any such origin (exact lower-case UUID syntax) besides the pinned `chrome-extension://` one, and echoes it in `Access-Control-Allow-Origin`. A web page can never send that origin; the pairing secret, which only the native host (started by Firefox for the FAI add-on IDs alone, with `[manifest path, add-on ID]` as its arguments) or the user hands out, remains the authentication.

**Event page lifetime.** The session lives in the background page's memory, as in Chrome's worker. In the headless smoke an approved session survived 70 s idle (Firefox's idle timeout is 30 s) with the WebSocket open; if Firefox ever unloads the page, the hello with `session: null` pauses the lease and the user approves again, as after a Chrome worker restart.

**Install options.** `fai-browser launch` sets up official Firefox with a separate FAI profile and the signed add-on, and `npm run setup` offers it ([docs/guide/install.md](guide/install.md): detection, the Mozilla download and its checks, the profile's `user.js`, add-on placement, `uninstall-launcher`). A temporary add-on (about:debugging) is gone after a Firefox restart. Unsigned add-ons install permanently only in Developer Edition, Nightly, ESR and unbranded builds with `xpinstall.signatures.required = false`; any Firefox installs one you signed as an unlisted add-on on AMO (`npx web-ext sign --channel unlisted` with your own API key). `npm run dev:firefox` is the source-development loop: it builds `dist/firefox`, watches `extension/` recursively, rebuilds with a 250 ms debounce (`--debounce <ms>`), and leaves web-ext's automatic reload enabled. It uses `profiles/fai-firefox-dev` unless `--profile <dir>` is given, and selects Firefox with `--firefox <path>` or `FIREFOX_PATH`. web-ext runs with `--keep-profile-changes` and `--profile-create-if-missing`, so profile changes and sign-ins persist and no temporary-add-on loading step is needed. With a `.parentlock` or `parent.lock`, the command checks for Firefox processes before building or launching and refuses if one uses or could use the selected profile, or if the process state cannot be checked; it never removes the lock or writes the profile's preferences itself. An explicit different absolute profile does not block it, and a stale lock is left for Firefox to handle on startup. Snap and Flatpak Firefox run sandboxed and cannot start the native host: pair by hand.

**No automation traces** (below Test site; there the [dev hook](#dev-logs-and-javascript-dialogs) runs in the page's world). The Firefox path adds nothing a site can see beyond the Chromium one: `page.js` runs as an isolated content script injected with `scripting.executeScript` (no DOM nodes, no page-world globals; the tab group and badge are browser UI), the offscreen frame lives in the add-on's own background page, and the user's Firefox runs with no remote protocol (`navigator.webdriver` stays false). Marionette and `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS` are used only by `npm run smoke:firefox`, on a throwaway profile under a temporary `HOME`. The separate `dev:firefox` loop does use web-ext's development remote control for loading and reloading; use a normally started browser for detection measurements.

**The smoke.** `npm run smoke:firefox` ([scripts/firefox-smoke.mjs](../scripts/firefox-smoke.mjs); Marionette through [scripts/marionette.mjs](../scripts/marionette.mjs), no geckodriver) builds the add-on, starts its own FAI service on a free port with a temporary `FAI_HOME`, writes the native host manifest under a temporary `HOME` (XDG layout), starts headless Firefox on a temporary profile and installs the add-on as a temporary add-on. It checks: pairing through native messaging, then the WebSocket; an agent request opens its page in a new tab and arms it; Firefox's own toolbar-button path (`triggerAction`, which grants `activeTab`) approves it, and the exact-origin prompt is allowed through its doorhanger; observe, an annotated screenshot, one `act` and its effect; a same-origin navigation keeps the session; no screenshot without the all-sites opt-in; with it, a screenshot of a page of fake keys with every secret boxed (`redactions` in the trace). It also runs the local detection fixture through normal observe/act calls and prints a capability matrix: event-sequence flags, exactly-once action effects, page-world globals, DOM mutations, untrusted events, user activation and `navigator.webdriver`. Marionette makes the last value `true` in this throwaway harness; the matrix reports that separately instead of treating it as an extension signal. On a small machine run it capped: `systemd-run --user --scope -p MemoryMax=2500M timeout 300 npm run smoke:firefox`.

**Detection in a dedicated profile.** This is separate from `npm run dev:firefox`: web-ext uses a development remote-control session to load and reload the add-on, so that browser is not valid for the no-remote-protocol measurement. Stop the development loop, build with `npm run build:firefox`, and start the dedicated development/test profile normally without Marionette or another remote protocol. Load `dist/firefox/manifest.json` from `about:debugging#/runtime/this-firefox` (or install the signed add-on), and pair it as above. Then run `npm run detect:firefox` ([scripts/manual-firefox-detection.mjs](../scripts/manual-firefox-detection.mjs)). It serves only `fixtures/detection/detector.html` on loopback, opens that page, waits for the user's interactive approval, drives the same shared matrix as the headless smoke and reads the fixture's loopback-posted report. A pass requires `navigator.webdriver: false`, no avoidable event flags, no FAI page-world globals or DOM mutations, and exactly-once actions. Content-script events remain `isTrusted: false` and user activation remains false; the runner reports those inherent limits rather than trying to hide them. No model, credential, testing mode, third-party site or remote debugging protocol is used.

## Check the real toolbar permission

The headless smoke uses a test manifest that grants `<all_urls>`. To exercise the shipped `activeTab` path, load the unmodified `extension/`, pair it (`npm run setup`) and run `npm run manual-smoke` (pinned ID, no Jev key). It serves a local fixture, asks your FAI service for a Read tab on it (the page opens by itself), waits up to three minutes for your click on the FAI Browser icon there, then observes, clicks **About project** through `act` with an expectation, checks the landing page again on its own, prints the screenshot and trace paths and releases the request. Exit 0 on PASS, 1 on FAIL.
