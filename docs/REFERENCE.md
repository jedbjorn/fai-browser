# FAI Browser reference

The detailed manual for FAI Browser: setup, the daemon, the MCP server and CLI, result shapes, status codes, screenshots, traces, the SDK, policies, guardrails and limits. The [README](../README.md) is the overview; [ARCHITECTURE.md](../ARCHITECTURE.md) covers the design and [PROPOSAL.md](design/PROPOSAL.md) the roadmap.

An agent opens a tab the user approved, reads a compact page and chooses one of the browser actions on offer; the extension runs it, and the agent gets back the next page, a verified outcome when it gave an expectation, annotated screenshots on request and a trace on disk. FAI makes no model or provider calls of its own.

Requires Node 22+ and Chrome/Chromium 116+. The runtime has no npm dependencies, and everything runs locally except the daily [update check](#updates) (one GET to GitHub's releases API; `FAI_UPDATE_CHECK=0` turns it off). Commands below run from the package root.

## One-time setup

1. Run `npm run setup` in the package directory. It moves settings left in the checkout by an older version, saves the pairing secret to `.env.local` (mode `0600`) in the settings directory (see [The daemon](#the-daemon)), installs the [native messaging host](#native-messaging-pairing) for every browser it finds, starts or reloads the FAI service (the daemon), and offers to register FAI Browser with each coding agent on your `PATH` ("Register FAI Browser with Claude Code? [Y/n]"; user scope, through `install --host`). It ends with a three-step checklist. No key is needed. `--yes` registers every detected agent without asking, `--no-register` skips that; `--extension-id <id>` overrides the pinned ID for a re-keyed manifest. Other settings are preserved.
2. Open `chrome://extensions` (`brave://extensions`, `edge://extensions`), turn on Developer mode, click **Load unpacked** and select `extension/`. The manifest `key` fixes the extension ID at `ikkpdnokohfcjhfidepcledkbepmkfcm`, so you don't need to copy it. The extension pairs by itself through the native host: nothing to paste.
   Firefox: setup offers the FAI profile with the signed add-on (`node src/cli.js launch`), or install the signed `.xpi` from GitHub Releases in your own Firefox ([install guide](guide/install.md)). For development, `npm run build:firefox` writes `dist/firefox/`; load it from `about:debugging#/runtime/this-firefox` (**Load Temporary Add-on**, pick its `manifest.json`). [Firefox](#firefox) has the details.
3. Pin the FAI Browser icon (puzzle-piece menu, then the pin) for the popup's controls, invites and the toolbar approval; most requests can also be approved with **Approve** in the task tab's request modal. The popup shows how to pin it while it is not pinned.
4. Restart your coding agent so it loads the MCP server and skill (or connect one by hand, [next section](#coding-agents-mcp-and-skill)), or use the CLI directly.

### Native messaging pairing

`npm run setup` (or `node src/cli.js install-native [--browser chrome,brave] [--all] [--dry-run]`) writes a launcher, `native-host` (`native-host.bat` on Windows) in the settings directory, that runs `src/native-host.js` with the absolute path of the Node that ran setup (and `FAI_HOME` when set), and a host manifest named `fai_browser` for every browser whose profile directory exists for this user:

| Browser | Linux | macOS |
|---|---|---|
| Chrome (Beta, Dev/Canary) | `~/.config/google-chrome{,-beta,-unstable}/NativeMessagingHosts/` | `~/Library/Application Support/Google/Chrome{, Beta, Canary}/NativeMessagingHosts/` |
| Chromium | `~/.config/chromium/NativeMessagingHosts/` | `~/Library/Application Support/Chromium/NativeMessagingHosts/` |
| Brave | `~/.config/BraveSoftware/Brave-Browser/NativeMessagingHosts/` | `~/Library/Application Support/BraveSoftware/Brave-Browser/NativeMessagingHosts/` |
| Edge (Beta, Dev) | `~/.config/microsoft-edge{,-beta,-dev}/NativeMessagingHosts/` | `~/Library/Application Support/Microsoft Edge/NativeMessagingHosts/` |
| Vivaldi | `~/.config/vivaldi/NativeMessagingHosts/` | `~/Library/Application Support/Vivaldi/NativeMessagingHosts/` |
| Firefox | `~/.mozilla/native-messaging-hosts/` | `~/Library/Application Support/Mozilla/NativeMessagingHosts/` |

On Windows the manifest goes next to the launcher and its path is the default value of `HKCU\Software\<Google\Chrome | Chromium | BraveSoftware\Brave-Browser | Microsoft\Edge | Vivaldi | Mozilla>\NativeMessagingHosts\fai_browser` (written with `reg add`). Chromium-family manifests allow only `chrome-extension://<pinned ID>/` (`allowed_origins`); the Firefox manifest allows only the add-on IDs `fai-browser@jedbjorn.github.io` (the signed ID the Firefox build declares) and `fai-browser@local` (older dev builds) (`allowed_extensions`). Firefox on Linux counts as installed when `~/.mozilla` or, for Firefox 147+ profiles, `$XDG_CONFIG_HOME/mozilla/firefox` (default `~/.config/mozilla/firefox`) exists; its manifest goes to `~/.mozilla/native-messaging-hosts/` in both layouts (Firefox 159 reads user manifests only there, and creating that directory leaves the profile location alone). `node src/cli.js uninstall-native` removes the launcher and every `fai_browser` manifest (files whose `name` is another host are left alone).

The host speaks the native messaging protocol (32-bit length, then JSON) and answers two requests: `ping` (`{ok, version}`) and `pair`, which starts the FAI service when it is not running and returns `{ok, endpoint, secret, version}`. It checks the caller again from its arguments (the extension origin Chromium passes, or the add-on ID Firefox passes) and refuses anyone else; it writes nothing but protocol frames and never logs. The worker pairs through it on install and browser start when no secret is saved, every 30 s while unpaired, and again when the service stops answering (it may have been restarted or set up again), at most every 30 s; the popup's **Pair with the FAI service** button asks at once. The secret goes only to `chrome.storage.local` and to the service on `127.0.0.1`; the popup never shows it. Without the host, paste the secret under **Advanced, Connection** (`node src/cli.js pair` prints it).

## Agent direct

**Your agent drives.** It reads each page and chooses every action; FAI makes no model or provider calls.
Setup belongs to the user; agents must not read pairing files or run interactive setup on their behalf.

**MCP surface.** The server lists `fai_browser_open`, `fai_browser_act`,
`fai_browser_observe` (these three with `_meta["anthropic/alwaysLoad"]`), `fai_browser_wait`,
`fai_browser_status`, `fai_browser_release` and `fai_browser_evidence`.

- `fai_browser_open {origins, reason, task?, requestId?, mode?, suppliedText?, allowedUrls?, policy?,
  returnImages?}` requests the tab (or reuses a covering request), waits for approval within the call
  and returns the page. `task` is shown on the request and ranks the digest and the action listing;
  it never runs. The first `allowedUrls` entry is the page approval opens.
- `fai_browser_act {actionId | point | url | nav | key | tab | fills | dialog, revision?, text?,
  submit?, hover?, path?, reason?, requestId?, expectation?, returnImages?}` runs one offered action
  (or a [host-composed act](#host-composed-acts)) and returns the landing page with its actions and a
  new revision, and `did`: one trusted line per action that ran (`fill "Search" (12 chars)`, `press
  Enter in "Search"`; a typed value is never echoed, only its length). Revisions are single-use; an
  unknown or spent one is refused with the current revision. Without `returnImages` nothing is
  captured.
- `fai_browser_observe {requestId?, task?, focus?, digestChars?, waitFor?, maxMs?, logs?, mode?,
  suppliedText?, allowedUrls?, policy?, returnImages?}` reads the page again. `focus` ranks this digest
  and this listing by its words (the phrase itself first: a link labelled with it is listed, even one the
  page script's control cap or the listing cap had left out) and shows the long blocks that hold them whole;
  `digestChars` (500-6000, default 1500) widens the digest and, above 1500, shows every long block whole.
  A block longer than 300 characters (a banner, a paragraph) otherwise ends in `…`, as does any block shown
  shorter than the page has it (over the budget, or past the page script's 1500 characters, which neither
  `focus` nor `digestChars` can show more of). The mark alone does not set `page.truncated` (the "more on
  the page" hint), which stays for relevant blocks the digest left out. `waitFor` (`textIncludes`,
  `textAbsent` and/or `urlIncludes`) polls the page every 400 ms until it matches, up to `maxMs`
  (default 10 s, at most 30 s), matched on the redacted page the host is shown (a secret never
  matches); the result says `waited {passed, ms}`. `logs: true`: see [Dev logs](#dev-logs-and-javascript-dialogs).

**Standing terms.** The daemon keeps every request's host terms: forbidden labels are unioned, supplied
values and allowed URLs added (a later value for a name replaces the earlier one). An observe that
omits them keeps them; nothing can remove them, and an act inherits the terms of its offer.

**Results.** Open, observe and act return `{status, code?, requestId, verification?, page{url, title,
digest, truncated}, granted{level, asked}, revision, actions, moreActions?, consent?, overlay?, needs?,
did?, tabs?, dialog?, logs?, waited?, warnings?, callsLeft?, next}`: `status` is `observed` for a page read, `acted` for an act that landed
without an expectation to check, else the runtime status (`completed`, `needs_user`, ...). No verdict,
answer candidates, cost or step list. The text block puts `next`, the status, `granted: <level> (asked
<level>)` when the user approved less, needs and warnings first, then the page under the untrusted
heading (digest, cookie dialog, popup, one line per action). `next.kind` is one of `choose`,
`observe`, `answer`, `relay`, `wait` or `stop`; a stale page, an unavailable target or a failed
capture says observe again and choose.

**Enter submits.** A filled single-line text field offers `press Enter in "<label>"` (`submit_field`):
the page script classifies what its form submit amounts to (a search field or a safe submit label is
`submit_safe`, granted from `interactive`; any other form `submit`, from `full`; a form with a password
or payment field `sign_in` or `purchase`) and checks it again before it dispatches the key and
submits the form.

The daemon makes no provider calls (no warm-ups, model-based action guards or answer ranking). Built-in
origin, permission, action and field restrictions, forbidden labels, approval and budgets apply to every
act. A purchase is offered as `needsApproval` ("asks the user") from `full` and runs only after the
user's **Approve once**; with that ask turned off, or below `full`, it is refused (`next.kind: stop`:
tell the user to do it themselves). Login and credentials stay the user's outside their approved
testing environment.

### Host-composed acts

Beyond one offered id, `fai_browser_act` (and `POST /v1/act`) takes these, checked against the offer
before anything runs (`src/runtime.js` `checkActChoice`; a malformed one is `invalid_params`). Levels,
`policy.forbid`, the origins, the Approve gate, standing terms and secret redaction apply to each as to
an offered action, and the page script checks each again at dispatch.

- **Typed text.** A host-driven offer lists `fill "<label>" (act with text)` for every ordinary text
  field from `reversible`: never a password, payment, secret or sensitive field (secrets go through
  `fill_secret`; the page script refuses typed text there at every level, `testing` included). `text`
  (at most 5000 characters) is typed through `extension/input.js` like any fill. `submit: true` then
  presses Enter in that field as its `press Enter in` action (`submit_field`): the form submit's own
  class decides (`interactive` for a search, `full` for any other form; sign-in and purchase forms are
  refused), checked on the page the fill left. `fills: [{actionId, text}]` (at most 20) types several
  fields in one call in order, each on the page the previous one left (a field that changed label or
  class there ends the batch `stale`), then `submit` in the last. `suppliedText` keeps working.
  Results, traces and the audit log record a typed value's length only.
- **Navigation.** `url` opens an http(s) URL (relative to the page) on the granted origins at any
  level; another origin is `cross_origin` with `needs.message` naming it (request the tab again with
  it added, `fai_browser_open` with the `requestId`), a URL that names an action (sign-out, delete,
  payment) is refused, and the landing page's origin is checked again. `nav: "back" | "forward" |
  "reload"` uses the tab's own history (`tabs.goBack`/`goForward`/`reload`, the same in Firefox);
  where the page can tell (the Navigation API lists same-origin entries) a move with no entry on the
  approved site is refused before it runs, and otherwise the landing page's origin check pauses the
  lease as for any navigation.
- **Keys and hover** (`reversible` and up). `key` is one of Escape, Tab, Shift+Tab, the arrows, Home,
  End, PageUp, PageDown, Space and Enter, pressed in `actionId`'s control (focused first) or where focus
  is; a Ctrl/Cmd shortcut (a letter or digit, Shift allowed) needs `full`. Enter only as a filled
  field's submit (above). Space activates a focused control only when the page script clears it at the
  level (never a Delete button below `full`). `hover: true` with an `actionId` rests the pointer on that
  control (pointer path and boundary events, no press): a menu that opens on hover. A hover or key is
  gated by the level, never by the control's class.
- **Revisions.** `revision` is optional for plain clicks, links, fills, scrolls, keys and navigation:
  without it the act runs on the host's latest offer, and if the page changed meanwhile the same
  control is re-resolved on the fresh page only when exactly one offered action there has the same
  type, role, label, value and destination, on the same origin and path, its control the same risk
  class, with the same neighbours and no dialog in between (a click on a button also needs the page
  text unchanged); a label that names a class (delete, submit, purchase, ...) is never re-resolved, and
  the result warns `act_reresolved`. `revision` stays required for actions marked `needsApproval`,
  `fill_secret`/`copy_secret` and `point`.
- **The Approve gate's wait.** One act waits for the user's Approve click at most 60 s
  (`GATE_MAX_WAIT_MS`; with the act itself a call stays near 90 s, under Codex's 120 s
  `tool_timeout_sec`), and in Agent direct an open waits as long for the tab approval. On timeout
  `next.kind` is `approve`: the approval stays open for 5 minutes, and repeating the same act picks up
  a click given meanwhile at once.

### Popups and new tabs

**Tab access** defaults to **One task tab**. A page-created child pauses control for the user; it is
not adopted or closed. An offered approved-site `target=_blank` link can still open in the same tab.
**Multiple task tabs** is an explicit approval grant (`tabMode: "multiple"`), with visible host-access
permission for the approved origins. Enabling the preference does not expand an existing grant;
disabling it pauses an active multiple-tab session until a new approval.

With that grant, `fai_browser_act {openTab: "https://approved.example/path"}` opens and follows an
additional task tab, and page-created children on approved origins can join. The same mode and
origin restrictions apply in every tab. At most eight task tabs belong to a request; unrelated
personal tabs are never adopted unless the user invites the agent to one from the FAI popup ([Invites and wakes](#invites-and-wakes)). Task tabs share the managed group/window where browser grouping
is supported. Results list `tabs [{id: "t0", url, title, current?}]` (untrusted page text);
`act {tab: "t1"}` switches only among that list. A child outside approved origins or without host
access pauses the request (`child_tab`). A closed child returns control to another remaining task tab. A
child in front takes the commands; one the page opened behind the working tab joins the list but the
commands stay where they are (switch with `tab`). A tab the browser names its opener for only after
creating it (Chromium for some tabs) is still recognised as the page's child, and a page-opened tab that
comes to the front, created during the session, is a child too, never a `tab_changed`; a tab that existed
before the session (a tab the user opened from the task page earlier) is never adopted: bringing it forward is a
tab switch (`tab_changed`), also with Multiple task tabs. A tab the user opens from the task page during the session
(Ctrl+click, Duplicate) on an approved origin joins the request under Multiple task tabs, like a page-opened tab. The worker keeps the tabs created during the session in
memory only; after a worker restart the session is gone anyway, so nothing is adopted from before. Firefox
names no opener for a page's popup window: it is neither followed nor paused, and the request keeps
working in its own tab. Another request's page that FAI opens by itself opens behind the tab a live
request works on (its prompt window's Approve brings it forward), so it no longer pauses that request.

A `child_tab` pause names the origin of the tab or window the page opened when the browser shows its address (site
access to that origin, or **Allow on all sites**): `childOrigin` in the request view and in the paused result, with
the untrusted page text (`page opened: …`), since the page chose it; `needs.message` only says where to find it. It
is the origin only, never the path or query, redacted like any reported URL. A window that opens on `about:blank`
first is reported once its page shows, within 10 s, for the same lease. Ask the user and request that origin up front
(a sign-up or sign-in window on another host, for example), or add it to the same request
([More on the same request](#more-on-the-same-request)); or turn on **Multiple task tabs** for a child on an
approved origin.

### More on the same request

An agent that needs more than the user approved asks on the request it holds, never with a new one:
`fai_browser_open` with its `requestId` and a higher `mode` (as `needs.level` says) and/or `origins` the
request does not cover yet (the origin a `cross_origin`, `origin_changed` or `child_tab` result names).
The request keeps its id, tab, page, lease and tab mode; nothing is granted until the user's click.

- **Daemon.** `POST /v1/requests/:id/ask {mode?, origins?}` (client `ask(requestId, body)`). A pending request
  may be on the user's screen, so it never grows: asking more on one creates its successor with everything
  (the answer's `requestId`, `replaced`: the old id; the successor's view names it as `replaces`), and the old one
  expires as `replaced` ("This request was replaced by a newer request."), so a click on its card approves nothing;
  the task tab FAI opened for the old one closes, so only the successor's page waits. On an approved request (active or paused) it records `ask {id, level, origins,
  access, at}` in the request view and answers `asked: true`: `origins` the request does not cover yet,
  `access` exact origins it lists that the extension cannot follow yet (no host access; the browser's site
  access is what is asked for). Origins are validated as for a new request (at most 10 in all); a domain root
  is refused on an approved request (`422 ask_root`: ask for the exact origins, which a frame list or
  `leftOrigin` names). A second ask while one waits replaces it, with both, under a new `id`. `POST /v1/wait
  {requestId, ask: true}` also waits while the ask is open. Without `requestId` the MCP server still opens a
  new request for origins the latest one does not cover.
- **Approval.** The ask shows as an **AGENT ASKS FOR MORE** card (the approval window opens for it once; the
  badge counts it): "Same task and tab: add `<origin>` · allow `<level>`", a level selector capped at the asked
  level, **Approve on the FAI tab** (or **Approve this tab** when this browser holds no session for it) and
  **Decline**. Invited tabs show it too. Approve asks the browser for site access to the asked exact origins
  inside the click, then sends the lease message with `ask: true` and the `askId` the card showed: the daemon
  applies only that exact ask (a changed or missing id is refused with `ask_changed`, nothing granted, and the
  card shows the current ask, marked "Updated" with its Approve held for a second), adds the origins and raises the
  request's mode, then
  re-approves the active lease in place (same `leaseId`; level, origins and tab mode updated, the worker's
  session keeps its tabs and page) or, for a paused request, binds the approved tab as a resume. A lease
  message without `ask` never applies an ask. Decline (`deny {requestId, ask: true}`) clears it and keeps the
  request as it was.
- **Following an added origin.** A lease's other exact origins are followed when the extension holds host
  access to them (the request modal's approval, or the ask card's, asks for it): the worker reports them as
  the observation's `reachable`, the runtime then offers links and `url` acts there (only to origins the lease
  lists; without the field nothing changes), page.js lets a link go there, and the session moves with the tab.
  Without host access (a toolbar-only approval in Chromium) such a link is not offered, and a `url` act there
  says the site is approved but not accessible yet (an ask for it is a site-access ask). Approving a request
  with several exact sites therefore lets the agent move between them in the tab: the request card says so.
- **Results.** The open that asked returns the page once the user approved. If the user did not answer within
  the call it returns `needs_user` / `ask_pending` (relay; the ask stays open); after a Decline, once,
  `needs_host` / `ask_declined` (`next.kind: "observe"`: continue at the granted level).

CLI equivalents are `act --request ID --open-tab URL --revision R` and
`act --request ID --tab t0 --revision R`; the SDK accepts `client.act({requestId, openTab, ...})`.

### Frames

A **same-origin** frame (depth 1) is read as part of the page, as before. A **cross-origin** frame is read only when
its own origin is one the request approved: one of its exact `origins` (or the tab's origin), or with an approved
domain root an https origin under that root, and only when every frame above it was read too (nested frames up to
four levels, at most eight frames per page). Every other frame stays unread: nothing of its text, controls or
screenshot boxes is used, and it is only named.

- **How.** `page.js` lists each cross-origin frame it sees as a slot (its position in `window.frames`, its box in the
  viewport, the origin its element's `src` names) and never reads it. The worker
  ([extension/frames.js](../extension/frames.js)) asks the browser which frames the extension can reach (one
  `scripting.executeScript` with `allFrames`: a probe that returns each frame's own origin and path, nothing else; no
  `webNavigation` permission), runs the same `page.js` in each approved frame (pinned to its document) and merges the
  result: text after the page's, blocks after its blocks, controls with ids `f<n>.<id>` (`frame: "f<n>"`,
  `frameOrigin`, bounds moved into the top viewport), a frame's cookie dialog or popup when the page has none, and
  the union of the warnings. Frames get up to half of the 100-control cap (more when the page leaves room) and up to
  half of the 200 blocks; text is capped at 12000 characters in all. Structured records and derived views come from
  the top document only. Every frame call is bounded, so a busy or hung frame never holds a command or a screenshot:
  a probe gets 2 s (one that does not answer leaves the frames `unavailable`, and a screenshot boxes the frame whole
  and is taken again, then withheld), a read 3 s, and an act fails as `timeout` once the frame has not answered for
  6 s and a further 2 s probe.
- **One revision.** With frames read, the observation's revision stands for the page and every frame
  (`<page revision>.<n>`). An act on `f<n>.<id>` runs in that frame on the frame's own revision; the worker first
  probes the frame again: gone or on an origin the request does not approve, `cross_origin` (nothing runs, the
  session stays active); another document on an approved origin, `stale`. It also looks at the page again (one cheap
  read of the top document): a page whose revision changed since the observation is `stale`, and the frame runs with
  the page's current facts (a page that turned into a checkout makes the frame's "Continue" a purchase). An act on a
  page control (click, Enter in a field, a key, a select, a fill, an upload; not a hover) first takes one cheap look
  at each frame read, for the same reason. A
  frame document the browser no longer has when the act is injected is never reported as done: the frame is probed
  again (`stale` or `cross_origin`). In the frame, `page.js` checks again that
  the frame and every ancestor the browser names (`location.ancestorOrigins`, Chromium) are on approved origins. A
  link that would navigate the tab from a frame (`_top`) must stay on the tab's approved site; a link that navigates
  the frame must land on an approved origin. A frame-local navigation is waited for (3 s cap), then the whole page is
  observed again.
- **Same protections.** The frame runs the same page script with the same level, `forbid` list, Approve gate, secret
  redaction, vault and consent detection. An Approve card for a frame control names the frame's own origin "in a frame
  of" the page, and the approval is bound to that origin (a secret's cross-site warning compares with it). One page context covers the tab: a purchase page, a password or payment
  field, or a credentials page in any document (page or frame) applies to every document (a "Continue" in a frame
  of a checkout page is a purchase control; a search submit is not a safe submit when a frame holds a password
  field). One that no longer applies anywhere is dropped again, and the documents are read again without it.
  Screenshots place each read frame's own boxes (secrets and fields) by where the frame is at the capture: the page
  script names every cross-origin frame's current box by its current position in `window.frames`, and the worker finds
  each read frame again by its frame id (its current position, origin, document and size), never by the position it
  had (removing an earlier frame, as ad rotation does, shifts every later one). The frames are asked in parallel within
  one 2 s cap. A read frame that does not answer, a box whose frame is not the one read there, and **every
  cross-origin frame, `<object>` or `<embed>` that was not read** are boxed whole, so nothing of them shows; frames
  past the slot and frame caps, deeper than four levels or not found in `window.frames` are boxed by the page script
  itself. A read frame that moved more than 2 px between the queries before and after the capture, that changed size,
  or that no query can place, makes the capture be taken again, then withheld.
  Strict mode still boxes every cross-origin frame. A frame whose own size does not match the box `page.js` saw at its
  position (the page moved its frames in between) is not read (`unavailable`), and an opaque (`null`) ancestor refuses
  every call in the frame. A point click on a frame is refused as
  `point_frame`: name the frame control's action id instead.
- **Results.** `frames` lists the page's cross-origin frames: `{id: "f1", origin, read: true}` for the ones read and
  `{origin, read: false, reason}` for the others, `reason` one of `not_approved` (the request does not list the
  origin), `no_access` (it does, but the browser gives the extension no access to it), `sandboxed` (an opaque
  origin), `limit` and `unavailable`. `declared: true` marks an origin only the frame element's `src` names (the
  browser did not report one). Every origin there is page content (a page chooses its frames): `frames` sits with the
  untrusted page text, and the trusted `next` only counts the unread frames and says to ask the user and call
  `fai_browser_open` with their origins added; check them with the user first. Any unread frame keeps the
  `cross_origin_frame` warning. Origins are all a result ever carries of an unread frame.
- **Browser access.** The extension needs host access to the frame's origin. Approving in the request modal asks
  the browser for the tab's host and the request's other exact origins in one prompt (at most 10 of them; the ones it
  adds are removed again when the session ends; a list it cannot ask for falls back to the tab's host alone); "Allow on all sites" covers every origin. A toolbar-icon approval grants `activeTab`, which covers
  the tab's own origin only, so approved frames on other origins come back as `no_access`: approve from the request
  modal instead. Firefox: the same code path (`frameIds` in place of document ids, no `ancestorOrigins` check) is
  untested.
- **Example: Microsoft Entra admin center / Azure portal.** The content blades are cross-origin frames on separate
  portal-hosting origins. Observe once with the portal's origin: `frames` names the blade origins (`not_approved`).
  Then request them up front, together with the sign-in origins, for example `origins: ["https://entra.microsoft.com",
  "https://login.microsoftonline.com", <the blade origins from frames>]`. The exact blade hosts vary by portal and
  tenant; take them from `frames`, not from this page.

### Dev logs and JavaScript dialogs

**Test site only.** A session granted at `testing` (every origin listed under Test sites) registers
`extension/devhook.js` in the page's own world and `extension/devlog.js` beside `page.js`, at
`document_start` for its origins (`scripting.registerContentScripts`, `world: "MAIN"`; Firefox 128+ has
the same), and injects both into the page open then. Nothing is registered at any other level, and the
registration goes when the session stops. The hook wraps `console.error`/`warn`, `fetch`,
`XMLHttpRequest`, `alert`, `confirm` and `prompt` in the page's world: **the page can see it and can
forge what it reports**, so it is acceptable only on the user's own test sites, and everything it
reports is untrusted page text, redacted like the page.

- `fai_browser_observe {logs: true}` returns `logs [{kind, text, method?, url?, status?}]` since the
  last read: console errors and warnings, uncaught errors and unhandled rejections, and fetch/XHR
  responses with status >= 400 or a network failure (method, URL without its query, status; never a
  request or response body or header). At most 50 per read (`logsDropped` counts the rest). Below
  `testing` the observe carries the warning `logs_need_testing` and nothing is read.
- **Dialogs.** `alert`, `confirm` and `prompt` never block on a Test site: each is answered at once,
  dismissed unless `act {dialog: "accept" | "dismiss", text?}` armed the answer for the next one (once,
  within 60 s; `text` is a prompt's value). The result after it shows `dialog {kind, text, answered}`.
  Accepting after a dialog whose text names a delete or purchase asks **Approve once** (kind `dialog`;
  the card shows the dialog's text). Below Test site no hook exists: a native dialog blocks the page,
  and a page call that stops answering (a one-line probe after 6 s gets no answer within 2 s) fails as
  `js_dialog` (`needs_user`, relay: the user answers it, then observe). No `debugger` permission is
  involved.

### Uploads

An `<input type=file>` is offered from `full` (Act and Test site) as `upload a file to "<label>" (act
with path) (asks the user)`; a styled picker that hides its input is offered at its label. `act
{actionId, path, revision}` names a file in the host's workspace: the MCP server resolves `path`
against `FAI_WORKSPACE` (else its own working directory, the project the host runs in) through every
symlink and refuses anything outside it (`..`, an absolute path elsewhere, a symlink that leads out),
anything but a regular file, and files over 10 MB. The daemon reads that real path again (same size)
and sends the bytes to the extension only. Every upload asks **Approve once**, whatever the settings:
the card shows the file name, its size and the site that receives it, and the approval binds to that
name and size (the worker checks the bytes it got against them). `page.js` delivers it as a user's pick
would (`DataTransfer`, the input's `files`, then `input` and `change`). Results, traces and the audit
log keep the name and size only.

CLI users use `request-tab`, `wait`, `observe` (`--capture last` for a screenshot), then `act`. The
installed [skill](../skills/fai-browser/SKILL.md) describes the loop.

## The daemon

One long-lived daemon on `127.0.0.1:4318` owns tab requests, leases, acts, traces, retention and the pairing secret. The CLI, the MCP server and the SDK client start it automatically on first use, so you rarely touch it:

```sh
node src/cli.js daemon status            # running?, extension connection, open requests and runs
node src/cli.js daemon logs --lines 50   # JSON lines; never contains keys, secrets or page text
node src/cli.js daemon stop | start | restart
node src/cli.js daemon                   # run in the foreground (what auto-start spawns)
```

State lives outside the checkout, in per-user directories. **Settings** (`.env.local`, the optional `config.json` with retention, request TTL, thresholds, `guardrails`, `budget`, `updateCheck`, and the native host launcher) go to `$XDG_CONFIG_HOME/fai-browser` (default `~/.config/fai-browser`) on Linux, `~/Library/Application Support/fai-browser` on macOS and `%APPDATA%\fai-browser` on Windows. **Runtime state** (`client-token`, created by the daemon on first start and sent by clients as a bearer token, `daemon.json`, `daemon.lock`, `daemon.pid`, `logs/daemon.log`) and `artifacts/` go to `$XDG_STATE_HOME/fai-browser` (default `~/.local/state/fai-browser`) on Linux, the same Application Support directory on macOS and `%LOCALAPPDATA%\fai-browser` on Windows. `$FAI_HOME` puts all of it in that one directory instead; under `node --test` without `FAI_HOME` a per-user temporary directory stands in, so tests never touch the real settings. Every CLI command except `install`, `install-native` and `uninstall-native` starts the daemon when it is not running; `--no-auto-start` makes it fail with `daemon_unreachable` instead. `--port N` (or `FAI_DAEMON_PORT`) selects the daemon port everywhere; a port other than 4318 also needs `host_permissions` in `extension/manifest.json` for the HTTP fallback (the native host tells the extension the port). `fai-browser serve` is a deprecated alias for `daemon`.

A tab request (`POST /v1/requests`) may carry `url`, the page the extension opens when the user approves: an http(s) URL on one of its `origins` (at most 2048 characters; off the origins is `422 origin_not_granted`). Without it the daemon uses the first exact origin's root, else `https://<root>/` for a request with only domain roots (the site may redirect that apex to www). Every request view (`GET /v1/requests`, `/v1/wait`, the extension's request list) has `url`. The same client instance (the whole `X-Fai-Client` header, `<name>/<instance id>`: one MCP server, SDK client or CLI run) repeating an identical request (same origins, `mode`, `reason`, `instruction`, `url`, `ttlMs` and `browser`, pinned or not) while its earlier one still waits for the user and has not expired gets that pending request back (`200`, `repeated: true`) instead of a second request, task tab and request window. Another instance (another agent session, a second CLI `request-tab` run, a client without an instance id), or the same instance under another `X-Fai-Session` owner session, always gets a request of its own. The MCP server fills it from the first `allowedUrls` entry on the origins, else the first URL the task names after a navigation verb ("Open https://...") on the origins; the CLI does the same from `--origin` and `--instruction` (it has no `--url` flag).

A paused request nobody is expected to continue is `stale` in its view (status, `wait`, the extension's list): `newer_request` when the agent that made it (the same `X-Fai-Session` owner session, else the same client instance) has asked for another tab since (a newer request that ended without ever being approved, denied, cancelled or expired, does not count), or `idle` when no live agent session owns it and nothing used it for 5 minutes since it paused (`STALE_IDLE_MS`; a CLI `wait` counts as use). A paused view also has `pausedAt`. Stale requests stay resumable and releasable, but the popup folds them under **Older paused tasks** and does not count them in its `Ⅱ` badge, and `fai_browser_status` lists them (`stale (newer_request)`) and its `next.text` names this session's own for release (a paused relay for a stale request tells the user to unfold Older paused tasks); a paused invited tab is never stale while its invite is open (`fai_browser_release`). Approving the newer request in the same browser releases a stale one anyway (one lease per browser).

### Approval events

Every approval surface the extension shows and every approval attempt that fails leaves one `approval` line in `daemon.log` (and no `hub_event` line besides), so an Approve that did nothing can be traced: `{"event":"approval","requestId","surface","step","reason","origin","browserId"}`. Codes only: no URL beyond the origin, no page text, nothing the user typed; the daemon drops a field that is not a plain code, request id or origin (`approvalEvent` in `src/bridge.js`). The extension sends them as `approval` messages (WebSocket, or `POST /approval` on the HTTP fallback), best effort; while it is not connected the newest 20 wait and go out after the next hello. A refusal that repeats without a new click (the modal preparing its approval again) is logged once per request, surface and reason.

| Field | Values |
|---|---|
| `surface` | `page_modal` (the request modal, `arm.html`), `toolbar` (the icon click on an armed tab), `popup` (the toolbar popup), `window` (the approval window) |
| `step` | `shown` (the modal rendered the request; the popup or window opened with it waiting), `attempt` (an Approve, Open or icon click), `waiting` (the browser's site-access prompt has not answered after 5 s), `failed`, `approved`, `denied` (Deny or Release, with the surface it came from; `reason: ask_declined` when it declined only the agent's ask on an approved request) |
| `reason` (on `waiting` and `failed`) | `site_access_pending`, `site_access_timeout` (the click was given up after 45 s), `popup_no_outcome` (a popup or window click whose `start`/`open` never came), `ask_no_outcome` (the same for an ask card's Approve; logged only), `site_access_denied`, `site_access_request_threw`, `page_not_loaded`, `still_loading`, `moved_on_site`, `moved_away`, `page_changed`, `not_waiting`, `arm_expired`, `stale_approval`, `request_changed`, `not_confirmed`, `level_not_asked`, `testing_not_listed`, `not_http_page`, `not_connected`, `prompt_window_failed`, a daemon refusal code (`request_not_pending`, `origin_not_requested`, ...), else `error` |

A `failed` event changes how the agent is told to approve a pending request only when it says something the user can act on (`APPROVAL_REMEDIES` in `src/daemon.js`): `site_access_timeout`, `site_access_request_threw`, `page_not_loaded`, `still_loading`, `moved_on_site`, `prompt_window_failed`, `not_confirmed`, `popup_no_outcome` and `error` set `approval: "toolbar"` ("the last approval attempt in the browser did not complete, so click the FAI Browser toolbar icon on its task tab once that tab shows the site"); `site_access_denied` (the user declined the browser's prompt) sets `approval: "declined"` ("the user declined the browser's site-access prompt for it, so nothing was approved; only if they want to continue, they approve again ... and allow site access"). The request view then carries `approvalIssue {surface, reason, at, remedy}`. Any other reason (a stale approval the modal retries itself, a request that changed) is only logged. A new `attempt` or an `approved` event clears it.

### Several browsers

The extension may be paired in more than one browser at a time (say the signed Firefox add-on and an unpacked
Chromium, or two Chrome profiles), all with the same daemon and pairing secret. Each install keeps a random browser
id in its extension storage (`browserId`, created once) and sends it with every connection: the `browser` parameter
of the WebSocket URL, the `X-Fai-Browser` header of every long-poll call, and `hello.browser {product, name,
version}`. Origins and the secret are checked per connection exactly as before, and an id is bound to the extension
Origin it first came from (kept in `browsers.json` in the state directory with the browser's last use): a claim of a
known id from another Origin is refused (WebSocket close `4004`, HTTP `403 identity_refused`). The refused extension
gives up its own claim once: it creates a new id and connects again; refused a second time, it stops and its popup
says so until opened again. Status then shows `extension_identity_refused` (how many connections, and when last) for
ten minutes. The daemon remembers the 64 ids it saw most recently, dropping disconnected ones first. Extensions are
never sent another browser's id or lease: their request list marks each request `browser {product, name, mine}`,
keeps `lease` only on the browser's own requests, and lists the connected browsers as `{product, name, self}` (two
with one name read "Chrome" and "Chrome (2)"); agents see ids and leases in status.

**Legacy extensions.** The 0.5.0 Firefox add-on and older unpacked builds send no id and are known by their extension
Origin (unique per Firefox install; shared by Chromium-family browsers that load the same unpacked extension). They
connect side by side with other browsers without fighting, but see only the requests meant for them, with no **Open
here**, until they update (the next release's signed add-on carries it). Two legacy Chromium-family builds of the same
unpacked Origin still count as one browser and can replace each other; `extension_flapping` shows it.

- **Connections.** The hub keeps one connection per browser, each with its own socket or long-polls, outbox and
  liveness. A newer connection of the same browser (a restarted service worker) closes the old socket with `4003`,
  and the extension never reconnects on `4003` (until the popup opens, or after five minutes), so two copies of one
  profile swap the connection at most on each popup open or every five minutes; a superseded socket that had said
  hello and lived over 10 s adds the warning `extension_duplicate_identity`. A connection of another browser never
  closes anyone. Before 0.6 every new connection closed the previous one with `4000`, whatever the
  browser, and two paired browsers replaced each other about twice a second (issue #9); the extension now backs off
  on repeated `4000`s from such an older service (at least 4 s, then 8 and 15 s) and its popup says another browser
  keeps taking the connection. A connection only resets its backoff after lasting 10 s.
- **Which browser a request opens in.** A new tab request waits in the browser the user used FAI in most recently:
  the last approval, popup open or toolbar click there (the extension's `used` message); never used, the one connected
  last. An agent may name one: `browser` on `fai_browser_open`, `request-tab --browser` and
  `POST /v1/requests`, matched (case-insensitive) on the product the extension reports (`firefox`, `chrome`,
  `chromium`, `edge`, `brave`, `opera`, `vivaldi`), its name, or a browser id from status. A browser that is not
  connected is refused with `409 browser_not_connected`, whose message names the connected ones ("Connected: Chromium
  (chromium), Firefox (firefox)"). When a request's browser has been gone longer than the disconnect grace (3 s), a
  request nobody named moves to the one used last; one the agent named, or the user moved with Open here, waits a
  minute first (a laptop sleep or a service restart moves nothing). It then gets `browserNote` ("Firefox disconnected;
  the request now waits in Chromium."), which the agent's approval hint repeats, until the user moves or approves it;
  with no browser connected it waits for the first one. The last
  use survives a daemon restart or update (`browsers.json`).
- **Every popup lists it.** Only the browser a request waits in opens its approval window or task tab and shows the
  `?` badge. Every other connected browser's popup lists it as **In another browser** with **Open here**, which moves
  it there (the `move` message; the request then stays in that browser). Deny works from any of them.
- **Leases belong to a browser.** The approval binds the lease to the browser that approved it; every command, cancel
  and `lease_update` for it goes to that connection only, and a status or `lease_level` from another browser is
  ignored, as is a result or screenshot from a connection the command was not sent to; Release (Deny on a paused
  request) works only in the browser that holds the tab. One active lease per browser: approving a second request in
  the same browser supersedes the first there,
  while a tab in another browser keeps running. A browser that disconnects, or whose worker restarts (a hello without
  a session), pauses only its own leases (`disconnected`, `session_inactive`).
- **Where it shows.** Request views carry `browser {id, product, name}` (the browser that holds the tab, else the
  one it waits in) and `lease.browserId`; receipts' `permissions.browser` and the direct result's `granted` line name
  it. `daemon status`, the CLI `status` and `fai_browser_status` list every connected browser under
  `extension.browsers` (and every known one under `browsers`): `id`, `product`, `name`, `version` (the extension's),
  `browserVersion`, `transport`,
  `connectedAt`, `lastSeen`, `lastUsedAt`, `closesLastMinute` and its `leases`. A browser whose connection closes more
  than 8 times in a minute adds the warning `extension_flapping: <name> (<id>) lost its connection N times in 60 s`
  (and logs `extension_flapping` once), so a reconnect loop is never silent again.
- **Settings.** Each browser's popup settings stay its own: the per-request budget, "Open requested pages right away"
  and the Approve gate's asks apply to the requests that browser holds or awaits (the browser used last when a request
  has none yet), and so do its Permissions, test sites and secret redaction. Status shows the budget of the browser
  used last.

### Updates

FAI Browser tells you when a newer **tagged release** of [jedbjorn/fai-browser](https://github.com/jedbjorn/fai-browser/releases) is out and installs it only on your click or command; it never tracks `main` and never installs on its own.

```sh
node src/cli.js update --check   # look now and print the update view (installs nothing)
node src/cli.js update           # install the latest release into this git checkout
```

**The check.** The daemon asks `GET https://api.github.com/repos/jedbjorn/fai-browser/releases/latest` (GitHub leaves drafts and prereleases out; a draft, prerelease or a tag other than a plain `vX.Y.Z` counts as no release) 30 s after it starts when the last check is more than a day old, then about once a day (after a failure, again after an hour; after a rate limit, after GitHub's reset time, at most a day away; a last check dated in the future counts as due). When the release is newer than `package.json`'s version, one more GET (`/repos/jedbjorn/fai-browser/commits/<tag>`) asks which commit the tag names (always the tag itself, never the release's `target_commitish`). Both requests are plain https: `User-Agent: fai-browser-update-check`, no token, no cookie, nothing about you or your machine, `If-None-Match` with the cached ETag, a 10 s timeout, no redirects. Nothing of the answer is kept but the tag, its version, the commit and the publish time; the release notes link is built from the tag. A failure only sets `status`, and a check stopped by a daemon shutdown records nothing. The result is cached in `update-check.json` in the runtime state directory (next to `daemon.json`), so the CLI and the daemon share it. Off: `FAI_UPDATE_CHECK=0` or `"updateCheck": false` in `config.json`; under `node --test` the daemon never checks unless a test asks it to.

**Fallback: `git ls-remote`.** When the anonymous API answers 404 (a fork without releases, or a repository it cannot see), a git clone falls back to `git ls-remote --tags <remote>` on the clone's own remote that is `github.com/jedbjorn/fai-browser`, with your own git credentials (ssh agent or credential helper; FAI stores and reads no token), never prompting (`GIT_TERMINAL_PROMPT=0`, ssh in batch mode unless you configured an ssh command for git), with a 30 s timeout and the same scrubbed environment as every updater git call. Every updater git call runs in a process group of its own, and a timeout kills the whole group, so no ssh or credential helper is left behind. When the API keeps answering 404, the automatic check runs this fallback about once a day, **using your ssh agent or credential helper in the background**: an agent that confirms each use (1Password's ssh agent, `ssh-add -c`, a FIDO key that wants a touch) may then ask once a day. `FAI_UPDATE_CHECK=0` or `"updateCheck": false` in `config.json` turns the automatic check off; `node src/cli.js update --check` still checks when you run it. It takes the highest plain `vX.Y.Z` tag and, for an annotated tag, its peeled commit (`^{}`). That path cannot see drafts or prereleases, so **only final releases may get a `vX.Y.Z` tag** (prereleases use `vX.Y.Z-rc.N`, which never counts). `source` says which path found the release (`api` or `git`); the notes link is still built from the tag. A fork or a clone with no remote of that repository has no release there: `not_found` (`update` says `no_release`, exit 0), as when no tag matches. A real git failure (network, credentials, timeout) is `error` with `git_failed`.

**Where it shows.** `node src/cli.js status`, `daemon status` and `fai_browser_status` carry `update`:

| Field | Meaning |
|---|---|
| `enabled` | the automatic check is on |
| `installable` | this copy is a git clone that can update itself; false (an npm install): the popup says to update the way you installed it and shows no button |
| `source` | `api` or `git` (see above), null before a check |
| `current`, `latest`, `tag` | this version; the latest release's version and tag (null before a check or when there is none) |
| `available` | `latest` is newer than `current` |
| `notesUrl` | `https://github.com/jedbjorn/fai-browser/releases/tag/<tag>` when available |
| `checkedAt`, `status`, `error` | last answered check; `never`, `ok`, `not_found` (no published release), `error` (`network`, `timeout`, `http_<status>`, `bad_json`, `git_failed`) or `rate_limited` |
| `install` | the last install: `{state: running\|succeeded\|failed\|rolled_back\|up_to_date, from, to, at, step, error, message}`, or null |

The extension popup shows **Update available vX.Y.Z** with a **Release notes** link and an **Update** button; `fai_browser_status` adds one line telling the agent to tell you, never to update itself.

**Installing** (the popup's Update button, or `node src/cli.js update`). The popup's click reaches the daemon only over the extension's paired channel, and there is no client-API route for it, so an agent's MCP call cannot start an update; an agent with a shell can run `node src/cli.js update` like any other CLI command, the same trust the CLI already has (it could run `git pull` just as well), and every refusal below still applies. On the click the daemon starts `node src/cli.js update --tag <tag>` in its own process (the update restarts the daemon) and at once creates `update.lock` (exclusively; when another update took it in the meantime, the child just started is stopped and the click is refused with `update_running`) and a `running` install record for it, so a second click finds the update running; an updater removes the lock only while it still names its own pid. **While an update runs the daemon refuses new tab requests** (`POST /v1/requests`: 503 `update_running`, "retry in a minute") **and tab approvals** (the popup shows the same reason), since the restart would cut such a task off. A lock or running record whose process is gone is stale, and so is one whose pid now belongs to another process: on Linux the record keeps the process start time (`/proc/<pid>/stat`) and compares it; elsewhere a record older than 45 minutes counts as stale.

1. **Refusals, before anything changes** (each prints what to do instead, and the popup shows it): a tab lease is active or paused (`lease_active`); the package is not a git clone (`not_git`: an npm install updates with npm); no remote is `github.com/jedbjorn/fai-browser` (`wrong_remote`); tracked files have local modifications (`dirty`; the updater never stashes, resets or discards them); the checkout is on a branch other than `main` (`other_branch`); `main` has commits its upstream lacks (`unpushed`); another update runs (`update_running`). An error of git itself here (a corrupt index) is reported with its own reason as `failed`, "Nothing was changed".
2. `git fetch --tags <remote>`, then the tag must name the commit the release names (from the API's `/commits/<tag>`, or the `ls-remote` peeled commit) and its `package.json` must carry the release's version (`tag_mismatch`, `tag_missing`), and the checkout's commit must be inside the release (`not_fast_forward`). A checkout already at the release commit is not moved or installed again.
3. **The move.** On `main`: fast-forward `main` to the tag's commit (`git merge --ff-only`). On a detached HEAD (an earlier update or a clone of a tag): check the tag's commit out, detached. Never any other branch. When git refuses (an untracked file in the way) nothing moved: `move_failed`.
4. **Best effort:** `npm ci --include=dev --ignore-scripts` only when `package-lock.json` changed and `node_modules/` exists. The runtime has no npm dependencies, so a failure is a warning in the result and the record (run `npm ci` yourself for the development tools), never a rollback.
5. The new version's refresh, `node src/cli.js update --finish`: the native messaging host launcher and the manifests that already exist, and the skill in each user-level skill directory an earlier `install` wrote (`~/.claude/skills/fai-browser`, `~/.agents/skills/fai-browser`; symlinked or foreign skills are left alone; a project-level install is not discovered, its version marker says to re-run `install`). Settings, keys and the pairing secret are never changed, printed or asked for (the manifest names the extension ID it already names).
6. The daemon restarts and must come back with the new version. **Right before it stops the daemon the updater reads the leases again**: a tab approved in the meantime (only a race gets past the gate above) rolls the update back without stopping the daemon, so that task keeps its tab (`lease_active`, "update again when it is done"). A Chromium-family browser then reloads the extension by itself (`chrome.runtime.reload()`, once per new service version, never during a session), so `extension/` loaded unpacked runs the new files. Restart your coding agent to load the new MCP server and skill.

A failure in steps 5 and 6 rolls back: `main` goes back with `git reset --keep <previous>` (only when `main` is still at the release commit; `--keep` refuses to touch a file with local changes), a detached checkout checks the previous commit out, then the refresh runs again for the old version, and the old daemon is started again only when the update had sent it a shutdown (after a refresh failure, or a restart that stopped at the lease check, the old daemon never stopped and keeps running); `node_modules/` is left as it is. The result and the popup say `rolled_back`, or `failed` with the reason when the rollback itself failed. From the move on, the install record names the release commit and the commit before it. An update that stopped after the move (the updater killed, a failed rollback that left the release checked out, or a resume a held tab refused, which keeps its resume marker) is finished by the next `node src/cli.js update`, but only when HEAD is that recorded commit and the checkout passes the same checks as an install (a git clone of the repository, no local changes, `main` or detached): the refresh and the restart of the version on disk. Anything else takes the normal path, so a checkout that merely says the same version in `package.json` is never "finished". Every run leaves an install record (also `up_to_date` and early refusals), except while another live updater owns it.

**Secrets and environment.** The updater and everything it starts get the daemon's launch environment, without `FAI_BRIDGE_SECRET`, `FAI_CLIENT_TOKEN` or any variable whose name ends in KEY, TOKEN, SECRET, PASSWORD, PASSWD, PASSPHRASE or CREDENTIALS (`OPENAI_KEY`, `AWS_SECRET_KEY`, `SSH_PRIVATE_KEY`), and without `GIT_DIR`/`GIT_WORK_TREE`. git and npm get only an allowlist (`PATH`, home and locale, ssh agent, the credential helper's session bus, `GCM_*` and `GH_CONFIG_DIR`, proxies and CA files, git config location). The restarted daemon reads its key from `.env.local` again, so a key you removed stays removed (a key exported only in the shell that started the daemon is not carried over). Each step goes to `logs/update.log` (events, versions, step names, first lines of git errors with any credentials in a URL removed). Every git, npm and node call is `execFile` with an argument list (no shell); the only values from the network that reach one are a tag matching `^v\d+\.\d+\.\d+$` and a 40-hex commit. `update` prints one JSON line with `state` and exits 0 (`succeeded`, `up_to_date`, `no_release`) or 1 (`refused` with a `code` and `hint`, `failed`, `rolled_back`, `check_failed`). Windows is untested.

**Firefox.** The signed add-on carries `update_url` (the latest release's `updates.json`), so Firefox updates the add-on itself; the updater updates the clone and the service only. If Firefox has not picked the new version up yet, install the release's `.xpi` by hand from the Releases page. A temporary add-on loaded from `dist/firefox/` needs `npm run build:firefox` and a reload in `about:debugging` after an update.

## Coding agents (MCP and skill)

```sh
node src/cli.js install --host claude     # ./.mcp.json + ./.claude/skills/fai-browser/
node src/cli.js install --host codex      # ~/.codex/config.toml + ./.agents/skills/fai-browser/
node src/cli.js install --host opencode   # ./opencode.json + ./.opencode/plugins/fai-browser.js + ./.agents/skills/fai-browser/
```

Options: `--scope user` (Claude: prints `claude mcp remove --scope user fai-browser 2>/dev/null; claude mcp add-json --scope user fai-browser '<entry>'`, since `claude mcp add` has no flag for `alwaysLoad` and `add-json` refuses an existing entry, and installs the skill in `~/.claude/skills/`; OpenCode: `~/.config/opencode/opencode.json` and `~/.config/opencode/plugins/fai-browser.js`, always under `~/.config`: `XDG_CONFIG_HOME` and `OPENCODE_CONFIG_DIR` are not honoured; skills in `~/.agents/skills/`), `--link` (symlink the skill), `--dry-run` (print the planned writes as JSON), `--force` (replace an existing Codex entry, a foreign skill directory or a foreign `plugins/fai-browser.js`), `--command-name` (write the bare `fai-browser-mcp`) and `--always-load` (Claude only, see below). It writes absolute `node` and `src/mcp-main.js` paths because the package is not on `PATH`, and adds `FAI_HOME` as server env when set. JSON configs are merged (only the `fai-browser` entry) after a `<file>.bak-<timestamp>` copy; running it twice changes nothing. A JSONC file or a hand-written Codex entry is left alone: the snippet is printed and the command exits 2. Restart the host afterwards.

The Claude Code entry is `{"mcpServers":{"fai-browser":{"type":"stdio","command":"/abs/node","args":["/abs/src/mcp-main.js"]}}}`. Claude Code defers MCP tools behind tool search by default, which costs one extra model round trip the first time a session uses them. The server marks the tools of its loop with `_meta: {"anthropic/alwaysLoad": true}`, which Claude Code honours per tool (`fai_browser_open`, `fai_browser_act` and `fai_browser_observe`), so the loop is in the first request without any config and the rarely used tools stay behind tool search. `--always-load` adds `"alwaysLoad": true` to the entry: all seven schemas (about 2k tokens, cached, of which about 1.5k are the six rarely used tools) go into every request, and Claude Code waits for such a server at startup (up to about 5 s) instead of connecting it in the background. Use it only when choose/wait/observe paths are frequent enough that their tool-search turn matters. Both were checked against Claude Code 2.1.289: its stdio server schema accepts `alwaysLoad` ("all tools from this server are always included in the prompt and never deferred behind tool search"; `"alwaysLoad": false` defers all seven, overriding the `_meta`) and `claude mcp add-json` keeps it. In project scope a rerun with or without `--always-load` updates the entry, with a backup; in user scope the printed command removes and re-adds it. Codex (0.160) and OpenCode (1.18) have no per-server loading option, so their entries are unchanged and `--always-load` is refused for them; Codex's first-use schema load stays. The Codex block also sets `startup_timeout_sec = 20`, `tool_timeout_sec = 120` and `default_tools_approval_mode = "approve"`, which `codex exec` needs because it cannot answer approval prompts.

`fai-browser-mcp` (`src/mcp-main.js`) is a stdio MCP server (spec 2025-11-25; also answers 2025-06-18 and 2025-03-26 clients) with seven tools: `fai_browser_open`, `fai_browser_act`, `fai_browser_observe`, `fai_browser_wait`, `fai_browser_status`, `fai_browser_release` and `fai_browser_evidence`, described in [Agent direct](#agent-direct); its server instructions (about 1.65k chars, bounded by `test/agent-direct.test.js`) cover that loop, and the skill ([skills/fai-browser/SKILL.md](../skills/fai-browser/SKILL.md)) is the full guide.

**Task guides.** The skill is installed with the task sub-skills' guides, `tasks/<name>/SKILL.md` under the skill directory (today `tasks/flights/SKILL.md`: flight search, and `tasks/hotels/SKILL.md`: hotel search; in the repository `skills/fai-browser/tasks` links to [tasks/](../tasks/)), and its first lines point a host at them for such a task. A task's code, `tasks/<name>/index.js` (its question vocabulary), is reviewed code listed statically in `tasks/index.js`; it is never loaded from `FAI_HOME` or any user path.

Every call returns within 45 s (`FAI_MCP_MAX_CALL_MS`), plus up to 60 s waiting for the user's approval (`FAI_MCP_APPROVAL_WAIT_MS`); a longer act returns `state: "running"` and the agent continues with `fai_browser_wait`. MCP results have **one model-visible payload, a readable text block, and no `structuredContent`** (the tools declare no `outputSchema`; see [the host research and choice](dev/mcp-result-shape.md)). An act or observe result puts `next (<kind>)` first, then trusted lines (status, grant, ids, revision, warnings, `needs`) and everything page-derived under one "untrusted page text" heading (digest, offered actions, tabs). Status, wait, release and evidence metadata use compact `key: value` lines rather than a JSON mirror; screenshots and trace JSON remain separate content blocks.

Loop stoppers: each `requestId` has a call budget (`maxCalls` act/observe calls and `maxMs` of time; 50 calls and 1200000 ms, 20 minutes, by default). Its ceiling is the user's: the popup's **Per-request budget** fields under Advanced (see [Per-request budget](#per-request-budget)), else `"budget": {"maxCalls", "maxMs"}` in `config.json`, else the defaults. Bounds everywhere: `maxCalls` 1 to 10000, `maxMs` 1000 to 14400000 (4 hours). With nothing left, further calls return `budget_exhausted` / `task_budget` without reaching the daemon. A `select_tab` result costs nothing. No image is sent by default: `returnImages` is `"none"`; `"final"` (a screenshot of the page) is explicit, and `fai_browser_evidence` serves an act's screenshot or trace. Tools declare input schemas only, with one- or two-sentence descriptions; the loop guidance is in the server `instructions`, the rest in the skill. Task outcomes such as `needs_user` or `failed` are normal results; `isError` is reserved for bad parameters, daemon HTTP errors and an unreachable daemon. Cancelling a call stops its act. When the host closes the server, it releases the tab requests it created.

## Invites and wakes

The user can bring a connected coding agent to a tab they already have open, and FAI wakes an idle agent when the user
approves or resumes its tab. Claude Code, Codex and OpenCode (1.19 to 1.x, through FAI's plugin) can be woken; any
other host gets the copy-text fallback.

**Agent sessions.** Every `fai-browser-mcp` process registers with the daemon right after `initialize` (it never starts
the daemon: while none answers it retries every 2 to 30 s, and it registers again when a restarted daemon no longer
knows it). It reports the host (`claude`, `codex`, `opencode` or `unknown`, from the MCP client's `clientInfo.name`
first, then the environment), the host's session id when known (Claude Code's `CLAUDE_CODE_SESSION_ID`; Codex's thread
id from its first tool call; OpenCode's newest session that made a FAI call, from the plugin's tag), the repository's folder name only (`CLAUDE_PROJECT_DIR`, else the working directory;
never the path), its pid, start time, last tool call and its wake capability. The daemon answers with a session id and
a random key only that process holds; it then holds one long-poll for wakes (`POST /v1/sessions/:id/poll`, at most 25 s,
which is also its heartbeat) and leaves on stdio close (`DELETE /v1/sessions/:id`). Entries whose pid is gone or that
stopped polling for 90 s are dropped. Every session route needs the client token and the `X-Fai-Session: <id>:<key>`
header for that id, so a session only receives, and only settles, the wakes addressed to it; status and the popup list
sessions without keys (`sessions` in `GET /v1/status`, `GET /v1/sessions`). Polls are not client activity: a registered
session never keeps an idle daemon up. `FAI_MCP_REGISTRY=0` turns registration off; `FAI_WAKE=0` keeps the session
listed but never wakes it.

| Capability | When | Delivery |
|---|---|---|
| `claude-socket` | Claude Code 2.1.224+ (the token since 2.1.228) gives the server `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` (`--bare` sessions have none), and the socket is `<dir>/<pid>.sock` with the MCP server's parent pid: the variables are inherited by everything Claude Code starts, so a server started through a wrapper (npx, a shell) or by a Bash command fails closed to `none` | the MCP server writes `{"type":"auth","token":…}` and `{"type":"user","message":{"role":"user","content":<text>}}`, one line each, to that socket; an idle session takes a new turn |
| `codex-queue` | Codex 0.149+, once a tool call named the thread (`_meta["x-codex-turn-metadata"].thread_id`, a UUID) and `codex queue --help` works (`codex` from an absolute `PATH` entry or `FAI_CODEX_BIN`) | `codex queue --thread <id> --message <text>`, argv only (no shell), 15 s timeout, `codex` from `PATH` or `FAI_CODEX_BIN`, no `FAI_*` variable passed on; a busy session runs it as its next turn with its own permissions |
| `opencode-plugin` | OpenCode 1.19 to 1.x (`clientInfo.version`; 2.x has another plugin API and is refused), FAI's plugin installed (`install --host opencode`; not with `opencode --pure`), the MCP server started by OpenCode itself (`FAI_OPENCODE_WAKE_SOCKET` names `oc-<parent pid>.sock` and `OPENCODE_PID` is that same pid: a server started through a wrapper or by a bash tool fails closed), and after a FAI tool call the plugin tagged with its (root) session | the MCP server connects to the plugin's private socket and writes `{"type":"auth","token":…}` and `{"type":"wake","sessionID":"ses_…","text":<text>}`; the plugin checks the token, that the session called a FAI tool and that the text matches one of FAI's three wake templates exactly, reads the session's last user message and calls OpenCode's `client.session.promptAsync` with that one text part and that message's `agent` and `model` (with its variant; a session without one is refused, `prompt_failed`), then answers `{"ok":true}` once OpenCode accepted the prompt and reported no error before the turn started (it watches OpenCode's events for at most 2 s; a session already running a turn is not watched, since an error then belongs to that turn); a busy session runs it as its next turn |
| `none` | anything else (an unknown host, Claude Code without the socket, Codex or OpenCode before its first FAI call, OpenCode without the plugin or outside 1.19 to 1.x) | none: the popup shows the copy line |

The socket format is the one Claude Code's own debug output prints; it is undocumented and may change. Claude Code's
`crossSessionInbound` setting (`accept`, `hold`, `refuse`, also set by a repository or managed settings) decides what
an inbound message does: `hold` keeps it for the user to accept, `refuse` drops it, and a session in
`bypassPermissions` may refuse senders that are not its own children. FAI only ever writes from the MCP server, the
session's own child, and never to another session's socket. A Codex session is listed as "not ready: ask it to run any
FAI command" until its first tool call; the server instructions ask Codex to call `fai_browser_status` once early.

**OpenCode.** OpenCode's default TUI has no HTTP listener and gives an MCP server no session id, so FAI wakes it from
inside: `install --host opencode` also installs FAI's plugin (`src/opencode-plugin.js`, copied to
`.opencode/plugins/fai-browser.js`, or `~/.config/opencode/plugins/fai-browser.js` with `--scope user`). At startup the
plugin creates `$XDG_RUNTIME_DIR/fai-browser/` (else `<tmpdir>/fai-browser-<uid>/`; mode 0700, owner checked, never a
symlink), listens on `oc-<OpenCode's pid>.sock` there (mode 0600, removed on a clean exit; the plugin sets no signal handlers, so
one left by a killed OpenCode is swept when the next plugin starts) and puts the socket path and a random
32-byte token in `FAI_OPENCODE_WAKE_SOCKET` and `FAI_OPENCODE_WAKE_TOKEN`, which the MCP server OpenCode starts next
inherits. Before each FAI tool call (`<server key>_fai_browser_…`) it drops any `_faiHostSession` the model wrote,
finds the calling session's root (a subagent's task session, also a task inside a task, has a `parentID`: the call
belongs to the conversation that started it; a root it cannot tell means no tag, so no wake), records that root and
adds its id as `_faiHostSession` to the call's arguments; the MCP server removes that argument before validation for every host and
honours it only from OpenCode with the plugin channel. One MCP server serves every session of its OpenCode, so wakes are
addressed by session: Approve and Resume wake the session whose call created or joined that request (a request no
tagged call made is never promised a wake: its relay text keeps the wait command and an Approve wake fails
`unknown_session`); an invite goes to the newest session that called a FAI tool, unless two or more did within the last
10 minutes, when it fails `ambiguous_session` and the popup shows the copy line for the user to paste into the session
they mean. A wake turn runs with the agent and model of the session's last user message, never OpenCode's default
agent (a session in `plan` stays in `plan`). The plugin's `ok` means OpenCode accepted the prompt and reported no error
before the turn started (errors later in the turn are not seen), not that the model answered, so the popup says "Sent to OpenCode · repo" and keeps the copy
line under it, as for Claude Code. OpenCode lists as
"not ready: ask it to run any FAI command" until its first tagged call; the server instructions ask it to call
`fai_browser_status` once early. `FAI_WAKE=0` in OpenCode's environment also turns the plugin off.

**Wake texts.** The daemon queues fields only (`kind`, `requestId`, `inviteId`, `level`, the user's invite text); the
MCP server writes the text from fixed templates in `src/wake.js`, prefixed `[FAI Browser]`: an invite ("The user
invited you … Call fai_browser_open with {"inviteId": "inv-…"}", then the user's words on one labelled line), an
approval ("The user approved tab request req_… at level …") or a resume ("The user resumed tab request req_…"), each
naming the tool to call next. A wake never contains a page title, URL, origin
or page text. It reports `delivered` (written to the channel: Claude Code's socket answers nothing, not even to a wrong
token or a message `crossSessionInbound` holds or refuses, checked on 2.1.319, so this means sent, not received, and the
popup says "Sent to …"; anything the socket does write back is kept as the wake's `detail`; for Codex, `codex queue`
exited 0; for OpenCode, OpenCode accepted the prompt), `failed` (`no_socket`, `connect_failed`, `refused`, `timeout`,
`unknown_thread`, `no_codex`, `codex_failed`; OpenCode adds `unknown_session` and `ambiguous_session`, and a `refused`
carries the plugin's reason in its message: a wrong token, a session that never used FAI, a text that is not a FAI
wake, or OpenCode not queuing the turn) or `skipped` (a call already waiting on that request returns the page itself); a wake no
poll picks up fails after 10 s (`not_polling`), one never reported after 25 s (`no_report`).

**Invite agent.** In the toolbar popup on any normal http(s) tab, the **Invite an agent to this tab** card lists the
live sessions, most recently active first (host · repo · last active):

- one session: **Invite Claude Code · my-repo**, one tap (two clicks with opening the popup);
- several: one row per session, one tap on the row;
- none: **Invite agent** makes an invite for no session in particular and shows the copy line.

The level chips (Read, Use, Act; Test site only on an origin listed under Advanced → Test sites) default to the level
last chosen for invites, initially Use (`interactive`: clicks, fills of your values, search, filter, sort and paging
submits, as the popup's "Preselect up to" calls Use); one tap changes it. The optional "What should it do?" field is
the user's own words: it goes to the agent as a labelled line in the wake and in the join result, and only ever comes
from that input. The click is the approval: inside the gesture the popup asks for browser site access where the
browser needs it (Firefox, the exact origin), and the worker, which accepts `invite` only from `popup.html` itself
(not the approval window, a page or a content script), sends one `invite` message (`tabId`, `origin`, `level`,
`sessionId`, `text`) over its paired channel. The daemon creates a request for that tab's exact origin (never a domain
root), binds it at once as the browser's lease at the chosen level (single tab; it supersedes that browser's other
lease as any approval does: when that lease belongs to another agent session, the card first says "This will end
<host · repo>'s current tab task" and the invite needs a second tap; request views carry their `owner` session for
this), creates a single-use invite id (`inv-` and 8 characters, 10 minutes), and queues the
wake. The tab gets the usual `FAI` group mark. The card then shows "Waking …", "Sent to …. It should start in a
moment" (with "If it does not start, tell it: join FAI invite inv-…" under it: a held message shows in Claude Code
for you to accept), or, when the wake failed or the session cannot be woken, **Tell your agent: join FAI invite inv-…** with
**Copy**, and **Cancel invite** until an agent joins. No client API route creates an invite.

**Joining.** `fai_browser_open {"inviteId": "inv-…"}` calls
`POST /v1/invites/:id/join` and returns the page as usual, preceded by a trusted line naming the invite and the user's
words. Joining needs a registered session (`X-Fai-Session`; `session_required`), and an invite made for one session
only takes that one (`invite_for_another_session`, 403); one made for no session (the copy line) takes any registered
session. It is single use; the joining session owns the request from then on (it is woken on Resume and releases it
when its stdio closes). An invited tab is never a bearer handle: before the join every observe, act, run and release
is refused (`invite_not_joined`, 409), after it any caller but the owner gets `not_owner` (403); status, the request
list and `GET /v1/requests/:id` show it in full only to its addressee or owner, and to anyone else as
`{requestId, state, stateReason, invited: true}` (the CLI's `wait --until active` still works). The same owner rule
covers its runs and observes: `GET /v1/runs` and status `runs` leave them out for anyone else, and `GET /v1/runs/:id`,
`/evidence` (trace and screenshot), `/stop` and `POST /v1/wait {runId}` answer `not_owner`; the traces carry
`options.invite` and `options.ownerSession`, so this holds from disk after the request record is gone. Ordinary requests stay
open to any client-token holder, as before: the CLI and SDK drive MCP-made requests too (the resume wait command is the
CLI). `fai_browser_status` lists only the invites this session may join, and its next is the join when one is for
this session; its other nexts only ever name this session's own requests.

**Registry safety.** The MCP server's session loop connects with `autoStart: false` and `takeover: false`: it never
starts a daemon and never stops one of another version (after an update an old server would otherwise shut the new,
idle daemon down); on `version_mismatch` it waits until the server's own tool call (which may replace the daemon as any
client call does) and then registers. Every new connection (the first, and every one after `closed: true`, a 5xx such
as `503 shutting_down`, or a transport error) asks `GET /v1/health?challenge=<nonce>` without the token and checks
`proof`, an HMAC-SHA256 of `fai-health:<daemon port>:<nonce>` under the client token, before the token or the session
key is sent, so a process squatting on the port gets nothing and cannot inject wakes (a daemon without the proof, an
older one, turns invites and wakes off). The daemon hands out at most 4 wakes a poll; the server acts on each wake id
once (the last 256 remembered) and at most 12 a minute, and reports one over a cap as `failed`/`rate_limited` at once.
It reports an outcome only over the connection the wake came from, while that is still its current, verified one
(otherwise the daemon fails the wake as `no_report`). After any failed wake the server's relay texts name the
`wait --until active` command again for ten minutes, and the request view's `ownerWake` (the owner's last Approve or
Resume wake) shows the failure, which the popup turns into "Could not wake … Tell it to continue.".
A session the daemon dropped for not polling registers again with `previous: {sessionId, key}` and takes its requests
and invites back; at most two entries per pid. A server registers (up to 3 s) before it creates a request or joins an
invite, so the daemon records it as the owner; a relay `next.text` says "FAI Browser wakes this session" only for
requests whose view names this session as `owner`. An invite ends `expired` after 10 minutes (the tab is released), `revoked` when
the tab closes or leaves its origin before an agent joined, `cancelled` by the user, or replaced by a new invite on the
same tab; joining then fails with `invite_expired`, `invite_revoked`, `invite_cancelled` (or `invite_joined` when used),
and the agent should ask the user to invite it again. A browser may make 6 invites a minute (`rate_limited`).

**Approve and Resume.** A request an MCP server created carries that session as its owner. When the user approves it,
or resumes it after a pause, the daemon wakes the owner, which continues with `fai_browser_observe` without a
background command. For a session FAI can wake, the relay `next.text` of a pending or paused request says "FAI Browser
wakes this session with a message once the user has done it (no wait command needed): tell the user, then end your
turn"; without a wake capability it keeps the `wait --until active` command ([Waking the agent on Resume](#running-a-task-from-the-shell)).

## Running a task from the shell

```sh
node src/cli.js request-tab --origin https://app.example.com --reason "Check the members list"
node src/cli.js wait req_Q2x9mP0aLk3s                         # until "state":"active"
node src/cli.js wait req_Q2x9mP0aLk3s --until active --timeout 30m   # blocks until approved/resumed (exit 0)
node src/cli.js observe --request req_Q2x9mP0aLk3s            # page digest, offered actions, revision
node src/cli.js act --request req_Q2x9mP0aLk3s --action a3 --revision r_ab12
node src/cli.js act --request req_Q2x9mP0aLk3s --point 640,310 --revision r_ab12   # pixels of the observe screenshot
node src/cli.js release req_Q2x9mP0aLk3s
node src/cli.js runs --limit 5 && node src/cli.js evidence <runId> --step 2 --kind screenshot
```

**Waking the agent on Resume.** `wait <requestId> --until active [--timeout 30m]` blocks until the request's lease is usable: the user approved a pending request or clicked **Resume** on a paused one. It loops over the daemon's own long poll (`POST /v1/wait` holds each round up to 30 s while the request is `pending` or `paused`; a round that returns early is not repeated within 250 ms), so it does not busy-poll. `--timeout` takes a duration with a unit (`ms`, `s`, `m`, `h`; default `30m`, the paused-lease lifetime; at most `24h`). It never starts a daemon, not even on its first connection (`--no-auto-start` makes no difference to it): tab requests live in the daemon's memory, so a newly started daemon could not know the request. When the daemon stops answering (a restart, a reset connection, `503 shutting_down`) it retries with a 0.25 to 5 s backoff, re-reading the client token on each reconnect; after 30 s without an answer (`FAI_WAIT_DAEMON_GONE_MS`) the request is taken as gone and the wait ends as `unknown` with `reason: "daemon_gone"`, and a daemon that answers but no longer knows the request ends it as `unknown` with `reason: "unknown_request"`. It prints one JSON line on exit: `{state, requestId, until: "active", reason, lastState?, waitedMs, reconnects, request, next {kind, text}}`, where `state` is `active`, the terminal request state (`released`, `expired`, `denied`, `cancelled`; `reason` says why, e.g. `stopped`, `superseded`, `paused_timeout`), `unknown`, `timeout` (with `lastState` `pending` or `paused`) or `interrupted` (SIGINT/SIGTERM); `reconnects` counts outages it rode out. `next` is `observe` with `fai_browser_observe`. A failure (a bad flag, a refused token, an unexpected daemon answer) prints `{state: "error", requestId, until, error {code, message, hint?}, next {kind: "relay", text}}`, whose next asks the user to say when they have resumed. Exit codes: 0 active, 3 the request ended or is unknown, 2 timeout, 130 interrupted, 1 an error. `--until` takes only `active` and a requestId (not `--run`); `--max-ms` is for the one-call `wait`; `--until` and `--timeout` are refused with any other command. A session FAI can wake ([Invites and wakes](#invites-and-wakes)) is told to end its turn instead; for every other session this is the command the trusted `next.text` of a paused or pending relay names: the MCP server's absolute node path and `src/cli.js`, preceded by shell prefix assignments of the MCP server's `FAI_HOME`, `FAI_DAEMON_DIR`, `FAI_DAEMON_PORT` and `FAI_BRIDGE_PORT` when they are set (never the client token), for example `/usr/bin/node /opt/fai-browser/src/cli.js wait req_Q2x9mP0aLk3s --until active --timeout 30m`. A host that runs background commands and is notified when they exit (Claude Code's Bash `run_in_background`) starts it, unless one is already running for that request, and ends its turn, so the user's click wakes it; other hosts ask the user to say when they are done. To let Claude Code run it without a prompt, allow its prefix: `Bash(/usr/bin/node /opt/fai-browser/src/cli.js wait:*)` with your node and install paths (as `next.text` shows them); with `FAI_HOME` or another carried variable set, the command starts with that assignment, so the rule must too: `Bash(FAI_HOME=/path/to/home /usr/bin/node /opt/fai-browser/src/cli.js wait:*)`.

`act` flags: `--request`, `--revision`, `--action`, `--point X,Y`, `--open-tab URL`, `--tab tN`, `--expect-url-includes`, `--expect-text-includes`, `--expect-title-includes`, `--capture each|last|none`, `--timeout-ms`, `--release`, `--no-prune`, `--pretty`, `--port`, `--no-auto-start`. `request-tab` takes `--origin` (repeatable), `--reason`, `--mode read-only|reversible|interactive|full|testing` (the level the task needs; the user's approval in the popup caps it, see [Permission levels](#permission-levels)), `--instruction` and `--browser`.

### Output, status and exit codes

Stdout is exactly one JSON line (`--pretty` indents it). `act` prints the lean agent result (the daemon/CLI object, which MCP renders as readable summary text rather than duplicating in `structuredContent`): `v`, `runId`, `status`, `code`, `reason`, `needs {who, message, level?}` (only when someone must act; `level` when re-approving the tab at that level would let the task go on), `verification {checked, passed, expectation}`, `page {url, title, digest, truncated}` (`digest` is a list of block texts; `textExcerpt` only when the digest is empty), `answer {method, candidates[{text, confidence, state?}], source?, aggregate?}` (top three; see [Fact memory](#fact-memory-and-aggregation)), `trail [{url, state, lines}]` (relevant lines of earlier page states in a multi-hop run, same-URL states included), `steps [{i, action {type, label, toUrl}, class?, confidence, ms}]` (`class: "consent"` marks a cookie-dialog button the host chose, see Blocking overlays under [Policies](#policies)), `cost {decisions, inputTokens, outputTokens, elapsedMs}`, for an `act` the landing page's offer (`revision`, `actions [{id, description}]` as `observe` lists them, `moreActions`: the next `act` may name that revision with no observe in between; absent after a cross-origin landing or a refused act), `warnings` (`password_field`, `blocking_overlay` (a popup other than a cookie dialog covers the page), `browser_error_page` (the tab shows the browser's own error page, see `error_page` below), `expectation_weak`, `expectation_prepassing` (see below), `controls_capped:<n>` ([Offered actions](#offered-actions)), `cross_origin_frame`, `unreadable_region:<kind>` (the page holds a region only as pixels or a derived view had to cut it: `chart` values only as bar geometry, `canvas`, a chart-like `image` with alt text only, a `table` over the text budget; the trace's observation lists each region's label, reason and bounds); MCP adds details after a colon), `permissions {requested, granted, effective, testing, scope}` (the level the agent asked for, the user's grant for the tab, null before approval, the level the run used, and `scope`: `origin` or `domain`, what the approved tab covers, see [Domain roots](#domain-roots); absent before approval), `lease {requestId, state}` and `trace`. Results are receipt v2 (`v: 2`): `verdict {kind, oversight, answer, why, budget}` (kind `verified|likely|needs_decision|needs_user|failed`; `answer.candidates` are ranked by a local heuristic and are never auto-confirmed, so `verdict.answer` is normally null: the auto-confirm rule takes a ranked candidate that is at least 0.8, has the question's shape (price: a currency amount, count: a digit, hours: a time of day, quantity (what share, how long, how often): a number or a frequency word), is not a navigation trail ("Home › Guides › Backups"), leads the runner-up by 0.5, and the question is not a list, Nth-item or late-load question (for an aggregating question, also only when the top candidate is the aggregation's unique first item over items the run fully read); `why` is machine codes) and `next {kind, text}` with `kind` one of `answer`, `choose`, `observe`, `relay`, `approve`, `stop` (MCP adds `wait` for an act that is still running). Per-step observations, screenshots, probabilities and control bounds stay in `trace.json` (and behind `evidence`). `observe` prints `{revision, page {url, title, digest}, actions [{id, description}], moreActions?, warnings?, consent? {text, buttons [{label, kind}]}, screenshot, trace, next {kind: "choose", text}}` (`moreActions` counts offered actions the listing left out; ids keep their offered numbers, so a gap in them shows where), MCP observe renders those fields as readable text (`consent.text` and button labels are untrusted page text). Other commands print the daemon's JSON, or `{"error":{code,message}}` with exit 1. Diagnostics go to stderr. Page-derived text appears only under `page`, `answer.candidates`, `answer.source.url`, `trail`, `steps[].action.label`, `verdict.answer.text`, `needs.dialog` and `needs.control`. `reason`, `needs.message`, `needs.level`, `permissions`, the rest of `verdict` and `next` are written by FAI Browser and can be trusted.

**Which pause, truthfully** (issue #31). `stopped` ("The user pressed Stop and released the tab") is reported only
for a request the user stopped (the extension's status `stopped` with reason `stopped`); a request ended any other
way is `request_closed` (a replaced one says another approved request replaced it). A request the user denied is
`stopped` / `denied` ("The user denied this tab request"; `next.kind: "stop"`: ask again only if the user asks), never a
technical close. When the user approves a request, or an agent joins an invited tab, the older requests that agent
still has pending in the same browser (the same owner session, else the same client instance; never an invited tab,
never a newer one) expire as `replaced` at once, so a click on one of them that arrives late (a request modal still
waiting for the browser's site-access answer) approves nothing and cannot supersede the approved one (issue #36). An
approval the extension gives back (`not_approved`) lets them wait again. A closed request names its successor only
when it is the same agent's own (`replacedBy`; `next.kind: "observe"` with that id); otherwise it says the user
approved another task in this browser (`next.kind: "stop"`). `tab_not_ready` three times in a row pauses the request as
`session_inactive` ("the browser extension no longer holds this tab"), so the user's Resume binds it again. Each pause names its cause in
`needs.message`: `tab_changed` (another tab came to the front in the task tab's window, or the task tab closed),
`origin_changed` (the tab left the approved sites; `leftOrigin`), `child_tab` (the page opened a tab or window the task
cannot follow; `childOrigin`), `session_inactive` (the extension restarted), `disconnected`, `paused` (the user's
Pause); each is resumable and says to ask the user to click Resume (and, with an origin named, how to add it to the
request). A lease code an act or observe gets from the browser (`stopped`, `paused`, a pause reason) is checked against
the request itself: the daemon waits up to 1.5 s for the extension's status report and then reports the request's own
state; a request still active was not paused or stopped at all (a command that reached the browser while it was still
switching to a newly approved tab), which is `needs_host` / `tab_not_ready` with `next.kind: "observe"`. The worker
also lets a command for a lease it is still binding wait for it (up to 5 s) and answers one for a lease it does not
hold `session_inactive`, never with another session's state. An approval the worker gives back right after making it
(its own last check of the tab failed, or a Test site lease bound to an unlisted origin) is status `stopped` with
reason `not_approved`: the daemon restores the request (pending again with the same id, or the earlier grant of an
active lease), never "stopped by the user".

A request paused as `origin_changed` because the tab went to an origin the request does not list names that origin
when the browser showed it: `leftOrigin` in the request view (status, `wait`) and in the paused result, shown with
the untrusted page text (a page decides where it sends the tab). `needs.message` only says that it went to an origin
the request does not list and where to find it. It is the origin only, never the path or query, redacted like any
reported URL; with a toolbar approval the browser often withholds the URL and nothing is
named. Ask the user and request that origin up front next time (a sign-in hop through another host, for example).

`wait <requestId> --until active` has its own exit codes (see [Waking the agent on Resume](#running-a-task-from-the-shell)): 0 active, 2 timeout, 3 ended or unknown, 130 interrupted, 1 error. Other commands exit 0 on success and 1 on an error.

`refused_action`: the instruction itself asks to buy, order, pay, delete, remove, send, submit or log in (an imperative clause that starts with the verb, in its dangerous sense: "remove the filter", "submit a search" and "send me the list" do not count) and the only page controls for it are ones the approved level refuses (refused filter chips and search buttons do not count). Nothing runs; the act ends in one of three ways. A purchase below `testing` stops: verdict `failed`, `next {kind: "stop", text: "FAI never purchases outside testing mode. Tell the user what to do in the tab."}`. A control the user's `forbid` additions reserve, or one no level allows, stops the same way with its own text. Anything a higher level would allow (a submit at `reversible`, a sign-in below `testing`) is a level request: `needs.level` names the lowest level that allows it, `needs.message` says "The user approved Use (no submit) for this tab; this task needs Act. Ask them to approve the new request at Act in FAI Browser (it is preselected).", the verdict is `needs_user` and `next.kind` is `relay` (call `fai_browser_open` again with the `requestId` and `mode` set to `needs.level`; the MCP server asks for that level on the same request, which keeps its tab, page and tab mode: [More on the same request](#more-on-the-same-request)); when the user's grant already covers it (the host asked for a lower `mode` itself) `needs.who` is `host` and `next.kind` is `observe` (observe again with that `mode`). `why` has `refused:<intent>` and, for a level request, `level:<needed>`. `error_page`: the run landed on a 404, 410, 500, 502, 503 or 504 page (the document's HTTP status from Navigation Timing, an error title or first heading such as "Page not found" or "Internal Server Error", or, only when the HTTP status is unknown, a tiny page whose first line is an error line; body text that merely mentions a status never counts, and "HTTP 404" titles count only without a successful status); it ends before any further decision with verdict `failed` and `next.kind: "stop"` naming the status (`why` has `http:<status>`). A host that asked for that page (its expectation passes there, "read the error reference the Billing page shows") is not stopped; `why` still notes `http:<status>`. The browser's own error page (below) is never exempt: it keeps the URL the tab tried and a fixed text, so an expectation that matches it is not a verified outcome (`verification.passed` is false). The browser's own error page counts too: for an HTTP error sent without a page body (an empty 500, for example) and for a refused or dropped connection, Chrome shows `chrome-error://chromewebdata/` while the tab keeps the URL it tried, and no extension script runs there. The extension reports it as an observation of that URL with `browserErrorPage: true`, no controls, a fixed text and the warning `browser_error_page`; the status is unknown, so `why` has `http:error` and `error_source:browser`, and `next.text` says the tab stays approved and can be reloaded later. The session stays active (it used to pause as `origin_changed`, or fail as `unsupported`): a page action on that page fails with `target_unavailable` (recoverable), while a history move (`nav: "reload"`, back, forward) and an approved `url` still run. In Agent direct an `observe` of it returns the page with the `browser_error_page` warning (no controls, no scroll actions), while an `act` that lands on it ends `error_page` (`next.kind: "stop"`) before any expectation is checked and keeps the page's offer for a later reload; an ordinary error page with a body is still read by the host. With a toolbar (activeTab) approval only, Chrome withdraws access when its error page commits: the URL is withheld and nothing can be read, so that session pauses as `origin_changed` (approve again once the site is back); approval in the request modal (browser site access for the exact host) keeps the session. Firefox's network error pages (`about:neterror`) are not handled and may still pause as `origin_changed`.

**Verification.** An act with an `expectation` is `completed` only when the expectation passes on the settled landing page; the host's own judgement is never a verified result. **Missed text.** When a run ends unverified (any status but `completed`) and the expectation's `textIncludes` or `titleIncludes` is not on the final page, `verification.hint` says what the page has instead, and `next.text` repeats it (not for an `answer`, `stop`, `relay` or `approve` next): `expected text "Departing flights" not found; the page has "Top flights", "Other departing flights" (quoted page text, untrusted)`, up to five of the page's headings and short prominent strings (blocks of at most six words: tabs, buttons, short lines) ranked by word overlap with the expected text (headings first, then page order; with fewer than three sharing a word, the first headings fill in), or for a title, the page's title; each page string is quoted, cut to 60 characters and stripped of control and format characters, and `verdict.why` gets `expectation:text_missing`. A host that guessed the page's wording ("Departing flights" where the live page said "Top flights") corrects its expectation from it. Declarative fields are `urlEquals`, `urlIncludes`, `urlMatches` (regex), `textIncludes`, `textAbsent`, `titleEquals`, `titleIncludes` and `changedSinceStart`. `textIncludes`, `textAbsent` and `titleIncludes` ignore case, and every field you supply must match. `textIncludes` and `textAbsent` are substrings of the observed visible text, in which the fields of one list row are joined with " · ", the cells of one table row with " | ", and a grid with row and column headers reads "Oct 10 × Oct 17: €312" (lines that used to be separate are joined this way, never text that used to be one line); write one field's text ("€121", "Air France"), not text spanning fields. `textIncludes` also passes on text the page renders outside the viewport: each observe sends it to the page script (`expectText`), which looks for it in the whole document's rendered text when the viewport text lacks it and lists what it found in the observation's `textFound`, so a run that scrolled below "departing 2026-10-12" (a "View more flights" click) still verifies; hidden text never counts there (display or visibility hidden, `aria-hidden="true"`, a screen-reader-only clip or a box of 1px or less, a zero-size box that clips its overflow). `textAbsent` reads only the viewport text, so an off-screen "Loading more" row does not hold a finished page back.

### Fact memory and aggregation

A long single run (12-15 hops in one call) often reads its answer on an earlier page state: a flight on Thursday's list when the run ends on Sunday, the cheapest tent on page 11 of 13, a token in a log panel of a single-page app whose URL never changes. With a question (`answerQuestion`, else the instruction), the runtime keeps a **fact memory** of every page state the run saw (`src/facts.js`): one state per semantic revision in first-seen order (so same-URL states count), each with at most 6 lines that match the question (page blocks, never generated, supplied values redacted; aggregation items come on top, see below), at most 12 lines per state seen and never fewer than 80 nor more than 400 in the run, a line seen in an earlier state not repeated. A line under a section heading (h2-h4) reads `<heading> › <line>` ("All 8 departures on Thu 15 Oct › 10:55 Vueling VY 7713 … €61").

- **`trail`** is the memory's lines of the states before the final one, grouped by state in run order: `[{url, state, lines}]`, at most 3 lines per state, 12 states (the most relevant when there are more) and 40 lines; lines the final page still shows are left out (`page.digest` has them). With an aggregating question a state shows its items first, then its other lines while it has room, except lines with a value of the aggregated measure that are not items (a decoy's price). Untrusted page text.
- **Answer candidates.** The final page's blocks as before; for a task that is not a join (`isJoinTask`: there the earlier fact is context, not the answer) and whose final page is weakly relevant (its best block scores under half the best remembered line), up to 8 remembered lines that outscore it go first. `choose()` gets at most 24 candidates and the most recent 4 trail states (lines that are not already candidates) as `earlierPages` (on a run that never left the final page's URL, only lines that state a fact, with a digit, a "label: value" or a name; a prompt such as "Select a region to see the shipping cost." is left out, and with no line left `earlierPages` is not sent). A candidate read on an earlier state has `state` in `answer.candidates[]`, and `answer.source {state, url}` names where the top one was read; `verdict.why` adds `answer:from_state:<n>`. The auto-confirm rule is unchanged.
- **Records.** The page script detects repeated records by structure, never by site (`detectRecords` in extension/page.js): sibling subtrees with the same tag, role and descendant shape (at least 3), or the same template under sibling wrappers that hold nothing else (a grid split into rows), scored as a list from several text boxes per member, a link or heading, prices, ratings and numbers (a shared class token is a weak bonus). Navigation, banner and footer landmarks, menus, tab lists, toolbars, dialogs, a blocking overlay's content, hubs of plain links (footer columns) and filter panels (two or more checkboxes, radios or sliders per member) are never records. Members are compared by their value skeleton too: a sibling with other markup that has the name, price and rating the similar members have is a member (badges, extra wrappers), and a same-tag sibling with no name, or none of their values, is an insert (a notice, a promo) and left out. When one group's members contain another, the inner one wins only when it spreads over two or more of them and holds most of their text with two or more members each (sections of cards, rows of tiles); a group of whole records (a name and a price or rating each) inside one member is a module of its own (a strip of other offers between the cards) and that member leaves the outer list; any other inner group is a record's parts (its name, score, room and price boxes) and the outer list wins. The page's main results rank first: among the lists scoring at least a quarter of the best, a carousel (a strip that scrolls or snaps on the x axis, or one row wider than the viewport) ranks after every other list, then the lists inside `main` and after the result-count line ("8 properties found", not a filter option's count; else after the h1), then the score. The best list and at most two more are sent as `records` (at most 60, from the whole list, not only the viewport): `{id, list, title, href?, ref?, fields, hints?, sponsored?, unavailable?, offscreen?, struck?, blocks}`, the title being the first heading or the main link, the fields the record's visible texts in order (screen-reader-only text only with a digit, struck-through prices dropped, a rating held in an aria-label or alt kept, template text most records repeat without a digit such as "See availability" dropped, at most 300 characters), the hints `price`, `prices` (when several differ), `rating` and `scale` (the rating stated nearest the review count, so a guest score beats a star class), `ratings` (every distinct one, when several), `reviews`, `when` and `counts`; `recordLists [{list, total, kept, main?, afterCount?, carousel?}]` and `recordsTruncated` say whether the list was cut and where each list sits (inside `main`, after the result-count line, a carousel; each flag only when true). Explicit page-level state goes in `recordState`: the global `resultCount` (with `approximate` for a count ending in +), `sort` only from a named sort select or `aria-sort`, and `pagination` only from a pagination landmark or `rel=next/prev` (current/total pages when stated, previous/next control refs when offered). A generic Next button elsewhere is not pagination and filters or ordering are never inferred. Agent direct projects list 0 as `page.results`: at most 600 characters of rows, chosen by task relevance and returned in document order, with their title, typed date/price/rating/reviews when known, only the remaining context `fields`, flags and an `open` action id when its title link was listed. `shown` is the projected count and `total` the detected rows on this page; `resultCount`, `sort`, `pagination`, `truncated` and `complete` retain the accuracy metadata. `complete` is false for a cut or projected list, either pagination direction, an approximate count, or an exact global count that differs from the detected primary-list total. Omitted rows remain in the direct digest, and only projected rows are replaced there and in text rendering. Two records never share a line of the visible text, and over the 200-block cap the blocks inside a record after its first are dropped first. In the core (`recordsOf`, `blocksOf` in src/digest.js) a list of at least 3 records replaces its blocks with one `li` block per record ("<title> · <field> · ..."; a record that already is one row block keeps that row when it holds every field with a number), so the digest, the candidates, the fact memory and the aggregation read a card as one item. Records aggregate on the final page alone too, the main list first: when the main list has items for a question that ranks or bounds a value (cheapest, rated 8 or more) only they count, else the other lists' records, else the blocks (a carousel of cheaper extras never answers a question about the results). The main list is list 0 (the page script's best); a rating bound above 5 reads a rating on a scale above 5 (a 5-point rating neither passes nor fails it), and a record line is remembered whole (300 characters); a sold-out record is no price item, a titled record is never `unnamed_item` or `decoy_name`, and a cut list adds `records_cut` to `partial`. Without records everything is as before.
- **Aggregation.** A question that asks for an extremum (cheapest, least expensive, most expensive, earliest, latest, lowest, highest, most, fewest, ...) or a filter (`between 10:00 and 12:00`, `before 2 pm`, `under €50`, `in stock`/`available`, a rating bound such as `a rating of 8 or more`, `rated 8+`, `4 stars or more`, `a score above 8`) has a measure: a price (the line's first currency amount: symbols and codes, thousands separators, `€1.299,50` and `$1,299.50`), a time (the first 24 h or 12 h time) a rating ("highest rated": "Scored 7.8", "4.5 out of 5 stars", "8.4/10", "8.7 Excellent", never a review count) or a count (a line's only number, else the one next to a question word). Items are remembered lines with the measure's value that pass the filters (a time inside the window, a price inside the bound, not out of stock or sold out); when an item has a whole table cell made of the question's item words (the `Tents` category column for "which tent"), only such items count (an accessory row is not a tent). Each state then keeps its items first (up to 30; the final page's own state keeps all of them, its observation being in hand) and at most 2 other lines, and its trail entry shows the items only. "Before noon", "midday", "midnight" and "morning" are time windows. When items come from two or more states, the 5 first in order (lowest first for a minimum) lead the candidates, and `answer.aggregate {op: min|max|filter, measure, items, states, partial, why?, tie?}` (trusted) summarizes it, with `verdict.why` `aggregate:<op>_<measure>:<items>`. `partial` (why `pages_unread`: a "Page X of Y" was not seen for every X; `more_unread`: a "showing X of Y" state was not followed by a fuller one; `more_offered`: the final state offers next page, load more or show more; `memory_full`: items fell off the memory bounds; `not_verified`: the run did not complete verified; and when every item was read but the order may still be wrong: `ambiguous_value`, an item line with several different amounts (a range, a struck-through old price, per person next to total), a number split by a plain space ("1 299 €"), several times when the question does not say departure or start, or a next-day marker; `approximate_value`, "from €94" or "€94+"; `stock_unknown`, the question asks for stock and the line says neither in stock nor sold out; `unnamed_item`, a short label and a value without the question's item word ("Shipping €4.99"); `decoy_name`, the item word is in the name but not as its last word ("Tent pegs" for "which tent"); `mixed_currency`; `mixed_units` (per person against total, per night, ...); `planted_text`, an item line that addresses an agent or asserts the answer) adds `aggregate:partial:<why>`. A time window that wraps midnight ("between 22:00 and 02:00") keeps the times on both sides and orders after-midnight times last. Items read on one earlier state only (the run then moved on) are aggregated too; when the question aggregates but its items are all on the final page, an earlier-state line is never auto-confirmed (`answer:aggregate_disagrees`). A remembered line that addresses an agent or asserts the answer ("the answer is ...") stays trail context and is never an answer candidate. `verdict.answer` is set for an aggregation only when the items were fully read, the first value is unique, the question is not a filter, and the usual rule confirms a top candidate that is the aggregation's first item; otherwise `verdict.why` names `answer:aggregate_partial`, `answer:aggregate_tie`, `answer:aggregate_filter` or `answer:aggregate_disagrees`. For a "which ..." question the confirmed answer is the whole item line (`exact: false`).
- **Answer scope (one page's question).** The answer candidates and the aggregation come from the states that belong to the question's page; the trail keeps every state. (1) A state followed by another of the same page with no action in between (a first paint, a loading placeholder, a late re-render) is superseded by it when it has at least as many text lines (`answerDetail.scope.collapsed`); a later revision that lost lines (a transient re-render, a skeleton after the rows) supersedes nothing. (2) A results page's day is its own sentence ("departing 2026-10-13", "Departures on Tue 13 Oct"), else a single date in its title, else a single date in its URL, as text or base64 inside a query value (Google Flights' `tfs`). Unless the question or the instruction spans days (two or more dates, a range such as "Oct 12-13", "12 or 13 October", "from the 12th to the 13th", "Monday or Tuesday", "which day", "any day", "each", "every", "week", "days", "across", ...; a time range such as "10:00 and 12:00" is not one), the target day is the one the question names, else the one the instruction names, else the final page's own sentence (never its title or URL date: a publication date or a tracking parameter is not the data's day); states keyed to another day are not candidates (`verdict.why` `answer:scoped_out:<n>`). Nothing is excluded when no state is keyed to the target day; when some state is keyed to another day, the answer is about a day the run never showed and is not auto-confirmed (`answer:scope_mismatch`, `answerDetail.scope.mismatch`). Pages without a date key are never scoped.
- **Action-only calls.** A run (or list step) is auto-confirmed only when it asks something: it carries an `answerQuestion`, or its instruction, with quoted labels ('…', "…", curly quotes, backticks, […]), URLs, an unquoted label that ends in "?" mid-sentence ("the Where to? field") and "then what?" left out, has a question mark, a wh-word (what, which, who, whose, how many, how much, ...) or a read verb (read, report, tell, extract, look up, show me, give me, find out; list, count or copy the ...; compare the ...; check, see, verify or confirm whether/if; check or confirm the <fact> such as a date, price or total). "get", "note" and "find" ask only with a fact as object: "get the phone number", "note the order number", "find the cheapest fare" ask; "get to Settings", "note: do not book", "find the Search box and click it" do not. An instruction that only performs actions ("Click Where to, type London and choose London, United Kingdom") keeps its ranked `answer.candidates`, gets no `verdict.answer` (`verdict.why` `answer:not_asked`), and `next` is what it is without an answer (a verified outcome is reported, never "your answer is verdict.answer.text"). Instruction-only reads ("Open the pricing page and tell me the Pro price") are unchanged.
- **No progress.** A step's `changed` is true when the URL or revision moved, or when its `moved` names content (title, blocks or controls; a revision-only `moved` does not count, nor a blocks-only `moved` under an unchanged revision that only replaced blocks one for one, such as a ticking live-region clock or a rotating ad; an off-screen append that adds blocks does count). Three consecutive actions that changed nothing end the run `needs_host` / `no_progress`, and so does the first repeat of a click that changed nothing (same page URL, target and label as the previous no-change click; `why` `no_progress:repeat`).
- **Fills the field did not keep.** After a `fill_supplied_text` the page script reads the field back once the page has settled (so a framework's re-render after the input event counts) and reports `fill: {kept, empty}`: `kept` when the field's value contains the supplied text with whitespace collapsed and case ignored, the same digits for a text of digits and separators (a field that formats numbers), or the same date in another form for an ISO date (`2027-01-12` shown as `12/01/2027`, `Jan 12, 2027`, `12 January 2027`, `Tue, Jan 12`, ...); the value itself never leaves the page. A bridge that reports nothing (an older extension) is read on the next observation's `filled` flag instead: a field left empty did not keep it. A fill not kept (a date picker's textbox that reverts or ignores typed text: Google Flights' Departure) is no progress (`changed` false) and no success, whatever the expectation says of the page: the run (or the `act`) ends `needs_host` / `fill_not_kept` right there, with `why` `fill:not_kept`, the step's `fill: {kept: false, empty}` in the trace and `fill: "not_kept"` on the lean step, and `next` (`observe`) names the field by its supplied-text name and says to set the value another way (a URL in `allowedUrls` that carries it, or the page's own picker or control), never to fill it again.
- **Multi-part question.** An `answerQuestion` that asks for two things (`isMultiPart`: a second wh-clause after `and`, `as well as`, `plus`, `along with` or `; `, two question marks, or two question nouns joined, as in "name and email"; `and` inside a noun phrase such as "the sales and support office" is one question; in an instruction only its question sentences count) is auto-confirmed only when the top line carries both parts, and then the line is kept whole instead of cut to one value: a byline ("<Title> by <Name>") for a question about a person and a work (`value:byline_whole`), an aggregation's item line, or a line where the asked price (count, hours) sits beside other text (`value:multi_part_line`, `exact: false` for a compound row). Any other top line is `answer:multi_part` and the host reads `page.digest`. FAI never joins two lines into one answer.

### Screenshots

`capture: "last"` is the default (CLI, SDK, daemon and MCP): every action runs without capture and only the final step is screenshotted, once, when the run ends, as a downscaled annotated JPEG (quality 70, at most 1280 px wide). `fai_browser_evidence` and `returnImages: "final"` serve that image. `capture: "each"` screenshots every action; the capture runs after the observation returns, but Chrome's `captureVisibleTab` quota caps the extension at one screenshot per 500 ms, so `each` cannot go faster than about 0.5 s per step. Ask for it explicitly when you need intermediate screenshots; an MCP `returnImages: "all"` without `capture` implies it. `none` captures nothing. `last` and `none` run at roughly 160 ms per step. An act that is stopped or cancelled with `last` has no screenshot; one that ran out of time still captures its final step, with a 1 s cap. Keep the selected tab active and visible.

**Badges.** Every screenshot boxes the controls in the frame. An `observe` capture (and an act's final capture, whose landing page is remembered for the next `act`) badges each in-view offered control with its **action id** (`a12`; a select or a field with several offered actions reads `a3–a5`, or `a3 +2` when the ids are not consecutive), only offered controls are boxed, badges move out of each other's way (left of the box, above, below, inside its corner, to its right), and the footer reads `tags: action ids (<n> in view)`. The daemon sends the extension the offer's ids with the revision they belong to; a frame of another revision (the page changed by itself) keeps the control refs, as a per-action capture of a run does (`boxes: ... refs`). Off-screen offered controls are not drawn. The `observe` result says what the image is: `image {revision, width, height, tags}` (`tags` is `actionIds` or `refs`; MCP also prints `image: revision ..., 1280x800 px; badges are action ids for fai_browser_act`), and a run or act result with `returnImages` lists `images [{step, revision, width, height, tags}]`; the trace's `screenshot.tags` holds each badge (`id`, `ref`, `x`, `y`, `width`, `height` in image pixels). `evidence` reports `revision` and `tags` too. Those pixels are the coordinates a [point click](#point-clicks) takes.

### Traces and retention

Each run (and each observe) writes `artifacts/<id>/trace.json` plus one image file per captured step. With a question, the trace's `facts` is the run's [fact memory](#fact-memory-and-aggregation): `[{state, step, url, title, revision, lines [{text, context?, score, t, item?, value?}]}]` (at most 40 states, supplied values redacted), and `answerDetail.aggregate` the aggregation (op, measure, item count, states, top values, `partial` and why). Without `--output-dir`, `artifacts/` is in the state directory (see [The daemon](#the-daemon)) or `$FAI_HOME`. The trace holds the result, the instruction, the options with credentials removed, timestamps, host versions and per-step observations without control bounds. It never embeds base64. Form fills are recorded by `suppliedName` only: the value you supplied is never written. Password values filled at `testing` are also replaced with `[redacted]` wherever the page echoed them (see [Permission levels](#permission-levels)). Supplied values of **4 or more characters** that the page echoes back (also URL-encoded) are replaced with `[supplied:<name>]`; shorter values are not redacted, so never pass short secrets. Page text in traces can still be sensitive, so treat traces as local task records. `readRun(path)` loads a trace.

After each write the daemon prunes the oldest runs (observes count too) until at most **50 runs, 500 MB and 7 days** remain. It never deletes the run it just wrote, and it only touches directories that contain a `trace.json`. Change the limits with `"retention": {"maxRuns", "maxBytes", "maxAgeMs"}` in `config.json` or `FAI_RETENTION_MAX_RUNS|BYTES|AGE_MS`, or skip pruning per run with `--no-prune`.

The extension's Pause pauses the lease and ends the current run as `needs_user`/`paused`; the user presses **Resume on this tab** and the agent continues (FAI wakes a Claude Code, Codex or OpenCode session on the click, see [Invites and wakes](#invites-and-wakes); otherwise its `next.text` names the background `wait --until active` command that does). Stop ends the run as `stopped` and releases the tab.

## SDK

```js
import { FaiBrowserClient } from './src/client.js';

const client = await FaiBrowserClient.connect({ clientName: 'my-script' }); // auto-starts the daemon
const { requestId } = await client.requestTab({ origins: ['https://example.com'], reason: 'Check About' });
await client.waitForTab(requestId, { timeoutMs: 120_000 }); // the user approves the tab in the extension
const page = await client.observe({ requestId, instruction: 'Open About' }); // digest, offered actions, revision
const about = page.actions.find(action => action.description.includes('About'));
const { result } = await client.act({ requestId, actionId: about.id, revision: page.revision, expectation: { urlIncludes: '/about' } });
console.log(result.status, result.verification.passed, result.page.digest);
await client.release(requestId);
```

`BrowserRuntime` and `createHub` stay exported for in-process use with your own bridge (`observe()`/`act()` for host-driven control, `act({ point })` on a bridge with `locate()` for a [point click](#point-clicks), tests). The standalone harness companion the benchmarks and smoke tests use lives in `bench/companion.js` and is not part of the package API. `writeRun`, `readRun`, `toAgentResult` and `prune` are exported for tooling. Types are in `src/index.d.ts`.

## Policies

Mechanical oversight runs on every page; nothing on it is clicked automatically. Sign-in controls and password fills are never offered below `testing` (FAI Browser never logs in outside testing mode; a password field alone is only a `password_field` warning), so on a login wall the user signs in. A cookie dialog (English, German, French, Spanish, Italian, Portuguese or Dutch labels: "Alle ablehnen", "Nur notwendige", "Tout refuser", "Continuer sans accepter", "Rechazar", "Solo necesarias", "Rifiuta", "Rejeitar", "Weigeren", "Alleen noodzakelijk") is reported as the observation's `consent {text, buttons [{label, kind}]}`, and from `reversible` its reject or necessary-only buttons are offered as actions (always listed): the host clicks the offered reject button; at `read-only` nothing on it is offered, so a read-only task that meets a dialog asks for `reversible` (needs.level). Below `full` accept buttons are never offered; at `full` and `testing` they are offered (an accept label that commits, such as "Accept and subscribe", never is). A whole-page consent wall on a `consent.*` host (consent.google.com, consent.youtube.com, "Before you continue") is a consent dialog too; when the request lists both origins the extension follows its redirect back to the `continue` URL after the host's reject click (one hop per session, only from a `consent.*` host and only to an origin of the same request). A page on an origin the request does not cover is `cross_origin`, naming the origin (for Google properties request `https://www.google.com` and `https://consent.google.com`; a consent host is always requested exactly); when it is a sibling subdomain of an approved https origin, `needs.message` suggests the [domain root](#domain-roots) instead. An act that comes back `stale` (the page changed after it was observed) re-observes once and runs the same control when exactly one action offered on the fresh page matches it (`decision.reason: "stale_reresolve"`, `why` `act:stale_reresolve`); otherwise it stays `stale` and the host observes again.

**Blocking overlays.** The page script looks for any other popup over the page (extension/page.js `detectOverlay`). Signals: an open dialog (`role="dialog"` or `alertdialog`, `aria-modal`, `<dialog open>`), a fixed or high z-index layer hit-tested under the viewport centre that lies over page content (an app shell fixed to the viewport is the page, not an overlay), a separate full-viewport backdrop, main content made `inert` or `aria-hidden`, and a fixed bottom sheet. It classifies it by its own text and controls: a nag (`sign_in`, `newsletter`, `promo`, `app`, `permission`), an `age_gate`, a `task` dialog (a form, a picker grid, a confirmation such as "Are you sure") or `unknown`, and reports it as the observation's `overlay {kind, nag, text, signals, closers, escape, backdrop}` with the warning `blocking_overlay` (not for a task dialog). Nothing is dismissed automatically: the host closes a popup with its offered close control (or a `key: "Escape"` act). Controls and blocks inside an overlay that is not a task dialog carry `overlay: true`: they are offered after the main content's controls, described as inside a popup, and ranked at half weight in the digest. The pattern corpus in fixtures/patterns/ (test/patterns.test.js) holds one page per common popup shape.

`read-only` (the default) offers clicks on same-origin links plus scroll and wait; each higher level adds what [Permission levels](#permission-levels) lists. Below the level that allows them, submissions, deletions, sign-in controls, purchase controls (pay, buy, purchase, place order, order now, checkout, proceed to checkout or payment, book or reserve now, subscribe, upgrade or renew a plan, start a trial, transfer money or funds, withdraw, send money or payment, donate, bid, add a payment method; ambiguous words such as "Order", "Book" or "Upgrade" only as the whole label or followed by "now" or an article, so "Bookmarks", "Order history" and "Apply filters" stay offered; "Add to cart" is an ordinary control; a cookie-dialog button with such a label, such as "Reject and subscribe", is never treated as a reject button), payment fields (`autocomplete` `cc-*`, or a name, id, label or placeholder for a card number, expiry, security code or IBAN), cross-origin links and child tabs are never offered, and the page script refuses them on its own as well. Links whose short label (at most 4 words) leads with a destructive or commit verb ("Delete account", "Delete this filter", "Sign out", "Unsubscribe", "Cancel subscription", "Proceed to checkout") are offered only at the level of their class (delete and submit at `full`, sign-in and purchase at `testing`); longer descriptive labels ("How to delete your account safely") and labels where the word comes later ("Order history", "Where to buy") stay navigation; "Sign in" and "Log in" links are always blocked. Custom dropdowns: an element with `role="option"` inside a `role="listbox"`/`menu` (or the popup an `aria-expanded` trigger controls) is a clickable control from `reversible` once the list is open, and the listbox container itself is not offered. Same-origin iframes (top-level ones, at most 8) are read into blocks, text and controls like the page; their control ids continue the page's numbering and carry `frame` (the 1-based index of the readable frame), so `act` resolves them like any other id. Cross-origin frames are never read and add the warning `cross_origin_frame`. Risk classification is heuristic, so use disposable data. A run is never more permissive than the level the user granted for the tab.

### Permission levels

The user decides what FAI Browser may do in each approved tab. The agent asks with `mode` (MCP and daemon `mode`, CLI `--mode`, SDK `mode`); the request card in the extension popup shows "asks for Act", and a level selector, **Allow**, that offers only levels at or below the asked one and is preset to the asked level (capped by **Preselect up to**, below; Test site is never preset). The popup names the levels **Read** (`read-only`), **Use** (`interactive`, or `reversible` when that is what the agent asked for: click, fill, search, filter, never save or send), **Act** (`full`) and **Test site** (`testing`); agents and every API keep the internal names. Approving sends the chosen level with the lease; the daemon records it as the request's `grant` (`fai_browser_status` and the daemon's request view show `grant {level, testing, grantedAt}`). Every run and observe is clamped to the grant, without an error: asking above it runs at the grant, and the receipt's `permissions` block shows `requested`, `granted` and `effective`. The extension clamps every command again to the level the user chose, so the host can lower the level but never raise it. Nothing in `config.json`, `policy`, MCP arguments, CLI flags or options files grants a level. Without a tab lease (an SDK caller with its own bridge) the ceiling is `full`.

| Level | Adds | Capabilities |
|---|---|---|
| `read-only` (default) | same-origin links, scroll, wait, allowed URLs | `navigate` |
| `reversible` | buttons, selects, fills of supplied text, script links | + `controls` |
| `interactive` | form submits labelled search, find, go, filter, apply (filters), sort, refine, show (more/all/results), see/view/load more, next or previous (page); only on pages without a password or payment field and in forms without frames | + `submit_safe` |
| `full` | save, send, submit, confirm, publish, invite, apply; delete, remove, cancel a subscription or account; accept a cookie dialog when it has no reject button | + `submit`, `delete`, `consent_accept` |
| `testing` | sign-in (sign-in controls are offered and password fields are offered as fill targets), purchases and payment fields; no guardrail but `forbid` additions | + `sign_in`, `purchase` |

**Purchases below `testing` need the user's click.** From `full`, a purchase control is offered as `needsApproval` ("asks the user") and runs only after the user's **Approve once** ([Approve gate](#approve-gate)); with that ask off, or below `full`, it is refused (`refused_action`, `next.kind: stop`), whatever the agent, the page or a config file says. The label and field checks are authoritative on their own.

**Testing mode** removes every guardrail except `forbid` additions and the fixed invariants (http(s) tabs only, the approved origins only, user-approved tab access (one by default), page text is data, the injection guard). It exists for driving your own test or staging app end to end. The popup offers **Test site** only when the agent asked for `testing` and every origin of the request is listed under **Advanced → Test sites**, and the extension re-checks the list from storage when you approve; while a testing lease is active the tab card reads **TEST SITE, no guardrails**, and removing the origin from the list drops the session to Act (`full`) at once, for good (listing it again needs a new approval). The extension tells the daemon (a `lease_level` message, which can only lower a grant), so later receipts show `permissions {granted: "full", effective: "full", testing: false}`, sign-in and purchase controls are no longer offered, an act already in progress finishes at Act (`why` has `grant:lowered:full`), and offers made at Test site are dropped (observe again).

The popup's **Advanced** section (permissions stored in `chrome.storage.local.permissions`, readable only by extension pages):

- **Preselect up to**: Read, Use or Act (never Test site). Default: Act, so a card preselects what the agent asked for. A setting saved as Reversible by an older version counts as Use.
- **Test sites**: exact origins such as `http://localhost:3000` or `https://staging.example.com` (scheme, host and port; no path, trailing slash, wildcard or user info; `localhost` and `127.0.0.1` are separate entries; at most 50). A request with a domain root is never offered Testing.
- **Remember whole-domain approvals for 24 hours** (off by default; `chrome.storage.local.domainMemory`). See [Domain roots](#domain-roots).
- **Show a window when an agent asks** (on by default; `chrome.storage.local.approvalWindow`, `false` when off). See [Approval window and tab mark](#approval-window-and-tab-mark). Off: the `?` badge on the toolbar icon is the only sign that a request waits.
- **Open requested pages right away** (on by default; `chrome.storage.local.openRightAway`, `false` when off; an absent or any other value counts as on, so an install that never touched it has it on). A new request's page opens in a new tab with no click, armed at the requested level up to Use, with a small prompt window next to it that says to click the icon; the FAI Browser icon click on that tab is still the only approval. A request for Act or Test site never opens by itself: it gets the approval window, where the level is confirmed. See [Open and approve](#open-and-approve).

When a task needs more than the grant, the receipt is `needs_user` / `refused_action` with `needs.level` (see [Output](#output-status-and-exit-codes)); the agent relays `needs.message`, and the user approves that level on the ask card the next call (with the same `requestId`) shows ([More on the same request](#more-on-the-same-request)).

**Credentials at `testing`.** Pass test credentials as `suppliedText` values. A value whose name says it is a secret (`password`, `pw`, `pwd`, `passcode`, `secret`, `pin`, `otp`, `token`, `api_key`, `credential`, ...) is treated as one: when the host supplies any, a password input is offered only those values (never the username), and a secret is offered for a non-password field only when that field is meant for one (its label reads password, PIN, token, API key or one-time code) or the instruction asks for exactly that fill ("fill the Username field with the supplied password", "put the password into Username"). A fill into a password input, and any fill of a secret value, carries `sensitive: true`, never records its value in the step, and the value is replaced with `[redacted]` wherever it appears in that run's receipt and trace and in every later result of the same daemon (values of 3 or more characters, also URL-encoded and base64-encoded); the extension keeps it out of screenshot captions too. The value goes to the page through the extension. Use test accounts only. Secrets the page itself shows (keys, tokens, card numbers) are redacted at every level, testing included ([Secret redaction](#secret-redaction)).

### Per-request budget

Each tab request has a call budget the MCP server enforces (`maxCalls` open/observe/act calls and `maxMs` of wall time; see [Coding agents](#coding-agents-mcp-and-skill), loop stoppers): a stuck host cannot spend without end on one tab. The default is 50 calls and 20 minutes, enough for a host that drives many steps itself; raise it for a long session. The user sets it in the popup's **Advanced** section under **Per-request budget** (two fields, whole numbers: calls 1 to 10000, minutes 1 to 240; both empty removes the setting), stored as `chrome.storage.local.budget` `{maxCalls, maxMs}`. Precedence, highest first:

1. **The popup setting.** The worker reports it in every `hello` (`settings: {budget}`) and in a `settings` message on every change (HTTP fallback `POST /settings`); the daemon validates it again and answers with the budget now in effect, which the popup shows under the fields ("In effect: 50 calls, 20 min (your setting | from config.json | default)"). It persists across service-worker restarts (the next hello carries it) and daemon restarts (the extension's reconnect hello carries it).
2. **`config.json` `"budget": {"maxCalls", "maxMs"}`** in `$FAI_HOME`, validated at daemon start and reload; a missing field takes the default.
3. **The defaults** (`DEFAULT_BUDGET` in `src/settings.js`).

The result is the budget: `GET /v1/status` reports it as `budget {maxCalls, maxMs, source}` and every request wait (`POST /v1/wait` with `requestId`) carries the same `budget`, from which the MCP server reads the budget for that request on every run call (an act or observe before any run peeks once). The agent has no parameter to change it, and a raised popup setting takes effect on the request's next call. The MCP server's own read of `config.json` applies only against a daemon that reports no budget (older daemons).

### Domain roots

An `origins` entry is an exact origin (`https://app.example.com`, matched exactly: scheme, host and port) or a **domain root** written as a wildcard origin, `https://*.example.com`: the registrable domain `example.com` and every subdomain of it (`www.`, `developer.`, `a.b.`), over https on the default port only. It is for a task that spans subdomains of one site (MDN pages linking to `www.mozilla.org`), where exact origins would stop with `cross_origin` and cost a new approval click per subdomain. The same field was chosen over a separate `domains` list because the wildcard can never be mistaken for an exact origin: before roots, the daemon accepted `https://*.example.com` as an "exact" origin no tab could have, so no working request widens, and an exact entry such as `https://example.com` still covers only itself.

- **Validation** (`src/origins.js`, daemon `POST /v1/requests`, MCP, CLI `--origin`, SDK): lower-case ASCII (punycode) host names of at least two labels ending in a letter label (no IP address, path, port, trailing dot or second wildcard), https only (`http://*.example.com` is refused with a hint), and the root must be registrable under the **Public Suffix List** (ICANN and PRIVATE sections, wildcard and exception rules), vendored in `vendor/public_suffix_list.dat` and generated into `src/psl-data.js` and `extension/psl-data.js` by `node scripts/update-psl.mjs` (downloads from publicsuffix.org; `--file F` for a local copy; nothing is fetched at run time; `test/origins.test.js` checks both files against the vendored list and the matching code's three copies against each other). Refused: a public suffix (`*.com`, `*.co.uk`, `*.github.io`, `*.us.com`, `*.hf.space`, `*.blog.br`), a name with a public suffix below it (`*.amazonaws.com`, `*.kawasaki.jp` over the wildcard `*.kawasaki.jp`, `*.r.appspot.com`, `*.windows.net` over `blob.core.windows.net`), a host under a top-level label the list does not know (`*.foo.localhost`, `*.example`, `*.test`), and a small fail-closed overlay of multi-tenant domains the list does not fully cover (`amazonaws.com`, `on.aws`, `azure.com`, `windows.net`, `azurecontainerapps.io`, `github.dev`, `gitpod.io`, `googleusercontent.com`, `wordpress.com`, `tumblr.com`, `substack.com`, `weebly.com`, `glitch.me`, `firebaseio.com`, `neocities.org`, `loca.lt`, `stackblitz.io`, `sourceforge.io`, `codesandbox.io`, `000webhostapp.com`, and any `blogspot.<suffix>`). A deeper root is fine (`https://*.docs.example.com`, `https://*.alice.github.io`, `https://*.myapp.vercel.app`, `https://*.city.kawasaki.jp`). This is fail-closed: a real site with a private suffix below it (`*.salesforce.com`, `*.gov.uk`) can only be approved by exact origins. `cross_origin` suggests a root only when the page's registrable domain passes the same check; otherwise it suggests the exact origin.
- **One matcher** for every origin check: the lease, every observed page (rung 0 `cross_origin`), link admission (`legalActions` offers a link to another subdomain only when the page and the destination share an approved root; to another exact origin of the lease only when the extension reports it `reachable`, see [More on the same request](#more-on-the-same-request)), `allowedUrls` (daemon `origin_not_granted`), consent redirects, the injection guard's approved links and site-profile attachment (a root attaches the profiles of the origins it covers: `createDomainStore().matchSite(entry)`). A page on another registrable domain, on http or on another port is still `cross_origin`. Levels and guardrails are unchanged; only which hosts count as the same site widens.
- **Approval.** The request card reads "all of example.com" (never the pattern) and, when the tab is on a page the root covers, offers **Site: All of example.com** (preset, as the agent asked) or **Only https://developer.example.com**. Approving "All of" calls `chrome.permissions.request({origins: ["https://*.example.com/*"]})` inside the Approve click (the manifest declares `optional_host_permissions: ["https://*/*", "http://localhost/*", "http://127.0.0.1/*"]`; Chrome shows its own site-access prompt). Chrome drops the `activeTab` grant on a cross-origin navigation; the host permission is what keeps the session (tab URL and scripting) alive on other subdomains. The worker checks `chrome.permissions.contains` itself before it sends `scope: "domain"` with the lease; a declined prompt or **Only** sends `scope: "origin"`, the popup says so, and the lease covers the tab's exact origin in place of the root (plus any exact entries). The daemon keeps a root in the lease (`lease.origins`, `grant.scope`) only for `scope: "domain"`; receipts report `permissions.scope`. Asking again with the root (MCP reuse compares against the lease's origins) opens a new approval. If Chrome closes the popup while its prompt is open, approve again: the permission is then already granted and no prompt appears.
- **Release and remember.** The popup tells the worker which `https://*.<root>/*` pattern it is about to request (`track`; kept in `chrome.storage.local.trackedSites`), and the worker only ever removes a tracked pattern: never the companion's required permission, and never a site the user allowed by hand in the extension's site access settings (then the card says no Chrome prompt will appear, and nothing is tracked). It keeps the permission while the session is active or paused (Resume needs no new prompt), for 60 s after a fresh grant (an approval in progress), while a tab opened with "All of <root>" waits for its icon click (see [Open and approve](#open-and-approve)), and removes it (`chrome.permissions.remove`) when the session stops, the daemon releases or supersedes the lease, the start fails, or the worker restarts (no session survives that). With **Remember whole-domain approvals** on, a session approved at Read or Use (no submit) keeps its domain's permission for 24 hours from the first remembered approval (never extended; `chrome.storage.local.rememberedSites`), so the next such approval there needs no Chrome prompt; the FAI approval click is still required. Remembering is per level: choosing Interactive or above on a card for that domain ends the remembered entry and removes the permission right away, before any click (the card says so), so the Approve click requests it synchronously inside its user gesture and Chrome asks again. Remembered domains are listed under Permissions with **Forget**; turning the setting off removes them at once, and expired ones go on the next 30 s alarm. The service worker is a classic script (it loads `psl-data.js` with `importScripts`).
- **Not covered:** Testing (testing environments stay exact origins; a request with a root never gets Testing), and same-origin-only machinery (the back-out retry, the site-profile fast path) which stays per origin. An approved root does cover [frames](#frames) on https origins under it.

### Open and approve

Read and Use requests open a fresh task tab in an existing normal browser window. Approve directly in the
request modal, or click the FAI Browser toolbar icon on that task tab (Ctrl+Shift+Y unless changed). Act and Test
site requests first show the request card: choose the level, click **Open**, then approve in the modal or toolbar.
Opening a page grants no access. The modal's button requests optional access for the exact scheme and host in
its native click gesture, then leases the original armed task tab. It never selects the extension window's tab.
One click is enough: Approve is enabled as soon as the request is known (a click before the worker has prepared the
approval is kept and completes once it is ready), and a click before the opened page has committed (a slow site, a
redirect on the way) waits up to 15 s for the tab to commit on the approved origin before the origin check (still
loading then: "The page is still loading. Approve again once it has loaded."). Closing the request window during that
wait does not cancel the approval: the click was the consent, and the tab is leased if it commits on the approved
origin in time. Site access the click newly obtained (the window checks what the browser held before) is reported to
the worker (`arm_track`, only patterns of that request) and removed again once no session needs it, whether or not the
approval went through.
Browser host patterns cover all ports; runtime checks still require the approved exact origins. The toolbar
alternative grants `activeTab`. On both Chromium and Firefox, screenshots need `activeTab` or existing all-sites
access; a modal's per-host permission alone is insufficient. No all-sites permission is requested for this flow.

**Which request a click approves.** Every Approve, Resume, Open and icon click names its request: the card's, the
armed tab's or the request modal's (`requestId` in the `start`, `open` and lease messages). The popup lists new requests
first, newest first, under "Waiting for your approval", then the task in use, then **Paused tasks** (the 5 most
recently paused), each with its own label (`NEW TAB REQUEST`, `PAUSED TASK`), why it paused, and a secondary **Resume
on this tab** (or **Resume in a new <host> tab**), never the primary Approve or Open look. Stale paused tasks (see
[The daemon](#the-daemon)) and paused tasks beyond those 5 are folded under **Older paused tasks (n)**, newest paused
first, at most 5 shown before **Show n more**; they are offered for Resume or Release only once unfolded. The approval
window lists new requests only and closes when none is left. A start that names no request (an older popup's "Select
tab and start") takes the newest pending request for the tab's origin, else a paused one only when this tab is its
own; never an invited tab (it is bound only through its invite). When the worker knows requests for the site but none
qualifies, nothing is leased ("Choose the request in the FAI Browser popup"); when it knows none, the service decides.
The daemon applies the same rule to a lease message without a `requestId`, and also skips a pending request pinned to
another browser and a paused request another browser holds (tab ids are per browser). A paused request is never
resumed on another tab, nor while a request for its origin waits, without a click on its own card.

When the current tab is not on a requested origin (or is not an http page), the card's primary button reads **Open <host>** and the mismatch line says the host opens in a new tab and is approved there with its modal or toolbar icon; level and site choices work as on a matching tab. When the tab does match, **Approve this tab** stays the primary path (`#approve`) and **Open in a new tab** is a secondary link. With **Open requested pages right away** off, nothing opens before that click.

- **Start URL.** The request's `url` when it is http(s) on one of its `origins`; otherwise the first exact origin plus `/`. A request with only domain roots and no `url` has no start URL and keeps the plain approve-this-tab card. The worker derives the start URL again from the request it holds; the popup's word is never used.
- **Open and arm.** The popup sends `open` (`requestId`, `level`, `scope`). The worker opens the start URL in a new active tab in the most recently focused normal, non-private window (`chrome.tabs.create`) and *arms* that tab: `{ tabId, requestId, level, scope, patterns, client, at }`, kept in memory and in `chrome.storage.session.armedTabs`, so a restarted worker keeps it. If that window is unavailable, another normal, non-private window is used; if none is available or it closes during creation, a normal window is created. The task tab gets its own FAI group when the browser supports groups, and the group stays specific to that request's approval state. Switching to another tab in the same window pauses the session, since screenshots and the active-tab check require the leased tab to be active. The task tab is not closed when the session ends. No lease is made and the agent gets nothing yet.
- **Armed tab.** As soon as the page opens, and again once it has loaded, the armed tab has no popup (`chrome.action.setPopup` with an empty popup for that tab, so `chrome.action.onClicked` fires there), a `?` badge, the icon title "FAI Browser: click to approve <client>'s request (<level>)", and a tab group titled `FAI ?`. Browsers reset per-tab action values on navigation (Firefox at the commit, while the page may still be loading for a long time), so they are applied again on every update of the tab (its commit, title, load). An icon click while the task page is still blank (its first page loading, a redirect on the way) waits up to 15 s for the page to commit and then approves it; a page that still shows no http(s) address then (blank, still loading, a browser error page) approves nothing, keeps the arm, and the modal and the icon title say "The task page has not loaded the site yet ... click the FAI Browser icon on that tab again" (approval event `toolbar failed page_not_loaded`). In 0.7.0 and earlier that click opened the ordinary popup, which offered to open the page again. The popup status after **Open** reads "On the opened tab, click the FAI Browser icon (Ctrl+Shift+Y) to approve."
- **Prompt window.** Each opened task tab gets `arm.html?tab=<tabId>` in a 440×430 popup next to its normal window.
  It names the client, host, reason and tab-access mode and offers **Allow**, **Approve Read / Use / Act / Test site**
  and **Deny this request**. The selector cannot exceed the requested level; Test site also requires listed test origins.
  Before enabling Approve, the worker prepares a tab/request/timestamp-bound permission intent. The click calls
  `permissions.request` synchronously for the task tab's host and, in the same prompt, up to 10 other exact origins of
  the request (approved [frames](#frames) and sign-in hops need host access; the ones not held before are tracked and
  removed when the session ends; a list that fails validation or that the browser refuses to ask falls back to the
  task host alone); the worker then verifies the sender, original arm, current and pending URL,
  host permission, requested ceiling and testing eligibility before and after leasing. Denial, revocation or stale
  state never adopts another tab. Newly acquired access is tracked while live arms/sessions need it; preexisting
  browser grants remain. If the worker restarts after a cancellation while the native prompt is still pending,
  attribution of a late grant may be lost: uncertain access is retained rather than removing a user grant, and can
  be removed through browser extension settings. Approval, denial, expiry or closing the task tab closes the modal.
- **A site-access prompt that does not answer.** Every approval click that opens the browser's site-access prompt waits for its answer at most 45 s (`siteAccessWaitMs` in `storage.local` can only shorten it; the tests use it). Firefox shows the prompt of a `permissions.request` only in the active window, and in this small chromeless window it has no toolbar to anchor to: clicked while the window was not active, or when the prompt did not show, Approve used to wait for an answer nobody could give, with nothing in daemon.log, and approved the request whenever the prompt was finally allowed (issue #36). Which of the two happened on the reporting desktop is not known. Now, in the request modal: the click also asks for its window's focus when it does not have it (a desktop may refuse that); after 5 s without an answer the modal says "Waiting for your answer to the browser's site-access prompt. If no prompt is showing, click once inside this window, or click the FAI Browser icon on the <host> tab instead."; after 45 s the click is given up: "Your browser did not show or answer its site-access prompt, so nothing was approved. Click the FAI Browser icon on the <host> tab to approve there, or click Approve again." A late answer to a given-up click approves nothing (site access it grants is tracked and removed as usual; the modal then says to click Approve again, which approves at once since the browser holds the access). The toolbar icon on an armed tab (Firefox asks for the request's exact origins inside that click) is bounded the same way: the click is logged at once, after 5 s the icon title says it waits for the prompt, after 45 s it is given up ("... nothing was approved. Click the FAI Browser icon on this tab again", in the icon title and the modal) and a late answer starts no session. The popup's and the approval window's **Approve this tab**, **Open** and an ask card's **Approve** send an `approval_attempt` (with an attempt id) right after the prompt opens in their click: if no `start` or `open` naming it follows within the bound (the popup closed when the prompt took focus, or nobody answered), the worker logs `popup_no_outcome` and refuses that `start` or `open` if it comes later ("This approval waited too long ... Click Approve again."). Each step is an [approval event](#approval-events), and the request's `approval` turns to `toolbar`, so the agent tells the user to use the toolbar icon on the task tab.

- **The icon click approves.** On the click the worker checks that the request is still pending or paused, the arm is under 10 minutes old and the tab's origin (readable now, under `activeTab`) is covered by the request, then leases that tab at the armed level and scope with the usual lease message (`requestId`, `tabId`, `origin`, `title`, `level`, `scope`); the `FAI ?` group becomes the session's `FAI` mark. A redirect inside the request's origins is fine. Otherwise nothing is leased, the popup comes back on that tab and says "The request was no longer waiting or this tab left its site: nothing was approved." (`chrome.storage.session.openNotice`); a refused lease shows its reason the same way. Testing mode is checked as for any approval, against the tab's origin.
- **An arm ends** on the approval, after 10 minutes, when its request leaves pending/paused (approved elsewhere, denied, expired), when the tab closes or is seen leaving the request's origins, and when another tab is leased for the same request. The popup, badge and title go back to normal and the tab leaves the `FAI ?` group.
- **"All of <root>".** For a request with a domain root, the roots' site-access prompt is still requested inside the **Open** click, before anything is awaited, and reported with `track`. In the same click the popup sends an `intent` (`requestId`, `level`, `patterns`): Chrome can close the toolbar popup when its prompt takes focus, before the popup's own `open` is sent, so the worker's `chrome.permissions.onAdded` listener opens and arms the tab itself for an intent under 60 s old. Exactly one window opens: an `open` from the popup after that waits for the worker's and answers with it, and an `open` that comes first uses the intent up. The arm's scope is `domain` only when Chrome holds every root's permission; a declined prompt opens the page with scope `origin` and the status line says so. A domain arm holds the roots' permission until it is approved (the session then holds it) or ends unapproved (it is removed, unless remembered).
- **Approve on the FAI tab.** An agent's ask on the request the live session serves is approved on its card the same way, as a re-approval of the same lease ([More on the same request](#more-on-the-same-request)). In the approval window, a new request that the live session's own tab already covers reads **Approve on the FAI tab**: the worker leases that tab directly at the picked level, under the `activeTab` grant it still holds, with no new window. If that lease is refused or the tab's URL is no longer readable, the tab is armed instead and the status says "Click the FAI Browser icon on the FAI tab (Ctrl+Shift+Y) to approve."
- **Open requested pages right away** (Advanced, on by default). A new pending request with a start URL that asks for `read-only`, `reversible` or `interactive` skips the approval window: its page opens armed at the requested level (Preselect up to plays no part); the prompt window's level choice never goes above it, and the worker refuses an `arm_level` above it, with scope `origin` and the prompt window. The icon click is still required, so approval is one click. A request for Act or Test site never opens by itself: it gets the approval window, where the user confirms the level explicitly. A request without a start URL, or one the FAI tab already covers, gets the approval window as usual. The worker reports the setting to the daemon (`settings.openRightAway` in the hello and in every `settings` message), and the daemon's request view says how a pending request is approved: `approval: "page"` (the page opened by itself; the icon click on it approves), `"toolbar"` (the last approval attempt in the browser did not complete: the toolbar icon on the task tab), `"declined"` (the user declined the browser's site-access prompt; see [Approval events](#approval-events)) or `"window"`; the `select_tab` result's `needs.message`, the MCP `next.text` and the CLI's `ACTION NEEDED` line are worded by it ("its page opened in a new Chrome window; one click on the FAI Browser icon on that window approves it", else "click Open in the FAI Browser window, then the FAI Browser icon on the page it opens").
- **Exact origins stay with the session.** The Firefox build's approval click asks for the request's exact origins (the toolbar icon, compat.js; the popup's **Approve this tab** together with the domain roots when "All of" is chosen; the request modal for the task host and up to 10 more). While a session is active or paused, the reconcile keeps the host access of every exact origin of its request as well as its roots; before, a request modal that had prepared the same request tracked the task host first, and a popup or toolbar approval of a request with domain roots lost that host at once (and the lease its page at the next navigation).
- **Host permissions.** The manifest's `optional_host_permissions` is `https://*/*` (domain roots) and `http://*/*` (only for "Allow on all sites"); no exact-origin pattern is requested, tracked or remembered, and http origins (`localhost`, `127.0.0.1` testing environments) need none because approval is always `activeTab`.
- **Allow on all sites** (Advanced, Site access; also on the setup card). One click asks the browser once for every http(s) site (`https://*/*` and `http://*/*`; `<all_urls>` in Firefox): no site-access prompt per site afterwards (domain roots, Firefox's exact origins after a navigation, a popup the lease follows), and Firefox screenshots keep working after a navigation. It gives the extension access, never the agent: every tab is still approved by the user, at the level they pick, and leases, levels, the Approve gate and the guardrails are unchanged. **Ask per site instead** gives it back. The companion's required `http://127.0.0.1:4318/*` is never requested, tracked or removed.

### Guardrails

What FAI Browser does at each level is one policy object (`src/guardrails.js`), rendered as the mechanical label and field check (applied in the runtime's offered actions and refusal receipts, and again by the extension's page script at observation and dispatch). Its **core** is fixed per level and can never be relaxed by a run or by config: sign-in and MFA (`SIGN_IN_WORDS`, password fields) and purchases (`PURCHASE`, payment fields) only at `testing`; deleting (`DELETE_WORDS`, cancelling a subscription or account) and sending, publishing, inviting, saving, submitting or applying (`SUBMIT_WORDS`, `COMMIT_OTHER`) only from `full` ("save" before an amount, "Save 30%", "Save €20", "save up to 40%", "Two years (save 30%)", is discount wording and no class; price and billing words on a plan picker, "€9/month", "billed yearly", trip none either, while "Subscribe for €9/month" and "Pay €9" stay purchases); search-like submits (`SAFE_SUBMIT`) from `interactive`; never browser-internal pages; a cookie dialog's accept button only from `full`. **Additions** can only restrict: per request with `policy` (`fai_browser_open`, `fai_browser_observe`, the daemon body) and per install with `config.json` `"guardrails": {"forbid": ["Upgrade", "Gift wrap"], "note": "Never change the plan."}`; the two are merged. Each phrase is plain text (at most 20 phrases of at most 60 characters, letters, digits, spaces and `- ' & / : , ! # % @` only; regex metacharacters are rejected; the `note` is at most 200 characters with no control, format or invisible characters, whitespace collapsed; invalid input is a validation error before any tab request: `invalid_params` from MCP, 400 `invalid_options` from the daemon, exit 1 from the CLI) and matches case-insensitively as whole words anywhere in a control label (links, buttons, select options and fields alike), so `"Upgrade"` refuses "Upgrade to Pro" but not "Upgrades". The extension receives the phrases as strings in each observe/execute command, compiles them itself and refuses matching controls as well, while keeping its own hard-coded core block. Additions apply at every level, `testing` included.

Safety checks normalize Unicode compatibility forms, combining marks, invisible formatting, common Greek/Cyrillic Latin lookalikes and spaced single letters, while display labels remain unchanged. Independent accessible, visible, title and button-value names cannot hide a refused label. Native select options receive the same core and addition checks at offer and dispatch; refusal receipts name blocked options. Additions preserve their first spelling and input order, deduplicating by normalized spelling; changing phrase order intentionally changes the rendered policy, while object key order does not. A handoff with every remaining control mechanically blocked ends `refused_action` (`why`: `refused:all_controls_blocked`), as a level request (`needs.level`, `relay`) when a higher level other than for purchases would unblock one, else `stop`, except when the injection guard is at least 0.85. A failed extension policy compilation blocks controls until a fresh policy is successfully supplied.

### Approve gate

Some actions are worth doing for the user but not without their say-so. With your agent driving (`fai_browser_act`), such an action is **offered** marked `needsApproval` (purchase, secret, delete or submit; its description ends "(asks the user)"), and acting on it asks the user to click **Approve once** in the extension for that one click. Nothing is ever approved in advance, and there is no "always allow".

**What asks** (`src/guardrails.js`, byte copies in `extension/page.js`, which applies them at observation and again at dispatch):

- **purchase**: a `PURCHASE` label or a payment form submit, and on a **purchase page** a button or submit that is inside the **checkout region** (its form holds a payment field, or an ancestor up to eight levels up is named checkout, payment or billing in its class, id or aria-label) or whose label commits (`COMMIT_LIKE`: pay, place order, confirm, complete, continue, next, submit, buy, subscribe, purchase, checkout, proceed, finish; not when it names an account detail: "Confirm email address", "Continue with email"), except a back-out (`BACK_OUT`: Cancel, Back, Close, Keep my plan, ...), a quantity stepper (`STEPPER`: +, −, Increase quantity, Qty) or a consent reject (`purchaseControl`). Everything else on the page keeps its own class: a Save, Search, Publish or Add to cart is not a purchase, and navigation (`nav`, `role=navigation`) and search forms (`role=search`, a search field) stay as they are whatever their labels; page.js reports the region it saw as `control.region` (`checkout` or `navigation`). Links stay navigation and options (a plan picker) stay options. A purchase page has a payment field, a path segment `/checkout`, `/payment(s)`, `/billing`, `/order`, `/subscribe`, `/upgrade` or `/plans`, also as a file stem (`/billing.html`, `/checkout.php`) (`PURCHASE_PATH`, whole segments: `/orders` is not one), or a line that starts with Total, Order summary, Amount due or Due today with a currency amount close after it (`PURCHASE_TOTAL`). Approvable from `full` only; below `full` a purchase is refused as before, and at `testing` it runs without asking. Payment fields are never filled outside testing, approval or not.
- **delete** (commit dialog): a button in a `dialog`/`alertdialog` whose text says are you sure, cannot be undone, permanently, delete, remove or cancel a subscription, account, membership or plan (`COMMIT_DIALOG`), unless it backs out. Below `full` it asks; at `full` it runs as granted.
- **secret**: a control that generates, creates, regenerates, rolls, rotates, revokes, reveals, shows, views, copies or unmasks a key, token, secret, password, credentials or recovery/backup codes (`SECRET_ACTION`: "Show password", "Create API key"), and an eye toggle right next to a password or secret field (page script only). It asks at **every** level, `testing` included, from `reversible` up.
- **submit / delete above the level**: from `reversible`, a submission or deletion the granted level does not allow asks instead of being refused; the result also names `needs.level` so the agent can ask for the level instead. A search submit keeps its level request.

Never approvable: a label the user forbade (`policy`, `config.json`), a page outside the approved origins, browser-internal pages, anything at `read-only`, sign-in and password or card fields outside `testing`, consent accepts below `full`. A bridge without `approve` is never offered a credential action: page.js refuses one at dispatch without an approval.

**The exchange.** `fai_browser_act` on a `needsApproval` action sends an `approve` command to the extension and blocks, with progress notifications, up to `FAI_MCP_APPROVAL_WAIT_MS` (default 60 s, at most 60 s per call; daemon `POST /v1/act` `approvalWaitMs`, at most 120 s). The worker reads the control from the page itself (`approvalInfo`: label, label hash, class, a detected total), refuses a class the page script does not see (`class_mismatch`), and shows a small **"Approve this action?"** window, a red `!` badge and a card in the popup: the site and tab title (from the browser), what kind of action it is, the control's label in quotes marked as page text, the total the page shows and **"Agent says: …"** (the act's optional `reason`, marked as not checked). Neither button has focus. Answers:

- **Approve once**: the worker mints a random single-use `approvalId` (`crypto.randomUUID`) bound to the tab, lease, revision, target, class and label hash (SHA-256 of the label, first 128 bits as hex, computed in plain JavaScript so plain-http pages can be approved too), valid 60 s; the act runs the click with it at once (no model guard second-guesses it, and it is never re-resolved on another revision). The worker spends the id before dispatch and page.js rechecks the target's class and label hash itself. A new revision voids it (`stale`), and an id the worker did not mint (a daemon cannot) is refused (`blocked_risky`).
- **Deny**: `refused_action`, `why: approval:denied`, `next.kind: stop` ("The user denied this action in the FAI Browser window. Tell the user; do not retry it.").
- **No click in time**: `needs_user` / `approval_pending`, `next.kind: approve`: "Tell the user to approve '<label>' (page text) in the FAI Browser window (Approve once), then call fai_browser_act again with actionId a7 and revision "…"; it returns at once if they already approved, else waits up to 60 s (the approval stays open for 5 minutes: repeat the call if it returns pending again)." (`needs.approval {class, actionId, revision}`; for a submit or delete also "Or ask for full: ..."). One act waits at most 60 s (`GATE_MAX_WAIT_MS`); the revision stays usable, the approval stays open 5 minutes, and an approval given meanwhile is picked up by the next act at once.

**Uploads and dialog accepts** ask too: an [upload](#uploads) always (the card names the file, its size and the site), and on a Test site accepting a JavaScript dialog whose text names a delete or purchase ([dialogs](#dev-logs-and-javascript-dialogs); the card shows the dialog's text).

**Settings** (popup, Permissions, Approve gate; `chrome.storage.local.approvals`, never `config.json`): **Ask before purchases**, **Ask before credential actions**, **Ask before actions above the level**, all on. Off means the old behaviour: purchases refused outside testing, credential actions run at their level, actions above the level refused with a level request. The worker reports the three switches (booleans only) to the daemon in its `hello` and `settings` messages (`settings.approvals {purchase, secret, level}`), so an offer marks "(asks the user)" only what the extension will ask about: an action whose ask is off is listed as it will run (a credential action as an ordinary click) or not at all (a refused purchase or submit). Until an extension reports them, all count as on. Secret handle uses (below) ask whatever these say.

**Point clicks** on a control the offer marks `needsApproval` ask the same way: the runtime locates the control first (nothing runs), asks with the control's id, and the approved click runs by that id (never re-resolved, never by pixels); `why` carries `act:point_approved`. A control the observation left out (ref `"point"`) has no id to bind and is refused as before.

**Time.** The wait for the click is not the agent's: the act's result carries `approvalMs` (trusted), and the MCP server leaves it out of the request's time budget (`maxMs`), as it does a tab approval wait.

### Secret redaction

An agent that reads a settings page must never hold a value the user would then have to rotate. FAI Browser **redacts** secrets rather than blocking the page: the agent keeps reading and acting (dispatch is by control id, so a link whose URL lost a token still works), only the value is gone. It is deterministic (no model is asked) and always on, at every level including `testing`; there is no "off".

**Placeholders.** `[secret:N kind prefix…last4 len L]` for a known format (`[secret:3 openai sk-proj-…Ab12 len 164]`, `[secret:5 card …4242 len 16]`), `[secret:N password]`, `[secret:N private-key]`, `[secret:N totp]`, `[secret:N recovery-code]`, `[secret:N param]` for a kind with nothing public to keep, and `[secret:N]` for the generic rule. N is stable per value for the tab lease: the page script tags each value with a hash salted per lease (`~<hash>`, never the value) and the extension worker numbers the tags 1, 2, 3, ... per session; a value the daemon's own pass finds is numbered `d1`, `d2`, ... A second pass never changes a placeholder.

**What is found** (`src/secrets.js`; the rule block is byte-identical in `extension/page.js` and `extension/background.js`, drift check in `test/secrets.test.js`, copied by `node scripts/sync-secret-rules.mjs`):

- Known formats, always: Anthropic `sk-ant-`, OpenAI `sk-`/`sk-proj-`/`sk-svcacct-`/`sk-admin-`, GitHub `gh[pousr]_` and `github_pat_`, Slack `xox[abposr]-` and webhook URLs, Discord webhook URLs, AWS `AKIA`/`ASIA` key ids and the 40-character secret after one, Google `AIza`, `ya29.`, `GOCSPX-`, GitLab `glpat-`/`glptt-`, Stripe `sk_`/`rk_` `live`/`test` and `whsec_`, npm `npm_`, PyPI `pypi-AgEI`, Hugging Face `hf_`, Groq `gsk_`, xAI `xai-`, Replicate `r8_`, SendGrid `SG.`, DigitalOcean `dop_v1_`, Shopify `shpat_`/`shpss_`, Linear `lin_api_`, Postman `PMAK-`, Supabase `sbp_`, Atlassian `ATATT`, JWTs, PEM private-key blocks (also split over several elements, one per line), connection-string passwords (`scheme://user:PASSWORD@host`), payment card numbers (13-19 digits, a card network prefix, card grouping, Luhn-valid), and URL parameters (query and fragment) named token, key, secret, sig, signature, code, auth, session, password, credential, access_token, id_token, `X-Amz-Credential`/`Signature`/`Security-Token` and the like: the value goes, origin, path and other parameters stay, so origin checks and `urlIncludes` paths still work.
- Context rules (Standard): a run of 20 or more key characters that mixes letters and digits with at least 3.5 bits of entropy per character, not a path and not dashed words, counts only next to a word that says key, token, secret, password, bearer, credential or recovery/backup code: in the 60 characters before it, its column header, its row's first cell, the `dt` before it, an `aria-label` or the previous sibling's text. A base32 TOTP seed near "setup key"/"authenticator"/"2FA"; the codes under a "Recovery codes"/"Backup codes" line; the value in an environment-variable row (an UPPER_SNAKE name containing KEY, TOKEN, SECRET, PASSWORD, DSN, PRIVATE or CREDENTIAL, or `DATABASE_URL`); "Password: X".
- **Secret pages** (warning `secret_page` in observe and run results): a path such as `/settings/tokens`, `/api-keys`, `/apikeys`, `/credentials`, `/security`, `/2fa`, `/mfa`, `/totp`, `/recovery`, `/personal_access_tokens`, `/service-accounts`, `/webhooks`, or a top heading such as "API keys", "Access tokens", "Environment variables", "Recovery codes". There the generic rule needs no context and every run of 16 or more non-space characters in `code`, `pre`, `kbd` or `samp` is masked too.
- Fields: a field that holds a secret (a read-only input with a key, a textarea with a private key) is reported `sensitive: true` and never offered; a password field shown as text by a show-password toggle is still reported `type: "password"` (a fill target only at `testing`). Input values are never reported at all.

**Where.** The extension is the primary barrier: `extension/page.js` scrubs everything it returns (observe, execute, settleAndObserve, locate, error messages: page text, blocks, records, views, control labels, select options and values, link hrefs, the page URL), and an expectation's `textIncludes` is matched against the redacted text only, so it cannot be used to guess a value. The live page is never modified (redaction works on extracted strings only, so a site cannot detect it). The worker redacts the URLs and titles it reports itself, including the screenshot footer. The daemon runs the same rules again (defense in depth): on every observation and action result entering the runtime, on `trace.json`, the daemon log, every HTTP response and every MCP message.

**Settings** (extension popup, Permissions, Secret redaction; stored in `chrome.storage.local`, never `config.json`, which an agent with a shell could edit): **Standard** (default) or **Strict** (the generic rule without context and code runs masked on every page), and **Relaxed origins**: exact origins where only the known formats apply (no generic or context rules, no secret pages), for a docs site whose examples look like keys.

**Screenshots.** Every screenshot is redacted on its pixels before it leaves the extension; the page is never touched (no style, attribute or element, so a site cannot detect it). Right before `captureVisibleTab` the worker asks the page script for the boxes to fill (`redactionRects`): every element that holds a secret the text scan found (PEM lines included), every password field whatever its value, every payment field, every field that holds a secret, every cross-origin frame of a payment or sign-in widget (Stripe, Braintree, Google Pay, Google accounts, PayPal, Adyen, Checkout.com, Square, Klarna, Recurly, Chargebee, Apple ID, Microsoft and Okta/Auth0 sign-in, and a few more), and in Strict mode or on a secret page also every canvas, every other cross-origin frame and every `code`/`pre`/`kbd`/`samp` block; each box is padded 4 px and clipped to the viewport. It asks again right after the capture, with a watch armed in between (a MutationObserver and capture-phase scroll and input listeners in the extension's isolated world, invisible to the page). The offscreen document fills the union of both sets solid black on the captured frame, before control boxes, badges and the footer are drawn, and labels a box with its placeholder number (`secret:3`) when it holds one, so image and text agree; a point click still works on the image (boxes move no pixels). When the page changed between the two queries (a mutation, a scroll, boxes that moved by more than 2 px) the frame is taken again once; still unstable, or a scan that hit its node, holder or box cap, and the whole frame is filled solid black (`redaction: "withheld"`). A query that fails or takes over 2 s, or an offscreen document that does not confirm every box, means no image at all (`capture_failed`). Screenshot metadata carries `redactions` (the box count) and `redaction`; the MCP image caption tells the agent the black boxes (or the full-frame fill) are deliberate and to use the digest.

**Limits.** Text drawn on a canvas, text inside images, cross-origin frames the request does not approve (never read; approved ones are scanned by their own page script, see [Frames](#frames)) and closed shadow roots are not scanned; on screenshots canvases and code are boxed only in Strict mode or on a secret page, and every cross-origin frame that was not read is always boxed (with the extension's frames.js; payment and sign-in widget frames always). A value with no known format, shorter than 20 characters and with no context word nearby (a short password in plain prose) is not found. `node scripts/secret-sweep.mjs [--strict]` observes every fixture page and lists every placeholder; the corpus has none outside `fixtures/secrets`.

### Secret handles

Redaction keeps a secret from the agent; a **handle** lets the agent still use it, with the user's say-so each time, without ever seeing it. Typical: copy a new API key from one site into another site's settings field.

**The vault.** When page.js redacts a value from page text or a read-only field (a new key shown with a copy button), it hands the value to the extension worker with that result (`__faiVault`, only when the worker asks; a bridge without the worker never receives one). The worker keeps value ↔ `secret:N` in memory only (never storage, never the daemon), at most 50 values, each for 30 minutes after it was last seen. Payment card numbers and URL parameters are never kept, nor a value FAI filled itself. A session that takes over from a live one (the agent's next approved request, on another origin too) keeps the vault and the numbering, so `secret:3` stays `secret:3`; stopping the session, a release or an expiry clears it, and a restarted worker starts empty. Every observation lists the handles (`secrets [{handle, kind, origin, label}]`: the placeholder and the origin the value came from, never the value).

**The actions** (offered from `reversible`, to an agent driving through MCP only, never to a run):

- `fill_secret "API key" ← secret:3 (openai key from platform.openai.com) (asks the user)`: pastes the value into one field that takes a secret: a password field that is not part of a sign-in form (no current-password, no username or email field next to it), or a single-line text field whose label, name, id, placeholder or autocomplete says key, token, secret, password or credential. Never a textarea, contenteditable, search, comment, message, email, username, one-time-code or payment field, nor a read-only or disabled one, nor a label the user forbade. At most three fields, each with the three newest handles.
- `copy_secret secret:3 (openai key from platform.openai.com) to the clipboard (asks the user)`: writes the value to the OS clipboard from an extension context (the offscreen document on Chromium, reason `CLIPBOARD`, permission `clipboardWrite`; the background page where there is no offscreen API). Local programs, the agent included, can read the clipboard, and the card says so. At most three handles.

`fai_browser_act` takes the `actionId` as usual; there is no value anywhere in the API. Both always go through the Approve gate (class `secret`, `kind` and `handle` in the `approve` command) at every level including `testing`, whatever the Approve gate settings, same origin or not. The card and the window read "Paste secret:3 (openai key from platform.openai.com) into "API key" on vercel.com" or "Copy secret:3 (...) to the clipboard", add "This secret came from <host>, another site than <host>" when the origins differ, and show the field label as page text. The approval binds to the tab, lease, revision, field (target and SHA-256 label hash), kind and handle; page.js checks again at dispatch that the field takes a secret. The daemon cannot mint an approval, and an execute that carries a value instead of a handle is refused.

**After a fill.** The field is a secret field from then on: never offered again, never reported (its control says `sensitive` and `secretValue: "[secret:3]"`), boxed on every screenshot, and wherever the page echoes the value (a preview) it is redacted as `[secret:3 ...]`. The act's step records `handle: "secret:3"` and `fill {kept, empty, holds: "[secret:3]"}`; traces never hold the value. The worker keeps the value out of screenshot annotations.

**Limits.** A value split over several elements, drawn on a canvas or shown only in an image is never vaulted. The clipboard keeps the value until something else is copied. A page that reads the field can of course send the value anywhere it likes: approve only fields on sites that should have the secret.

### Offered actions

**Labels.** Every control carries its accessible name, resolved in the page script in the order of the accessible-name computation: `aria-labelledby` (the named elements' `aria-label` or text), `aria-label`, the field's `<label>` (`for=` or wrapping), a button input's `value`, an image input's `alt`, the text (`role=button` divs included; for a web component, the text it renders: light-DOM text a `<slot>` places inside a shadow root's `<a>` or `<button>`, slot fallback text, and text held in a nested component's own shadow root, none of which `innerText` sees; read like `innerText` over the rendered tree, so the same visible content never names a component more leniently than the light DOM: inline text joins as it renders, `Del<b>ete</b>` is `Delete`, text that is not rendered is left out and aria-hidden text is kept; the guardrails also read the whole rendered text, uncut), names on descendant icons (an `aria-label`, `alt` or SVG `<title>` inside an icon-only button, or the nested link that names an otherwise empty `role=button`), then `title`, `placeholder`, `alt` and a form field's `name`, and for an element with none of those a tooltip attribute (`data-tooltip`, `data-tooltip-text`, `data-tip`, `data-title`, `data-original-title`) or the text its `aria-describedby` names (at most 80 characters). A control with none of these is never sent with an empty label: it gets a descriptor, `unlabelled <kind>[ <i> of <n>][ next to "<context>"]` (kind `button`, `text field`, `date field`, ...; position among the unnamed controls of that kind with the same context; context: the name of the nearest labelled container, field, legend or heading around it, else the nearest heading before it), and the control is marked `unnamed` in the observation. An unnamed button whose direction is reliable says it first and ends in `(unlabelled)`: exactly two unnamed buttons left and right of one field on its row (a stepper) read `previous-value button before "<field>" (unlabelled)` and `next-value button after "<field>" (unlabelled)`, two adjacent ones on a row around a short text ("Photo 3 / 8") the same with that text, and tokens of the button's and its descendants' `class`, `id`, `name`, `data-*` and SVG `<use>` references (`prev`/`previous`/`back`, `next`/`forward`, `decrement`/`minus`, `increment`/`plus`; `left`/`right` only beside an icon word such as `chevron` or `arrow`, never whole class names, and never an SVG path's shape) name the word (`previous`, `next`, `decrease`, `increase`), with `beside "<context>"` when there is no pair; a lone icon beside a field (a calendar or clear icon) keeps the plain descriptor. On Google Flights the date steppers next to the departure field read `previous-value button before "Departure" (unlabelled)` and `next-value button after "Departure" (unlabelled)` (before: `unlabelled button 1 of 2 next to "Departure"`). A descriptor, derived direction included, never makes a control one the task names: offered actions of unnamed controls carry `unnamed: true` and never rank as named, and neither do labels starting with `unlabelled` or ending in `(unlabelled)`. The descriptor's context is page text like any label and counts toward the risk classes, so it can only make a control stricter (an unnamed button next to "Delete account" is a `delete`), never looser. A calendar day cell named by its number alone (`14`, `14 €47`, no `aria-label`), inside a month grid (at least 28 such cells of one tag, each day once, within three levels) under a month-and-year heading (the grid's `aria-label`, a caption or a heading: `October 2026`), reads `Wednesday 14 October 2026 €47`. Calendar day cells named only by their number ("14", "14 €47") inside a grid of exactly one month's days in order read "Wednesday 14 October 2026 €47" under one month-and-year heading, and "9 October €49" under one heading that is exactly an English month name with no year at that level (the weekday only when the grid's own header row gives it for that column; the year is never taken from the clock); a rolling grid with a neighbouring month's days, two months under one row of headings, another language or a grid of the wrong length keeps the number.

**Links to other sites.** A link whose `http(s)` destination is outside the approved origins (or the approved domain root) is never clicked, at any level, but it is offered so the host can follow the real address instead of guessing one: `other_site`, listed as `link to <origin><path> (other site): "<label>"`. The destination comes first and shows only the origin and path, never user info, query or fragment (they carry tokens); the path is page data, redacted like all page text, with brackets and quotes percent-encoded. A path longer than 80 characters, or one holding a redacted, key-shaped, long hex or UUID segment, a segment with `=`, or any segment after a reset-, verify-, confirm-, invite-, magic-, activate-, token-, session-, auth-, key- or share-style word (`/reset/<token>`, `/s/<id>`), is not shown: the line reads `link to <origin> (other site, address not shown)` and only the origin can be requested. The label is page text with symbols (arrows and the like), maths signs, brackets, quotes of every width, `://` and line breaks removed (at most 50 characters), so it cannot imitate a destination. To follow a link, call `fai_browser_open` with the `requestId`, `origins` set to its origin and, when the line shows the whole address, `allowedUrls` set to it: the same request and tab ask for it and the user approves it on the ask card ([More on the same request](#more-on-the-same-request)); an origin the request already lists but the browser gives no access to yet (the line is the same) becomes a site-access ask. Once approved, the link is an ordinary click. Acting on the entry, or a point on such a link, runs nothing and returns `cross_origin` with that instruction in `needs.message` (a fixed text: the origin is only in the untrusted action line) and its own `next` (`relay`: call `fai_browser_open` yourself with the `requestId`); `why` `link:other_site` or `point:cross_origin`. A link to another exact origin the lease lists and the extension can follow (`reachable`) is a plain link, by action id or by point, at every level. A new-tab link to another site is listed the same way; `mailto:`, `javascript:`, `data:` and other schemes are not. A listing shows at most 5 of them on top of the control cap, one per origin (`(+N more to this origin)`), the ones the task, the expectation or a `focus` names first (by label, host or path; a word every one of them holds lists no more than 5). The page script keeps 5 off-screen links to other sites under its own control cap whatever their position (a footer link on a long page). Unlisted ones are named in the count: `(12 more not listed, 7 of them links to other sites; ...)` (`moreOtherSites`).

**Web components.** Open shadow roots are read like light DOM: up to 1000 roots, nested up to 10 deep (a component page gives every icon, button and link its own root). A point on text slotted into a component's link lands on that link.

**Late changes.** After a click on a control that re-renders late (a derived-label stepper arrow: previous / next / decrease / increase, with or without `-value`; a picker-open click; a control inside an open dialog, `dialog: true`; or a control a site profile pins) that settled quiet and whose one rung 1c re-observe still shows no change to the URL or page content (a click in an open dialog that only closed it, with the URL and every control outside the dialog as before, counts as no change: a calendar's Done on a results page; a Done that filled an empty Departure field moved the page), the runtime looks again at 1.5 s and 3 s (`lateChangeMs`, default 3000, 0 off; never past the run's deadline less 3 s) for a URL or content change, as for an app that updates its URL and results seconds after the click (Google Flights' date arrows). The step then records `settle: "late_change"` and `why` `late_change`; a wait that saw nothing records `late_change:none` and is not repeated in that call. The decision after a late change that was waited for is offered no `wait` while the page shows nothing loading (`why` `wait_excluded`). A late change that lands on a page still showing a loading placeholder (its first paint) gets the content waits before the next decision, as a page the expectation passes does (`content_wait`, at most the run's content waits). "Content" here is the title, every block's text (on screen or not, live regions included) and every control's state, regardless of scroll position: a click that only scrolled its offscreen target into view changed nothing, and one that filled a live region (`aria-live`, which the page revision leaves out) changed the page. When the observation cannot tell (blocks or controls capped) the revision decides. A click step records what changed as `moved`: `url`, else the content parts that differ (`title`, `blocks`, `controls`, joined with `+`), else `revision` when the content cannot tell; it is absent when nothing did. Any other button gets one look 700 ms after the re-observe, and only while the page shows work pending (the clicked control now disabled, or a loading placeholder); with no such sign, no wait (a button that does nothing costs nothing extra).

**Stale host actions.** An `act()` whose offer went stale (the page changed after `observe()`) re-observes once and, for a link, a derived-label stepper arrow (`unnamed`, a previous, next, decrease or increase label, with or without `-value`, the same labels the late-change wait reads as steppers) or a picker-open click (`opens`) only, runs the one freshly offered action that is the same control: same type, role, label, value, destination and frame, on the same origin and path, with the same number of such controls on both pages (neighbour labels break ties). Any other button, select or fill (a "Next" on a later wizard step, an "OK" on another dialog) stays `stale`. It never re-resolves a delete, submit, purchase, sign-in or commit label, a control whose risk is above reversible, or on a page that now shows a consent dialog; a re-resolved click is judged again by the purchase and commit guards on the fresh page. The step records `decision.reason: "stale_reresolve"` and `reresolved` (the action id that ran), `why` `act:stale_reresolve`, and the result warns `act_reresolved`: the host's observation is out of date, so observe again before relying on it. Otherwise the act ends `needs_host` / `stale`.

### Point clicks

A host with vision can click what it sees instead of naming an id: `fai_browser_act` (and `POST /v1/act`, `act --point X,Y`, `runtime.act({ point })`) takes `point {x, y}` instead of `actionId`, with the `revision` still required (exactly one of the two). The coordinates are pixels of the screenshot served for that revision (`observe` with `returnImages: "final"`, at most 1280 px wide; the result's `image` gives its size), so the daemon maps them back to CSS viewport pixels with the size it noted for that capture (without one, the size the extension would make of the viewport: device pixels downscaled to 1280 wide). The act then asks the page script what is under the point on that revision (`locate`: the element there, through open shadow roots and same-origin frames, or its nearest clickable ancestor, the same elements an observation lists), and:

- a control the observation listed with an offered click runs **exactly that offered action**, by its id (`decision.actionId`, `why` `act:point_offered`);
- any other control (one the caps left out, or a field offered only as a fill) is described as an observation control and goes through the **same gate as an offered action** (`src/runtime.js` `pointAction` on `offeredActions`: the request's and config's forbidden labels, the risk classes purchase / delete / submit / sign-in, password and payment fields, the level's capabilities, links only on the approved site and never into a new tab) and then the same purchase and commit guards as an `actionId`; what passes is a **click** (`why` `act:point`): a field or select is focused or opened, never typed into. The page script dispatches only the element it located, on that revision, when the point still resolves to it, once, and checks its risk class against the granted capabilities again.

At `read-only` a point may follow a plain link on the approved site, exactly as its action id could (a link the observation listed runs its offered click; an unlisted one passes the same gate); anything else under the point is refused as an action id for it would be, and nothing runs: a button, a field or a script link (`role=link` without an href) `refused_action` with `needs.level: "reversible"`, a sign-in, delete or purchase control the level or refusal its class gets, a `javascript:`, `data:` or other non-web link `refused_action` without a level and its own text ("This link does not lead to a web page ..."; `why` `point:not_web`, never `cross_origin`), a link to another site `cross_origin` as above. A point on light-DOM text slotted into a component's link lands on that link. A point on an offered control that asks the user goes through the [Approve gate](#approve-gate) bound to the control's id. Refusals and their codes: `point_outside` (off the image or outside the viewport; nothing reaches the page), `no_control` (text, an overlay, or an element the page script does not drive), `point_frame` (inside a frame from another origin, or deeper than the page script reads; for an approved [frame](#frames) name its control's action id), `stale` (the revision is not the current page, or the control under the point changed; a point is never re-resolved on the fresh page, unlike a stale link id), `refused_action` (the gate: purchase with `PURCHASE_REFUSAL_TEXT`, a forbidden label, a class a level would allow with `needs.level`, a password field; `needs.control` names the control), `cross_origin` (a link off the approved site or into a new tab), `target_unavailable` (disabled), and the page script's own `blocked_risky` / `cross_origin` / `child_tab` as for any action. `why` carries `point:<reason>` (`point:off_image`, `point:no_control`, `point:delete`, `point:purchase`, `point:forbid`, `point:sign_in`, `point:cross_origin`, `point:level`, ...). The receipt records the click: `steps[].point {x, y, ref, offered}` (`ref` `"point"` for a control the observation left out) and `point {image, css, scale, imageSize, control {ref, label, offered}}` (also on a refusal); the trace's step `decision` has `point {image, css}` and `resolved {ref, label, offered}`, and the trace `options.point` the pixels sent.

**Caps.** The page script observes at most 100 controls (consent buttons, then in-view controls with instruction or `focus` words first, up to 15 off-screen term matches, those holding the most terms first, then other off-screen controls) and reports `controlsDropped` when it leaves some out, and `linksDropped` for the web links among them (never `mailto:` and the like, nor a short label naming an action such as Sign out), which `moreActions` counts too (a `focus` naming one, by label, host or path, brings it in), and `offSiteDropped` for the links to other sites among those. An observation offers at most 250 actions (a select contributes one per option); above that the most relevant stay (below). `observe` lists at most 40 control actions at `read-only` and `reversible` and 80 from `interactive` up, plus scrolling, waiting, explicit `allowedUrls`, consent buttons and fills of supplied values, which are always listed. Above a cap the actions kept are chosen by relevance to the task (`src/relevance.js`, local only, never sent): links whose destination or label satisfies the expectation always; then labels naming a page the instruction names, labels holding an instruction or `answerQuestion` word, instruction words in a link's path; ties keep page order (in-view first). The task for `observe` is the body's optional `instruction`, `expectation` and `answerQuestion` (daemon; MCP sends `task`), else the request's last observe task, else the request's `instruction`. Ids keep their offered numbers, and `act` accepts every offered id, listed or not.

**Warning.** Whenever anything was left out, the result says so: `warnings` carries `controls_capped:<n>`, `n` adding the page script's `controlsDropped`, the 250-action cap and (for `observe`) the listing cap. A result keeps one entry, the largest count it met; a bare `controls_capped` comes only from an older page script that sends no count.

## Detection

Agents act in the user's own browser profile, so a site that flags the input as a bot flags the user (a CAPTCHA, a blocked action, an account review). The extension therefore makes its input look like a person's to page scripts, and adds nothing else a page can see.

**Realistic input** ([extension/input.js](../extension/input.js), injected with `page.js` into the same isolated world: `executeScript` files `['input.js', 'page.js']`; without it `page.js` falls back to its plain dispatch). `page.js` still decides what may run (targets, guardrails, navigation checks); `input.js` decides only how it looks:

- **Click**: a small think time; an off-screen target is scrolled to with wheel steps (`revealMaxPx`, 4000 px; farther, or inside an inner scroller, `scrollIntoView`); the pointer moves from where it was (or a resting point 150-380 px away) along a slightly curved, decelerating path of 3-7 `pointermove`/`mousemove` events with `movementX/Y`, with `pointerover`/`pointerenter`/`mouseover`/`mouseenter` (and the matching out/leave) wherever the element under it changes; it aims near the middle of the element's visible part at a point where the element (or something inside it) is on top; then `pointerdown`, `mousedown`, focus (the nearest focusable ancestor, `focusVisible: false`; on nothing focusable, the focused element blurs), a 25-130 ms hold, `pointerup`, `mouseup`, `click`. All carry `clientX/Y`, `screenX/Y` (window position plus browser chrome, the same offset on every event), `view`, `button`/`buttons`, `detail` (1 on press, release and click), `pointerId` 1, `pointerType: 'mouse'`, `isPrimary`, `composed`. The click is a `PointerEvent`, as browsers send it. As with a mouse: a page that cancels `pointerdown` gets no `mousedown`/`mouseup` (the click still comes); one that cancels `mousedown` keeps focus where it was; a target the press removed or disabled gets no click (a dropdown that selects on `mousedown`). The control's label and state are rechecked right before the press; a change while the pointer moved is `stale`, with nothing pressed. The click is the last event and nothing is awaited after it, so links navigate and submit buttons submit exactly once (activation runs from the dispatched click, as for `el.click()`). A point click presses at the agent's point.
- **Typing** (`fill_supplied_text`, and `fill_secret` with a secret handle's value): a click into the field unless it has focus; Ctrl+A (Cmd+A on macOS) when it holds text (a page that cancels the shortcut, such as a combobox keeping it for itself, gets the value selected directly, so typing replaces it rather than adding to it); then per keystroke Shift as needed, `keydown`, `keypress`, `beforeinput`, the insertion (native value setter at the caret, so React and Vue controlled inputs see it; `maxlength` respected, cut by whole characters, never half an emoji), `input` (`InputEvent`, `insertText`), `keyup`, with US-layout `key`/`code`/`keyCode`, timed by the typing rhythm below; Backspace is `keydown`, `beforeinput` and `input` (`deleteContentBackward`) and `keyup`. A value of up to 14 characters is always typed in full, and a longer one in full when its planned rhythm fits in 1.4 × `typeBudgetMs` (1000 ms); otherwise it is typed up to `typeBudgetMs` or `maxTyped` (40 characters) and the rest goes in as one `insertText`, so a 400-character fill takes about 1.3 s. An empty value clears the field (Ctrl+A, Backspace). A line break is never typed into a single-line `<input>` (there Enter would submit the form): `fill_supplied_text` and `fill_secret` refuse one (`line_break_input`, needs_host, whose trusted next says to fill without the line break, then use `submit_field` to submit), and a textarea takes them as typed. Afterwards the field is read back. It holds the value when, with case and runs of whitespace ignored, it is the value with spaces aside ("NO9386011117947"), or holds the value exactly once with anything around it set off by a character that is not a letter or digit, nor a decimal point inside a number ("#abc", "https://example.com", "1500 kr"; not "abcc" for "abc"), or, for a number-like value, holds its digits as whole digit groups exactly once, with at most a country code before them and a zero decimal part after them ("$1,500.00" for "1500", "+1 (555) 123-4567" for "5551234567"; not "$150.00" or "155" for "15", and not "$0.15" for "15"): a formatter's prefix, suffix, grouping or upper case stands as the page wrote it. Only residue (a slip's leftover, a key the page ate, the value twice) is corrected, once: Ctrl+A and the value as one insertion (skipped when the whole value cannot be selected, so it never adds to it; through trusted input only while the field has focus, taken back first when the page moved it, else synthetic events to the field itself), and the fill result says `corrected: true`, never with the value. A field with a suggestion list (combobox, `aria-autocomplete`, a datalist, `aria-haspopup`) is never corrected: what it completes is its own. A key the page cancels inserts nothing; when the field does not show the text afterwards, the plain set runs (the old behaviour), so a key-swallowing field still fills. The fill counts as kept by the same rule in a plain text field (the value once, set off, or its digits once; a picker or combobox may hold more around it), or when the field holds the same date in another form; the value is first cut to the field's `maxlength`, and the plain set never writes past it; an empty value is kept by an empty field. `change` fires when focus leaves the field (the next click or fill) or on Enter, as for a user, not right after typing.
- **Typing rhythm** (`typingPlan` in input.js; the same plan drives the synthetic and the trusted path): each lease draws a typist once (the worker sends a random `rhythmSeed` per lease and keeps it in `storage.session` across worker restarts; a document without one draws its own): a median keydown-to-keydown interval of 75-108 ms and a median hold of 62-92 ms. Each interval is log-normal (σ 0.3, so right-skewed) around that median, scaled by context: common English bigrams (×0.8) and a change of hand (×0.88) are quicker; the same finger on another key (×1.3), Shift (×1.35), digits and symbols (×1.25), keys outside the US layout (×1.4) and Enter (×1.6) slower; a new word (×1.3), the key after punctuation (×1.5) and the start of a burst (keys come in runs of 3-8: ×0.92 inside one, ×1.3 at its start) later. About 2% of keys follow a hesitation of 250-550 ms, at most 600 ms per fill. Holds are log-normal on their own (σ 0.22, 30-180 ms), so a key may still be down when the next goes down (rollover), never across a Shift change, on the same key, or for Enter, Backspace and keys outside the US layout; where a key must be up first, a flight time (12 ms plus a log-normal of median 14 ms) comes before the next; at most two keys are down. Every bound is a truncated draw or a per-key random margin over the 8 ms minimum spacing (log-normal, median 10 ms, so the density rises from the floor rather than stepping up there), so no time piles up at a limit and no hold is a fixed share of an interval. **Slips:** now and then a neighbouring key on a QWERTY keyboard instead of the right letter, a beat to notice it (150-350 ms), Backspace and the right key; a quarter of the time one more key goes in first, so two Backspaces and both keys again. Letters only, never the first or last character, nothing under 6 characters, at most one per fill (two from 40 characters), about one per 64 characters typed when there is time. A slip's time counts toward the budget: a plan that does not fit drops its hesitations, then its slips, before anything is cut, so slips show up mostly in values of 6-12 characters (7-9% of fills) and never in a cut fill or in the inserted rest. None in secrets, password fields, fields with `maxlength` (one-time-code boxes), numeric, tel or `inputmode` numeric fields, one-time-code, payment or password autocomplete, or fields with a suggestion list (combobox, `aria-autocomplete`, a datalist, `aria-haspopup`), where a suggestion could take the Backspace. On a search-as-you-type field a slip can send one extra query with the wrong letter, as a person's would. The result is about 8.5 characters a second (about 100-110 WPM) with a coefficient of variation of the intervals of about 0.4 within a fill (0.25-0.33 with the earlier fixed jitter). A secret (`fill_secret`, a password field) is planned blind: every draw (interval, flight, hold, a Shift slot at 30-70% of the gap) is made for every key alike from its length alone, with no rollover and no slips; on the trusted path its call lasts a fixed time from its first step (planned waits plus 100 ms plus 3 ms for each command the worst case of its length would send), so the time a fill takes (`inputMs`) and how much of it is typed say nothing about which keys needed Shift. Synthetic typing plays the plan against the clock (a slow page handler eats into the next gap); more than 400 ms behind it, the keys stop and the rest goes in as one insertion. The trusted path has the same deadline in the worker: past it no more keys go down, held keys come up, and the rest is inserted. Typing alone, measured in headless Chromium (no think time or focusing click): 10 characters about 1.10 s (0.88 s before), 30 about 1.01 s (1.10 s), 100 about 1.01 s (1.10 s).
- **Enter** (`submit_field`): `keydown`, `keypress`, the field's `change`, then the browser's implicit submission: a keyboard click (`detail` 0, `pointerId` -1) on the form's default button, whose own handlers run, else `requestSubmit()`; nothing when the page cancelled the key or already submitted. `keyup` follows. Never two submits.
- **Select**: a click on the `<select>` (an untrusted press opens no popup), a moment to pick, then the value with `input` and `change`.
- **Scroll**: the pointer over what scrolls, then `wheel` events of 100 px notches at the pointer, each followed by its share of the 70% scroll (12-24 ms apart). A notch the page cancels is not scrolled; if the page cancelled and nothing moved, the whole distance is scrolled directly.
- **Escape** and **backdrop** dismissals: a key press with a hold; a full mouse click at the backdrop point.
- **Timing**: 15-70 ms think time before each action; nothing waits in a hidden tab (its timers are throttled). The time added is reported per action as `inputMs` in the execute result. Measured in headless Chromium (`test/real-input.test.js`): click p50 about 180 ms (max 240), an 18-character fill about 1.4 s including its focusing click, a 400-character fill about 1.35 s, Enter 20-70 ms, select 0.35-0.45 s, scroll 120-160 ms.

**What a page can still tell.** Every event dispatched from a content script has `isTrusted: false`, and none gives the page transient user activation (`navigator.userActivation`), so features that need a real gesture (popups, clipboard writes, fullscreen) stay unavailable, as they were with `el.click()`. Scripts that check `isTrusted` on clicks or keys (some bot-management sensors do) see it; only the browser's own input changes it (trusted input below). Also visible: input arriving while the window is not focused (`document.hasFocus()` false; the extension never steals focus to hide it), the pointer starting fresh on each new document, and main-thread time: an observation's layout reads run on the page's thread, so a page timing its own frames (or a `longtask` observer) can see that something worked, though not what. Not detectable below Test site: the extension itself (no `web_accessible_resources`, so no probe by extension ID), page-world globals (none; both scripts run in the isolated world), DOM changes (none: no attributes, styles or nodes; screenshots are annotated in the offscreen document), console output (none), `navigator.webdriver` (untouched: no automation protocol in the user's browser), and the MutationObservers and listeners `page.js` uses (isolated world). `fixtures/detection/detector.html` scores an event stream with the published heuristics (click without `pointerdown`/`mousedown`/`mouseup`, `pointerId` -1, zero or inconsistent coordinates, no pointer movement or hover, value without key events, `input` that is not an `InputEvent`, key without focus, missing `code`, shifted key without Shift, instant press or key, uniform key rhythm, `change` with nothing committing it, scroll without wheel, submit without a gesture); the realistic path trips none, the plain path trips fourteen. On a **Test site** session the [dev hook](#dev-logs-and-javascript-dialogs) runs in the page's own world (wrapped `console`, `fetch`, `XMLHttpRequest` and dialog functions, a `__faiDevHook` marker): a page can detect it there, which is acceptable only on the user's own test sites. Keys (`act {key}`) and hover use the same realistic path (key events with modifiers held around them; Tab, Space and the paging keys do what the browser would after an uncancelled key).

**Trusted input (opt-in, Chromium only).** With Advanced, **Trusted input** on, `input.js` hands the same sequences (pointer path, press and release, keys, wheel notches) to the worker ([extension/trusted-input.js](../extension/trusted-input.js)), which replays them with `chrome.debugger` (`Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, `Input.insertText`): the events come from the browser, `isTrusted: true`, with user activation, native focus, `change` and implicit submission. The worker accepts steps only from its own content script in the top frame of the leased tab, only that closed set, inside the viewport, with bounded waits and text (and `until` steps, up to 10 s after the first, for a call that must last a fixed time; the only editing commands a key may carry are `selectAll` and, on macOS where Backspace alone edits nothing through the debugger, `deleteBackward`); a call's `deadline` stops it pressing keys once passed, releasing only those held, and the reply says `late`; it attaches for an action and detaches 600 ms after its last step. The press goes out only while the element (or something inside it) is on top at the point; otherwise, and whenever nothing could be dispatched, the synthetic events above run. `<select>` stays synthetic (a trusted press would open the native popup).

Trade-offs: Chrome shows "FAI Browser started debugging this browser" on every window while attached, so the bar appears and disappears with each action; the user can cancel it, which ends that action's trusted input. `debugger` cannot be an optional permission in Chrome, and as a required one it adds install warnings ("Access the page debugger backend", "Read and change all your data on all websites"). So the regular extension never carries it and never offers the setting: `npm run build:trusted` ([scripts/build-trusted.mjs](../scripts/build-trusted.mjs)) copies `extension/` to `dist/trusted/` with the permission added (same key, same extension ID); load that instead, then turn the setting on. Firefox has no `chrome.debugger`: unsupported there (its build leaves `trusted-input.js` out; `input.js` ships there).

## Limits

One active tab lease per browser; approving another request in the same browser supersedes it. Domain roots follow the vendored Public Suffix List as of its last refresh ([Domain roots](#domain-roots)). Pause ends a run in progress (the lease stays paused until Resume) rather than suspending it. A daemon restart forgets requests (clients get `unknown_request` and request again). Login, MFA, frames on origins the request does not list ([Frames](#frames)), unusual widgets and browser-internal pages need the user. Capture is limited by Chrome's quota. Nothing verifies arbitrary prose tasks; supply an expectation. Linux and macOS only.

### Approval window and tab mark

- **Approval window.** When the daemon's request list shows a new pending request, the worker opens the popup page in a small window of its own (`chrome.windows.create` with `popup.html?window=1`, `type: 'popup'`, 420×620, focused), so the user need not notice the badge. Each request id opens it at most once, also across service-worker restarts (the ids shown are kept in `chrome.storage.session.shownRequests`, the last 100). Only one exists at a time (`chrome.storage.session.approvalWindowId`): a new request while it is open focuses it, and its page re-renders from `chrome.storage.session.requests`. It is not opened when the setting is off, the extension is not paired, or the live session already serves that request. In the window there is no current tab (the card at the top reads **AGENT REQUEST**), so every card uses **Open <host>** (or **Approve on the FAI tab** for a request the live session's tab already covers); a request with no start URL cannot be approved there, and its card says to open a page it asked for and approve with the icon. The window closes itself after a successful open, and when no pending or paused request is left (approved, denied or expired). With **Open requested pages right away** on (the default), a request whose page opened by itself gets no approval window: its prompt window (`arm.html`, see [Open and approve](#open-and-approve)) stands in; a Full or Testing request still gets the approval window.
- **Tab mark.** While a session is active or paused its tab sits in a Chrome tab group titled `FAI` (`FAI ⏸` while paused, grey), whether the tab was opened with **Open <host>** or approved with **Approve this tab**; a tab that is open and armed but not yet approved sits in a group titled `FAI ?` with a `?` badge. The group is made by the extension (`chrome.tabs.group`, `chrome.tabGroups.update`) and the tab is ungrouped when the session stops, the daemon ends or supersedes the lease, or a new session takes over; a restarted worker ungroups the tab its predecessor marked (`chrome.storage.session.markedTab`). A tab already in a group the user made is left there and gets no group mark. The toolbar badge shows `ON` (active) or `Ⅱ` (paused) only on that tab (per-tab badge text, visible while it is the selected tab), cleared when the session ends; the pending `?` and a paused request without a session show on every tab. Nothing is injected into the page and its title is never changed (run expectations read titles; screenshots are evidence). Popup-type windows have no tab strip, which is one reason the opened tab gets a normal window. The `tabGroups` permission this needs shows the install warning "View and manage your tab groups"; `chrome.tabs.group` and `ungroup` need no `tabs` permission.

### Firefox

`npm run build:firefox` ([scripts/build-firefox.mjs](../scripts/build-firefox.mjs)) copies `extension/` unchanged to `dist/firefox/` (`--out <dir>` for another place) and writes a Firefox manifest; the Chromium extension is never modified and loads nothing Firefox-specific. The manifest differences: `background.scripts` (an event page: `compat.js`, `psl-data.js`, `frames.js`, `background.js`) instead of the service worker; `browser_specific_settings.gecko` with `id: "fai-browser@jedbjorn.github.io"` (the AMO-signed ID; `--gecko-id fai-browser@local` builds the old dev ID; the native host's `allowed_extensions` take both), `update_url` (the latest GitHub Release's `updates.json`; signed-ID builds only), `strict_min_version: "140.0"` (the oldest supported ESR; `tabGroups` needs 139) and `data_collection_permissions: {required: ["none"]}`; no `key`, `minimum_chrome_version` or `offscreen` permission; `content_security_policy.extension_pages` `script-src 'self'; object-src 'none'`, without Firefox's MV3 default `upgrade-insecure-requests`, which rewrote the worker's `ws://127.0.0.1` WebSocket to `wss://` and left only the long-poll; no `host_permissions` (a Firefox match pattern with a port matches nothing, and neither the WebSocket nor the CORS-answered long-poll needs one); `optional_host_permissions` `https://*/*`, `http://*/*` and `<all_urls>`. `npm run lint:firefox` runs `web-ext lint` on the build: 0 errors, and the only warnings are `offscreen.hasDocument` and `offscreen.createDocument`, which compat.js provides.

**compat.js** ([extension/compat.js](../extension/compat.js)) loads first in the Firefox event page and only fills in what is missing, so the rest of the extension keeps calling `chrome.*` (Firefox's `chrome` namespace returns promises in MV3):

- `chrome.offscreen`: Firefox's background is a page with a DOM, so the offscreen document is a hidden `<iframe src="offscreen.html">` in it. The same `offscreen.js` runs there and answers the same `annotate` message, so screenshot drawing, action-id tags and [secret boxes](#secret-redaction) are one code path in both browsers.
- Exact-origin keeper. Chrome keeps `activeTab` until the tab leaves its origin; Firefox drops it at any navigation, after which the worker could neither read the tab's URL nor run `page.js`, and paused the lease (`origin_changed`). In the Firefox build the approval click (the toolbar click on an armed tab, or the popup's **Approve** or **Open <host>**) also asks, inside that click, for the request's exact origins as host permissions (`https://host/*`, port dropped; domain roots keep their own prompt). Firefox shows its permission prompt once per new site. The keeper records each pattern Firefox reports added after such a click (`chrome.storage.local.compatGrantedOrigins`) and removes it once no pending, active or paused request in `chrome.storage.session.requests` needs it; a site the user allowed by hand is never recorded, so never removed. Declining the prompt keeps the approval: the session works until the first navigation, which pauses it.
- Feature-detected as in Chrome: `tabGroups` (the tab mark; without it the badge and title remain), `action.getUserSettings` (the pin hint), `storage.local.setAccessLevel` (absent in Firefox, where `storage.local` is also readable by the add-on's own content scripts; `page.js` runs isolated from the page, so a page still cannot read it). The same in both: `storage.session`, `scripting.executeScript` with `func`/`args` (Firefox returns no `documentId`, so the injection retry targets the tab), `action.setPopup`/`onClicked`, `windows.create({type: 'popup'})`, `commands` (`_execute_action`, Ctrl+Shift+Y), `alarms`, `runtime.sendNativeMessage`.

`chrome.tabs.group` names the tab's own window (`createProperties.windowId`): Firefox otherwise moved the tab into the last focused window, the prompt popup, and closing the prompt then closed the leased tab. Chrome already grouped the tab in its own window.

**Screenshots.** Firefox's `captureVisibleTab` needs `activeTab` or `<all_urls>`; a host permission for the site is not enough (`Missing activeTab permission`). The approval click grants `activeTab`, so the first page captures; after the first navigation an observe or act returns no image (never a wrong one) unless the user chose **Allow on all sites** (Advanced, or the setup card), which requests `<all_urls>` once, or turned on **Access your data for all websites** (about:addons, FAI Browser, Permissions). With it the exact-origin prompts after a navigation disappear too. The add-on requests it only on that click.

**The service side.** Firefox gives every install a random origin, `moz-extension://<UUID>`, so the hub accepts any such origin (exact lower-case UUID syntax) besides the pinned `chrome-extension://` one, and echoes it in `Access-Control-Allow-Origin`. A web page can never send that origin; the pairing secret, which only the native host (started by Firefox for the FAI add-on IDs alone, with `[manifest path, add-on ID]` as its arguments) or the user hands out, remains the authentication.

**Event page lifetime.** The session lives in the background page's memory, as in Chrome's worker. In the headless smoke an approved session survived 70 s idle (Firefox's idle timeout is 30 s) with the WebSocket open; if Firefox ever unloads the page, the hello with `session: null` pauses the lease and the user approves again, as after a Chrome worker restart.

**Install options.** `fai-browser launch` sets up official Firefox with a separate FAI profile and the signed add-on, and `npm run setup` offers it ([docs/guide/install.md](guide/install.md): detection, the Mozilla download and its checks, the profile's `user.js`, add-on placement, `uninstall-launcher`). A temporary add-on (about:debugging) is gone after a Firefox restart. Unsigned add-ons install permanently only in Developer Edition, Nightly, ESR and unbranded builds with `xpinstall.signatures.required = false`; any Firefox installs one you signed as an unlisted add-on on AMO (`npx web-ext sign --channel unlisted` with your own API key). `npm run dev:firefox` is the source-development loop: it builds `dist/firefox`, watches `extension/` recursively, rebuilds with a 250 ms debounce (`--debounce <ms>`), and leaves web-ext's automatic reload enabled. It uses `profiles/fai-firefox-dev` unless `--profile <dir>` is given, and selects Firefox with `--firefox <path>` or `FIREFOX_PATH`. web-ext runs with `--keep-profile-changes` and `--profile-create-if-missing`, so profile changes and sign-ins persist and no temporary-add-on loading step is needed. With a `.parentlock` or `parent.lock`, the command checks for Firefox processes before building or launching and refuses if one uses or could use the selected profile, or if the process state cannot be checked; it never removes the lock or writes the profile's preferences itself. An explicit different absolute profile does not block it, and a stale lock is left for Firefox to handle on startup. Snap and Flatpak Firefox run sandboxed and cannot start the native host: pair by hand.

**No automation traces** (below Test site; there the [dev hook](#dev-logs-and-javascript-dialogs) runs in the page's world). The Firefox path adds nothing a site can see beyond the Chromium one: `page.js` runs as an isolated content script injected with `scripting.executeScript` (no DOM nodes, no page-world globals; the tab group and badge are browser UI), the offscreen frame lives in the add-on's own background page, and the user's Firefox runs with no remote protocol (`navigator.webdriver` stays false). Marionette and `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS` are used only by `npm run smoke:firefox`, on a throwaway profile under a temporary `HOME`. The separate `dev:firefox` loop does use web-ext's development remote control for loading and reloading; use a normally started browser for detection measurements.

**The smoke.** `npm run smoke:firefox` ([scripts/firefox-smoke.mjs](../scripts/firefox-smoke.mjs); Marionette through [scripts/marionette.mjs](../scripts/marionette.mjs), no geckodriver) builds the add-on, starts its own FAI service on a free port with a temporary `FAI_HOME`, writes the native host manifest under a temporary `HOME` (XDG layout), starts headless Firefox on a temporary profile and installs the add-on as a temporary add-on. It checks: pairing through native messaging, then the WebSocket; an agent request opens its page in a new tab and arms it; Firefox's own toolbar-button path (`triggerAction`, which grants `activeTab`) approves it, and the exact-origin prompt is allowed through its doorhanger; observe, an annotated screenshot, one `act` and its effect; a same-origin navigation keeps the session; no screenshot without the all-sites opt-in; with it, a screenshot of a page of fake keys with every secret boxed (`redactions` in the trace). It also runs the local detection fixture through normal observe/act calls and prints a capability matrix: event-sequence flags, exactly-once action effects, page-world globals, DOM mutations, untrusted events, user activation and `navigator.webdriver`. Marionette makes the last value `true` in this throwaway harness; the matrix reports that separately instead of treating it as an extension signal. On a small machine run it capped: `systemd-run --user --scope -p MemoryMax=2500M timeout 300 npm run smoke:firefox`.

**Detection in a dedicated profile.** This is separate from `npm run dev:firefox`: web-ext uses a development remote-control session to load and reload the add-on, so that browser is not valid for the no-remote-protocol measurement. Stop the development loop, build with `npm run build:firefox`, and start the dedicated development/test profile normally without Marionette or another remote protocol. Load `dist/firefox/manifest.json` from `about:debugging#/runtime/this-firefox` (or install the signed add-on), and pair it as above. Then run `npm run detect:firefox` ([scripts/manual-firefox-detection.mjs](../scripts/manual-firefox-detection.mjs)). It serves only `fixtures/detection/detector.html` on loopback, opens that page, waits for the user's interactive approval, drives the same shared matrix as the headless smoke and reads the fixture's loopback-posted report. A pass requires `navigator.webdriver: false`, no avoidable event flags, no FAI page-world globals or DOM mutations, and exactly-once actions. Content-script events remain `isTrusted: false` and user activation remains false; the runner reports those inherent limits rather than trying to hide them. No model, credential, testing mode, third-party site or remote debugging protocol is used.
